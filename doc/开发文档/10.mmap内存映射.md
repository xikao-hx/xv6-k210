# mmap 内存映射

本文面向需要阅读和修改 mmap 代码的开发者，介绍当前实现的程序架构、核心数据结构和主要数据流。

阅读完本文后，应该能够回答下面几个问题：

- 一次 `mmap()` 调用会经过哪些模块？
- 为什么调用 `mmap()` 时没有立即分配物理页？
- 文件映射、匿名映射和设备映射的物理页分别来自哪里？
- `MAP_PRIVATE` 和 `MAP_SHARED` 在缺页、`fork()` 和回收时有什么区别？
- `munmap()`、`fork()`、`exec()` 和进程退出时，VMA、页表和 backing object 如何配合？
- 为什么同一个用户页需要同时维护用户页表和进程内核页表？

## 1. 当前 mmap 支持范围

当前实现支持三类映射：

| 映射类型 | backing | `MAP_PRIVATE` | `MAP_SHARED` | 主要用途 |
| --- | --- | --- | --- | --- |
| 普通文件映射 | 文件和 mmap 文件页缓存 | 支持，`fork()` 后写时复制 | 支持，多次映射可共享物理页并在解除映射时写回 | 按需读取文件、共享文件页 |
| 匿名映射 | 零页或匿名共享对象 | 支持，`fork()` 后写时复制 | 支持父子进程共享 | 不依赖文件的用户内存 |
| 设备映射 | 设备提供的 `kbuf` | 不支持 | 支持 | 把内核页缓冲区映射到用户空间 |

支持的主要参数如下：

- 保护属性：`PROT_READ`、`PROT_WRITE`、`PROT_EXEC`。
- 映射属性：`MAP_PRIVATE`、`MAP_SHARED`、`MAP_ANONYMOUS`。
- 普通文件和设备映射要求 offset 按页对齐。
- 匿名映射要求 `fd == -1` 且 `offset == 0`。
- 地址参数当前只支持 `addr == 0`，由内核自动选择地址。
- `MAP_SHARED | PROT_WRITE` 的普通文件映射要求文件描述符可写。

当前没有实现的 Linux mmap 能力包括：

- `MAP_FIXED` 和用户指定映射地址。
- `mprotect()`。
- `msync()`。
- 换页和 swap。
- 完整的统一文件 page cache。
- 普通 `read()`、`write()`、文件截断和 mmap 文件页之间的完整并发一致性。

因此，阅读代码时不要默认它具有 Linux mmap 的所有语义。当前实现是一套适合 xv6 的核心子集。

## 2. 整体架构

mmap 由五层协作完成：

```text
用户程序
  │
  │ mmap / munmap / 内存访问
  ▼
系统调用层
  kernel/syscall/sysfile.c
  │
  │ 解析参数，识别文件、匿名或设备映射
  ▼
VMA 管理层
  kernel/vm/mmap.c
  │
  ├── 记录虚拟地址区间和访问权限
  ├── 处理缺页、解除映射、fork 和销毁
  └── 持有 mmap_object
        │
        ▼
backing 层
  ├── 普通文件：kernel/vm/mmap_file.c
  ├── 匿名共享对象：kernel/vm/mmap.c
  └── 设备 kbuf：kernel/vm/kbuf.c
        │
        ▼
页表与物理内存
  kernel/vm/vm.c、kalloc 引用计数
```

缺页入口不只来自 CPU 异常：

```text
CPU load/store/instruction page fault ──> kernel/trap/trap.c ──┐
                                                               │
kernel copyin/copyinstr 发现 PTE 不存在 ──> kernel/vm/vmcopyin.c ├─> vm_fault()
                                                               │
kernel copyout 发现 PTE 不存在 ────────> kernel/vm/vm.c ────────┘
```

这意味着用户直接访问 mmap 地址，以及内核通过系统调用参数读写 mmap 地址，都会触发同一套按需建页逻辑。

## 3. 用户虚拟地址布局

传统 xv6 用 `p->sz` 表示进程低地址空间的边界。mmap 没有继续向上扩展 `p->sz`，而是在高地址区域从上向下选择 VMA：

```text
低地址
0x0
  ┌──────────────────────────┐
  │ ELF text / data          │
  ├──────────────────────────┤
  │ heap                     │
  ├──────────────────────────┤  p->sz
  │                          │
  │          空洞             │
  │                          │
  ├──────────────────────────┤
  │ 后创建的 mmap VMA         │
  ├──────────────────────────┤
  │ 先创建的 mmap VMA         │
  ├──────────────────────────┤  MMAP_TOP = KSTACK(0)
  │ 高地址保留区域             │
  └──────────────────────────┘
高地址
```

这样设计有两个直接结果：

1. `mmap()` 不需要改变 `p->sz`，原有 ELF、heap 和用户栈逻辑可以保持原来的职责。
2. heap 继续增长时必须查询 `vma_heap_limit()`，避免低地址内存与高地址 mmap 区域相撞。

VMA 采用半开区间：

```text
[vma->start, vma->end)
```

其中：

- `start` 和 `end` 都按页对齐。
- `valid_end` 记录用户最初请求的字节末尾。
- 页表映射以整页为单位，但文件尾页写回只能写到 `valid_end`，不能把页内补零区域也写进文件。
- `offset` 表示 VMA 起始地址对应的 backing offset。

例如，映射文件 offset `0x2000` 的 5000 字节：

```text
start                                     valid_end
  │                                           │
  ▼                                           ▼
  ┌───────────────────┬───────────────────────┬──────┐
  │ 第 0 页有效 4096B  │ 第 1 页有效 904B       │ 补零 │
  └───────────────────┴───────────────────────┴──────┘
  ▲                                                   ▲
  │                                                   │
offset = 0x2000                                      end
```

## 4. 核心数据结构

### 4.1 `vma_area`：描述一段虚拟地址

每个进程在 `struct proc` 中保存固定数量的 VMA：

```c
struct vma_area {
  int used;
  enum vma_type type;
  uint64 start;
  uint64 end;
  uint64 valid_end;
  uint64 offset;
  int prot;
  int flags;
  struct mmap_object *object;
};
```

它回答的是“这段虚拟地址应该如何访问”：

- 地址范围是什么？
- 允许读、写还是执行？
- 是 `MAP_PRIVATE` 还是 `MAP_SHARED`？
- 从 backing 的哪个 offset 开始？
- backing object 是谁？

VMA 本身不等于物理页。刚完成 `mmap()` 时，通常只有 VMA，没有对应 PTE，也没有为每个页面分配物理内存。

### 4.2 `mmap_object`：描述映射背后的对象

```c
struct mmap_object {
  struct spinlock lock;
  int refcnt;
  enum vma_type type;
  struct file *file;
  struct anon_object *anon;
  struct kbuf *kbuf;
};
```

它回答的是“缺页时从哪里取得页面”：

- `VMA_FILE`：从普通文件或 mmap 文件页缓存取得。
- `VMA_ANON`：创建零页，或者从匿名共享对象取得。
- `VMA_KBUF`：从设备的页缓冲区取得。

把 VMA 和 object 分开非常重要。一个 object 可以被多个 VMA 引用，例如：

- `fork()` 后父子进程各有一份 VMA，但共享同一个 object。
- `munmap()` 从 VMA 中间挖掉一段后，左右两段 VMA 仍引用同一个 object。
- 文件描述符关闭后，VMA 仍可通过 object 持有文件。

### 4.3 匿名共享页

匿名共享 object 用稀疏链表按页号保存物理页：

```text
anon_object
  │
  └── pages
       ├── index 0 -> physical page A
       ├── index 3 -> physical page B
       └── index 8 -> physical page C
```

没有发生缺页的 page index 不占用物理页。

这种共享主要发生在 `fork()` 形成的亲缘进程之间。当前没有命名匿名对象机制，两个无关进程不能仅凭相同参数找到同一个匿名 object。

### 4.4 mmap 文件页缓存

`MAP_SHARED` 普通文件使用全局 mmap 文件页缓存。缓存项的身份由下面二元组决定：

```text
(文件身份 file->ep, 页对齐文件 offset)
```

核心字段可概括为：

```text
mmap_file_page
  ├── identity       文件身份
  ├── offset         文件内页偏移
  ├── pa             物理页
  ├── dirty_length   最多需要写回多少字节
  ├── mappings       当前映射数量
  └── state          LOADING / READY / WRITING / EVICTING
```

不同进程即使通过不同的 `open()` 得到不同 `struct file`，只要底层文件身份和页 offset 相同，`MAP_SHARED` 缺页就可以命中同一个缓存页。

状态的作用是避免在持有自旋锁时做磁盘 I/O：

```text
首次缺页
  │
  ├── 创建 LOADING 项
  ├── 释放锁
  ├── 从文件读取
  ├── 重新加锁，切换为 READY
  └── 唤醒等待者

最后一个映射释放
  │
  ├── 切换为 EVICTING
  ├── 释放锁
  ├── 必要时写回文件
  ├── 重新加锁并移除缓存项
  └── 释放缓存持有的物理页
```

### 4.5 `kbuf`：设备可映射页缓冲区

`kbuf` 是由整页组成、带引用计数的内核缓冲区：

```text
kbuf
  ├── refcnt
  ├── size
  ├── npages
  └── page list
       ├── physical page 0
       └── physical page 1
```

设备通过 `file_operations.mmap` 返回一个可映射的 `kbuf`。VMA 不直接保存设备私有指针，而是持有独立引用的 `kbuf`，所以关闭设备 fd 后，已有映射仍然有效。

`kernel/devsw/kbufdev.c` 是当前示例设备，也可以作为新增 mmap 设备驱动的参考骨架。

## 5. mmap 系统调用数据流

用户调用：

```c
addr = mmap(0, length, prot, flags, fd, offset);
```

主要数据流如下：

```text
user mmap()
  │
  ▼
sys_mmap()
  │  读取 length/prot/flags/fd/offset
  │
  ├── MAP_ANONYMOUS
  │     └── vma_map_anon()
  │
  ├── FD_DEVICE
  │     └── vma_map_device()
  │           └── file_operations.mmap()
  │                 └── 设备返回 kbuf
  │
  └── 普通文件
        └── vma_map_file()
  │
  ▼
vma_map_create()
  ├── 检查 prot 和 flags
  ├── 查找空闲 VMA 槽
  ├── 从 MMAP_TOP 向下查找地址空洞
  ├── 创建/引用 mmap_object
  └── 写入 vma_area
  │
  ▼
返回 vma->start
```

这里不会遍历整个映射范围创建 PTE。系统调用成功只表示：

> 内核已经预留这段虚拟地址，并知道将来每一页应该如何建立。

物理页直到第一次访问时才取得，这就是按需分页。

## 6. 缺页处理数据流

### 6.1 入口

CPU 对尚未驻留的 mmap 地址进行访问时，会产生三类异常：

| 异常 | 传给 `vm_fault()` 的访问类型 |
| --- | --- |
| instruction page fault | `VM_FAULT_EXEC` |
| load page fault | `VM_FAULT_READ` |
| store page fault | `VM_FAULT_WRITE` |

`usertrap()` 先调用 `vm_fault()`。如果该地址不属于 VMA，再回到原来的低地址 COW 或 lazy heap 处理逻辑。

内核代表用户访问内存时不会经过同一条用户态 CPU 异常路径，因此：

- `copyin()` 和 `copyinstr()` 在 PTE 不存在时主动调用 `vm_fault(..., READ)`。
- `copyout()` 在 PTE 不存在时主动调用 `vm_fault(..., WRITE)`。

这样，下面这种代码在 mmap 页尚未驻留时仍可以正常工作：

```c
read(fd, mapped_address, size);
write(fd, mapped_address, size);
```

### 6.2 `vm_fault()` 的公共步骤

```text
vm_fault(va, access)
  │
  ├── 1. 按地址查找 VMA
  ├── 2. 检查 PROT_READ / WRITE / EXEC
  ├── 3. 页已存在且是 COW 写故障？
  │        └── 是：复制私有页
  ├── 4. 按 VMA 类型取得 backing page
  ├── 5. 根据 prot 生成 PTE 权限
  ├── 6. 映射到用户页表
  ├── 7. 同步到进程内核页表
  └── 8. 刷新 TLB
```

页对应的 backing offset 由下面关系得到：

```text
backing_offset = vma->offset + page_va - vma->start
```

### 6.3 普通文件 `MAP_PRIVATE`

```text
第一次缺页
  │
  ├── 分配新的零页
  ├── fileread_at(file, page, offset)
  └── 只映射到当前进程
```

它不进入共享文件页缓存。用户修改的是自己的物理页，解除映射时不写回文件。

`fork()` 时，已驻留的可写私有页改为 COW：

```text
fork 前
parent PTE ── W ──> page A

fork 后
parent PTE ── COW ─┐
                   ├──> page A
child  PTE ── COW ─┘

child 首次写
parent PTE ────────> page A
child  PTE ── W ──> page B
```

未驻留的页面不需要在 `fork()` 时处理。父子以后各自缺页，各自从文件读取私有页。

### 6.4 普通文件 `MAP_SHARED`

```text
第一次缺页
  │
  ├── 用 (文件身份, offset) 查询 mmap 文件页缓存
  ├── 未命中：创建缓存页并从文件读取
  ├── 已命中：增加映射和物理页引用
  └── 把同一物理页映射到当前进程
```

多个共享映射关系如下：

```text
process A PTE ──┐
process B PTE ──┼──> mmap cache page ──> file offset N
process C PTE ──┘
```

对共享可写 VMA，当前实现采用保守脏页策略：只要页面可能被写，就记录需要写回的有效长度，而不是依赖硬件 dirty bit。

写回发生在解除映射或销毁 VMA 的路径中。因为当前缓存是 mmap 专用缓存，不应假设并发普通文件 I/O 与映射页完全一致。

### 6.5 匿名 `MAP_PRIVATE`

```text
第一次缺页
  ├── 分配零页
  └── 映射到当前进程
```

没有文件读取，也没有写回。

`fork()` 后，已经驻留的可写页使用 COW；尚未驻留的页由父子分别在将来分配。

### 6.6 匿名 `MAP_SHARED`

```text
第一次缺页
  │
  ├── 按 page index 查询 anon_object
  ├── 没有页面：分配零页并发布到 object
  └── 当前 PTE 增加一份物理页引用
```

父子进程通过同一个 `anon_object` 找到相同的物理页：

```text
parent VMA ──┐
             ├──> anon_object[index] ──> physical page
child VMA  ──┘
```

即使某一页在 `fork()` 时还未驻留，父子进程以后对该 page index 缺页时，仍会汇合到匿名 object 中的同一页。

### 6.7 设备 `kbuf` 映射

设备映射目前只允许 `MAP_SHARED`：

```text
设备 fd
  │
  └── file_operations.mmap(offset, length, prot, flags)
        │
        └── 返回 kbuf
              │
              └── vm_fault() 按 page index 取得物理页
                    │
                    ├── user process PTE
                    └── kernel/device 持有同一缓冲区
```

设备和用户进程看到的是同一组物理页，适合 DMA 缓冲区、帧缓冲区或其他共享数据区。具体设备仍需自行检查 offset、length、权限和硬件约束。

## 7. 为什么维护两套页表

本项目除用户页表 `p->pagetable` 外，还维护进程内核页表 `p->kpagetable`。

当 mmap 缺页建立用户 PTE 后，必须通过 `upg2ukpg()` 同步对应映射：

```text
                    ┌──> p->pagetable
physical mmap page ─┤
                    └──> p->kpagetable
```

解除映射时也必须从两套页表中同时删除。

如果只更新用户页表，可能出现：

- 用户态直接访问成功，但内核访问同一用户地址失败。
- PTE 权限或物理地址在两套页表中不一致。
- `munmap()` 后进程内核页表仍留下旧映射。

所以“安装或删除一个 mmap 页面”是一个同时更新两套页表的操作，而不只是一次 `mappages()`。

## 8. munmap 数据流

`munmap(addr, length)` 不仅删除 PTE，还可能改变 VMA 的形状。

### 8.1 四种区间变化

假设原 VMA 是：

```text
[---------------- 原 VMA ----------------)
```

完整删除：

```text
[xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx)
```

删除头部：

```text
[xxxxxxxxxx|----------- 保留 ------------)
             新 start
             offset 同步向前移动
```

删除尾部：

```text
[----------- 保留 -----------|xxxxxxxxxxxx)
                              新 end
```

删除中间：

```text
[------ 左 VMA ------|xxxxxxxx|------ 右 VMA ------)
                                  新 start
                                  新 offset
```

中间删除需要额外一个 VMA 槽。代码会在修改原 VMA 前预留该槽，避免修改到一半才发现无法表示右半段。

### 8.2 操作顺序

共享文件映射的解除过程采用先检查和写回、后修改的思路：

```text
vma_unmap()
  │
  ├── 验证地址、长度和所有重叠区间
  ├── 为可能的中间切分预留 VMA 槽
  ├── 第一遍：写回共享可写文件页
  └── 第二遍：
       ├── 删除用户页表 PTE
       ├── 删除进程内核页表 PTE
       ├── 释放 backing 对应引用
       └── 删除、裁剪或切分 VMA
```

先写回是为了让 I/O 失败时尽量不留下“部分 VMA 已删、部分还在”的状态。

解除映射允许页面仍处于 lazy 状态。没有 PTE 的页面只需修改 VMA，不需要假装存在一个物理页。

## 9. fork 数据流

`fork()` 需要同时复制 VMA 元数据和处理已驻留页面：

```text
vma_fork(parent, child)
  │
  ├── 复制 VMA 描述
  ├── 增加 mmap_object 引用
  └── 遍历已经存在的 PTE
       │
       ├── MAP_PRIVATE 可写页
       │     └── 父子都改成 COW
       │
       ├── MAP_SHARED 匿名页
       │     └── 映射相同物理页
       │
       ├── MAP_SHARED 文件页
       │     └── mmap 文件缓存增加 hold
       │
       └── kbuf 页
             └── 映射相同物理页
```

这里有一个重要原则：

> `fork()` 只复制已经驻留的 PTE；VMA 本身足以描述尚未驻留的页面。

如果中途失败，子进程通过 `vma_destroy_all()` 回收已复制的 VMA、PTE 和引用，不影响父进程已有映射。

## 10. exec、exit 和关闭 fd

### 10.1 关闭 fd 不等于解除映射

创建文件映射时，`mmap_object` 会独立持有文件引用；设备映射 object 也会独立持有 `kbuf` 引用。

```text
fd 引用 ───────────┐
                   ├──> file / kbuf
mmap_object 引用 ──┘
```

关闭 fd 只删除上面一条引用。只要 VMA 还存在，映射就可以继续缺页和访问。

### 10.2 exec

`exec()` 只有在新地址空间准备成功、准备提交时，才销毁旧 mmap VMA。

这样，如果加载新程序失败，旧进程映射仍然可用；如果加载成功，则旧共享文件页按规则写回并释放。

### 10.3 exit

进程退出和释放进程资源时会调用 `vma_destroy_all()`：

```text
vma_destroy_all()
  ├── 写回需要写回的共享文件页
  ├── 删除两套页表中的 mmap PTE
  ├── 释放每个 PTE 的物理页引用
  ├── 释放 mmap_object 引用
  └── object 最后一个引用消失时释放 file/anon/kbuf
```

## 11. 引用计数和所有权

mmap 代码最容易出错的部分不是地址计算，而是“谁持有一份引用”。可以按下表理解：

| 对象 | 谁持有引用 | 何时释放 |
| --- | --- | --- |
| `mmap_object` | 每个 VMA | VMA 删除、进程销毁 |
| `struct file` | 文件类型 `mmap_object` | object 最后一个引用消失 |
| `anon_object` 中的物理页 | object 自身持有 owner 引用 | object 销毁 |
| 匿名共享页的 PTE | 每个已驻留映射持有一份物理页引用 | `munmap()`、exit |
| `kbuf` | fd 私有数据、`mmap_object` 分别持有引用 | fd 关闭、object 销毁 |
| `kbuf` 中的物理页 | kbuf 自身持有 owner 引用 | kbuf 销毁 |
| kbuf 页的 PTE | 每个已驻留映射持有一份物理页引用 | `munmap()`、exit |
| mmap 文件缓存页 | 缓存项持有 owner 引用 | 缓存项驱逐 |
| 文件共享页的 PTE | 每个映射持有一份物理页引用和 cache mapping | 解除映射 |

以匿名共享页为例：

```text
anon object owner ref ──┐
parent PTE ref ─────────┼──> physical page
child PTE ref ──────────┘
```

父进程先退出不会释放物理页，因为 object 和子进程 PTE 仍持有引用。只有所有 VMA、PTE 和 object owner 引用都消失后，物理页才真正回到分配器。

## 12. 并发控制要点

### 12.1 不在自旋锁内做文件 I/O

文件读取和写回可能睡眠，因此 mmap 文件页缓存使用状态机：

- 锁内决定由谁负责加载或写回。
- 把状态改成 `LOADING`、`WRITING` 或 `EVICTING`。
- 释放自旋锁后执行 `fileread_at()` 或 `filewrite_at()`。
- 完成后重新加锁、更新状态并唤醒等待者。

### 12.2 匿名共享页的重复分配竞争

两个进程可能同时对同一匿名 page index 缺页。处理方式可以概括为：

```text
锁内第一次查询
  │
  ├── 已存在：直接引用
  └── 不存在：
       ├── 锁外分配候选页
       ├── 锁内第二次查询
       ├── 仍不存在：发布候选页
       └── 已被别人发布：释放自己的候选页
```

第二次查询避免同一个 page index 被发布两个不同物理页。

### 12.3 显式 offset 文件 I/O

mmap 使用 `fileread_at()` 和 `filewrite_at()`，不会修改共享 `struct file` 的 `file->off`。

否则一次缺页读取可能悄悄改变同一 fd 后续 `read()` 的位置，也会让并发缺页互相干扰。

## 13. 推荐代码阅读顺序

如果第一次阅读 mmap 实现，建议按下面顺序跟踪：

1. `kernel/include/mmap.h`
   - 先认识 `vma_area`、`mmap_object` 和公开接口。
2. `kernel/syscall/sysfile.c` 中的 `sys_mmap()`、`sys_munmap()`
   - 看用户参数如何分流到三类映射。
3. `kernel/vm/mmap.c` 中的 `vma_map_create()`
   - 看地址如何选择、VMA 和 object 如何建立。
4. `kernel/trap/trap.c` 和 `kernel/vm/mmap.c` 中的 `vm_fault()`
   - 跟踪一次用户 load/store 缺页。
5. `kernel/vm/vmcopyin.c`、`kernel/vm/vm.c`
   - 理解内核 copyin/copyout 为什么也能触发 mmap 缺页。
6. 根据 backing 类型继续阅读：
   - 普通共享文件：`kernel/vm/mmap_file.c`
   - 匿名映射：`kernel/vm/mmap.c`
   - 设备映射：`kernel/vm/kbuf.c`、`kernel/devsw/kbufdev.c`
7. 回到 `vma_unmap()`、`vma_fork()`、`vma_destroy_all()`
   - 理解完整生命周期和引用释放。
8. `testcase/mmaptest.c`
   - 用测试场景反向验证每一条数据流。

## 14. 用一个完整例子串起代码

下面以共享文件映射为例：

```c
fd = open("data", O_RDWR);
p = mmap(0, 8192, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
p[5000] = 'A';
munmap(p, 8192);
```

### 第一步：创建 VMA

```text
sys_mmap()
  └── vma_map_file()
        └── 创建 file mmap_object
              └── 创建 [start, start + 8192) VMA
```

此时：

```text
有 VMA
没有 p[5000] 对应 PTE
没有读取 data 的第二页
```

### 第二步：写访问触发缺页

`p[5000]` 位于 VMA 的第二页：

```text
page_va = PGROUNDDOWN(p + 5000)
file_offset = 0 + page_va - vma->start = 4096
```

数据流：

```text
store page fault
  └── usertrap()
        └── vm_fault(WRITE)
              ├── 找到 VMA，确认允许写
              ├── mmap_file_page_get(file, 4096)
              │     └── 从文件 offset 4096 读一页
              ├── 安装用户 PTE
              └── 同步进程内核页表 PTE
```

CPU 返回用户态后重新执行 `p[5000] = 'A'`，这一次 PTE 已存在，写入成功。

### 第三步：解除映射

```text
sys_munmap()
  └── vma_unmap()
        ├── 写回共享文件页的有效内容
        ├── 删除两套页表中的 PTE
        ├── mmap_file_page_put()
        └── 删除 VMA 和 object 引用
```

如果这是该缓存页的最后一个映射，缓存项也会被驱逐，物理页最终释放。

## 15. 修改代码时的检查清单

修改 mmap 代码时，可以逐项确认：

- 新路径是否同时处理用户页表和进程内核页表？
- PTE 建立失败时，刚取得的 backing page 引用是否释放？
- VMA 切分后，右侧 `offset` 是否随 `start` 正确前移？
- 文件尾页是否只读取和写回有效字节？
- `MAP_PRIVATE` 是否避免写回文件？
- `MAP_SHARED` 的父子进程是否仍指向同一 backing page？
- `fork()` 失败回滚是否只清理子进程资源？
- 关闭 fd 后，object 是否仍持有 file 或 kbuf？
- 可能睡眠的文件 I/O 是否发生在自旋锁之外？
- 没有驻留 PTE 的 lazy 页面能否安全地被 `munmap()` 或销毁？
- `copyin()`、`copyout()` 和直接用户访问是否得到一致的权限检查？
- 新增 mmap 设备是否严格验证 offset、length、flags 和 prot？

完成改动后，应至少通过 QEMU 构建和对应 mmap 测试；涉及每一类 backing 时，分别覆盖 private、shared、fork、partial unmap 和进程退出路径。
