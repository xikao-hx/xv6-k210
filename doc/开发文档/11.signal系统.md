# Signal 系统设计与代码导读

## 1. 这套 Signal 系统解决什么问题

原来的 xv6 只有 `killed` 标志，只能表达“进程应该退出”，不能表达：

- 为什么退出；
- 信号应该被忽略、默认处理还是交给用户 handler；
- 正在睡眠的系统调用是否应该提前返回；
- `Ctrl+C` 应该发给哪个前台任务；
- 一个管道中的多个进程如何一起被中断。

当前实现提供了一套精简的异步信号系统，重点是形成完整闭环，而不是完全复制 POSIX。

支持的主要能力：

- `signal(signum, handler)`：注册默认动作、忽略动作或用户 handler；
- `sigsend(target, signum)`：按 PID 或 PGID 发送信号；
- `sigreturn()`：用户 handler 执行完后恢复被中断现场；
- `setpgid()` / `getpgrp()`：管理进程组；
- 信号可以中断显式标记的用户可见睡眠；
- TTY 模式下 `Ctrl+C` 向 Console 前台进程组发送 `SIGINT`；
- RAW 模式下 `0x03` 仍作为普通字节读取；
- Shell 为前台命令、管道和后台任务建立独立进程组；
- pipe 无读端时产生 `SIGPIPE`；
- 子进程退出时产生 `SIGCHLD`。

当前定义的信号位于 `kernel/include/signal.h`：

| 信号 | 编号 | 默认动作 |
| --- | ---: | --- |
| `SIGHUP` | 1 | 终止 |
| `SIGINT` | 2 | 终止 |
| `SIGQUIT` | 3 | 终止 |
| `SIGKILL` | 9 | 强制终止，不可捕获或忽略 |
| `SIGPIPE` | 13 | 终止 |
| `SIGALRM` | 14 | 终止 |
| `SIGTERM` | 15 | 终止 |
| `SIGCHLD` | 17 | 默认忽略 |

## 2. 总体架构

Signal 系统可以分成六层：

```text
用户程序 / Shell
  │ signal、sigsend、sigreturn、setpgid、getpgrp
  ▼
系统调用层
  │ 只负责解析参数
  ▼
Signal Core（kernel/proc/signal.c）
  │ 统一管理 pending、默认动作、忽略、handler、现场恢复
  ▼
struct proc + trap
  │ 保存信号状态；返回用户态前完成实际投递
  ▼
信号来源
  ├─ 用户 sigsend
  ├─ Console Ctrl+C
  ├─ pipe 无读端
  └─ 子进程 exit
```

各模块的职责边界如下：

| 模块 | 职责 |
| --- | --- |
| `kernel/proc/signal.c` | 信号核心状态转换、PID/PGID 查找、选择信号、进入 handler、sigreturn |
| `kernel/proc/proc.c` | 进程信号字段生命周期、PGID、可中断睡眠、SIGCHLD 来源 |
| `kernel/trap/trap.c` | 返回用户态前调用 `signal_deliver()` |
| `kernel/trap/sigtramp.S` | 用户 handler 返回后发起 `sigreturn` |
| `kernel/devsw/console.c` | TTY 控制字符、前台 PGID、延迟 SIGINT 事件 |
| `kernel/driver/uarths.c` | 原始 UART 字节和通用 RX observer，不理解信号 |
| `kernel/ipc/pipe.c` | 无读端时产生 SIGPIPE |
| `user/sh/sh.c` | 建立 job PGID、切换 Console 前台归属、处理 Shell 自身 SIGINT |

最重要的依赖规则是：

```text
信号来源 ──> Signal Core

Signal Core 不反向依赖 Console、UART、pipe 或 Shell。
```

这样可以避免 signal 核心知道过多设备和业务细节。

## 3. 核心数据结构

每个进程的信号状态保存在 `struct proc`：

```c
int pgid;
uint32 sig_pending;
uint32 sig_mask;
uint64 sig_handlers[NSIG];
int sig_handling;
int sig_current;
int sig_term;
int interruptible_sleep;
struct trapframe sig_saved_trapframe;
```

### 3.1 `pgid`

进程组编号。多个进程拥有相同 PGID 时，可以通过一次组发送命中所有成员。

典型例子：

```text
Shell PGID = 2

前台管道 PGID = 10
  ├─ cpuburn，PID=11，PGID=10
  ├─ cat，PID=12，PGID=10
  └─ 管道管理进程，PID=10，PGID=10
```

Console 只需要向 PGID 10 发送一次 SIGINT，整个管道都会收到。

### 3.2 `sig_pending`

待处理信号位图：

```c
sig_pending |= 1U << signum;
```

因此同一种信号在被处理前最多记录一次，不进行计数和排队。

### 3.3 `sig_mask`

当前实现没有开放用户可配置 mask。该字段主要用于 handler 执行期间屏蔽正在处理的同类信号，防止 handler 嵌套进入自身。

### 3.4 `sig_handlers`

每个信号对应一个处理方式：

```text
0                 -> SIG_DFL，默认动作
1                 -> SIG_IGN，忽略动作
其他用户代码地址   -> 用户 handler
```

注意：本项目的用户 ELF 从虚拟地址 0 开始链接，而地址 0 被 ABI 用作 `SIG_DFL`。因此用户 handler 不能位于地址 0。Shell 和测试程序将 handler 放入独立的 `.text.signal_handler` section，确保它获得非零地址。

### 3.5 `sig_saved_trapframe`

用户 handler 会临时改变用户态的 PC、返回地址和参数寄存器。为了在 handler 完成后继续执行原程序，内核先保存完整 trapframe，然后由 `sigreturn()` 恢复。

## 4. 信号从产生到处理的公共数据流

无论信号来自用户、Console、pipe 还是 exit，最终都会进入 Signal Core。

```text
信号来源
  │
  ├─ signal_send_pid(pid, signum)
  ├─ signal_send_pgrp(pgid, signum)
  └─ signal_send_locked(proc, signum)
  │
  ▼
signal_mark_locked()
  ├─ 忽略动作：直接丢弃
  ├─ 设置 sig_pending 位
  ├─ SIGKILL：立即设置 killed
  └─ 进程处于可中断睡眠：改为 RUNNABLE
  │
  ▼
进程运行或从睡眠醒来
  │
  ▼
usertrap() 返回用户态前
  │
  ▼
signal_deliver()
  ├─ 默认终止
  ├─ 忽略
  └─ 改写 trapframe 进入用户 handler
```

### 4.1 三种发送接口为什么并存

`signal_send_pid(pid, signum)`：

- 扫描进程表；
- 找到指定 PID；
- 获取目标 `p->lock` 后标记信号。

`signal_send_pgrp(pgid, signum)`：

- 扫描整个进程表；
- 对每个 PGID 匹配的进程分别加锁并标记；
- 任意时刻只持有一个进程锁。

`signal_send_locked(p, signum)`：

- 调用方已经持有目标 `p->lock`；
- 不再扫描进程表，也不重复加锁；
- 主要供 `exit()` 产生 SIGCHLD 使用。

如果 `exit()` 已持有父进程锁，却再次调用 PID 扫描接口，扫描到父进程时会尝试重复获取同一把锁，从而死锁。

## 5. 默认、忽略和用户 Handler

### 5.1 默认终止

大部分信号的默认动作是：

```c
p->sig_term = signum;
p->killed = 1;
```

`trap.c` 随后统一执行：

```c
exit(signal_exit_status(p));
```

退出状态使用负信号编号，例如默认 SIGTERM 退出状态为 `-15`。

### 5.2 忽略

如果当前 disposition 是 `SIG_IGN`，或者信号是默认忽略的 SIGCHLD，则信号在产生时直接丢弃：

```text
不设置 pending
不唤醒可中断睡眠
不打断 wait
```

这点对 Shell 非常重要。Shell 默认不安装 SIGCHLD handler，如果默认 SIGCHLD 仍然进入 pending，子进程退出时就会把 Shell 的 `wait()` 提前中断，导致僵尸进程无法正常回收。

### 5.3 用户 Handler

`signal_deliver()` 选择一个 pending 信号后：

1. 保存当前完整 trapframe；
2. 设置 `sig_handling=1`；
3. 在内部 mask 中屏蔽当前信号；
4. 设置 `a0=signum`，作为 handler 第一个参数；
5. 设置 `epc=handler`，使用户态从 handler 开始执行；
6. 设置 `ra=SIGTRAMP`，使 handler 的 `ret` 跳到固定 trampoline。

数据流如下：

```text
原用户程序
  │ trap
  ▼
signal_deliver()
  │ 保存原 trapframe
  │ epc = handler
  │ a0  = signum
  │ ra  = SIGTRAMP
  ▼
用户 handler(signum)
  │ ret
  ▼
SIGTRAMP
  │ ecall SYS_sigreturn
  ▼
signal_sigreturn()
  │ 恢复 sig_saved_trapframe
  │ 清除内部 mask / handling 状态
  ▼
原用户程序继续执行
```

用户不能给 `sigreturn()` 传入 trapframe 指针。需要恢复的现场只保存在内核 `struct proc` 中，防止用户伪造特权寄存器状态。

## 6. 为什么在返回用户态前投递

Signal Core 不会在任意内核函数中直接跳到用户 handler。实际投递统一发生在 `usertrap()` 返回用户态之前：

```c
signal_deliver(p);
if(p->killed)
  exit(signal_exit_status(p));
usertrapret();
```

这样做有三个好处：

- 当前进程拥有完整、可修改的用户 trapframe；
- 内核不需要从设备中断或 pipe 代码直接切换到用户地址；
- 所有信号来源共享同一套默认动作和 handler 入口逻辑。

## 7. 可中断睡眠

并非所有内核睡眠都允许被信号打断。

### 7.1 两类睡眠

```text
sleep()                 不可中断
sleep_interruptible()   可由普通信号中断
```

可中断的主要是用户可见等待：

- `sys_sleep()`；
- `wait()`；
- pipe read/write；
- Console/UART read；
- 用户 UART TX ring 等待。

保持不可中断的主要是：

- 磁盘和 virtio 请求；
- sleeplock；
- buffer cache；
- DMAC；
- mmap file cache；
- `uart_flush_tx()`。

这些底层等待如果提前返回，调用者通常没有安全的错误恢复路径。

### 7.2 避免丢失唤醒

进入可中断睡眠时，pending 检查和设置 `SLEEPING` 必须在同一个 `p->lock` 临界区内完成：

```text
获取 p->lock
  ├─ 已有 pending：不睡眠，直接返回 -1
  └─ 无 pending：
       设置 interruptible_sleep
       设置 state=SLEEPING
       调度出去
```

信号发送方也持有同一把 `p->lock`。因此不会出现“发送方检查时进程还没睡，发送结束后进程才睡下去”的丢失唤醒问题。

## 8. Ctrl+C 数据流

Ctrl+C 是本系统跨层最多的一条路径。

```text
键盘/串口输入 0x03
  ▼
UART IRQ：uartintr()
  ▼
通用 RX observer：console_rx_observer()
  ├─ RAW 模式：保留 0x03，写入 UART RX ring
  └─ TTY 模式：
       消费 0x03
       清除当前排队输入
       记录一次性 read 取消
       原子记录 SIGINT 延迟事件
  ▼
UART 中断返回后的安全 trap 上下文
  ▼
console_dispatch_events()
  ├─ 输出 ^C 和换行
  └─ signal_send_pgrp(foreground_pgid, SIGINT)
  ▼
前台 job 整组收到 SIGINT
```

### 8.1 UART 为什么不直接发送 SIGINT

`uartintr()` 执行时持有 UART RX spinlock，并处于中断上下文。扫描进程表和获取 `p->lock` 会扩大锁依赖，也可能造成中断上下文死锁。

因此 UART driver 只提供一个通用 observer：

```text
KEEP            保留字节
CONSUME         消费字节
CONSUME_CANCEL  消费字节、清输入并取消一次 read
```

observer 只做原子状态更新，不打印、不睡眠、不扫描进程表。

真正的进程组发送由 `console_dispatch_events()` 延迟到安全 trap 上下文执行。

### 8.2 为什么还要取消一次 read

仅发送 SIGINT 并清空当前 RX ring 仍存在竞态：

```text
Ctrl+C 先到达
下一次 Console read 尚未开始
read 开始后看不到刚才的控制字符
```

UART 因此保存一次性 `rx_cancel_pending`。当前或下一次 `uart_read()` 会原子消费它并返回 `-1`，确保 Shell 的半行输入能够可靠取消。

## 9. Console 前台组与控制者

Console 保存两个不同概念：

```text
foreground_pgid        当前接收 TTY 信号的前台任务组
foreground_owner_pgid  有权切换前台归属的控制者，通常是 Shell
```

不能只保存 `foreground_pgid`。因为 Shell 把终端交给子 job 后，Shell 已经不是前台组成员；如果修改权限只属于当前前台组，Shell 在 job 退出后就无法收回终端。

典型切换过程：

```text
Shell 启动：
  owner = Shell PGID
  foreground = Shell PGID

运行前台 job：
  owner = Shell PGID
  foreground = Job PGID

job 退出：
  owner = Shell PGID
  foreground = Shell PGID
```

如果 Shell 异常退出，下一次设置操作会检查 owner PGID 是否仍存在，并回收陈旧控制权，使 init 重新启动的 Shell 可以接管 Console。

## 10. Shell Job Control

Shell 启动时：

1. 把自己设为独立 PGID；
2. 注册 Shell 自身 SIGINT handler；
3. 取得 Console 控制权和前台归属。

每次运行命令时：

```text
Shell fork 顶层 child
  ├─ child：setpgid(0, 0)
  └─ parent：setpgid(child_pid, child_pid)
```

父子双方都调用 `setpgid`，用于封闭调度竞态：无论父进程还是子进程先运行，job 都会尽快进入正确的进程组。

### 10.1 前台任务

```text
建立 Job PGID
  ▼
Console foreground = Job PGID
  ▼
Shell wait()
  ▼
Job 退出
  ▼
Console foreground = Shell PGID
```

顶层 job 进程会在执行命令树前把 SIGINT 恢复为 `SIG_DFL`。管道内部创建的子进程继承相同 PGID 和默认 SIGINT 动作，因此 Ctrl+C 能终止整个管道。

### 10.2 后台任务

后台任务同样拥有独立 PGID，但 Shell 不把 Console 前台归属交给它。因此用户在 Shell 提示符按 Ctrl+C 时：

- Shell 处理并清除当前输入；
- 后台任务不在前台 PGID 中，不会收到该 SIGINT。

## 11. SIGPIPE 数据流

当 pipe 已没有读端时，`pipewrite()`：

1. 释放 pipe lock；
2. 向当前写进程发送 SIGPIPE；
3. 保持原有 write 返回规则：尚未写入则返回 `-1`，已部分写入则返回已写长度。

```text
write(pipe)
  ▼
pipewrite()
  ▼
readopen == 0
  ▼
释放 pipe lock
  ▼
signal_send_pid(current_pid, SIGPIPE)
  ▼
默认：进程退出，状态 -SIGPIPE
忽略/handler：write 返回 -1 或 partial count
```

必须先释放 pipe lock，再调用 Signal Core。信号发送可能获取进程锁，不应把 pipe 锁带入进程表扫描。

## 12. SIGCHLD 数据流

子进程在 `exit()` 中首次切换为 ZOMBIE 时向稳定父进程发送 SIGCHLD：

```text
child exit()
  ▼
确定并锁定 original_parent
  ▼
reparent(child 的子进程)
  ▼
signal_send_locked(original_parent, SIGCHLD)
  ▼
wakeup1(original_parent)
  ▼
child state = ZOMBIE
  ▼
父进程 wait() 回收
```

SIGCHLD 只负责通知，不负责回收。`wait()` 仍然是唯一回收 ZOMBIE 的入口。

SIGCHLD 默认忽略，因此普通 Shell 的 wait 不会被额外中断。安装用户 handler 后，SIGCHLD 可以唤醒可中断 wait；handler 执行后用户程序应继续调用 wait 完成回收。

多个子进程同时退出时，同一种 pending 信号只保留一位，因此 handler 只保证“至少发生过一次子进程状态变化”。用户程序仍应循环调用 wait 扫描全部 ZOMBIE。

## 13. fork、exec 和进程退出生命周期

### 13.1 alloc

新进程：

- pending 清空；
- mask 清空；
- handler 全部为默认；
- handling/current/term 清空；
- PGID 初始等于自己的 PID。

### 13.2 fork

子进程继承：

- PGID；
- handler 表；
- 内部 mask。

子进程不继承：

- pending 信号；
- 正在执行 handler 的临时状态；
- 保存的 trapframe；
- 信号终止原因。

### 13.3 exec

`exec()`：

- 保留 `SIG_IGN`；
- 用户自定义 handler 恢复为 `SIG_DFL`；
- 清空 pending、mask 和 handler 临时状态。

原因是 exec 后原 handler 对应的用户代码映射已经被替换，旧函数地址不再有效。

### 13.4 exit

信号默认终止最终仍进入统一 `exit()` 路径：

- 关闭文件；
- 清理 VMA；
- reparent；
- 产生 SIGCHLD；
- 设置 ZOMBIE；
- 等待父进程回收。

## 14. 锁与并发规则

理解代码时应重点记住以下规则：

1. 修改 `sig_pending`、`sig_mask`、handler、PGID、睡眠状态时持有目标 `p->lock`。
2. PGID 扫描一次只持有一个进程锁，不能同时锁多个 `struct proc`。
3. 已持有目标进程锁时使用 `signal_send_locked()`，不能调用会重新扫描加锁的 PID 接口。
4. UART observer 不睡眠、不打印、不扫描进程表、不获取进程锁。
5. Console 释放自身锁后才能调用进程信号接口。
6. pipe 释放 pipe lock 后才能产生 SIGPIPE。
7. pending 检查和进入可中断睡眠必须位于同一个 `p->lock` 临界区。
8. 默认或显式忽略的信号在生成时丢弃，不能无意义地唤醒睡眠进程。

## 15. 系统调用接口

| syscall | 编号 | 说明 |
| --- | ---: | --- |
| `signal(signum, handler)` | 32 | 设置处理方式，返回旧 handler |
| `sigsend(target, signum)` | 33 | 正 target 表示 PID，负 target 表示 PGID，0 非法 |
| `sigreturn()` | 34 | 恢复内核保存的 handler 前现场 |
| `setpgid(pid, pgid)` | 35 | 设置自己或直接子进程的 PGID；0 使用默认含义 |
| `getpgrp()` | 36 | 返回当前进程 PGID |

`setpgid` 是精简实现：

- `pid == 0` 表示当前进程；
- `pgid == 0` 表示使用目标 PID；
- 只允许修改自己或直接子进程；
- 不实现 session、停止/继续和完整 POSIX job control。

## 16. 用户虚拟地址中的 SIGTRAMP

固定映射关系：

```text
高地址
┌─────────────────────┐
│ TRAMPOLINE          │ 内核/用户 trap 切换代码
├─────────────────────┤
│ TRAPFRAME           │ 不带 PTE_U，用户不可访问
├─────────────────────┤
│ SIGTRAMP            │ PTE_U | PTE_R | PTE_X
└─────────────────────┘
低地址
```

`SIGTRAMP` 只允许用户读取和执行，不允许写入。QEMU 与 K210 链接脚本都保留一页 sigtramp 代码，并在每个用户页表中建立相同虚拟地址映射。

## 17. 推荐代码阅读顺序

第一次阅读时建议按以下顺序：

1. `kernel/include/signal.h`
   - 先看信号编号、用户 ABI 和核心接口。
2. `kernel/include/proc.h`
   - 理解每进程信号字段。
3. `kernel/proc/signal.c`
   - 重点看 `signal_mark_locked()`、`signal_deliver()`、`signal_sigreturn()`。
4. `kernel/trap/sigtramp.S`
   - 理解 handler 返回后如何进入 sigreturn。
5. `kernel/trap/trap.c`
   - 找到返回用户态前的统一投递位置。
6. `kernel/proc/proc.c`
   - 查看 alloc/fork/exit、PGID、可中断睡眠。
7. `kernel/devsw/console.c`
   - 理解前台 PGID、控制者和延迟事件。
8. `kernel/driver/uarths.c`
   - 理解 observer、RX ring 和一次性取消。
9. `user/sh/sh.c`
   - 理解 Shell 如何建立和切换 job PGID。

## 18. 测试方法

构建并启动：

```bash
make build platform=qemu
make fs platform=qemu
make run platform=qemu
```

QEMU Shell 中可运行：

```text
signaltest sources   # SIGPIPE、SIGCHLD
signaltest pgrp      # 进程组发送
signaltest tty       # TTY Ctrl+C，需要输入 Ctrl+C
signaltest raw       # RAW 0x03 透传
signaltest sleep     # 可中断睡眠
signaltest           # 完整基础与来源回归
```

预期关键输出：

```text
signaltest sources: ALL PASSED
signaltest pgrp: ALL PASSED
signaltest tty: ALL PASSED
signaltest raw: ALL PASSED
signaltest sleep: ALL PASSED
signaltest: ALL PASSED
```

Shell job control 可手动验证：

```text
cpuburn 400
cpuburn 400 | cat
cpuburn 20 1 &
```

- 前两个命令按 Ctrl+C 应立即结束并返回 Shell；
- 后台命令运行时，在 Shell 提示符按 Ctrl+C 不应杀死后台任务；
- 输入半行命令后按 Ctrl+C，应清空输入并重新显示提示符。

## 19. 当前实现有意保留的边界

当前版本没有实现：

- 实时信号和多次排队；
- `sigaction` flags；
- 用户可配置 signal mask；
- handler 嵌套；
- syscall 自动重启；
- stopped/continued 状态；
- session 和完整 `jobs` / `fg` / `bg`；
- 完整 POSIX wait status 编码。

阅读代码时，应把它理解为一套适合教学内核的“小而完整”的信号闭环，而不是 Linux/POSIX 信号系统的完整复刻。
