# I2C 驱动开发记录

## 背景

在 xv6-k210 上移植 I2C 驱动，驱动 SSD1306 OLED 显示屏（128×64，I2C 地址 0x3C）。

K210 的 I2C 控制器是 Synopsys DW APB I2C IP，需要通过 FPIOA 将 I2C 信号映射到物理引脚。

**硬件连接：**
- SCL — 物理引脚 30 (I2C0_SCLK)
- SDA — 物理引脚 31 (I2C0_SDA)
- OLED 地址 — 0x3C (7-bit)

---

## 问题与解决

### 1. PLL 寄存器读回错误

**原因：** PLL 寄存器结构体使用了 `__attribute__((packed, aligned(4)))`，在 K210 上 bitfield 读回异常。

**解决：** 改为从 CPU 频率推算 I2C 时钟频率，硬编码分频系数：

```c
uint32_t v_i2c_freq = sysctl_clock_get_freq(SYSCTL_CLOCK_CPU) / 4;    // 时钟频率：计算 I2C 模块的实际输入时钟频率
uint16_t v_period_clk_cnt = v_i2c_freq / i2c_clk / 2;                 // 时钟周期：计算高低电平各需要维持多少个时钟周期，从而得到想要的 I2C 速率
```

**以下几点是可能的错误：** 调试过程中发现主机发送数据正常，但是从机没有回应ACK，但是后续整理又发现改完 CLK 之后 I2C 驱动就可以正常使用了

### 2. I2C_CON_SPEED 使用错误的计数值

**现象：** 使用 Fast Mode (`I2C_CON_SPEED(1)`) 时，控制器读取 `fs_scl_hcnt/fs_scl_lcnt` 寄存器，但这些寄存器位于 struct 的 `resv2[4]` 填充区域（未初始化），导致 SCL 时钟异常。

**解决：** 改用 Standard Speed (`I2C_CON_SPEED(0)`)，使用 `ss_scl_hcnt/ss_scl_lcnt` 寄存器。

### 3. enable_status 未轮询

**现象：** 硬件 I2C 工作不稳定，有时 ACK 有时无响应。

**原因：** DW APB I2C 控制器写入 `enable` 寄存器后，需要在另一个时钟域同步。直接写 `enable = 0` 可能被忽略，导致寄存器在控制器仍然启用时被修改。

**解决：** 增加 `enable_status` 轮询：

```c
i2c_adapter->enable = 0;
for (int i = 0; i < 1000; i++) {
    if ((i2c_adapter->enable_status & I2C_ENABLE_STATUS_IC_ENABLE) == 0)
        break;
}
// ...配置寄存器...
i2c_adapter->enable = I2C_ENABLE_ENABLE;
for (int i = 0; i < 1000; i++) {
    if ((i2c_adapter->enable_status & I2C_ENABLE_STATUS_IC_ENABLE) != 0)
        break;
}
```

### 4. TX_ABRT 后总线未空闲

**现象：** 地址扫描时大量 NACK 导致 TX_ABRT，返回后立即调用 `i2c_init` 可能冲突。

**原因：** `i2c_send_data` 检测到 TX_ABRT 后直接返回，未等待 `ACTIVITY=0`。

**解决：** 在 TX_ABRT 分支中增加等待总线空闲：

```c
if(i2c_adapter->tx_abrt_source != 0)
{
    while((i2c_adapter->status & I2C_STATUS_ACTIVITY) || !(i2c_adapter->status & I2C_STATUS_TFE))
        ;
    return 1;
}
```

### 5. 缺少 SDA 保持时间

**现象：** 数据字节偶发出错。

**原因：** DW APB I2C 默认 `sda_hold = 0`，即 SDA 在 SCL 跳变后无保持时间，从设备可能采样失败。

**解决：** 设置 SDA 保持时间 ~1.25µs：

```c
i2c_adapter->sda_hold = I2C_SDA_HOLD_TX(v_period_clk_cnt / 4) | I2C_SDA_HOLD_RX(v_period_clk_cnt / 8);
```

### 6. 缺少总线空闲时间

**现象：** 连续 I2C 事务间无停顿。

**原因：** 硬件控制器连续发送 STOP → START 之间没有足够的空闲时间，OLED 来不及处理。

**解决：** 在 `i2c_send_data` 结束时增加 ~5µs 延迟和清除 STOP_DET 标志：

```c
i2c_adapter->clr_stop_det = i2c_adapter->clr_stop_det;
for (volatile int i = 0; i < 200; i++);
```

# I2C 驱动框架

## 框架说明
  
* 用户态使用 `i2c_msg` 传输数据：发送和接收使用两个 `i2c_msg`

```c

struct i2c_msg {

    uint16 addr;    // slave address (7-bit)

    uint16 flags;

#define I2C_M_RD    0x0001  // read data, from slave to master

    uint16 len;     // msg length

    uint8 *buf;     // user-space pointer to msg data

};

```

* 内核态使用传输统一入口：`i2c_transfer`
    * 支持 `DMA` 和 `POLLing` 模式，后续再支持中断模式
    * 通过 `len` 大小选择传输模式：`DMA_THRESHOLD`

## 修改说明

* `ioctl`：修改参数传递形式，进行三次数据拷贝过程
* 优化 `i2c` 驱动框架，实现读和写分离，接入统一入口 `i2c_transfer`
    * 增加 `repeat start` 和 `stop`
    * 支持多种传输模式

## 问题说明

* 因为现在读和写事务分离，所以必须要要增加 `repeat start` 和 `stop`，注意怎么去改数据：
    * 随着数据一起发送： `i2c_adapter->data_cmd`
* 接收也必须先发送：`I2C_DATA_CMD_CMD`
* 必须清除硬件状态：触发一次 `volatile` 寄存器读取

```c

(void)i2c_adapter->clr_tx_abrt;

(void)i2c_adapter->clr_stop_det;

```

* 必须控制使用 DMA 传输的场景，要是一定长度才好：`DMA_THRESHOLD`
* 当前不能开启 `LOG_LEVEL_DEBUG` 否则会读取失败，原因不详
* 当前驱动还是有些小问题后续再继续优化
* 等待 `done` 一定要有超时时间，否则程序卡死
* 合理的日志打印和程序设计，当前很多时候就是对程序的设计不清除，导致自己也没办法明确知道如何调试

# SPI 驱动框架

## 当前实现思路

当前 SPI 设备层通过 `devsw` 暴露给用户态，用户态使用 `ioctl` 提交传输请求。底层驱动使用 DesignWare SSI 控制器，当前主要走 polling 路径，DMA 路径保留但不作为默认路径。SPI 通过 spi_config.h 进行配置工作

SPI 采用全双工传输模型：发送一个字节的同时也会接收一个字节。对于 W25Q64 这类 flash，读 JEDEC ID 的真实总线行为不是“只写命令再单独读”，而是：

```text

CS 拉低

发送 0x9f

继续发送 dummy 字节 0xff 0xff 0xff，用这些 dummy 产生时钟

同时从 MISO 收到 ff ef 40 17

CS 拉高

```

用户态可以使用 Linux spidev 风格的 `SPI_IOC_MESSAGE(n)`，把多段 message 传给内核。例如一段发送命令，一段接收数据。内核会把多段 message 合并成一次底层 `spi_transfer()`，这样 CS 会在整个 message 期间保持不释放。

## ioctl message 长度解析

`spidev_ioctl()` 支持从 ioctl command 中解析传输数组长度，逻辑与 Linux spidev 类似：

```text

检查 _IOC_TYPE(cmd) == SPI_IOC_MAGIC

检查 _IOC_NR(cmd) == _IOC_NR(SPI_IOC_MESSAGE(0))

检查 _IOC_DIR(cmd) == _IOC_WRITE

通过 _IOC_SIZE(cmd) 得到 struct spi_ioc_transfer 数组总大小

n_ioc = _IOC_SIZE(cmd) / sizeof(struct spi_ioc_transfer)

```

这样用户态调用 `SPI_IOC_MESSAGE(2)` 时，内核可以知道本次 message 中有 2 段 transfer。旧的 `SPI_IOCTL_TRANSFER` 单段兼容入口已经移除，SPI 数据传输统一走 `SPI_IOC_MESSAGE(n)`。

## CS 保持策略

SPI flash 的很多命令要求 CS 在命令、地址、dummy、数据阶段之间保持拉低。如果每段 transfer 后都释放 CS，外设会把后续字节当作新事务，读出来常见是 `0xff 0x00 0x00` 或全 `0xff`。

当前策略是：

```text
用户态多段 spi_ioc_transfer
  -> spidev_message() 复制并拼接 tx/rx 缓冲
  -> 构造一个内核 spi_transfer
  -> 调用底层 spi_transfer(..., num = 1)
  -> 底层只在这一整段开始时拉低 CS，结束时释放 CS
```

对于 rx-only 段，内核会填充 `0xff` 作为 dummy 发送数据，用于产生 SCLK。

## 已修复问题

* 8 bit frame 不能用 `uint32` 读写 FIFO
	* SPI 初始化为 8 bit data frame 时，每个 FIFO entry 对应 1 字节。旧代码在 polling 路径里按 `uint32` 写入和读取，会导致收到的数据错位，JEDEC ID 表现为 `ff 00 00` 或异常值。

	 * 当前根据 frame width 分别使用：

   ```text

   SPI_TRANS_CHAR  -> uint8

   SPI_TRANS_SHORT -> uint16

   SPI_TRANS_INT   -> uint32

   ```

* 长读不能先把 TX 全部塞完再读 RX
	* SPI 是全双工，发送时 RX FIFO 也会不断产生数据。K210 SSI FIFO 深度有限，长读时如果只写 TX、不及时读 RX，RX FIFO 会满，后续传输卡住。
	* 当前 polling 逻辑改成边读边写：

   ```text

   while rx_left:
     先尽量 drain RX FIFO
     再根据 TX FIFO 空位继续填 TX
     如果长时间没有任何进展，触发 timeout 返回错误
   ```

* 等待必须有超时
	* 驱动调试阶段不要写无限等待。当前 polling 路径加入 `SPI_POLL_WAIT_TIMEOUT`，出问题时会打印剩余 `tx_left/rx_left` 和寄存器状态，而不是让 shell 卡死。

## 调试方法

### 1. 确认构建和测试程序

当前正式代码不保留临时 SPI 调试日志，避免串口输出影响正常测试。排查问题时先确认内核和文件系统都已经更新：

```bash
make build platform=k210
make fs platform=k210
make run platform=k210
```

注意：只执行 `make download` 只会更新 `target/fs.img`，不会更新内核驱动代码。修改内核驱动后必须重新构建并启动/烧录新的内核镜像。

最小验证命令是读 JEDEC ID：

```bash
spitest
w25q64
```

正常情况下，W25Q64 应返回类似：

```text
JEDEC: ef 40 17
```

判断要点：
* 用户态应调用 `SPI_IOC_MESSAGE(2)` 或 `SPI_IOC_MESSAGE(1)`，不要再使用旧的 `SPI_IOCTL_TRANSFER`。
* 读 ID 的总线发送内容应是 `9f ff ff ff`，命令后面的 dummy 字节用于产生时钟。
* 第一个接收字节通常是发送命令同时收到的无效字节，真正 ID 是后续 `ef 40 17`。
* 若需要进一步定位，可以临时在 `spidev_message()`、`spi_dw_poll_transfer()` 和 timeout 分支加 `LOG_D`，调完后移除。

如果看到：

```text
JEDEC: ff 00 00
JEDEC: ff ff 81
JEDEC: ff ff ff
```

优先怀疑 CS、MISO/MOSI 接线、frame width、dummy clock 或多段 message 期间 CS 被释放。

### 2. 用逻辑分析仪确认总线

建议连接 4 个通道：

```text
CLK  -> SCLK
MOSI -> MOSI
MISO -> MISO
CS#  -> CS0
GND  -> GND
```

采样率建议至少是 SPI 时钟的 8 到 10 倍。当前 1 MHz SPI 时，逻辑分析仪设置 10 MHz 或更高更稳。

触发方式：

```text
CS# 下降沿触发
```

读 JEDEC ID 时，应该看到：

```text
CS# 先拉低并保持
CLK 出现连续 32 个周期
MOSI 第一个字节是 0x9f，后面是 0xff 0xff 0xff
MISO 第一个字节通常无效，后面是 0xef 0x40 0x17
CS# 最后拉高
```

如果逻辑分析仪上只有 MOSI 有一个脉冲、CLK 基本不动，说明没有产生完整时钟，检查底层 transfer 是否真的发送了总长度字节。

如果 CLK 正常、MOSI 正常，但 MISO 一直高，读到通常是 `0xff`，重点检查：
* MISO 是否接反或悬空。
* flash 是否供电正常，3V3/GND 是否可靠。
* CS 是否接到实际使用的 CS0。
* WP#/HOLD# 是否被拉到有效电平，部分模块需要上拉。

如果 CS 在命令段后短暂拉高，再进入读数据段，说明多段 message 没有被合并成一次底层 transfer，外设会重新解释后续 dummy 字节。

### 3. 调试顺序

推荐按下面顺序排查，不要一开始就改代码：

```text
确认用户态调用
  -> 看 spidev 是否打印 message/n_ioc/tx bytes
确认底层配置
  -> 看 spi_test init/poll start/frame_width/baudr
确认 FIFO 收发
  -> 看 poll tx/poll rx 和 timeout
确认物理总线
  -> 用逻辑分析仪看 CLK/MOSI/MISO/CS
确认外设响应
  -> JEDEC ID 是否为 ef 40 17 或同类厂商 ID
```

调试时先用最小命令 `spitest` 或 `w25q64` 的 JEDEC ID，不要直接做 erase/program。只有 JEDEC ID 稳定正确后，再继续测试读、擦、写。

### 4. 常见现象解释

* `JEDEC: ff 00 00`：命令阶段可能有响应，但后续读数据错位或没有正确采样，常见于 frame width/FIFO 读写宽度错误。
* `JEDEC: ff ff ff`：MISO 一直为高，常见于外设未响应、MISO 悬空、CS 不对、flash 未供电。
* `w25q64` 无法退出或 shell 卡死：驱动可能在等待 FIFO/DMA 完成时没有超时，或长读时 RX FIFO 满后没有继续进展。
* 逻辑分析仪只看到很慢的边沿或单个脉冲：检查 SPI 时钟是否真正启动、采样率是否足够、触发条件是否正确。
* OLED 没显示、SPI flash 也不响应：优先检查 FPIOA 复用和引脚冲突，两个外设可能复用了同一 SPI bus 或 GPIO。

## 注意事项

* `SPI_IOCTL_INIT` 当前读取了用户态传入的 `clk_rate`，但底层仍主要使用默认 `baudr` 配置；如果需要严格控制 SPI 频率，后续应把 `clk_rate` 转换为 `baudr`。
* DMA 路径涉及对齐和 transfer width，指针强转后直接解引用存在未对齐风险。调试 flash 基础功能时优先使用 polling。
* 在 RISC-V 上，未对齐的 16/32 bit 访问可能触发异常或行为不稳定。处理用户态字节流时应优先逐字节搬运，除非明确保证对齐。
* 多段 SPI message 中，只要外设协议要求一个完整事务，就必须保证 CS 在这些段之间不释放。
