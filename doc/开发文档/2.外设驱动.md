# 外设驱动架构与开发记录

## 1. 当前总体架构

文件与设备操作抽象重构后，普通文件、管道和设备文件统一由 `struct file`
表示，但根据 `file.type` 进入不同的数据通路：

```text
用户程序
  -> open/read/write/ioctl/close
  -> syscall
  -> struct file
       ├── FD_ENTRY  -> FAT32
       ├── FD_PIPE   -> pipe
       └── FD_DEVICE -> struct file_operations
                          -> console/stats/spidev/i2cdev/sdcarddev
                          -> board controller
                          -> K210 底层驱动
                          -> 外设控制器与芯片
```

设备不再通过一个只接收 `major` 的全局 `devsw[]` 读写函数处理。每个 major
在启动时注册自己的 `struct file_operations`：

```c
struct file_operations {
  int (*open)(struct file *);
  int (*read)(struct file *, uint64, int);
  int (*write)(struct file *, uint64, int);
  int (*ioctl)(struct file *, uint64, uint64);
  int (*close)(struct file *);
};
```

设备打开后，`struct file` 保存：

- `major/minor`：设备类型和逻辑设备编号；
- `ops`：该设备的操作表；
- `private_data`：本次打开实例的状态。

`dup()` 和 `fork()` 共享同一个 `struct file`，因此也共享 `private_data`。
只有最后一个引用关闭时才调用设备的 `close()` 并释放打开实例状态。

### 1.1 设备路径、major 和 minor

`kernel/device.c` 维护静态路径映射。`sys_open()` 先查询设备路径，命中后走
`devicefdalloc()`；未命中才进入 FAT32。当前 `/dev/*` 是内核逻辑路径，不是
SD 卡 FAT32 中必须存在的普通目录项。

| 路径 | major | minor | 平台 | 设备实现 |
| --- | ---: | ---: | --- | --- |
| `/dev/console` | `DEV_CONSOLE` | 0 | QEMU/K210 | `console.c` |
| `/dev/stats` | `DEV_STATS` | 0 | QEMU/K210 | `stats.c` |
| `/dev/sdcard` | `DEV_SDCARD` | 0 | K210 | `sdcarddev.c` |
| `/dev/w25q64` | `DEV_SPI` | `SPI_DEV_W25Q64` | K210 | `spidev.c` |
| `/dev/oled` | `DEV_I2C` | `I2C_DEV_OLED` | K210 | `i2cdev.c` |
| `/dev/mpu6050` | `DEV_I2C` | `I2C_DEV_MPU6050` | K210 | `i2cdev.c` |

兼容系统调用 `dev(omode, major, minor)` 与 `open("/dev/...")` 最终都调用
`devicefdalloc()`，不会形成两套设备打开逻辑。普通程序优先使用 `/dev/*`；
`dev()` 只保留给兼容代码和底层接口测试。

### 1.2 注册和初始化顺序

hart 0 的主要初始化顺序为：

```text
fileinit()
  -> statsinit()
  -> fpioa_pin_init()
  -> dmac_init()
  -> k210_devices_init()
  -> spidev_init()
  -> i2cdev_init()
  -> sdcarddev_init()
  -> disk_init()
```

其中：

- `fileinit()` 初始化全局 file table；
- `k210_devices_init()` 初始化板级 controller 锁；
- 各 `*dev_init()` 注册 major 到操作表；
- `disk_init()` 初始化内核文件系统使用的磁盘通路。

QEMU 不注册 K210 的 SD、SPI、I2C 逻辑设备，但保留 console 和 stats。

### 1.3 分层职责

| 层次 | 代表文件 | 职责 |
| --- | --- | --- |
| 系统调用/文件层 | `kernel/syscall/sysfile.c`、`kernel/fs/file.c` | fd、访问权限、引用计数、操作表分发 |
| 路径映射 | `kernel/device.c` | `/dev/*` 到 major/minor 的静态映射 |
| 字符设备适配 | `kernel/devsw/*.c` | 用户参数校验、copyin/copyout、per-open 状态 |
| 板级绑定 | `kernel/board/k210_devices.c` | controller、逻辑设备、片选、地址、频率上限 |
| 底层驱动 | `kernel/driver/*.c` | 寄存器、FIFO、DMA、轮询和硬件时序 |

重要边界：

- 用户指针只在设备适配层通过 `copyin/copyout` 访问；
- controller 和底层驱动只接收内核缓冲区；
- 逻辑设备只描述板级事实，不直接实现寄存器访问；
- 同一总线由 controller `sleeplock` 串行化；
- 设备不支持的 `read/write/ioctl` 必须明确返回 `-1`。

### 1.4 启动期约束

`spi_controllers[]`、`i2c_controllers[]` 等静态对象依赖 `.bss` 零初始化。
K210 使用裸二进制镜像，`.bss` 不包含在 `kernel.bin` 中，因此启动汇编必须
在进入 C 代码前清零 `__bss_start..__bss_end`，并在双核间同步完成状态。

这不是 I2C 的局部约束，而是整个 C 运行环境的前置条件。曾经出现的
`i2c_controllers[0].bus_num` 脏值和 `i2c_init()` load fault，就是启动入口
未清零 `.bss` 的表现。

# I2C 驱动开发记录

## 背景

在 xv6-k210 上移植 I2C 驱动，驱动 SSD1306 OLED 显示屏（128×64，I2C 地址 0x3C）。

K210 的 I2C 控制器是 Synopsys DW APB I2C IP，需要通过 FPIOA 将 I2C 信号映射到物理引脚。

**硬件连接：**
- SCL — 物理引脚 30 (I2C0_SCLK)
- SDA — 物理引脚 31 (I2C0_SDA)
- OLED 地址 — 0x3C (7-bit)

---

## 问题与解决

### 1. PLL 寄存器读回错误

**原因：** PLL 寄存器结构体使用了 `__attribute__((packed, aligned(4)))`，在 K210 上 bitfield 读回异常。

**解决：** 改为从 CPU 频率推算 I2C 时钟频率，硬编码分频系数：

```c
uint32_t v_i2c_freq = sysctl_clock_get_freq(SYSCTL_CLOCK_CPU) / 4;    // 时钟频率：计算 I2C 模块的实际输入时钟频率
uint16_t v_period_clk_cnt = v_i2c_freq / i2c_clk / 2;                 // 时钟周期：计算高低电平各需要维持多少个时钟周期，从而得到想要的 I2C 速率
```

**以下几点是可能的错误：** 调试过程中发现主机发送数据正常，但是从机没有回应ACK，但是后续整理又发现改完 CLK 之后 I2C 驱动就可以正常使用了

### 2. I2C_CON_SPEED 使用错误的计数值

**现象：** 使用 Fast Mode (`I2C_CON_SPEED(1)`) 时，控制器读取 `fs_scl_hcnt/fs_scl_lcnt` 寄存器，但这些寄存器位于 struct 的 `resv2[4]` 填充区域（未初始化），导致 SCL 时钟异常。

**解决：** 改用 Standard Speed (`I2C_CON_SPEED(0)`)，使用 `ss_scl_hcnt/ss_scl_lcnt` 寄存器。

### 3. enable_status 未轮询

**现象：** 硬件 I2C 工作不稳定，有时 ACK 有时无响应。

**原因：** DW APB I2C 控制器写入 `enable` 寄存器后，需要在另一个时钟域同步。直接写 `enable = 0` 可能被忽略，导致寄存器在控制器仍然启用时被修改。

**解决：** 增加 `enable_status` 轮询：

```c
i2c_adapter->enable = 0;
for (int i = 0; i < 1000; i++) {
    if ((i2c_adapter->enable_status & I2C_ENABLE_STATUS_IC_ENABLE) == 0)
        break;
}
// ...配置寄存器...
i2c_adapter->enable = I2C_ENABLE_ENABLE;
for (int i = 0; i < 1000; i++) {
    if ((i2c_adapter->enable_status & I2C_ENABLE_STATUS_IC_ENABLE) != 0)
        break;
}
```

### 4. TX_ABRT 后总线未空闲

**现象：** 地址扫描时大量 NACK 导致 TX_ABRT，返回后立即调用 `i2c_init` 可能冲突。

**原因：** `i2c_send_data` 检测到 TX_ABRT 后直接返回，未等待 `ACTIVITY=0`。

**解决：** 在 TX_ABRT 分支中增加等待总线空闲：

```c
if(i2c_adapter->tx_abrt_source != 0)
{
    while((i2c_adapter->status & I2C_STATUS_ACTIVITY) || !(i2c_adapter->status & I2C_STATUS_TFE))
        ;
    return 1;
}
```

### 5. 缺少 SDA 保持时间

**现象：** 数据字节偶发出错。

**原因：** DW APB I2C 默认 `sda_hold = 0`，即 SDA 在 SCL 跳变后无保持时间，从设备可能采样失败。

**解决：** 设置 SDA 保持时间 ~1.25µs：

```c
i2c_adapter->sda_hold = I2C_SDA_HOLD_TX(v_period_clk_cnt / 4) | I2C_SDA_HOLD_RX(v_period_clk_cnt / 8);
```

### 6. 缺少总线空闲时间

**现象：** 连续 I2C 事务间无停顿。

**原因：** 硬件控制器连续发送 STOP → START 之间没有足够的空闲时间，OLED 来不及处理。

**解决：** 在 `i2c_send_data` 结束时增加 ~5µs 延迟和清除 STOP_DET 标志：

```c
i2c_adapter->clr_stop_det = i2c_adapter->clr_stop_det;
for (volatile int i = 0; i < 200; i++);
```

# I2C 驱动框架

## 当前调用链

```text
open("/dev/oled") 或 open("/dev/mpu6050")
  -> device_path_lookup()
  -> fileopen_device(DEV_I2C, minor)
  -> i2cdev_open()
  -> private_data = const struct i2c_device *

ioctl(fd, I2C_IOCTL_TRANSFER, &rdwr)
  -> fileioctl()
  -> i2cdev_ioctl()
  -> copyin i2c_rdwr_ioctl_data、i2c_msg 和数据
  -> i2c_controller_transfer()
  -> I2C0 controller sleeplock
  -> i2c_init() + i2c_transfer()
  -> copyout 读消息
```

板级设备定义为：

| 逻辑设备 | minor | controller | 地址 | 最大频率 |
| --- | ---: | --- | ---: | ---: |
| OLED | 0 | I2C0 | `0x3c` | 100 kHz |
| MPU6050 | 1 | I2C0 | `0x68` | 50 kHz |

设备地址和速率是板级绑定，不由每次用户消息任意覆盖。`i2cdev_ioctl()` 会拒绝
地址不等于绑定地址的消息，也会拒绝未知 flag、空消息、过长缓冲区或超过
`I2C_MAX_MSGS` 的请求。这样 `/dev/oled` 不能被用来访问 MPU6050。

当前 I2C 设备只实现 ioctl，不提供通用 `read()`/`write()`。组合事务使用最多
两个 `i2c_msg` 表示，例如“写寄存器地址 + repeated START + 读寄存器数据”。

## 用户态消息 ABI

用户态使用 `i2c_msg` 传输数据：

```c
struct i2c_msg {
  uint16 addr;    // 7-bit slave address，必须匹配打开的逻辑设备
  uint16 flags;
#define I2C_M_RD  0x0001
  uint16 len;
  uint8 *buf;     // user-space pointer
};
```

ioctl 参数：

```c
struct i2c_rdwr_ioctl_data {
  uint32 nmsgs;
  struct i2c_msg *msgs;
};
```

内核不能直接解引用 `msgs` 或 `buf`。当前封送顺序为：

1. copyin 顶层 `i2c_rdwr_ioctl_data`；
2. 逐项 copyin `i2c_msg`；
3. 为每个消息分配内核缓冲区；
4. 写消息 copyin，读消息在事务完成后 copyout；
5. 无论成功或失败都释放已分配缓冲区。

## 底层传输策略

`i2c_transfer()` 逐项处理消息：

- 第一条消息正常 START；
- 后续消息设置 repeated START；
- 最后一条消息设置 STOP；
- 读消息先向 `data_cmd` 写入 `I2C_DATA_CMD_CMD` 产生接收时钟；
- 每次事务结束读取 clear 寄存器，清除 TX_ABRT/STOP_DET。

```c
(void)i2c_adapter->clr_tx_abrt;
(void)i2c_adapter->clr_stop_det;
```

底层保留 `DMA_THRESHOLD=16` 的 polling/DMA 选择，但当前全局
`dma_enable=false`，因此正常 I2C 事务实际使用 polling。启用 DMA 前必须单独
验证 repeated START、STOP、abort 清理、超时和 DMA channel 并发，不能只因
长度达到阈值就假定 DMA 路径可靠。

所有等待必须有超时，不能让 shell 永久卡死。调试日志应集中在事务边界、
abort source、status、FIFO level 和 timeout，避免逐字节串口日志改变外设
时序。

## 当前实机状态

- `.bss` 清零修复后，I2C controller 的 `bus_num` 不再是脏值；
- MPU6050 `WHO_AM_I` 已实机读到 `0x68`，证明 I2C0 和基本组合读事务可用；
- OLED 曾出现 `0x3c` probe NACK，不能被“fixed-address binding PASS”或
  用户态成功提示掩盖；
- OLED 问题应继续检查模块地址、上拉、供电、首次事务时序和错误传播。

详细证据链见
[2.文件设备重构K210实机调试记录.md](../调试文档/2.文件设备重构K210实机调试记录.md)。

# SPI 驱动框架

## 当前实现思路

SPI 设备层通过 `/dev/w25q64` 暴露给用户态，数据事务只使用 ioctl
`SPI_IOC_MESSAGE(n)`；通用 `read()` 和 `write()` 当前明确返回 `-1`。

当前分层：

```text
open("/dev/w25q64")
  -> spidev_open()
  -> spi_file_context
       speed_hz = 1 MHz
       mode = mode 0
       bits_per_word = 8
       device = W25Q64 board binding

SPI_IOC_MESSAGE(n)
  -> spidev_ioctl()
  -> copyin transfer 数组和 TX 数据
  -> 合并为一段、最多一页的内核 transfer
  -> spi_controller_transfer()
  -> SPI1 controller sleeplock
  -> spi_init() + spi_set_clk_rate() + spi_transfer()
```

板级 W25Q64 绑定为 SPI1、CS0、mode 0、8 bit，默认 1 MHz、最大 10 MHz。
controller 锁保护同一 SPI bus 的寄存器和事务；per-open 锁保护当前 fd 的
mode/speed 配置以及传输。锁顺序固定为：

```text
spi_file_context.lock -> spi_controller.lock
```

用户缓冲区复制和临时页管理发生在设备适配层，底层控制器只接收内核地址。

DesignWare SSI 底层同时保留 polling 和 DMA。短小或不满足 DMA 对齐、长度、
缓冲区条件的事务走 polling；满足 `spi_can_dma()` 条件的事务才走 DMA。JEDEC
ID 只有 4 字节，实际走 polling。

SPI 采用全双工传输模型：发送一个字节的同时也会接收一个字节。对于 W25Q64 这类 flash，读 JEDEC ID 的真实总线行为不是“只写命令再单独读”，而是：

```text

CS 拉低

发送 0x9f

继续发送 dummy 字节 0xff 0xff 0xff，用这些 dummy 产生时钟

同时从 MISO 收到 ff ef 40 17

CS 拉高

```

用户态可以使用 Linux spidev 风格的 `SPI_IOC_MESSAGE(n)`，把多段 message 传给内核。例如一段发送命令，一段接收数据。内核会把多段 message 合并成一次底层 `spi_transfer()`，这样 CS 会在整个 message 期间保持不释放。

## ioctl message 长度解析

`spidev_ioctl()` 支持从 ioctl command 中解析传输数组长度，逻辑与 Linux spidev 类似：

```text

检查 _IOC_TYPE(cmd) == SPI_IOC_MAGIC

检查 _IOC_NR(cmd) == _IOC_NR(SPI_IOC_MESSAGE(0))

检查 _IOC_DIR(cmd) == _IOC_WRITE

通过 _IOC_SIZE(cmd) 得到 struct spi_ioc_transfer 数组总大小

n_ioc = _IOC_SIZE(cmd) / sizeof(struct spi_ioc_transfer)

```

这样用户态调用 `SPI_IOC_MESSAGE(2)` 时，内核可以知道本次 message 中有 2 段 transfer。旧的 `SPI_IOCTL_TRANSFER` 单段兼容入口已经移除，SPI 数据传输统一走 `SPI_IOC_MESSAGE(n)`。

## CS 保持策略

SPI flash 的很多命令要求 CS 在命令、地址、dummy、数据阶段之间保持拉低。如果每段 transfer 后都释放 CS，外设会把后续字节当作新事务，读出来常见是 `0xff 0x00 0x00` 或全 `0xff`。

当前策略是：

```text
用户态多段 spi_ioc_transfer
  -> spidev_message() 复制并拼接 tx/rx 缓冲
  -> 构造一个内核 spi_transfer
  -> 调用底层 spi_transfer(..., num = 1)
  -> 底层只在这一整段开始时拉低 CS，结束时释放 CS
```

对于 rx-only 段，内核会填充 `0xff` 作为 dummy 发送数据，用于产生 SCLK。

当前实现会把所有段拼接到两张页大小的 TX/RX 缓冲区中，因此单次
`SPI_IOC_MESSAGE(n)` 的总数据长度不能超过 `PGSIZE`。各段的 `rx_buf` 只复制
对应偏移的数据，命令段同时收到的无效字节不会被误当作 JEDEC ID。

## 已修复问题

* 8 bit frame 不能用 `uint32` 读写 FIFO
	* SPI 初始化为 8 bit data frame 时，每个 FIFO entry 对应 1 字节。旧代码在 polling 路径里按 `uint32` 写入和读取，会导致收到的数据错位，JEDEC ID 表现为 `ff 00 00` 或异常值。

	 * 当前根据 frame width 分别使用：

   ```text

   SPI_TRANS_CHAR  -> uint8

   SPI_TRANS_SHORT -> uint16

   SPI_TRANS_INT   -> uint32

   ```

* 长读不能先把 TX 全部塞完再读 RX
	* SPI 是全双工，发送时 RX FIFO 也会不断产生数据。K210 SSI FIFO 深度有限，长读时如果只写 TX、不及时读 RX，RX FIFO 会满，后续传输卡住。
	* 当前 polling 逻辑改成边读边写：

   ```text

   while rx_left:
     先尽量 drain RX FIFO
     再根据 TX FIFO 空位继续填 TX
     如果长时间没有任何进展，触发 timeout 返回错误
   ```

* 等待必须有超时
	* 驱动调试阶段不要写无限等待。当前 polling 路径加入 `SPI_POLL_WAIT_TIMEOUT`，出问题时会打印剩余 `tx_left/rx_left` 和寄存器状态，而不是让 shell 卡死。

## 调试方法

### 1. 确认构建和测试程序

当前正式代码不保留临时 SPI 调试日志，避免串口输出影响正常测试。排查问题时先确认内核和文件系统都已经更新：

```bash
make build platform=k210
make fs platform=k210
make run platform=k210
```

注意：只执行 `make download` 只会更新 `target/fs.img`，不会更新内核驱动代码。修改内核驱动后必须重新构建并启动/烧录新的内核镜像。

最小验证命令是读 JEDEC ID：

```bash
spitest
w25q64
```

正常情况下，W25Q64 应返回类似：

```text
JEDEC: ef 40 17
```

判断要点：
* 用户态应调用 `SPI_IOC_MESSAGE(2)` 或 `SPI_IOC_MESSAGE(1)`，不要再使用旧的 `SPI_IOCTL_TRANSFER`。
* 读 ID 的总线发送内容应是 `9f ff ff ff`，命令后面的 dummy 字节用于产生时钟。
* 第一个接收字节通常是发送命令同时收到的无效字节，真正 ID 是后续 `ef 40 17`。
* 若需要进一步定位，可以临时在 `spidev_message()`、`spi_dw_poll_transfer()` 和 timeout 分支加 `LOG_D`，调完后移除。

如果看到：

```text
JEDEC: ff 00 00
JEDEC: ff ff 81
JEDEC: ff ff ff
```

优先怀疑 CS、MISO/MOSI 接线、frame width、dummy clock 或多段 message 期间 CS 被释放。

### 2. 用逻辑分析仪确认总线

建议连接 4 个通道：

```text
CLK  -> SCLK
MOSI -> MOSI
MISO -> MISO
CS#  -> CS0
GND  -> GND
```

采样率建议至少是 SPI 时钟的 8 到 10 倍。当前 1 MHz SPI 时，逻辑分析仪设置 10 MHz 或更高更稳。

触发方式：

```text
CS# 下降沿触发
```

读 JEDEC ID 时，应该看到：

```text
CS# 先拉低并保持
CLK 出现连续 32 个周期
MOSI 第一个字节是 0x9f，后面是 0xff 0xff 0xff
MISO 第一个字节通常无效，后面是 0xef 0x40 0x17
CS# 最后拉高
```

如果逻辑分析仪上只有 MOSI 有一个脉冲、CLK 基本不动，说明没有产生完整时钟，检查底层 transfer 是否真的发送了总长度字节。

如果 CLK 正常、MOSI 正常，但 MISO 一直高，读到通常是 `0xff`，重点检查：
* MISO 是否接反或悬空。
* flash 是否供电正常，3V3/GND 是否可靠。
* CS 是否接到实际使用的 CS0。
* WP#/HOLD# 是否被拉到有效电平，部分模块需要上拉。

如果 CS 在命令段后短暂拉高，再进入读数据段，说明多段 message 没有被合并成一次底层 transfer，外设会重新解释后续 dummy 字节。

### 3. 调试顺序

推荐按下面顺序排查，不要一开始就改代码：

```text
确认用户态调用
  -> 看 spidev 是否打印 message/n_ioc/tx bytes
确认底层配置
  -> 看 spi_test init/poll start/frame_width/baudr
确认 FIFO 收发
  -> 看 poll tx/poll rx 和 timeout
确认物理总线
  -> 用逻辑分析仪看 CLK/MOSI/MISO/CS
确认外设响应
  -> JEDEC ID 是否为 ef 40 17 或同类厂商 ID
```

调试时先用最小命令 `spitest` 或 `w25q64` 的 JEDEC ID，不要直接做 erase/program。只有 JEDEC ID 稳定正确后，再继续测试读、擦、写。

### 4. 常见现象解释

* `JEDEC: ff 00 00`：命令阶段可能有响应，但后续读数据错位或没有正确采样，常见于 frame width/FIFO 读写宽度错误。
* `JEDEC: ff ff ff`：MISO 一直为高，常见于外设未响应、MISO 悬空、CS 不对、flash 未供电。
* `w25q64` 无法退出或 shell 卡死：驱动可能在等待 FIFO/DMA 完成时没有超时，或长读时 RX FIFO 满后没有继续进展。
* 逻辑分析仪只看到很慢的边沿或单个脉冲：检查 SPI 时钟是否真正启动、采样率是否足够、触发条件是否正确。
* OLED 没显示、SPI flash 也不响应：优先检查 FPIOA 复用和引脚冲突，两个外设可能复用了同一 SPI bus 或 GPIO。

## 注意事项

* per-open 速度现在通过 `SPI_IOC_WR_MAX_SPEED_HZ` 设置，并在每次 controller
  事务前调用 `spi_set_clk_rate()` 转换为硬件 `BAUDR`，不再是只保存参数。
* K210 当前 SPI threshold 配置为 0，`spi_set_clk_rate()` 使用 CPU 时钟计算
  偶数分频值。不能再通过真实硬件上不可靠的 SPI threshold 位域反推输入时钟。
* DMA 路径涉及对齐、transfer width 和一页临时缓冲区容量。虽然
  `spi_can_dma()` 已限制长度和形态，修改 DMA 代码时仍需重点检查未对齐访问、
  边界和超时；基础 JEDEC 测试优先保持 polling。
* 在 RISC-V 上，未对齐的 16/32 bit 访问可能触发异常或行为不稳定。处理用户态字节流时应优先逐字节搬运，除非明确保证对齐。
* 多段 SPI message 中，只要外设协议要求一个完整事务，就必须保证 CS 在这些段之间不释放。

## 当前 SPI1 引脚与实机状态

| K210 FPIOA | SPI 信号 | W25Q64 |
| --- | --- | --- |
| IO15 / `SPI1_D0` | MOSI | DI、IO0、D0 |
| IO16 / `SPI1_D1` | MISO | DO、IO1、D1 |
| IO17 / `SPI1_SCLK` | SCLK | CLK |
| IO18 / `SPI1_SS0` | CS0 | `/CS` |

`SPI1_D0` 在当前标准 SPI 发送路径中就是接 W25Q64 的 D0/DI/MOSI，
`SPI1_D1` 接 D1/DO/MISO。Flash 使用 3.3V 并共地，`/WP` 和 `/HOLD` 应保持
高电平。

重构后曾实机读到 `JEDEC: FF FF FF`。由于同一接线在旧驱动可用，当前已经
先修复新增速度配置中的分频输入时钟问题，但修复后的 JEDEC 结果仍需实机
确认。若仍失败，按“CS、32 个 SCLK、MOSI 的 `0x9f`、MISO 响应、实测频率”
顺序采集四通道波形，再比较旧驱动 receive 模式与当前全双工 polling 时序。


SPI 采用全双工是为了提供统一事务模型。receive-only 阶段仍要发送 dummy
字节产生时钟；`ctrlr1` 等接收数量寄存器必须按 frame 数而不是字节数配置。
DMA 中把字节指针直接强转为 `uint16 *` 或 `uint32 *` 前必须证明地址和长度
满足对齐要求，否则 RISC-V 上可能触发异常或产生不可移植行为。

# SD 卡设备框架

## 两条 SD 使用路径

K210 SD 卡同时服务于：

1. FAT32 文件系统内部的 block/buffer cache 路径；
2. 用户态 `/dev/sdcard` 的原始扇区路径。

两条路径最终都访问同一张卡，但语义不同：

```text
普通文件 open/read/write
  -> FAT32
  -> buffer cache
  -> disk/sdcard driver

open("/dev/sdcard")
  -> sdcarddev
  -> raw 512-byte sector read/write
  -> sdcard driver
```

原始扇区写会绕过 FAT32 和 buffer cache。因此 burn 写完镜像后必须执行
`SDCARD_IOCTL_INVALIDATE_CACHE`，使 FAT 和 buffer cache 丢弃旧内容。否则磁盘
已经更新，内核仍可能继续读取旧目录和旧数据。

## per-open 扇区位置

`sdcarddev_open()` 为每次打开分配：

```c
struct sdcard_file_context {
  struct sleeplock lock;
  uint32 sector;
};
```

初始 sector 为 0。每次成功读写一个完整的 512 字节扇区后自动加一。
`dup()`/`fork()` 共享同一 `struct file`，因此也共享 sector 位置和锁；不同
`open()` 得到独立位置。

当前只接受 `n == 512` 的 read/write，防止设备层隐式处理半扇区读改写。用户
缓冲区先复制到内核页，原始 SD 驱动不直接访问用户地址。

## SD ioctl

| 命令 | 参数 | 说明 |
| --- | --- | --- |
| `SDCARD_IOCTL_SEEK` | 扇区号值 | 设置当前扇区 |
| `SDCARD_IOCTL_TELL` | `uint32 *` | 返回当前扇区 |
| `SDCARD_IOCTL_NSECTORS` | `uint32 *` | 返回卡片总扇区数 |
| `SDCARD_IOCTL_INVALIDATE_CACHE` | 无 | 原始写后失效 FAT/buffer cache |

原始写测试可能破坏文件系统。调试时先确认目标扇区和数据备份，优先使用只读
测试；不要把文件系统正在使用的元数据扇区当作临时测试区。

## SPI0/DMAC 风险

SD 卡底层使用 SPI0，并可能使用 DMAC。DMA 描述、传输宽度、缓冲区所有权或
等待时序错误会表现为文件系统损坏、allocator 异常，甚至在 UART burn 过程中
由 RustSBI 报内存访问异常。发生这类问题时，应：

1. 保存板端完整 panic；
2. 用对应 `target/kernel` 对 `sepc/mepc` 执行 `addr2line`；
3. 检查 `mtval/stval` 指向的实际坏地址；
4. 临时切到 SPI0 polling 做控制变量；
5. 通过固定测试扇区、读回 CRC、guard 和 freelist 检查验证 DMA。

详细 UART 烧录与 SPI0/SD DMA 调试过程见
[1.UART烧录SD卡故障调试记录.md](../调试文档/1.UART烧录SD卡故障调试记录.md)。

# UART 驱动框架

## 当前分层

UART 与 Console 已拆分为字节流驱动层和终端语义层：

```text
用户程序（shell / burn / consoletest）
                │
                │ read / write / ioctl
                ▼
       /dev/console（console.c）
        ├── TTY：回显、控制字符、CR/LF
        └── RAW：原始二进制字节流
                │
                │ uart_read / uart_write
                ▼
          uarths.c（UART 驱动）
        ├── 唯一 RX 软件 ring
        ├── TX 软件 ring
        ├── RX/TX 中断
        └── 波特率与硬件状态
                │
                ▼
       QEMU 16550A / K210 UARTHS
```

依赖方向固定为：

```text
console.c -> uarths.c
```

`uarths.c` 不包含 `console.h`，UART 中断也不会调用 Console 的字符处理函数。用户态只保留 `/dev/console`，旧的 `/dev/uart`、`DEV_UART`、`uartdev.c` 和 `UART_IOCTL_*` 已删除。

## 关键文件

| 文件 | 职责 |
|------|------|
| `kernel/driver/uarths.c` | QEMU/K210 UART 硬件访问、RX/TX ring、中断、阻塞读写、flush 和波特率 |
| `kernel/include/uarths.h` | UART 字节流驱动接口 |
| `kernel/devsw/console.c` | `/dev/console`、TTY/RAW 模式、字符处理和 ioctl |
| `kernel/include/console.h` | Console ioctl、模式和统计结构 |
| `user/app/burn.c` | 使用 Console RAW 模式执行二进制烧录协议 |
| `user/test/consoletest.c` | mode、baud、RX stats 和写路径测试 |

## UART 驱动状态

UART 驱动维护独立的 RX/TX 锁和环形缓冲：

```c
#define UART_RX_BUF_SIZE 32768
#define UART_TX_BUF_SIZE 4096

struct uart_state {
  struct spinlock rx_lock;
  struct spinlock tx_lock;
  char rx_buf[UART_RX_BUF_SIZE];
  char tx_buf[UART_TX_BUF_SIZE];
  uint rx_r;
  uint rx_w;
  uint tx_r;
  uint tx_w;
  uint rx_dropped;
  uint rx_epoch;
  uint32 requested_baud;
};
```

两个 ring 都保留一个空槽区分“空”和“满”，因此对外报告的 RX capacity 是 32767 字节。

锁的职责如下：

| 锁 | 保护内容 |
|----|----------|
| `rx_lock` | RX 数据、读写索引、dropped 和模式边界 epoch |
| `tx_lock` | TX 数据、读写索引以及 TX 中断启停状态 |
| `cons.lock` | Console mode、ANSI 回显、CR/LF 和 EOF 状态 |

Console 不持有 `cons.lock` 调用可能睡眠的 `uart_read()` 或 `uart_write()`，避免 Console 与 UART 形成锁顺序环路。

## RX 接收路径

`uartintr()` 在 RX IRQ 中循环读取硬件 FIFO，并把字节写入唯一 RX ring：

```text
硬件 RX FIFO
  -> uart_hw_getc()
  -> RX ring
  -> wakeup_reason(&uart.rx_r, WAKEUP_DEVICE)
  -> uart_read()
  -> console TTY/RAW 处理
```

RX ring 满时丢弃新字节并增加 `rx_dropped`，不会覆盖尚未读取的数据。一次 IRQ 搬完当前 FIFO 后只唤醒一次读者，避免逐字节重复唤醒。

主要接口：

```c
int  uart_read(char *dst, int n);
int  uart_try_read(char *dst, int n);
void uart_flush_rx(void);
void uart_get_rx_stats(uint32 *info);
```

`uart_read()` 在 ring 为空时睡眠；出现数据后返回当前可用的最多 `n` 字节，不要求等待填满。进程被 killed 时返回 `-1`。

`uart_flush_rx()` 同时清空硬件 FIFO 和软件 RX ring，并递增 `rx_epoch`。阻塞读取者被唤醒后发现 epoch 改变，会返回到 Console 层重新判断当前 TTY/RAW 模式。

## TX 发送路径

用户态 Console 写入使用 4096 字节 TX ring：

```text
consolewrite()
  -> 分块 copyin
  -> uart_write()
  -> TX ring
  -> uartstart()
  -> 硬件 TX FIFO
```

TX ring 满时，进程通过 `sleep(&uart.tx_r, &uart.tx_lock)` 等待空间。`uartstart()` 从 ring 向硬件 FIFO 搬运数据，并在索引前进后唤醒写者。

TX 中断按需管理：

```text
TX ring 非空 -> 开启 TX IRQ
TX IRQ       -> 继续填充硬件 FIFO
TX ring 为空 -> 关闭 TX IRQ
```

这样既能持续发送长输出，也不会在空闲时产生 TX 空中断风暴。

内核 `printf()`、panic 和不允许睡眠的上下文继续通过 `consputc()` -> `uartputc_sync()` 使用同步轮询输出。不能让持有 printf spinlock 的路径进入可能睡眠的 TX ring。

## K210 TX watermark 注意事项

K210 UARTHS 的 TX watermark 条件是：硬件 TX FIFO 中的字节数小于 `txcnt` 时置位 `txwm`。

初始化必须使用：

```c
uarths->txctrl.txcnt = 1;
```

不能设置为 0。FIFO 字节数不可能小于 0，因此 `txcnt = 0` 时 TX IRQ 永远不会触发。其典型现象是：

```text
执行 ls 后只输出一部分
必须敲一次回车才继续输出一段
```

原因是回车产生了 RX IRQ，公共 `uartintr()` 在处理 RX 后顺带调用 `uartstart()`，暂时掩盖了 TX IRQ 不工作的事实。设置 `txcnt = 1` 后，FIFO 清空会触发 TX IRQ，软件 TX ring 能自行持续发送。

## QEMU 16550A 中断位

QEMU 16550A 的 IER 位定义为：

```c
#define IER_RX_ENABLE (1 << 0)
#define IER_TX_ENABLE (1 << 1)
```

RX/TX 中断启停使用 IER 读改写，不能为了切换某一类中断而覆盖另一类中断的状态。bit 0/bit 1 如果写反，会表现为 shell 无法接收输入或 TX 中断行为异常。

## Console TTY 与 RAW 模式

Console 当前提供两种全局模式：

```c
#define CONSOLE_MODE_TTY 0
#define CONSOLE_MODE_RAW 1
```

TTY 模式保持项目原有约定：

* 非规范模式，收到字符即可交给读者。
* 退格、Tab 补全和行编辑由 shell 处理。
* 只回显可打印字符和换行，ANSI 转义序列不回显。
* `Ctrl-P` 在 Console 读取路径中执行 `procdump()`。
* `Ctrl-D` 保持 EOF 语义。
* QEMU 将 `\r` 转换为 `\n`。
* K210 将 Enter 的 `\r\n` 合并为单个 `\n`。

RAW 模式不做任何字符解释：

* `0x00` 到 `0xff` 原样读取。
* 不回显。
* 不处理控制字符。
* 不转换 `\r`/`\n`。
* 读写均使用 UART ring。

设备框架已经支持 `struct file.private_data`，SPI 和 SD 都使用 per-open 状态。
Console 没有使用该字段，而是有意把 TTY/RAW mode 保持为全局终端状态，因为
所有 `/dev/console` fd 最终对应同一个物理控制台和同一条 RX ring。同一时间
仍只允许一个二进制传输会话；某个进程进入 RAW 后，其他 Console 读者也会
受到影响。这是 Console 当前语义选择，不是通用设备框架的限制。

## Console ioctl

当前 Console ioctl 定义如下：

```c
#define CONSOLE_IOCTL_FLUSH_INPUT    0x01
#define CONSOLE_IOCTL_SET_MODE       0x02
#define CONSOLE_IOCTL_GET_MODE       0x03
#define CONSOLE_IOCTL_SET_BAUD       0x04
#define CONSOLE_IOCTL_GET_BAUD_INFO  0x05
#define CONSOLE_IOCTL_GET_RX_STATS   0x06
```

统计结构：

```c
struct console_baud_info {
  uint32 requested;
  uint32 actual;
  uint32 div;
  uint32 clock;
};

struct console_rx_stats {
  uint32 dropped;
  uint32 buffered;
  uint32 capacity;
  uint32 mode;
};
```

`CONSOLE_IOCTL_GET_MODE` 直接通过 ioctl 返回值返回当前 mode；baud info 和 RX stats 通过用户指针 copyout。

模式切换按以下顺序执行：

```text
暂停 RX IRQ
  -> 清空硬件 FIFO 和 RX ring
  -> 重置 Console TTY 状态
  -> 更新 mode
  -> 恢复 RX IRQ
```

TTY→RAW 和 RAW→TTY 都清空输入，避免 shell 残留字符污染二进制协议，也避免协议尾部字节进入 shell。

## 波特率切换

`CONSOLE_IOCTL_SET_BAUD` 由 Console 校验参数，再调用 UART 层的 `uart_set_baud()`。K210 切换顺序为：

```text
等待软件 TX ring 清空
  -> 等待硬件 TX 完成
  -> 暂停 RX IRQ
  -> 排空硬件 RX FIFO
  -> 更新 UARTHS 分频寄存器
  -> 恢复 RX IRQ
```

`burn` 使用同一个 Console fd 完成：

```text
TTY -> RAW -> 可选高波特率 -> 二进制传输
    -> 115200 -> 获取 RX stats -> TTY
```

正常完成和协议错误路径都会经过统一清理逻辑，恢复默认波特率及 TTY 模式。当前 QEMU 路径不实际修改 UART 波特率，只保留接口兼容。

## 构建与验证

基础构建：

```bash
make build platform=qemu
make build platform=k210
make fs
```

QEMU 验证：

```text
启动 shell
执行 consoletest
确认显示：Console test PASSED
执行长文本输出，确认无停顿或死锁
```

K210 实机验证：

```text
1. 在 115200 波特率启动 shell。
2. 连续执行 ls，确认无需敲回车即可完整输出。
3. 执行 consoletest，确认 TTY -> RAW -> TTY 往返。
4. 检查 Enter 的 CR/LF 只产生一次换行。
5. 执行完整 burn 高波特率传输。
6. 人为制造 CRC/协议错误，确认恢复 115200 和 TTY。
7. 检查 RX dropped，并确认 UART 空闲时没有 TX 中断风暴。
```

若长输出必须依靠输入才能继续，优先检查 K210 `txctrl.txcnt` 和 `ie.txwm`；若 shell 完全收不到输入，优先检查 RX IRQ、PLIC 和 QEMU 16550A IER 位定义。
