# 内存管理

## kmalloc/kfree

### 设计目标

原来的内核分配器只提供页级分配接口，一次分配和释放 `PGSIZE` 大小的物理页。页级接口适合页表、用户页、DMA 缓冲区等场景，但对于内核中的小对象和临时数组会造成明显浪费，例如只需要几十字节时也会占用完整 4KB 页。

因此新增一层小对象分配器：

* `kalloc_page()` / `kfree_page()`：继续负责整页物理内存分配。
* `kmalloc()` / `kfree()`：负责小块内核内存分配，内部按需向页分配器申请整页。

这样可以保持页分配器职责单一，同时为驱动、设备层和内核临时对象提供更细粒度的内存管理。

### 基本结构

`kmalloc` 使用固定大小 bucket 的 slab 思路实现。当前支持的对象大小为：

```c
16, 32, 64, 128, 256, 512, 1024, 2048
```

每个 bucket 维护一条 slab 页链表：
* slab_page 的 next 节点表示下一个 slab 链表

```c
struct slab_bucket {
  struct spinlock lock;
  uint obj_size;
  struct slab_page *slabs;
};
```

每个 slab 页开头保存页元信息，后面的空间切分成固定大小对象：
* slab_page 的 free_list 节点，维护一个 slab page 的固定大小对象

```text
一页 4096 字节
+----------------------+-----+-----+-----+-----+-----+
| struct slab_page     | 32B | 32B | 32B | 32B | ... |
+----------------------+-----+-----+-----+-----+-----+
```

```c
struct slab_page {
  uint magic;
  uint obj_size;
  uint total;
  uint free_count;
  struct slab_page *next;
  struct slab_node *free_list;
};
```

空闲对象本身复用为链表节点：

```c
struct slab_node {
  struct slab_node *next;
};
```

### kmalloc 流程


`kmalloc(size)` 的流程如下：`len -> bucket -> slabs -> slab -> node`

1. 如果 `size == 0`，直接返回 `0`。
2. 根据 `size` 选择最小可容纳的 bucket。
3. 在该 bucket 的 slab 链表中查找还有空闲对象的 slab 页。
4. 如果没有可用 slab，则调用 `kalloc_page()` 申请一整页。
5. 在新页开头初始化 `struct slab_page`，剩余空间按 `obj_size` 切成对象，并挂到 `free_list`。
6. 从 `free_list` 弹出一个对象，更新 `free_count`。
7. 返回对象地址。

分配时会用固定字节填充返回对象，方便暴露未初始化使用等问题。

### kfree 流程


`kfree(ptr)` 只释放 `kmalloc()` 返回的小对象，不能用于释放 `kalloc_page()` 返回的整页。

释放流程如下：`ptr -> page/node -> slab -> bucket -> slabs`

1. 如果 `ptr == 0`，直接返回。
2. 通过 `PGROUNDDOWN(ptr)` 找到对象所在的 slab 页。
3. 检查地址范围、`SLAB_MAGIC`、bucket 大小和对象边界，防止释放非法指针。
4. 将对象填充为固定字节，并重新挂回 slab 的 `free_list`。
5. 增加 `free_count`。
6. 如果 `free_count == total`，说明该 slab 页中所有对象都空闲：
    * 从 bucket 的 slab 链表中摘掉该页。
    * 清除 `magic`。
    * 调用 `kfree_page()` 把整页还给页分配器。

注意这里归还整页时调用的是 `kfree_page()`，不是 `kfree()`。因为 `kfree()` 是小对象释放入口，如果用它释放 slab 页会重新进入 slab 释放逻辑。

### 使用约定

* `kalloc_page()` / `kfree_page()` 成对使用。
* `kmalloc()` / `kfree()` 成对使用。
* 页表页、用户物理页、DMA 缓冲区、需要页对齐或完整物理页的对象继续使用页级接口。
* 小对象、指针数组、短生命周期临时结构优先使用 `kmalloc()`，减少整页浪费。

# 进程管理

## 调度算法优化

### 设计目标

原来的 `scheduler()` 使用 xv6 默认的 Round-Robin 思路：每次调度都从 `proc[0]` 开始线性扫描，找到第一个 `RUNNABLE` 进程后切换运行。这个实现简单可靠，但存在两个问题：

* 每轮都从低下标进程开始扫描，严格意义上不是完全公平的轮转。
* 所有进程使用同一种调度策略，无法区分 CPU 密集型任务和外设/IO 唤醒后的交互型任务。

本次优化保留 RR 作为 baseline，同时新增 MLFQ 多级反馈队列作为主调度算法。项目目标不是单纯替换算法，而是结合 K210 嵌入式场景，提高外设事件到来后的用户任务响应能力。

### 构建切换

通过 `Makefile` 的 `SCHED` 参数选择调度算法：

```bash
make run platform=qemu SCHED=rr
make run platform=qemu SCHED=mlfq
make run platform=k210 SCHED=rr
make run platform=k210 SCHED=mlfq
```

对应编译宏：

* `SCHED_RR`：启用 Round-Robin baseline。
* `SCHED_MLFQ`：启用多级反馈队列调度。

当前构建产物统一放在 `build/` 下，不再按 `platform-SCHED` 分目录：

```text
build/kernel
build/user
build/.config
```

`build/.config` 记录本次构建的 `platform`、`SCHED` 和 `LOG_LEVEL`。切换这些参数时，依赖 `build/.config` 的目标会重新编译，避免继续使用旧宏编译出来的目标文件。

注意不要并行执行不同配置的构建命令，例如不要同时运行：

```bash
make build platform=k210 LOG_LEVEL=LOG_LEVEL_INFO
make build platform=k210 LOG_LEVEL=LOG_LEVEL_DEBUG
```

因为它们会共享同一个 `build/` 目录，可能互相覆盖中间产物。需要对比不同配置时，应串行构建。

### 调度框架拆分



调度入口仍然是 `kernel/proc/proc.c` 中的 `scheduler()`，但将“选择哪个进程运行”和“执行上下文切换”拆开：

```c
static struct proc *pick_next_proc(void);
static void run_proc(struct cpu *c, struct proc *p);
```

`run_proc()` 只负责公共切换逻辑：

```text
RUNNABLE -> RUNNING
设置 c->proc
切换到进程内核页表
swtch()
切回内核页表
清空 c->proc
```

具体算法只需要修改 `pick_next_proc()` 及其子函数，避免把算法逻辑散落在上下文切换路径中。

### RR baseline

RR baseline 不再每轮固定从 `proc[0]` 扫描，而是维护一个全局游标：

```c
static int rr_next;
```

调度时从 `rr_next` 开始环形扫描 `proc[]`：

```text
从 rr_next 开始查找 RUNNABLE 进程
找到后更新 rr_next = idx + 1
下一轮从后续位置继续扫描
```

这样可以作为更公平的 baseline，用于和 MLFQ 对比。

### MLFQ 调度策略

MLFQ 使用 4 级队列：

```text
level 0: 最高优先级，时间片 1 tick
level 1: 时间片 2 ticks
level 2: 时间片 4 ticks
level 3: 最低优先级，时间片 8 ticks
```

相关字段加入 `struct proc`：

```c
int queue_level;
int sched_ticks;
uint total_run_ticks;
uint wait_ticks;
uint preempt_count;
uint boost_count;
uint io_wakeup_count;
uint device_wakeup_count;
int last_wakeup_reason;
```

这些字段可以按用途分为两类：

**调度决策字段**

| 字段 | 含义 | 作用 |
| --- | --- | --- |
| `queue_level` | 当前进程所在的 MLFQ 队列层级 | 调度器优先选择高优先级队列中的 `RUNNABLE` 进程。数值越小优先级越高，`MLFQ_TOP_LEVEL` 表示最高优先级。 |
| `sched_ticks` | 进程在当前队列层级内已经运行的 tick 数 | 用来判断是否耗尽当前队列时间片。达到该层级时间片上限后，CPU 密集型进程会被降到下一层队列。 |
| `last_wakeup_reason` | 最近一次唤醒来源 | 记录普通唤醒、timer、IO、device 等来源。MLFQ 可据此识别 IO/设备唤醒进程，并在唤醒时给予短期优先级提升。 |

**观测统计字段**

| 字段 | 含义 | 作用 |
| --- | --- | --- |
| `total_run_ticks` | 进程累计运行 tick 数 | 用于观察进程实际获得的 CPU 时间，CPU 密集型任务通常该值增长较快。 |
| `wait_ticks` | 进程处于 `RUNNABLE` 但尚未被调度的累计 tick 数 | 用于观察等待时间和潜在饥饿情况，也可以辅助评估 boost 是否有效。 |
| `preempt_count` | 进程因时间片结束被抢占的次数 | 用于区分经常跑满时间片的 CPU 密集型任务。 |
| `boost_count` | 进程经历全局 priority boost 的次数 | 用于确认 MLFQ 的防饥饿机制是否周期性生效。 |
| `io_wakeup_count` | 因 IO 完成被唤醒的次数 | 用于观察磁盘/文件系统相关进程的 IO 交互特征。 |
| `device_wakeup_count` | 因设备事件被唤醒的次数 | 用于观察 console、UART、DMAC 等 K210 外设事件对进程唤醒的影响。 |

初始化时，新进程从最高优先级队列开始运行，并将运行、等待、抢占、boost 和唤醒统计清零：

```c
p->queue_level = MLFQ_TOP_LEVEL;
p->sched_ticks = 0;
p->total_run_ticks = 0;
p->wait_ticks = 0;
p->preempt_count = 0;
p->boost_count = 0;
p->io_wakeup_count = 0;
p->device_wakeup_count = 0;
p->last_wakeup_reason = WAKEUP_NORMAL;
```

基本规则：

* 新进程进入最高优先级队列 `level 0`。
* 调度时从 `level 0` 到 `level 3` 依次选择 `RUNNABLE` 进程。
* 同一队列内使用 RR 游标轮转，避免同层进程饥饿。
* 进程因定时器抢占调用 `yield()` 时，累计当前队列运行 tick。
* 如果进程用完整个当前队列时间片，则降到下一层。
* 主动 `sleep()` 不降级，并清空当前 `sched_ticks`，保留交互型任务优势。
* 每隔 `MLFQ_BOOST_INTERVAL` tick 执行一次全局 boost，将非 `UNUSED` 进程提升回最高级，防止低优先级任务长期饥饿。

### 外设唤醒优化

为了体现 K210 嵌入式场景，本次新增 `wakeup_reason()`：

```c
void wakeup_reason(void *chan, int reason);
```

原来的 `wakeup()` 保留，并作为普通唤醒入口：

```c
void wakeup(void *chan)
{
  wakeup_reason(chan, WAKEUP_NORMAL);
}
```

当前唤醒原因包括：

```c
#define WAKEUP_NORMAL 0
#define WAKEUP_TIMER  1
#define WAKEUP_IO     2
#define WAKEUP_DEVICE 3
```

关键路径标记：

* `clockintr()` 中唤醒 `ticks` 使用 `WAKEUP_TIMER`。
* console 输入、UART raw/tx、DMAC 完成使用 `WAKEUP_DEVICE`。
* virtio disk 描述符释放和磁盘请求完成使用 `WAKEUP_IO`。

在 MLFQ 下，如果进程因为 `WAKEUP_IO` 或 `WAKEUP_DEVICE` 被唤醒，则提升一级优先级：

```text
level 3 -> level 2
level 2 -> level 1
level 1 -> level 0
level 0 保持不变
```

这样形成一条面向外设事件响应的链路：

```text
外设中断到来
  -> 驱动处理并唤醒等待进程
  -> wakeup_reason 标记唤醒来源
  -> MLFQ 对 IO/设备唤醒进程短期提权
  -> 用户任务更快获得 CPU 响应事件
```

### 观测方式

`procdump()` 增加调度字段输出。启用 MLFQ 时输出格式为：

```text
pid state  name q run wait preempt boost io dev wake
```

字段含义：

* `q`：当前 MLFQ 队列层级。
* `run`：累计被定时器抢占的运行 tick。
* `wait`：处于 `RUNNABLE` 等待状态的累计 tick。
* `preempt`：被定时器抢占次数。
* `boost`：经历全局 boost 的次数。
* `io`：因 IO 唤醒计数。
* `dev`：因设备唤醒计数。
* `wake`：最近一次唤醒原因。

通过串口输入 `Ctrl-P` 可以打印当前进程表，用于观察 CPU 密集任务是否逐步降级、设备/IO 唤醒任务是否获得优先级提升。

### Demo 程序

新增两个用户态 demo 程序：

```text
cpuburn
iotest
```

`cpuburn` 用于制造 CPU 密集型后台负载：

```bash
cpuburn
cpuburn 800
cpuburn 800 1
```

参数含义：

* 第一个参数是运行 tick 数，默认 `400`。
* 第二个参数控制是否周期性打印运行进度，默认 `0`，设置为 `1` 时每隔一段时间输出 elapsed。
* 程序循环执行整数计算，默认只打印启动和结束信息，避免后台程序抢占串口输出。
* 在 MLFQ 下，长时间运行的 `cpuburn` 预期会逐步降到低优先级队列。

`iotest` 用于模拟周期性阻塞和文件 IO 响应：

```bash
iotest
iotest 20 10 8
```

参数含义：

* 第一个参数是测试轮数，默认 `20`。
* 第二个参数是每轮 `sleep` 的 tick 数，默认 `10`。
* 第三个参数是每轮读写的 512B 块数，默认 `8`。
* 每轮 wakeup 后写入并读回 `iotest.tmp`，输出：

```text
iotest: round=0 wake_delay=0 io_ticks=1
```

其中：

* `wake_delay` 表示 `sleep` 预期时间之外额外等待的 tick。
* `io_ticks` 表示本轮文件写入和读回消耗的 tick。

```bash

```

进入 shell 后运行：


* `iotest` 因 sleep/IO 唤醒更容易保持较高响应。
* 通过 `Ctrl-P` 查看 `q`、`run`、`io`、`dev`、`wake` 等字段，观察调度状态变化。

### 当前效果

该方案保留了原 xv6 调度路径的锁语义和上下文切换方式，只在进程选择策略、时间片统计、唤醒原因标记上扩展：

* RR 可作为对照组，验证基础公平性。
* MLFQ 可改善交互型和外设事件驱动任务的响应。
* 全局 boost 避免 CPU 密集型任务被长期压在低优先级队列。
* `wakeup_reason()` 将 K210 的 UART、DMAC 等外设事件和调度策略联系起来，更适合实机项目展示。



# 设备管理

## I2C

### 框架说明

* 用户态使用 `i2c_msg` 传输数据：发送和接收使用两个 `i2c_msg`
```c
struct i2c_msg {
    uint16 addr;    // slave address (7-bit)
    uint16 flags;
#define I2C_M_RD    0x0001  // read data, from slave to master
    uint16 len;     // msg length
    uint8 *buf;     // user-space pointer to msg data
};
```

* 内核态使用传输统一入口：`i2c_transfer`
    * 支持 `DMA` 和 `POLLing` 模式，后续再支持中断模式
    * 通过 `len` 大小选择传输模式：`DMA_THRESHOLD`

### 修改说明

* `ioctl`：修改参数传递形式，进行三次数据拷贝过程
* 优化 `i2c` 驱动框架，实现读和写分离，接入统一入口 `i2c_transfer`
    * 增加 `repeat start` 和 `stop`
    * 支持多种传输模式

### 问题说明

* 因为现在读和写事务分离，所以必须要要增加 `repeat start` 和 `stop`，注意怎么去改数据：
    * 随着数据一起发送： `i2c_adapter->data_cmd` 
* 接收也必须先发送：`I2C_DATA_CMD_CMD`
* 必须清除硬件状态：触发一次 `volatile` 寄存器读取
```c
(void)i2c_adapter->clr_tx_abrt;
(void)i2c_adapter->clr_stop_det;
```
* 必须控制使用 DMA 传输的场景，要是一定长度才好：`DMA_THRESHOLD`
* 当前不能开启 `LOG_LEVEL_DEBUG` 否则会读取失败，原因不详
* 当前驱动还是有些小问题后续再继续优化
* 等待 `done` 一定要有超时时间，否则程序卡死
* 合理的日志打印和程序设计，当前很多时候就是对程序的设计不清除，导致自己也没办法明确知道如何调试

## SPI

### 当前实现思路

当前 SPI 设备层通过 `devsw` 暴露给用户态，用户态使用 `ioctl` 提交传输请求。底层驱动使用 DesignWare SSI 控制器，当前主要走 polling 路径，DMA 路径保留但不作为默认路径。SPI 通过 spi_config.h 进行配置工作

SPI 采用全双工传输模型：发送一个字节的同时也会接收一个字节。对于 W25Q64 这类 flash，读 JEDEC ID 的真实总线行为不是“只写命令再单独读”，而是：

```text
CS 拉低
发送 0x9f
继续发送 dummy 字节 0xff 0xff 0xff，用这些 dummy 产生时钟
同时从 MISO 收到 ff ef 40 17
CS 拉高
```

用户态可以使用 Linux spidev 风格的 `SPI_IOC_MESSAGE(n)`，把多段 message 传给内核。例如一段发送命令，一段接收数据。内核会把多段 message 合并成一次底层 `spi_transfer()`，这样 CS 会在整个 message 期间保持不释放。

### ioctl message 长度解析

`spidev_ioctl()` 支持从 ioctl command 中解析传输数组长度，逻辑与 Linux spidev 类似：

```text
检查 _IOC_TYPE(cmd) == SPI_IOC_MAGIC
检查 _IOC_NR(cmd) == _IOC_NR(SPI_IOC_MESSAGE(0))
检查 _IOC_DIR(cmd) == _IOC_WRITE
通过 _IOC_SIZE(cmd) 得到 struct spi_ioc_transfer 数组总大小
n_ioc = _IOC_SIZE(cmd) / sizeof(struct spi_ioc_transfer)
```

这样用户态调用 `SPI_IOC_MESSAGE(2)` 时，内核可以知道本次 message 中有 2 段 transfer。旧的 `SPI_IOCTL_TRANSFER` 单段兼容入口已经移除，SPI 数据传输统一走 `SPI_IOC_MESSAGE(n)`。

### CS 保持策略

SPI flash 的很多命令要求 CS 在命令、地址、dummy、数据阶段之间保持拉低。如果每段 transfer 后都释放 CS，外设会把后续字节当作新事务，读出来常见是 `0xff 0x00 0x00` 或全 `0xff`。

当前策略是：

```text
用户态多段 spi_ioc_transfer
  -> spidev_message() 复制并拼接 tx/rx 缓冲
  -> 构造一个内核 spi_transfer
  -> 调用底层 spi_transfer(..., num = 1)
  -> 底层只在这一整段开始时拉低 CS，结束时释放 CS
```

对于 rx-only 段，内核会填充 `0xff` 作为 dummy 发送数据，用于产生 SCLK。

### 已修复问题

1. 8 bit frame 不能用 `uint32` 读写 FIFO

   SPI 初始化为 8 bit data frame 时，每个 FIFO entry 对应 1 字节。旧代码在 polling 路径里按 `uint32` 写入和读取，会导致收到的数据错位，JEDEC ID 表现为 `ff 00 00` 或异常值。

   当前根据 frame width 分别使用：

   ```text
   SPI_TRANS_CHAR  -> uint8
   SPI_TRANS_SHORT -> uint16
   SPI_TRANS_INT   -> uint32
   ```

2. 长读不能先把 TX 全部塞完再读 RX

   SPI 是全双工，发送时 RX FIFO 也会不断产生数据。K210 SSI FIFO 深度有限，长读时如果只写 TX、不及时读 RX，RX FIFO 会满，后续传输卡住。

   当前 polling 逻辑改成边读边写：

   ```text
   while rx_left:
     先尽量 drain RX FIFO
     再根据 TX FIFO 空位继续填 TX
     如果长时间没有任何进展，触发 timeout 返回错误
   ```

3. 等待必须有超时

   驱动调试阶段不要写无限等待。当前 polling 路径加入 `SPI_POLL_WAIT_TIMEOUT`，出问题时会打印剩余 `tx_left/rx_left` 和寄存器状态，而不是让 shell 卡死。

### 调试方法

#### 1. 确认构建和测试程序

当前正式代码不保留临时 SPI 调试日志，避免串口输出影响正常测试。排查问题时先确认内核和文件系统都已经更新：

```bash
make build platform=k210
make fs platform=k210
make run platform=k210
```

注意：只执行 `make download` 只会更新 `target/fs.img`，不会更新内核驱动代码。修改内核驱动后必须重新构建并启动/烧录新的内核镜像。

最小验证命令是读 JEDEC ID：

```bash
spitest
w25q64
```

正常情况下，W25Q64 应返回类似：

```text
JEDEC: ef 40 17
```

判断要点：

* 用户态应调用 `SPI_IOC_MESSAGE(2)` 或 `SPI_IOC_MESSAGE(1)`，不要再使用旧的 `SPI_IOCTL_TRANSFER`。
* 读 ID 的总线发送内容应是 `9f ff ff ff`，命令后面的 dummy 字节用于产生时钟。
* 第一个接收字节通常是发送命令同时收到的无效字节，真正 ID 是后续 `ef 40 17`。
* 若需要进一步定位，可以临时在 `spidev_message()`、`spi_dw_poll_transfer()` 和 timeout 分支加 `LOG_D`，调完后移除。

如果看到：

```text
JEDEC: ff 00 00
JEDEC: ff ff 81
JEDEC: ff ff ff
```

优先怀疑 CS、MISO/MOSI 接线、frame width、dummy clock 或多段 message 期间 CS 被释放。

#### 2. 用逻辑分析仪确认总线

建议连接 4 个通道：

```text
CLK  -> SCLK
MOSI -> MOSI
MISO -> MISO
CS#  -> CS0
GND  -> GND
```

采样率建议至少是 SPI 时钟的 8 到 10 倍。当前 1 MHz SPI 时，逻辑分析仪设置 10 MHz 或更高更稳。

触发方式：

```text
CS# 下降沿触发
```

读 JEDEC ID 时，应该看到：

```text
CS# 先拉低并保持
CLK 出现连续 32 个周期
MOSI 第一个字节是 0x9f，后面是 0xff 0xff 0xff
MISO 第一个字节通常无效，后面是 0xef 0x40 0x17
CS# 最后拉高
```

如果逻辑分析仪上只有 MOSI 有一个脉冲、CLK 基本不动，说明没有产生完整时钟，检查底层 transfer 是否真的发送了总长度字节。

如果 CLK 正常、MOSI 正常，但 MISO 一直高，读到通常是 `0xff`，重点检查：

* MISO 是否接反或悬空。
* flash 是否供电正常，3V3/GND 是否可靠。
* CS 是否接到实际使用的 CS0。
* WP#/HOLD# 是否被拉到有效电平，部分模块需要上拉。

如果 CS 在命令段后短暂拉高，再进入读数据段，说明多段 message 没有被合并成一次底层 transfer，外设会重新解释后续 dummy 字节。

#### 3. 调试顺序

推荐按下面顺序排查，不要一开始就改代码：

```text
确认用户态调用
  -> 看 spidev 是否打印 message/n_ioc/tx bytes
确认底层配置
  -> 看 spi_test init/poll start/frame_width/baudr
确认 FIFO 收发
  -> 看 poll tx/poll rx 和 timeout
确认物理总线
  -> 用逻辑分析仪看 CLK/MOSI/MISO/CS
确认外设响应
  -> JEDEC ID 是否为 ef 40 17 或同类厂商 ID
```

调试时先用最小命令 `spitest` 或 `w25q64` 的 JEDEC ID，不要直接做 erase/program。只有 JEDEC ID 稳定正确后，再继续测试读、擦、写。

#### 4. 常见现象解释

* `JEDEC: ff 00 00`：命令阶段可能有响应，但后续读数据错位或没有正确采样，常见于 frame width/FIFO 读写宽度错误。
* `JEDEC: ff ff ff`：MISO 一直为高，常见于外设未响应、MISO 悬空、CS 不对、flash 未供电。
* `w25q64` 无法退出或 shell 卡死：驱动可能在等待 FIFO/DMA 完成时没有超时，或长读时 RX FIFO 满后没有继续进展。
* 逻辑分析仪只看到很慢的边沿或单个脉冲：检查 SPI 时钟是否真正启动、采样率是否足够、触发条件是否正确。
* OLED 没显示、SPI flash 也不响应：优先检查 FPIOA 复用和引脚冲突，两个外设可能复用了同一 SPI bus 或 GPIO。

### 注意事项

* `SPI_IOCTL_INIT` 当前读取了用户态传入的 `clk_rate`，但底层仍主要使用默认 `baudr` 配置；如果需要严格控制 SPI 频率，后续应把 `clk_rate` 转换为 `baudr`。
* DMA 路径涉及对齐和 transfer width，指针强转后直接解引用存在未对齐风险。调试 flash 基础功能时优先使用 polling。
* 在 RISC-V 上，未对齐的 16/32 bit 访问可能触发异常或行为不稳定。处理用户态字节流时应优先逐字节搬运，除非明确保证对齐。
* 多段 SPI message 中，只要外设协议要求一个完整事务，就必须保证 CS 在这些段之间不释放。
