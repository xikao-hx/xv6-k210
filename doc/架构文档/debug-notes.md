# 真实调试问题复盘

## 1. 复盘目的

这份文档用于记录项目中真实遇到的问题，重点不是只写“最后怎么改”，而是记录完整定位过程。

秋招面试中，经常会被问：

- 你遇到过最难的问题是什么？
- 你怎么定位驱动问题？
- QEMU 能跑但真板不能跑时你怎么排查？
- 你怎么证明问题已经解决？

因此每个问题都建议按统一模板记录。

## 2. 问题复盘模板

每个问题建议包含：

```text
问题现象：
  看到什么错误、日志、异常行为。

复现条件：
  平台、命令、硬件连接、波特率、镜像版本。

初步怀疑：
  当时怀疑哪些方向。

定位过程：
  看了哪些代码，加了哪些日志，做了哪些对比实验。

根因分析：
  最终确认的原因。

修复方案：
  改了哪些代码或参数。

验证方式：
  如何证明修复有效。

复盘收获：
  这个问题说明了什么工程经验。
```

后续每次解决一个真实问题，都可以按这个格式追加。

## 3. K210 Enter 输入异常

### 问题现象

K210 真板上使用 shell 时，按 Enter 后输入行为异常。QEMU 中没有同样问题。

### 初步怀疑

- shell 行编辑逻辑问题。
- console 输入处理问题。
- K210 串口和 QEMU 串口输入字符不同。

### 根因分析

K210 上 Enter 会发送：

```text
'\n'
'\r'
```

而 QEMU 常见路径只需要处理 `\n`。如果内核 console 把 `\r` 也交给 shell，shell 会收到额外字符，导致输入表现异常。

### 修复方案

在 K210 平台的 `consoleintr()` 路径中过滤 `\r`，避免它进入 shell 行编辑逻辑。

### 验证方式

- K210 真板上进入 shell。
- 多次执行 `ls`、`cat`、`burn` 等命令。
- 确认按 Enter 后不会出现多余字符或命令异常。

### 复盘收获

串口输入行为和终端环境有关，QEMU 正常不代表真板正常。遇到 console 问题时，需要打印或抓取实际收到的字符值，而不是只看屏幕表现。

## 4. UART 二进制传输被 console 干扰

### 问题现象

通过 UART 发送 `fs.img` 时，板端接收二进制数据不稳定，协议包解析失败，可能出现 CRC 错误或 INFO/ACK 阶段异常。

### 初步怀疑

- 主机发送脚本打包错误。
- UART 读写接口逐字节调用开销过大。
- console 输入路径吞掉或处理了二进制字节。
- K210 UARTHS RX FIFO 太小导致溢出。

### 根因分析

普通 UART RX 中断路径是：

```text
uartintr()
  -> uartgetc()
  -> consoleintr()
```

这条路径适合 shell 输入，不适合任意二进制流。二进制数据中可能包含 `\n`、`\r`、退格等字符，console 会按照交互输入处理它们。

另外，K210 UARTHS RX FIFO 很小，如果用户态逐字节 ioctl 读取或在热路径中频繁打印，很容易错过后续字节。

### 修复方案

实现 `DEV_UART` raw 模式：

```text
UART_IOCTL_RAW_START:
  关闭 RX 中断
  清空硬件 FIFO
  开启 raw 模式
  恢复 RX 中断

raw mode:
  uartintr()
    -> uart_raw_input()
    -> raw ring buffer

UART_IOCTL_RAW_END:
  退出 raw 模式
  清空 raw buffer
  恢复 console 输入路径
```

板端 `burn` 在 raw 模式下通过 `read(uart_fd, ...)` 从 ring buffer 读取二进制协议流。

### 验证方式

- 运行 `burn`。
- 主机端发送 INFO/DATA/DONE。
- 确认 INFO 能稳定 ACK，DATA 能逐扇区写入并 ACK。
- 多次传输确认不再被 shell/console 干扰。

### 复盘收获

console 和 raw 设备是两种不同语义。驱动开发中不能只考虑“能收到字符”，还要考虑数据路径是否适合目标场景。二进制协议应该走 raw buffer，而不是复用行编辑路径。

## 5. 高波特率 UART 接收不稳定

### 问题现象

提高 UART baud 后，烧写 `fs.img` 时可能出现 CRC 错误、ACK 超时、包丢失或协议同步失败。

### 初步怀疑

- baud 分频不准确。
- 主机和板端实际 baud 不一致。
- K210 UARTHS FIFO 太小。
- 板端处理 DATA 后刷新 OLED 或打印日志耗时过长。
- SD 卡写入期间没有及时接收后续字节。

### 根因分析

UART 数据到达速度提高后，任何慢操作都可能导致 RX FIFO 溢出。调试中发现 OLED I2C 刷屏和 `printf()` 都不适合放在数据热路径中。

另外，baud 切换如果没有同步流程，可能出现主机已经切到新 baud，而板端仍在旧 baud，或反过来的情况。

### 修复方案

- 使用 raw ring buffer 缓冲中断接收数据。
- 数据阶段使用 stop-and-wait，板端写完 SD 并 ACK 后，主机才发下一包。
- OLED 只做稀疏进度显示，例如每 128 个扇区刷新一次。
- raw 模式期间避免 `printf()`。
- 增加两步 baud 切换同步。
- 提供 `UART_IOCTL_GET_BAUD_INFO` 查询 requested、actual、div、clock。

### 验证方式

- 使用 115200 baud 完成基础烧写。
- 使用较高 baud 重复烧写。
- 观察主机重试次数、CRC 错误和 ACK 超时。
- 对比 OLED 刷新频率调整前后的稳定性。

### 复盘收获

嵌入式串口传输不是只改 baud 就能提速。高 baud 下需要一起考虑 FIFO 深度、中断响应、用户态处理耗时、外设写入耗时和调试输出开销。

## 6. raw 写 SD 卡后读到旧文件系统内容

### 问题现象

UART 烧写 `fs.img` 完成后，SD 卡内容已经被写入，但系统中后续 `ls`、`exec` 或文件访问可能仍然表现为旧内容。

### 初步怀疑

- SD 卡写入失败。
- FAT32 镜像没有完整发送。
- 文件系统缓存没有更新。

### 根因分析

`burn` 通过 `DEV_SDCARD` 直接写 SD 卡扇区：

```text
burn.c
  -> write(sdcard_fd, payload, 512)
  -> sdcarddev_write()
  -> sdcard_write_sector()
```

这条路径绕过了 FAT32 和 buffer cache。如果之前系统已经访问过文件系统，内核可能还保留旧目录项或旧块缓存。

### 修复方案

在 `DEV_SDCARD` 中增加：

```text
SDCARD_IOCTL_INVALIDATE_CACHE
```

烧写完成后调用：

```text
fat32_invalidate()
binvalidate(0)
```

使后续 FAT32 访问重新从 SD 卡读取。

### 验证方式

- 烧写新 `fs.img`。
- 执行 `ls`、`cat` 或运行新用户程序。
- 确认看到的是新镜像内容。
- 连续烧写多次，确认不会读到旧缓存。

### 复盘收获

绕过文件系统直接写块设备时，必须考虑缓存一致性。驱动和文件系统不是孤立模块，raw block 操作会影响上层缓存语义。

## 7. I2C OLED 调试问题

### 问题现象

K210 上 I2C 驱动 OLED 时，曾出现从设备不 ACK、通信不稳定、数据偶发错误等问题。

### 初步怀疑

- FPIOA 引脚映射错误。
- I2C 时钟频率错误。
- 控制器寄存器配置不完整。
- OLED 地址或硬件接线错误。

### 根因分析与修复

已有调试记录中总结了几个关键点：

- PLL 寄存器 bitfield 读回异常，改为根据 CPU 频率推算 I2C 输入时钟。
- `I2C_CON_SPEED` 使用错误会导致控制器读取未初始化的 fast-mode 计数寄存器，改用 standard speed 对应计数。
- 写 `enable` 后需要轮询 `enable_status`，等待跨时钟域同步完成。
- `TX_ABRT` 后需要等待总线空闲。
- 设置 SDA hold time，避免从设备采样不稳定。
- 连续事务之间增加短暂 bus free time。

### 验证方式

- 使用 OLED 初始化和显示接口验证。
- 用逻辑分析仪观察 SCL/SDA 波形。
- 对比软件 I2C 与硬件 I2C 表现。

### 复盘收获

I2C 这类低速总线问题很适合用逻辑分析仪定位。驱动不能只看寄存器写入，还要关注控制器手册中的 enable 同步、hold time、bus idle 等时序要求。

## 8. QEMU 正常但 K210 失败

### 问题现象

某些代码在 QEMU 中正常，但在 K210 真板上失败。

### 可能原因

- 链接地址或入口符号不匹配。
- K210 外设寄存器配置错误。
- FPIOA 引脚复用未配置。
- 外部中断没有打开。
- UART 输入行为不同。
- SD 卡、SPI、I2C 真实时序问题。
- 内核使用了不适合 freestanding 环境的代码。
- 内核中使用了 `float` 或 `double`，但没有保存/恢复浮点上下文。

### 定位方法

建议按以下顺序排查：

1. 确认 `make build platform=k210` 编译的是 K210 分支。
2. 确认链接脚本地址和 RustSBI 加载地址一致。
3. 在早期启动路径加最小串口输出。
4. 对比 QEMU 和 K210 的 `#ifdef QEMU` 分支。
5. 如果是外设问题，先验证引脚复用和时钟。
6. 如果是中断问题，检查 PLIC enable、hart enable、外设 pending/clear。
7. 如果是总线问题，用逻辑分析仪看波形。
8. 如果是文件系统问题，先脱离 FAT32 做 raw sector 测试。

### 复盘收获

QEMU 是验证通用逻辑的工具，真板是验证硬件适配的工具。双平台项目的优势是可以把问题分成“通用内核 bug”和“平台相关 bug”。
