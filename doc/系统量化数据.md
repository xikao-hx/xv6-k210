# 系统量化数据

## 进程调度

### 实验目标

验证 MLFQ 调度器在后台 CPU 密集负载下，对交互型和 IO 型任务的响应优化效果。

对比关注点：

* CPU 密集型任务是否会因为持续占用时间片而逐级降级。
* 周期性 sleep/IO 的任务是否能保持较高优先级。
* 在后台负载存在时，IO 型任务唤醒后是否能及时继续运行。
* 周期性 boost 是否能防止低优先级任务长期饥饿。

### 实验环境

构建配置：

```bash
make build platform=k210 SCHED=mlfq
make fs
```

调度策略：

```text
MLFQ_LEVELS = 4
level 0 时间片 1 tick
level 1 时间片 2 ticks
level 2 时间片 4 ticks
level 3 时间片 8 ticks
MLFQ_BOOST_INTERVAL = 200 ticks
```

观测工具：

* `cpuburn`：CPU 密集型任务，持续整数计算。
* `iotest`：周期性 sleep 后执行文件写入和读回。
* `Ctrl-P`：触发 `procdump()` 输出调度状态。

### 实验命令

启动多个后台 CPU 密集任务，再运行前台 IO 测试：

```bash
cpuburn 800 &
cpuburn 800 &
cpuburn 800 &
iotest 20 10 8
```

参数说明：

* `cpuburn 800`：运行约 800 tick。
* `iotest 20 10 8`：运行 20 轮，每轮 sleep 10 tick，并读写 8 个 512B 数据块。

### procdump 结果

示例输出：

```text
 PID  STATE  NAME          Q    RUN   WAIT  PREEMPT  BOOST    IO   DEV  WAKE
----  -----  ------------  -  -----  -----  -------  -----  ----  ----  ----
   1  sleep  initcode      0      0      0        0     31     0     0     0
   2  sleep  sh            0      0      0        0     31     0   140     3
 141  sleep  iotest        1      2      0        2      0     0     0     1
```

后台 CPU 密集任务运行时的典型现象：

```text
cpuburn 进程逐步降到 q=3
run / preempt 持续增长
iotest 保持在高优先级队列附近
sh 因 console 输入唤醒记录 DEVICE wakeup
```

字段解释：

| 字段 | 含义 |
| --- | --- |
| Q | MLFQ 队列层级，0 最高，3 最低 |
| RUN | 被定时器抢占累计运行 tick |
| WAIT | 处于 RUNNABLE 等待状态的累计 tick |
| PREEMPT | 被定时器抢占次数 |
| BOOST | 被周期性 priority boost 提升次数 |
| IO | IO 唤醒次数 |
| DEV | 设备唤醒次数 |
| WAKE | 最近一次唤醒原因，1=timer，2=IO，3=device |

### 结果分析

#### CPU 密集任务降级

`cpuburn` 持续执行整数计算，基本不会主动 sleep。它会不断用完整个时间片，因此在 MLFQ 中逐级下降：

```text
level 0 -> level 1 -> level 2 -> level 3
```

这说明调度器能够识别 CPU 密集型任务，并将其压到低优先级队列，减少对交互型任务的影响。

#### IO/交互任务响应

`iotest` 每轮都会主动 sleep，然后执行文件 IO。它不会长期连续占用 CPU，因此不会像 `cpuburn` 一样快速降级。

实测中：

```text
wake_delay = 0
avg_io = 2
max_io = 2
```

说明在后台 CPU 密集负载存在时，IO 型任务仍能及时响应，且 IO 耗时稳定。

#### 设备唤醒路径

shell 进程的 `DEV` 计数增长，表示 console/UART 输入通过 `WAKEUP_DEVICE` 唤醒 shell。

这条路径体现了嵌入式场景下的调度优化：

```text
UART/console 输入
  -> 驱动 wakeup_reason(..., WAKEUP_DEVICE)
  -> MLFQ 对设备唤醒任务短期提权
  -> shell 更快获得 CPU
```

#### 防饥饿机制

`BOOST` 字段增长表示周期性 priority boost 生效。即使 `cpuburn` 被降到低优先级队列，也会周期性回到高优先级队列，避免长期饥饿。

### 总结

本次调度实验表明：

1. MLFQ 能够将持续占用 CPU 的 `cpuburn` 任务降至低优先级队列。
2. 周期性 sleep/IO 的 `iotest` 在后台负载下仍能保持 `wake_delay=0`。
3. `avg_io=2`、`max_io=2`，说明 IO 延迟稳定。
4. console/UART 等设备唤醒路径能通过 `WAKEUP_DEVICE` 参与调度提权。
5. 周期性 boost 能避免低优先级任务饥饿。

因此，当前调度器相比普通 RR 更适合 K210 这类事件驱动、外设交互频繁的嵌入式场景。

### 每扇区时间预算（2M，实测 11.18ms/扇区）

`每扇区周期 = 57.52s / 5144 扇区 = 11.18ms`，分解：

| 环节 | 计算 | 时间 | 占比 | 依据 |
|---|---|---|---|---|
| DATA 帧线时 | 527B × 10bit ÷ 2Mbps | 2.635ms | 23.6% | 物理可精确计算（8N1 = 1 start + 8 data + 1 stop） |
| ACK 帧线时 | 20B × 10bit ÷ 2Mbps | 0.100ms | 0.9% | magic4+hdr7+payload5+crc4 = 20B |
| SD 写 | `sd_ticks_total=1727` × 5.03ms ÷ 5144 | 1.69ms | 15.1% | 板端实测（含一次 cache flush） |
| 固定开销 | 11.18 − 上三项 | 6.76ms | 60.4% | 见下节分析 |
| **合计** | | **11.18ms** | 100% | |

### 理论值如何计算

**吞吐公式**：`吞吐 = 512 字节 / 每扇区周期`

```
每扇区周期 = DATA线时 + ACK线时 + SD写 + 固定开销
```

- 2M 理论：`512 / 11.18ms = 45,788 B/s = 44.7 KiB/s`，与实测 **44.7 完全吻合** —— 本分解式解释了实测值的全部来源。
- 线时极限（不计任何开销）：`512 / 2.635ms = 189.8 KiB/s` —— 物理天花板，但 stop-and-wait 协议永远达不到。
- 加 SD 写：`512 / (2.635+0.1+1.69)ms = 113 KiB/s`。
- 再加固定开销 → 落到 44.7，说明固定开销 ~6.76ms 是当前真正的瓶颈（占 60%）。

### 为什么调度/等待时间变大会拖慢速率

**根因是除法关系 + stop-and-wait 全串行**，二者叠加：

1. **速率是除法**：`吞吐 = 512 / 每扇区周期`，而每扇区周期是**串行加法**（DATA线时 + ACK线时 + SD写 + 固定开销）。任何一项变大，速率都是**反比**下降，不是线性。
2. **stop-and-wait 无重叠**：主机必须收到 ACK 才发下一帧。板端收帧 → SD 写 → 发 ACK 的**每一步处理都在关键路径上**，无法与下一帧并行。板端让出/唤醒期间主机在空等，什么都不做。

板端调度时间进入关键路径的具体路径（[burn.c:675](user/app/burn.c#L675) 收帧 → [burn.c:742](user/app/burn.c#L742) SD写 → [burn.c:754](user/app/burn.c#L754) 发ACK）：

```text
主机发 DATA → 板端 read() 阻塞让出 CPU → UART 中断唤醒 → 等下一个 tick 调度 → 板端写SD → 发ACK → 主机收ACK → 发下一帧
                                    ↑                                    ↑
                         （这段时间主机在等，无任何数据流动）
```

- 唤醒**不等于立刻运行**：MLFQ 每 **tick**（时钟中断）才做一次调度决策，进程需等下一个 tick 才拿到 CPU。**唤醒延迟 ≤ 1 tick（5.03ms）**。
- 在等 CPU 期间 ACK 未发出 → 主机收不到 ACK → 不发下一帧 → 整条流水停顿，tick 时长直接成为每帧的潜在等待上限。

**实测佐证**（阶段 14，见 UART 烧录调试记录）：tick 假设错误变成 125ms/tick 时，数据循环 `sleep(1)` 实为 125ms/帧，每帧周期多了 ~120ms，吞吐从 **12 KiB/s 掉到 4 KiB/s**（约 1/3）。正常 tick=5.03ms 时，I/O 唤醒路径提权（`WAKEUP_DEVICE`）使 iotest 实测 `wake_delay=0`，调度仅占 ~0.1ms，非主瓶颈。

**推论**：当前瓶颈是 6.76ms 固定开销（主机侧往返占大头），调度时间已不是主项。要提速只能**减少每帧次数**（多扇区 DATA 包）或**打破 stop-and-wait 串行**（滑动窗口），压缩单帧内的调度/等待收益有限。

### 固定开销 6.76ms 的构成（量级推断，未逐项打点）

固定开销是每帧一次、与波特率基本无关的串行等待，成分：

1. **主机侧往返（最大头，推断 ~ms 级）**：Python `pyserial` 每次 `write`+`flush`+`read` 循环的解释器开销、USB-TTL 适配器批量传输延迟（CH340/CP210x 常见 ms 级）。主机每帧先等 ACK 再发下一帧，这两段等待都在周期内。
2. **板端调度让出/唤醒（~0.1ms 级）**：burn 收完一帧 → SD 写（释放 CPU）→ 等 ACK 回填时 `read` 阻塞。MLFQ 每 tick 5.03ms 调度一次，I/O 唤醒路径提权，iotest 实测 `wake_delay=0`（见上文调度实验）。上下文切换 ~µs 级，非主项。
3. **DMA 中断处理（~0.01ms 级，可忽略）**：DW UART1 DMA 模式每帧 2 次中断（done + CTI），每次 ISR 读 dar、harvest ring、re-arm，µs 级。RDA 收割已禁用（见 `k210-dw-uart-rda-dma-race`）。

**为什么升更高波特率收益有限**：波特率只压缩 2.635ms 的 DATA 线时。2M → 4M 线时降到 1.32ms，但 6.76ms 固定开销不变，周期 11.18 → 9.81ms，吞吐 44.7 → 50.9 KiB/s（仅 +14%）。要数量级提升只能减少**每帧次数**（见提升方向）。

### 提升方向

只有减少**每帧固定开销的摊销次数**才有意义：

1. 多扇区 DATA 包（推荐）：payload 512 → 4096（8 扇区/帧），帧格式不变，2M 下 4111B 帧线时 20.6ms 摊 8 个扇区，周期 ≈ 20.6 + 6.76 + 8×1.69 ≈ 40.8ms → `4096B / 40.8ms ≈ 98 KiB/s`。
2. 滑动窗口流水线：不等 ACK 连续发，需重构握手与重传，改动大、风险高。
