# 外设驱动调试文档

# I2C 驱动开发记录

## 背景

在 xv6-k210 上移植 I2C 驱动，驱动 SSD1306 OLED 显示屏（128×64，I2C 地址 0x3C）。

K210 的 I2C 控制器是 Synopsys DW APB I2C IP，需要通过 FPIOA 将 I2C 信号映射到物理引脚。

**硬件连接：**
- SCL — 物理引脚 30 (I2C0_SCLK)
- SDA — 物理引脚 31 (I2C0_SDA)
- OLED 地址 — 0x3C (7-bit)

---

## 问题与解决

### 1. PLL 寄存器读回错误

**原因：** PLL 寄存器结构体使用了 `__attribute__((packed, aligned(4)))`，在 K210 上 bitfield 读回异常。

**解决：** 改为从 CPU 频率推算 I2C 时钟频率，硬编码分频系数：

```c
uint32_t v_i2c_freq = sysctl_clock_get_freq(SYSCTL_CLOCK_CPU) / 4;    // 时钟频率：计算 I2C 模块的实际输入时钟频率
uint16_t v_period_clk_cnt = v_i2c_freq / i2c_clk / 2;                 // 时钟周期：计算高低电平各需要维持多少个时钟周期，从而得到想要的 I2C 速率
```

**以下几点是可能的错误：** 调试过程中发现主机发送数据正常，但是从机没有回应ACK，但是后续整理又发现改完 CLK 之后 I2C 驱动就可以正常使用了

### 2. I2C_CON_SPEED 使用错误的计数值

**现象：** 使用 Fast Mode (`I2C_CON_SPEED(1)`) 时，控制器读取 `fs_scl_hcnt/fs_scl_lcnt` 寄存器，但这些寄存器位于 struct 的 `resv2[4]` 填充区域（未初始化），导致 SCL 时钟异常。

**解决：** 改用 Standard Speed (`I2C_CON_SPEED(0)`)，使用 `ss_scl_hcnt/ss_scl_lcnt` 寄存器。

### 3. enable_status 未轮询

**现象：** 硬件 I2C 工作不稳定，有时 ACK 有时无响应。

**原因：** DW APB I2C 控制器写入 `enable` 寄存器后，需要在另一个时钟域同步。直接写 `enable = 0` 可能被忽略，导致寄存器在控制器仍然启用时被修改。

**解决：** 增加 `enable_status` 轮询：

```c
i2c_adapter->enable = 0;
for (int i = 0; i < 1000; i++) {
    if ((i2c_adapter->enable_status & I2C_ENABLE_STATUS_IC_ENABLE) == 0)
        break;
}
// ...配置寄存器...
i2c_adapter->enable = I2C_ENABLE_ENABLE;
for (int i = 0; i < 1000; i++) {
    if ((i2c_adapter->enable_status & I2C_ENABLE_STATUS_IC_ENABLE) != 0)
        break;
}
```

### 4. TX_ABRT 后总线未空闲

**现象：** 地址扫描时大量 NACK 导致 TX_ABRT，返回后立即调用 `i2c_init` 可能冲突。

**原因：** `i2c_send_data` 检测到 TX_ABRT 后直接返回，未等待 `ACTIVITY=0`。

**解决：** 在 TX_ABRT 分支中增加等待总线空闲：

```c
if(i2c_adapter->tx_abrt_source != 0)
{
    while((i2c_adapter->status & I2C_STATUS_ACTIVITY) || !(i2c_adapter->status & I2C_STATUS_TFE))
        ;
    return 1;
}
```

### 5. 缺少 SDA 保持时间

**现象：** 数据字节偶发出错。

**原因：** DW APB I2C 默认 `sda_hold = 0`，即 SDA 在 SCL 跳变后无保持时间，从设备可能采样失败。

**解决：** 设置 SDA 保持时间 ~1.25µs：

```c
i2c_adapter->sda_hold = I2C_SDA_HOLD_TX(v_period_clk_cnt / 4) | I2C_SDA_HOLD_RX(v_period_clk_cnt / 8);
```

### 6. 缺少总线空闲时间

**现象：** 连续 I2C 事务间无停顿。

**原因：** 硬件控制器连续发送 STOP → START 之间没有足够的空闲时间，OLED 来不及处理。

**解决：** 在 `i2c_send_data` 结束时增加 ~5µs 延迟和清除 STOP_DET 标志：

```c
i2c_adapter->clr_stop_det = i2c_adapter->clr_stop_det;
for (volatile int i = 0; i < 200; i++);
```

# SPI 驱动开发记录

## 调试记录一：启动阶段使用 sleeplock 导致 load access fault

### 现象

SPI 驱动接入 SD 卡启动路径后，内核在 `disk_init()` 阶段崩溃，串口输出如下：

```text
xv6 kernel is booting

scause 0x0000000000000005
sepc=0x00000000800243ec stval=0x0000000000000038
panic: kerneltrap
backtrace:
0x0000000080023b40
0x00000000800293b6
0x0000000080029424
0x00000000800297d2
0x0000000080029d1a
0x000000008002b446
0x00000000800211ee
0x000000008002019e
```

`scause=5` 表示 load access fault，`sepc` 是发生异常的指令地址，`stval`
是该指令尝试读取的虚拟地址。这里 `stval=0x38` 是非常典型的“空指针加
结构体字段偏移”访问。

### 定位过程

首先使用带调试信息的内核 ELF 把 `sepc` 和 backtrace 地址转换为函数及源码
位置：

```sh
riscv64-unknown-elf-addr2line -e target/kernel -f -C \
  0x800243ec 0x80023b40 0x800293b6 0x80029424 \
  0x800297d2 0x80029d1a 0x8002b446 0x800211ee 0x8002019e
```

转换后得到的关键调用链为：

```text
main
  -> disk_init
  -> sdcard_init
  -> sd_write_data
  -> spi_write
  -> spi_transfer
  -> acquiresleep
```

`sepc` 对应 `acquiresleep()` 中下面一行：

```c
lk->pid = myproc()->pid;
```

再使用反汇编确认故障指令：

```sh
riscv64-unknown-elf-objdump -dSl \
  --start-address=0x800243c0 \
  --stop-address=0x80024420 target/kernel
```

相关指令为：

```asm
jalr  ... <myproc>
lw    a5,56(a0)
```

RISC-V 函数返回值保存在 `a0`。当 `myproc()` 返回 `NULL` 时，第二条指令
实际读取的地址就是：

```text
0x0 + 56 = 0x38
```

这与异常寄存器中的 `stval=0x38` 完全一致，因而可以确认不是 SPI MMIO
寄存器地址错误，而是 `myproc()` 返回空指针。

### 根因

当时 hart 0 的启动顺序是先执行：

```text
disk_init()
  -> sdcard_init()
  -> SPI 传输
```

之后才执行：

```text
userinit()
```

`procinit()` 只初始化进程表，并不会让当前 CPU 进入某个进程上下文。在
`userinit()` 创建首个用户进程并由调度器真正运行它之前，`c->proc` 仍为
`NULL`，所以 `myproc()` 返回 `NULL`。睡眠锁除了记录持有者 PID，发生竞争
时还要调用 `sleep()`，因此不能直接用于没有当前进程的启动期路径。

当时 CPU 使用的是全局内核页表，其低地址未映射，所以读取 `0x38` 立即产生
load access fault。本工程运行用户进程时会安装 `p->kpagetable`，并通过
`upg2ukpg()` 把用户页按相同低虚拟地址映射到进程内核页表，只是清除
`PTE_U`。因此还要注意：如果另一个内核空指针错误发生在进程上下文中，并且
用户地址 0 所在页已映射，那么对 `NULL+offset` 的访问可能不会立即报错，
而会错误地访问用户页。原故障能够稳定得到 `stval=0x38`，依赖的是它发生在
尚无当前进程的启动阶段。

### 修复原则

1. controller 锁只在 SPI 子系统或板级设备初始化时初始化一次，不能在每次
   `spi_transfer()` 中重新初始化。
2. 启动期 SD 卡初始化不能直接进入依赖 `myproc()` 的睡眠锁竞争路径。可以
   提供仅供单 hart 启动阶段使用的底层传输入口，或者选择不需要进程上下文
   且符合传输时延约束的锁方案。
3. 不能只把 `myproc()` 判空后令 `pid=0`。一旦锁发生竞争，`sleep()` 仍然
   要求存在当前进程，这种修改只能掩盖第一处崩溃。
4. 启动期无锁入口只能在其他 hart 和用户进程尚未开始并发访问 SPI 时使用；
   进入正常运行阶段后，所有共享 SPI bus 的事务仍必须由 controller 锁
   串行化。

### 验证

修复后启动过程应越过 `disk_init()`，继续出现类似输出：

```text
SDHC/SDXC detected
hart 0 init done
hart 1 starting
init: starting sh
```

这说明故障已从“启动期进程上下文/锁使用错误”中解除。后续仍需运行 SD
读写测试和 SPI 设备测试，确认启动期入口与正常运行期入口没有破坏总线互斥。

## 调试记录二：spidev_ioctl() 持锁直接返回导致自死锁

### 现象

内核和 shell 均能正常启动，但运行 `spitest` 后只输出：

```text
$ spitest
SPI dev test
============
```

之后既没有 panic，也没有 JEDEC ID 或失败信息，测试进程永久不返回。

### 根据输出缩小范围

`spitest` 在打印标题后依次执行：

```text
open("/dev/w25q64")
SPI_IOC_RD_MAX_SPEED_HZ
SPI_IOC_WR_MAX_SPEED_HZ
再次 open("/dev/w25q64")
其他配置检查
SPI_IOC_MESSAGE(2)
```

程序没有打印 `FAIL: dev(DEV_SPI)`，说明第一次 `open()` 已经成功。真正访问
SPI FIFO、片选和 W25Q64 的 `SPI_IOC_MESSAGE(2)` 位于多个配置 ioctl 之后，
所以此时不能先假定是 SPI 硬件轮询或 DMA 卡死，应先检查标题输出与 message
之间的配置路径。

### 锁控制流分析

当时 `spidev_ioctl()` 的结构如下：

```c
acquiresleep(&spidev->lock);

switch(cmd) {
case SPI_IOC_RD_MAX_SPEED_HZ:
  value = spidev->speed_hz;
  return copyout(p->pagetable, arg, (char *)&value, sizeof(value));

case SPI_IOC_WR_MAX_SPEED_HZ:
  /* ... */
  return 0;
}

releasesleep(&spidev->lock);
return ret;
```

`case` 中的直接 `return` 绕过了函数尾部的 `releasesleep()`。第一次读取默认
速率时，执行过程是：

```text
acquiresleep()
  -> lock->locked = 1
copyout()
return
  -> 未释放 spidev->lock
```

随后同一个进程发起写速率 ioctl，再次执行：

```c
acquiresleep(&spidev->lock);
```

睡眠锁发现 `lock->locked == 1`，于是进入：

```c
while(lk->locked) {
  sleep(lk, &lk->lk);
}
```

持锁者和等待者是同一个进程。该进程已经睡眠，无法继续执行到任何释放锁的
路径，也没有其他执行者能够替它释放这把 per-open 锁，因此形成自死锁：

```text
持有锁
  -> 再次申请同一把非递归锁
  -> 等待自己释放
  -> 永久睡眠
```

### 动态验证方法

如果仅通过静态控制流还不能确认，可以在锁前后临时增加日志：

```c
printf("spidev_ioctl: before lock cmd=%p\n", cmd);
acquiresleep(&spidev->lock);
printf("spidev_ioctl: after lock cmd=%p\n", cmd);
```

复现时第二次 ioctl 会打印 `before lock`，但不会打印 `after lock`。进一步
检查进程表可以看到 `spitest` 处于 `SLEEPING` 状态，等待通道 `chan` 指向
这把 sleeplock。该证据可以把“硬件 busy loop”与“睡眠锁等待”区分开：

- 硬件轮询卡住时，进程仍在 CPU 上运行，PC 位于 SPI polling/DMA 等待代码；
- 睡眠锁死锁时，进程状态为 `SLEEPING`，PC 不会继续越过 `acquiresleep()`。

### 修复

持锁后的所有分支统一通过函数尾部退出，不在 `switch` 中直接 `return`：

```c
acquiresleep(&spidev->lock);

switch(cmd) {
case SPI_IOC_RD_MAX_SPEED_HZ:
  value = spidev->speed_hz;
  ret = copyout(p->pagetable, arg, (char *)&value, sizeof(value));
  break;

case SPI_IOC_WR_MAX_SPEED_HZ:
  if(copyin(p->pagetable, (char *)&value, arg, sizeof(value)) < 0) {
    ret = -1;
    break;
  }
  spidev->speed_hz = value;
  ret = 0;
  break;

default:
  /* 解析并执行 SPI_IOC_MESSAGE(n)，错误同样使用 break 退出。 */
  break;
}

releasesleep(&spidev->lock);
return ret;
```

修复时需要审计所有持锁后的错误分支，包括 `copyin/copyout` 失败、非法 ioctl
command、消息分配失败和长度校验失败，确保它们都不会绕过解锁。对于包含多种
资源的函数，可以使用统一的 `out_unlock`/`done` 清理标签，但必须保证资源
释放顺序与获取顺序相反。

### 验证

修复锁泄漏后，`spitest` 应能越过配置 ioctl 并执行到消息传输。即使后续因
per-open 默认值、最大速率或设备上下文生命周期问题报告 `FAIL`，只要测试
能够继续打印这些结果和 JEDEC ID，就说明原来的 ioctl 自死锁已经解除。例如：

```text
SPI dev test
============
JEDEC: EF 40 17
SPI test PASSED, failures=0
```

其中 `EF 40 17` 还说明 SPI1、CS0、8-bit 全双工消息以及 W25Q64 的 JEDEC
读取链路已经正常工作。

## 调试记录三：多次 open 覆盖共享 dev 指针导致 use-after-free

### 现象

修复 ioctl 锁泄漏后，`spitest` 能继续执行，但在第二次打开并关闭设备后，
进入 JEDEC 消息传输时发生 load access fault：

```text
$ spitest
SPI dev test
FAIL: independent SPI open state
FAIL: SPI sscause 0x0000000000000005
sepc=0x0000000080029c9a stval=0x0000000482ca03b0
panic: kerneltrap
backtrace:
0x0000000080023b40
0x00000000800293b6
0x0000000080029424
0x000000008002a7ae
0x0000000080023650
0x0000000080026c56
0x00000000800262f6
0x000000008002919a
peed exceeded board limit
```

`FAIL: SPI speed exceeded board limit` 被异常输出拆成了 `FAIL: SPI s` 和
`peed exceeded board limit`。这是双 hart 串口输出交错的结果，不能把拼接后
的单行当作一条完整异常信息。`panic()` 在打印 panic 和 backtrace 之后才设置
全局 `panicked` 标志，在该窗口中另一个 hart 仍可能输出已经开始的测试文本。
定位时应优先使用 `scause/sepc/stval` 和 backtrace，而不是依赖字符出现顺序。

### 地址定位

使用当前发生故障的 `target/kernel` 解析地址：

```sh
riscv64-unknown-elf-addr2line -e target/kernel -f -C \
  0x80029c9a 0x80023b40 0x800293b6 0x80029424 \
  0x8002a7ae 0x80023650 0x80026c56 0x800262f6 0x8002919a
```

得到的关键调用链为：

```text
usertrap
  -> syscall
  -> sys_ioctl
  -> fileioctl
  -> spidev_message
  -> spi_transfer
```

`sepc=0x80029c9a` 位于 `spi_transfer()` 查找 controller 的位置：

```c
struct spi_controller *spi_ctrl = spi_ctrls[dev->bus_num];
acquiresleep(&spi_ctrl->lock);
```

对应反汇编的主要步骤是：

```asm
lwu   a5,0(a0)       # 读取 dev->bus_num
slli  a4,a5,0x3      # bus_num * sizeof(pointer)
add   a5,a5,a4       # &spi_ctrls[dev->bus_num]
ld    s1,0(a5)       # 读取 spi_ctrls 数组项时触发异常
```

`stval=0x482ca03b0` 不是任何合法 SPI MMIO 地址，而是使用损坏的
`dev->bus_num` 计算出的数组访问地址。因此问题不在 `acquiresleep()` 本身，
而在传入 `spi_transfer()` 的 `dev` 已经失效。

### 根因还原

当时的打开逻辑为每次 open 分配一个 `struct spi_device`，但把指针保存到共享
的静态 `spidev` 对象中：

```c
dev = kmalloc(sizeof(*dev));
f->private_data = spidev;
spidev->dev = dev;
```

关闭逻辑又通过共享对象读取并释放该指针：

```c
struct spi_device *dev =
    ((struct spidev_data *)f->private_data)->dev;
kfree(dev);
```

`spitest` 的执行序列恰好触发了这个所有权错误：

```text
fd1 = open()
  -> 分配 dev_A
  -> shared_spidev->dev = dev_A

fd2 = open()
  -> 分配 dev_B
  -> shared_spidev->dev = dev_B，dev_A 指针丢失

close(fd2)
  -> kfree(shared_spidev->dev)
  -> dev_B 被释放，但 shared_spidev->dev 仍指向 dev_B

fd1 执行 SPI_IOC_MESSAGE
  -> spidev_message(shared_spidev->dev)
  -> 使用已经释放的 dev_B
```

slab 分配器释放对象时会把对象空间用于空闲链表节点。`struct spi_device` 的
第一个字段正好是 `bus_num`，所以释放后该字段可能被空闲链表指针覆盖。
`spi_transfer()` 再把这个值当作数组下标，最终访问
`spi_ctrls[垃圾值]`，产生本次 load access fault。

前面的 `FAIL: independent SPI open state` 也是同一设计错误的早期信号：
两个 fd 并没有持有独立的打开状态，而是同时读写静态 `spidev` 中的共享配置
和共享 `dev` 指针。测试失败后继续执行，才进一步演变成 use-after-free。

### 正确的对象与所有权关系

物理设备描述和打开实例必须分开：

```c
struct spi_device {
  /* 板级固定属性，生命周期覆盖整个内核运行期。 */
  spi_device_num_t bus_num;
  spi_chip_select_t chip_select;
  uint32 max_speed_hz;
};

struct spidev_file_context {
  /* 每次 open 的可变配置。 */
  const struct spi_device *device;
  uint32 speed_hz;
  uint8 mode;
  uint8 bits_per_word;
  struct sleeplock lock;
};
```

推荐的生命周期是：

```text
静态 spi_device
  -> 只描述 bus/CS/最大频率
  -> 不执行 kfree()

每次 open 的 spidev_file_context
  -> kmalloc()
  -> private_data 指向它
  -> 保存 const spi_device *
  -> 最后一个 struct file 引用关闭时 kfree()
```

两个打开实例可以指向同一个物理 `spi_device`，这不等于复制了两个物理设备；
它们只是分别保存默认速率、mode 和 bits-per-word。执行事务时获取共享
controller 锁，在锁内根据当前 file context 配置 SPI 控制器，再访问同一个
bus/CS。

如果设计明确要求所有 fd 共享速度和 mode，那么这些可变字段也应放入共享
设备对象，并由一把共享锁保护，同时修改 `spitest` 的 per-open 独立性预期。
不能一方面让各 fd 使用不同的锁，另一方面又让它们修改同一个共享配置。

### 防御性检查与验证

底层接口还应在数组访问前校验：

```c
if(dev == 0 || dev->bus_num >= SPI_DEVICE_MAX ||
   spi_ctrls[dev->bus_num] == 0)
  return -1;
```

该检查不能替代正确的生命周期管理，但能把 use-after-free 或配置错误转化为
可诊断的 `-1`，避免直接越界访问。修复后应重复执行 `spitest`，并特别确认：

1. 第二次 open/close 后，第一个 fd 仍能读取 JEDEC ID；
2. 连续多次运行测试不会因上一次运行遗留的共享配置而改变默认值；
3. `close(fd2)` 只释放 fd2 的 file context，不影响 fd1；
4. `EF 40 17` 能稳定返回，且不再出现 `scause=5`。

## 调试记录四：把静态设备对象交给 kfree() 导致 panic

### 现象

另一个中间版本运行 `spitest` 时出现：

```text
$ spitest
SPI dev test
FAIL: default SPI speed
FAIL: set per-open SPI speed
panic: kfree
backtrace:
0x0000000080023b40
0x0000000080027876
0x000000008002a53e
0x0000000080023254
0x0000000080026698
0x00000000800262f6
0x000000008002919a
FAIL: independent SPI open state
```

这个问题与上一节的 use-after-free 来自不同的代码迭代：

- 上一节释放的是动态分配的 `dev_B`，随后又继续使用它；
- 本节则直接把静态对象地址传给 `kfree()`，分配器立即检测到非法指针并
  panic。

### 回溯定位

解析 backtrace：

```sh
riscv64-unknown-elf-addr2line -e target/kernel -f -C \
  0x80023b40 0x80027876 0x8002a53e 0x80023254 \
  0x80026698 0x800262f6 0x8002919a
```

关键调用链为：

```text
usertrap
  -> syscall
  -> sys_close
  -> fileclose
  -> spidev_close
  -> kfree
  -> panic
```

这说明 panic 发生在关闭第二个测试 fd 时，而不是 SPI message 或 JEDEC
传输过程中。

### 根因

当时 `spidev_open()` 从静态设备表取得对象：

```c
struct spidev_data *spidev = spidevs[f->minor];
f->private_data = spidev;
```

`spidevs[]` 指向的是编译期定义在内核数据段中的静态对象，并非
`kmalloc()` 的返回值。但 `spidev_close()` 无条件执行：

```c
if(f->private_data)
  kfree(f->private_data);
```

因此实际发生的是：

```text
静态内核对象地址
  -> f->private_data
  -> kfree(静态对象地址)
  -> panic("kfree")
```

本工程的 slab `kfree()` 会先检查指针所在页是否位于可分配物理内存范围内，
然后检查 slab magic、对象大小和对象边界。内核静态数据段地址不满足这些
条件，所以在错误进一步破坏分配器前就触发了 panic。这是分配器的保护行为，
不是分配器本身出错。

### 调试方法：建立分配与释放对照表

遇到 `panic: kfree` 时，不应首先怀疑“双重释放”，而应沿 backtrace 找到
具体释放点，并逐一回答：

| 指针 | 来源 | 所有者 | 允许释放的位置 |
| --- | --- | --- | --- |
| 静态设备描述 | 全局/静态初始化 | 内核设备表 | 不释放 |
| file context | `spidev_open()` 中 `kmalloc()` | `struct file` | 最后一次 `fileclose()` |
| ioctl message 数组 | `spidev_get_ioc_message()` 中 `kmalloc()` | 当前 ioctl | ioctl 结束路径 |
| TX/RX 页缓冲 | `kalloc_page()` | 当前 message | message 的统一清理路径 |

必须满足“谁分配、谁负责释放”的对称关系：

```text
kmalloc()    <-> kfree()
kalloc_page() <-> kfree_page()
静态对象      <-> 不释放
```

不能根据“指针保存在 `private_data` 中”就推断它一定需要 `kfree()`；
`private_data` 只表示设备私有关联，不表达所有权。

### 修复

如果 `private_data` 直接指向静态设备描述，则 `close()` 不应释放它：

```c
static int
spidev_close(struct file *f)
{
  f->private_data = 0;
  return 0;
}
```

如果设备需要 per-open 配置，则应在 `open()` 中明确分配 file context：

```c
ctx = kmalloc(sizeof(*ctx));
if(ctx == 0)
  return -1;

ctx->device = spi_devices[f->minor];
ctx->speed_hz = SPI_DEFAULT_SPEED_HZ;
f->private_data = ctx;
```

对应的 `close()` 只释放这个 context：

```c
ctx = f->private_data;
if(ctx) {
  f->private_data = 0;
  kfree(ctx);
}
```

`fileclose()` 只有在 `struct file.ref` 下降到 0 后才调用设备的 `close()`，
所以 `dup()` 和 `fork()` 共享同一个 `struct file/private_data` 时，不应由
任意一次用户态 `close(fd)` 提前释放 context。

### 验证

修复后至少执行以下场景：

1. 单次 `open -> ioctl -> close`；
2. 同一设备同时打开两个 fd，先关闭第二个，再使用第一个；
3. `dup()` 后分别关闭两个 fd；
4. 连续多次运行 `spitest`；
5. 检查失败路径中 message、TX/RX 缓冲和 file context 均只释放一次。

测试即使仍报告默认速率或上限配置错误，也不应再出现 `panic: kfree`。配置
断言失败和内存所有权错误必须分开处理，不能因为 JEDEC 读取尚未执行就把
panic 误判为 SPI 硬件故障。

## 附录：空指针解引用的通用诊断方法 — stval 与结构体偏移

### 核心思路

RISC-V 的 `stval` 在 Load/Store access fault 中保存的是**指令尝试访问的虚拟地址**。当 `stval` 是一个很小的值（通常是 `0x00`、`0x08`、`0x10`、`0x18`、`0x20`、`0x38` 等对齐地址）时，几乎一定是**空指针 + 结构体字段偏移**：

```
stval ≈ NULL(0x0) + offsetof(结构体, 被访问字段)
```

这是因为内核的 NULL 页（`0x0 ~ 0xFFF`）通常没有映射，或者虽然有映射但权限不足，所以 CPU 发起的对该地址的访问会立即触发缺页或权限异常。

### 反推步骤

1. **查 `stval`**：记下该值。
2. **算偏移**：如果 `stval` 很小（< 4096），大概率是 `NULL + 字段偏移`。偏移量就是 `stval` 本身。
3. **找结构体**：用 `addr2line` 从 `sepc` 反查出错的源文件行号，找到被解引用的结构体指针。
4. **对偏移**：根据结构体的字段布局，看哪个字段的偏移等于 `stval`。

### 典型偏移速查表

下表汇总了本项目的实际案例：

| `stval` | 可能含义（取决于结构体） | 案例 |
|---|---|---|
| `0x00` | 访问结构体的**第一个字段** | `ptr->bus_num`、`ptr->flags` |
| `0x08` | 第三个字段（4B 对齐）或第二个字段中的第 8 字节位置 | I2C `i2c_ctrl->i2c_data.speed_hz`（见下文） |
| `0x38` | 第 14 个字段（4B）或第 7 个字段（8B） | SPI `myproc()->pid`（`0 + 56 = 0x38`） |
| `0x48` 起 | 更大的偏移或指针本身是垃圾值 | SPI `dev->bus_num` use-after-free 后被链表指针覆盖 |

### 示例：I2C 空指针（`stval=0x8`）

**现场信息：**

```
scause 0x0000000000000005   /* Load access fault */
sepc   0x0000000080029d2a
stval  0x0000000000000008
```

**反推过程：**

```
addr2line 得: i2c_dw_init @ kernel/driver/i2c.c:92
```

第 89~92 行的代码：

```c
struct i2c_controller *i2c_ctrl = i2c_ctrls[i2c_num];
// ...
uint32_t i2c_clk = i2c_ctrl->i2c_data.speed_hz;  /* ← 崩在这里 */
```

检查结构体布局，确认偏移吻合：

```c
struct i2c_controller {          /* 偏移 */
    i2c_device_number_t bus_num;  /* 0x00 (4B) */
    struct i2c_dw_data i2c_data;  /* 0x04 —— */
        uint8 index;              /* 0x04 (1B) */
        // 3B padding            /* 0x05~0x07 */
        uint32 speed_hz;         /* 0x08 ◄── stval=0x8 匹配！ */
        dmac_channel_number_t chan_tx;  /* 0x0C */
        ...
    ...
};
```

**根因：** `i2c_ctrls[1]` 未被板级文件初始化（只有 `I2C_DEVICE_0` 定义了控制器），值为 NULL。`i2c_init()` 在循环中先调用了 `i2c_dw_init(i)` 后才判断 `i2c_ctrls[i] == 0`，导致对 `i=1` 的解引用。

```c
void i2c_init(void) {
    for (int i = 0; i < I2C_DEVICE_MAX; i++) {
        i2c_dw_init(i);          /* BUG: i2c_ctrls[1] == NULL 时在此处崩溃 */
        if(i2c_ctrls[i] == 0)   /* 检查在调用之后，永远执行不到 */
            continue;
    }
}
```

**修复：** 将 NULL 检查移到 `i2c_dw_init()` 之前。

### 示例：SPI `myproc()` 返回 NULL（`stval=0x38`）

（详见本文档「启动阶段使用 sleeplock 导致 load access fault」一节。）

```c
lk->pid = myproc()->pid;  /* myproc() 返回 NULL，NULL + 56 = 0x38 */
```

`struct proc` 中 `pid` 字段的偏移恰好是 56（0x38）。

### 局限与陷阱

1. **地址 0 页被映射时不会报 fault。** 如果内核映射了用户地址 `0x0` 所在的页（例如进程内核页表通过 `upg2ukpg()` 映射了用户页），那么 `NULL + offset` 的访问可能不会触发异常，而是错误地读写用户空间的数据，产生更难定位的静默数据损坏。

2. **非空但损坏的指针。** 如果 `stval` 是一个很大的数（如 `0x482ca03b0`），说明指针不是 NULL 而是被垃圾值覆盖了。这通常是 use-after-free 的特征（slab 空闲链表指针覆盖了已释放对象的第一个字段），参见本文档「多次 open 覆盖共享 dev 指针导致 use-after-free」一节。

3. **`stval=0` 的特殊情况。** 如果 `stval=0`，可能是访问结构体第一个字段，也可能是 `NULL->array[index]` 其中 index 也为 0。需要结合反汇编确认具体是哪种。

### 定位流程总结

```
收到 panic: kerneltrap
       │
       ├── 读取 scause / sepc / stval
       │
       ├── scause=5/7/13/15 ? (Load/Store fault)
       │       │
       │       ├── stval 很小 (< 0x1000) ?
       │       │       │
       │       │       ├── 几乎肯定是空指针 + 字段偏移
       │       │       │    → addr2line: 找到源文件和解引用的指针
       │       │       │    → 比较偏移与 struct layout
       │       │       │    → 找出哪个指针为 NULL 并追查原因
       │       │       │
       │       │       └── 不是空指针，可能是 MMIO 地址或页表错误
       │       │
       │       └── stval 很大 ?
       │               │
       │               └── 大概率 use-after-free
       │                   → 检查对象的分配 / 释放 / 重用生命周期
       │
       ├── 其他异常类型 → 按对应规则处理
       │
       └── 总是用 addr2line 验证猜测，不要仅凭 stval 下结论
```
## SPI优化

本次SPI优化的主要内容是把配置文件放入.c文件中，然后通过函数来获取配置，**出现了以下三个问题：**
* 问题一：spi_handle->ctrlr0的配置分为两步，开始没有注意到这点，要使用set_bit来单独配置位
  * 表现为SD卡直接读取失败，开始时全部修改后就出现了问题，后面就只修改init过程，还是有这个问题，AI分析出来了
* 问题二：spi_adapter->dmacr = 0x00，这个使用完后必须要清楚，否则读写出错
  * 表现为SD卡直接读取失败，同上
* 问题三：w25q64就是无法读取，原因分析和总结如下
  * 首先就是SD卡就是能正常使用，但是W25Q64就是使用不了，就此怀疑是片选引脚的问题，一个是从波形上就是不对，还有就是我在改的就是这个
  * 然后就是排查了，这个时候其实是没有头绪的，AI也查不出来问题，后来是实验出来的，以及查看了Linux的dw的SPI驱动里面有一段关于cs的使用的注释
  * 问题就是，dw的SPI控制器的一个设计缺陷，以及W25Q64要求“一个完成的操作”，必须保持cs低，否则通信失败
* 问题四：不使用SPI原生的cs，也必须设置 SER 寄存器，否则无法产生时钟

**为什么轮询方式会出问题，问题出在循环间隙：**
* 第一批数据：写入，FIFO 非空 → 硬件自动拉低 CS，开始传输
* 等待结束：FIFO 里的数据发完了，硬件检测到 FIFO 空 → 自动拉高 CS（片选释放）
* 第二批数据：再次写入，FIFO 又有数据了 → 硬件再次自动拉低 CS
* 后果： 本来应该是一次连续的传输（CS 一直低），结果被拆成了多次短暂的片选脉冲，中间 CS 会弹高再拉低。
* 对于很多 SPI 从设备（比如 Flash、ADC），片选中途拉高会被视为传输结束，导致数据错乱或通信失败。

**关于DMA配置的解释：**
* DW SPI 控制器的 DMA 请求逻辑是这样的：
  * 当 DMACR 的 Tx/Rx 位 = 1 时，只要 Tx FIFO 有空位或 Rx FIFO 有数据，硬件就会持续向 DMA 控制器发出请求信号（dma_request 线拉高）。
  * DMA 传输完成后，虽然 DMA 控制器不再响应这些请求，但请求信号线本身可能还处于活跃状态（因为 FIFO 状态触发了请求条件）。
* 切换到轮询模式会发生什么？
  * 如果不清除 DMACR，直接开始轮询传输：
  * 轮询传输开始：代码往 Tx FIFO 写数据
  * 硬件误判：由于 DMACR 还是 0x3，硬件认为应该用 DMA 方式传输
  * DMA 请求线保持断言：Tx FIFO 一旦有空位，DMA 请求线立刻拉高
* 后果：
  * 对于轮询代码来说，它无法清除或响应 DMA 请求
  * DMA 请求线可能和硬件内部状态机冲突，导致数据流异常

**最终解决：**改为gpio控制片选，同时随便设置一个 SER 寄存器中的片选引脚

**补充说明**：CTRLR1(NDF)只在两种 TMOD 下有效DW SPI 的 CTRLR1 字段是 NDF(Number of Data Frames),作用只有一个:告诉控制器"本次要接收多少帧"。但只有 TMOD 为以下两种时它才有意义:

| TMOD | 模式含义 | RX 长度如何确定 |
| :---: | :--- | :--- |
| 00 | Transmit & Receive (全双工) | 由 TX FIFO 推断，RX 长度 = TX 长度，NDF 被忽略 |
| 01 | Transmit Only (只发) | 无 RX，不需要确定长度 |
| 10 | Receive Only (只收) | **必须**使用 NDF (结束符) 来确定 |
| 11 | EEPROM Read (先发命令再持续收) | **必须**使用 NDF (结束符) 来确定 |

因为 Receive Only / EEPROM Read 模式下主机发送的帧数 ≠ 接收的帧数(EEPROM read:只发命令+地址几个字节,然后要连续收一大段数据),控制器无法从 TX FIFO 推断 RX 长度,所以必须用 NDF 显式告诉它"收多少帧"。
