# UART 烧录 SD 卡调试记录

# 第一次调试

## 1. `Timeout waiting for magic`

现象：

```text
sec=2 attempt=1 failed: timeout waiting for magic
sec=2 attempt=2 recv ACK seq=2
```

初步怀疑是 ACK 丢失或 SD 写入慢。后来通过 ACK 诊断 payload 看到：

```text
reason=OK ticks=0
```

说明 SD 写入本身不是 10 秒级卡顿。真正原因之一是 OLED 调试输出放在正常 ACK 前后，导致板端不能及时回到 UART 接收路径。

修复：

- 正常路径不再刷 OLED。
- 写 SD 后立即 ACK。
- ACK 后立即回到 `recv_msg()`。
- `tools/burn.py` 保留主机端详细诊断。

## 2. 重复 DATA 与 ACK 幂等

如果主机没收到 ACK，会重发同一个扇区。板端如果已经写入并推进 `sec`，重发包的 `seq` 会小于当前 `sec`。

修复：

```c
if (type == PKT_DATA && plen == 512 && rseq < sec) {
  send_ack_payload(uart_fd, rseq, ACK_DUP, sec);
  continue;
}
```

这样不会重复写 SD，也能让主机恢复同步。

主机端也增加 seq 校验：

```python
if seq != sec:
    # stale response
    continue
```

## 3. `Sector 1/524288` 太多

原因不是整张 SD 卡，而是 `target/fs.img` 原先固定为 256MiB：

```make
dd if=/dev/zero of=$T/fs.img bs=512k count=512
```

256MiB / 512B = 524288 sectors。

后来改为可配置：

```make
FS_SIZE_MB ?= 64
dd if=/dev/zero of=$T/fs.img bs=1M count=$(FS_SIZE_MB)
```

默认 64MiB，对应 131072 个扇区。64MiB 避免了 32MiB FAT32 簇数过低警告，同时比原来的 256MiB 少 4 倍刷写量。

后续进一步优化为：`tools/burn.py` 默认只发送 FAT32 实际使用区域。脚本读取 BPB 和 FAT 表：

- 保留 reserved sector、FSInfo、FAT1/FAT2 等元数据区。
- 扫描 FAT 表中最后一个非 0 的 cluster。
- 发送到该 cluster 结束位置。
- 免费空间尾部不再通过 UART 发送。

示例：

```text
Image: target/fs.img
Size: 2689024 bytes (5252 sectors)
FAT32 trim: full=67108864 bytes, send=2689024 bytes, saved=64419840 bytes (95%)
FAT32 layout: data_start=2050 sectors, spc=1, last_cluster=3203
```

旧行为仍可通过 `--full-image` 保留：

```sh
python3 tools/burn.py --full-image /dev/ttyUSB0 target/fs.img
```

为了验证裁剪结果而不打开串口，可以使用：

```sh
python3 tools/burn.py --dry-run --baud 460800 --board-baud 500000 /dev/ttyUSB0 target/fs.img
```

## 4. `panic: init exiting`

现象：

```text
SDHC/SDXC detected
hart 1 starting
panic: init exiting
```

原因是 `make run platform=k210` 只烧 kernel，不会写 SD 卡文件系统。虽然 make 输出中生成了 `target/fs.img`，但板子启动时读的是 SD 卡上的内容。

后续发现 `/dev/sdc` 不是块设备，而是普通文件：

```text
-rw-r--r-- 1 root root 67108864 /dev/sdc
lsblk: /dev/sdc: not a block device
```

这说明之前 `dd of=/dev/sdc` 时真实块设备不存在，`dd` 在 `/dev` 下创建了普通文件，SD 卡并没有被更新。

修复：

- `sdcard` 目标增加块设备保护：

```make
@test -b "$(dev-sd)" || (echo "$(dev-sd) is not a block device; refusing to write fs.img"; exit 1)
```

- 增加 `verify-sd` 目标，比较 SD 卡开头内容是否和 `target/fs.img` 一致。

验证方式：

```sh
make verify-sd dev-sd=/dev/sdX
```

必须使用整卡设备，如 `/dev/sdc`，不要使用分区 `/dev/sdc1`。

## 5. 高波特率切换

UARTHS 文档说明速率最高可到 5Mbps，但 K210 UARTHS 只有 8 字节 FIFO，且没有硬件流控。最终采用两阶段 baud，并把主机 baud 与板端 baud 分开：

1. 115200 下启动 `burn`。
2. INFO 中携带板端 baud 设置。
3. 板端先在 115200 下发送 INFO ACK。
4. 主机在 115200 下发送 BAUD 请求，板端回 BAUD READY。
5. 板端等待 TX FIFO 空闲后切到板端 baud。
6. 主机切到主机传输 baud，并发送 BAUD 同步包。
7. 板端收到同步包后回 BAUD ACK。
8. 数据阶段开始发送 DATA。

单独测试发现，主机设置为 230400、板端也设置为 230400 时，板端发出的 `BSET\n` 会被主机读成类似：

```text
b'\x82\xb3\x85\xb4\n'
```

这说明两端实际速率没有对齐。使用独立测试程序验证后，主机仍使用 230400，但板端请求 baud 改为约 253400，可以稳定通过：

```sh
python3 tools/uartbaud.py /dev/ttyUSB0 --baud 230400 --board-baud 253400
```

输出：

```text
Board transmitted at new baud
Sending 64-byte pattern at 230400 baud
Board reply: b'OK\n'
UART baud test passed
```

因此 `tools/burn.py` 最初默认使用主机 230400，同时把发给板端的 baud 按 1.10 倍补偿。默认等价于：

```sh
python3 tools/burn.py --baud 230400 --board-baud 253440 /dev/ttyUSB0 target/fs.img
```

如果需要复现本次手动验证的精确值，可以使用：

```sh
python3 tools/burn.py --baud 230400 --board-baud 253400 /dev/ttyUSB0 target/fs.img
```

后续继续测试 460800、921600、1500000 时，也必须先用 `tools/uartbaud.py` 找到对应的板端补偿值。由于没有硬件流控，高速下仍需严格保持 stop-and-wait，或加入更完整的窗口/重传策略。

后续实测结果：

```text
python3 tools/uartbaud.py /dev/ttyUSB0 --baud 460800 --board-baud 500000
Board transmitted at new baud
Sending 64-byte pattern at 460800 baud
Board reply: b'OK\n'
UART baud test passed
```

而 576000、768000、921600 多组补偿值都出现 `BSET` 或返回包无法干净解码的问题。当前工程的 `make download` 使用稳定组合：

```sh
python3 tools/burn.py --baud 460800 --board-baud 500000 /dev/ttyUSB0 target/fs.img
```

64MiB 完整镜像在 460800 baud 下理论仍需二十多分钟；但配合 FAT32 裁剪后，当前实际发送约 2.6MiB，刷写时间大幅缩短。

### 5.1 补偿根因确认：主机高速档量化，公共精确速率可免补偿（2026-08-12）

用逻辑分析仪实测 + 实机烧写确认了为什么需要 ~1.1x 补偿：

- 板端 UARTHS 准确：390MHz 整数分频，`/uartbaud 500000` 量到位宽 2.0µs（=500,000 精确）。
- 主机 USB 转串口芯片（12MHz 晶振）高速档实际速率量化：
  - 标称 230400 → 实际 250,000（12M÷48，+8.5%，逻辑分析仪量到 8µs 周期）；
  - 标称 460800 与 500000 → 都落在实际 500,000（12M÷24）。
- 115200 档误差 <0.2%，握手正常；两端同为标称 230400 时实际差 8.5%，超出 UARTHS 采样容差 → 乱码。

因此只要两端都选能同时整除 390M 与 12M 的公共速率，就不需要补偿。
实测主机、板端同为 500000 可直接烧写成功（板端报 actual=500000）：

```sh
python3 tools/burn.py --baud 500000 --board-baud 500000 /dev/ttyUSB0 target/fs.img
```

注意：逻辑分析仪在"标称 500000"下早期量到 17~26µs 周期（0x55 应为 4µs）、
解出 0x78/0x80 并报 stop bit error，是采样率不足（≤1MS/s）对 4µs 方波欠采样
混叠造成的误读。把采样率提到 2MS/s 后即正确解出 0x55。500000 不是坏档，
实机烧写与 2MS/s 重测双确认主机 500000 = 精确 500,000（12M÷24）；测 500k
UART 采样率至少 2MS/s（4 采样/bit 起步，推荐 5MS/s+）。

## 6. `/burn`、`/bin/burn` 与 fs.img 未更新

`tools/mkfs.py` 会递归扫描 `build/user/**/_*`，并把用户程序同时写入根目录和 `/bin`：

```python
vfs.open("/" + name, "wb").write(data)
vfs.open("/bin/" + name, "wb").write(data)
```

因此理论上 `_burn` 会生成：

```text
/burn
/bin/burn
```

调试过程中出现：

```text
exec /burn failed
exec burn failed
/bin/burn 成功
```

以及后续全部路径失败：

```text
Board shell could not exec burn program
```

定位时发现一个容易误判的问题：`build/user/app/_burn` 已经是新版，但 `target/fs.img` 仍是旧时间戳。原因是 Makefile 还包含已经删除的 `_uartbaud` 目标，`make fs` 在生成镜像前失败，导致用户以为刷了新版，实际仍在反复刷旧 `fs.img`。

修复：

- 从 `UPROGS` 移除已经不存在的 `_uartbaud`。
- 重新执行 `make fs`。
- 用 `stat` 确认 `target/fs.img` 时间戳晚于 `build/user/app/_burn`。

验证：

```text
build/user/app/_burn  11:11:32
target/fs.img     11:11:37
```

`tools/burn.py` 也增加了 `--burn-cmd` 和 fallback 顺序。默认先尝试 `/burn`，失败后尝试 `burn`、`/bin/burn`、`bin/burn`。如果当前板子只有 `/bin/burn` 可执行，可以直接指定：

```sh
python3 tools/burn.py --burn-cmd /bin/burn --baud 460800 --board-baud 500000 /dev/ttyUSB0 target/fs.img
```

## 7. 连续刷写第二次 `usertrap(): addr is illegal`

现象：

第一次刷写成功：

```text
Sector 5252/5252 (100%)
Transfer completed successfully! ACK reason=DONE ticks=0
```

不重启马上第二次执行：

```text
Sending '/burn' command to board at 115200 baud...
Waiting for BURN signal...
Timeout waiting for BURN, retrying '/burn' (1); last serial='/burn\nusertrap(): addr is illegal\n$ '
```

原因是板端 `/burn` 通过 `sdcarddev_write()` 直接调用 `sdcard_write_sector()` 覆盖 SD 卡，绕过了 FAT32 文件系统层和 buffer cache。第一次刷写成功后，磁盘内容已经换成新版 `fs.img`，但旧 kernel 内存中仍缓存着旧的 FAT、目录项或文件块。第二次 shell `exec /burn` 时，`exec()` 可能读到“旧缓存 + 新磁盘”的混合内容，导致 ELF 装载错误，用户程序一启动就触发非法地址异常。

修复内容：

- `kernel/fs/bio.c`
  增加 `binvalidate(dev)`，将指定设备中 `refcnt == 0` 的 buffer 标记为 invalid。

- `kernel/fs/fat32.c`
  增加 `fat32_invalidate()`，清除空闲目录项缓存，避免路径查找命中旧目录项。

- `kernel/devsw/sdcarddev.c`
  增加 `SDCARD_IOCTL_INVALIDATE_CACHE`，统一调用 `fat32_invalidate()` 和 `binvalidate(0)`。

- `user/app/burn.c`
  在 DONE 成功后、console 恢复 TTY 模式前调用：

```c
int cache_rc = ioctl(sdcard_fd, SDCARD_IOCTL_INVALIDATE_CACHE, 0);
```

为了验证该修复是否真的在板端 kernel 生效，`burn.c` 成功结束时会打印：

```text
burn: done sectors=5252 bytes=2689024 cache=0
```

其中 `cache=0` 表示新版 kernel 已经执行缓存失效；如果看到 `cache=-1`，说明板子仍是旧 kernel，不认识该 ioctl。

注意：这是 kernel 改动。只刷 `fs.img` 不会让它生效，必须先：

```sh
make run platform=k210
```

然后再刷 SD：

```sh
python3 tools/burn.py --baud 460800 --board-baud 500000 /dev/ttyUSB0 target/fs.img
```

最终验证输出：

```text
Sector 5252/5252 (100%)
Transfer completed successfully! ACK reason=DONE ticks=0
Board console tail:
burn: done sectors=5252 bytes=2689024 cache=0\n$
```

看到 `cache=0` 后，连续第二次刷写不应再因为旧 FAT/buffer cache 触发 `usertrap(): addr is illegal`。


# 第二次调试

## 1. 问题背景

项目通过主机端 `tools/burn.py` 将 FAT32 文件系统镜像经 UART 发送给
K210。板端 shell 启动 `/burn`，用户态烧录程序接收分包、校验 CRC，
再通过 SD 卡设备接口把每个 512 字节扇区写入 SD 卡。

本次调试先后遇到两类表象不同的问题：

1. INFO 握手阶段出现 CRC mismatch。
2. INFO 和波特率切换成功后，传输若干扇区便超时，串口中出现 RustSBI
   panic。

第二类问题最终定位到内核物理页分配器读取了已经损坏的 freelist
指针。故障与 UART 波特率无直接关系，SPI0 的 SD 卡 DMA 路径是当前
最主要的破坏来源嫌疑。现阶段采用的隔离措施是让 SPI0 使用轮询传输，
SPI1 仍可使用 DMA。

本文重点记录完整的排查过程、证据链、使用的命令，以及哪些结论已经
证实、哪些仍需要进一步实验确认。

## 2. 烧录链路

烧录链路如下：

```text
主机 tools/burn.py
  -> UART 帧协议
  -> K210 UARTHS
  -> /burn 用户程序
  -> write(sdcard_fd, payload, 512)
  -> sdcarddev_write()
  -> sdcard_write_sector()
  -> spi_write(SPI_DEVICE_0, ...)
  -> SPI0 轮询或 DMAC
  -> SD 卡
```

UART 帧格式为：

```text
magic(4) + seq(4) + type(1) + plen(2) + payload(plen) + crc32(4)
```

正常的 INFO ACK：

```text
seq     = 0
type    = ACK
plen    = 5
payload = reason(1) + ticks(4)
```

这个固定格式是分析第一阶段 CRC 错误的重要依据。

## 3. 第一阶段：INFO ACK CRC mismatch

### 3.1 原始现象

第一次失败发生在 115200 波特率的 INFO 握手阶段：

```text
Board ready, sending image info...
ValueError: INFO ACK: CRC mismatch seq=0 type=ACK plen=12905
got=0x64612031 expected=0x1DA22926
```

此时尚未切换到 `host=460800, board=500000`，因此不能把问题直接归因于
高速波特率误差。

### 3.2 从错误字段判断数据流被插入

INFO ACK 的 `plen` 应固定为 5，但读到：

```text
12905 = 0x3269
```

按 UART 收到的字节顺序，`0x69 0x32` 对应 ASCII：

```text
i2
```

收到的 CRC：

```text
0x64612031
```

按小端字节查看为：

```text
31 20 61 64 -> "1 ad"
```

仓库中存在如下内核错误输出：

```c
printf("i2cdev: transfer failed ret=%d addr=%x nmsgs=%d\n", ...);
```

它包含 `"i2cdev"`、`"-1 addr"` 等片段，与损坏帧中的 ASCII 特征高度
一致。板端 `/burn` 又会在进入 RAW 模式后更新 OLED，OLED 地址正是
I2C `0x3c`。

因此第一阶段的判断是：二进制 ACK 与控制台文本共用同一 UART，当
I2C/OLED 错误日志同步输出时，文本可能插入 UART 缓冲发送的协议帧。

### 3.3 I2C 独立验证

随后运行：

```text
$ i2ctest
scan: 0x3C 0x68
OLED probe: 0x3C OK
OLED display updated
I2C test PASSED
```

再次烧录时 INFO ACK 也成功：

```text
INFO ACK seq=0 reason=INFO ticks=0
```

这说明 OLED/I2C 并非持续不可用。第一阶段更像瞬时 I2C 错误或控制台
输出与二进制协议帧的并发串流问题，不是后续板端崩溃的根因。

### 3.4 这一阶段得到的调试经验

- 先确定错误发生在哪个协议阶段，再判断波特率是否已经切换。
- CRC mismatch 不一定说明 CRC 算法错误，也可能是帧中混入其他输出。
- 将数值按小端拆成字节并转换为 ASCII，常能发现日志插入痕迹。
- RAW 二进制协议期间不应通过同一 UART 输出普通内核日志。
- 二进制发送与同步 `printf` 应共享发送锁，或者 RAW 模式应抑制非协议
  输出。

## 4. 第二阶段：传输若干扇区后超时

### 4.1 高速传输下的现象

INFO 和 BAUD 握手成功后，传输到 sector 27 时超时：

```text
INFO ACK seq=0 reason=INFO ticks=0
BAUD READY seq=0 reason=BAUD target=500000
BAUD ACK seq=0 reason=BAUD actual=500000
Sector 27/6298
timeout waiting for magic
last=... /main.rs:530:18
```

`main.rs:530:18` 位于：

```text
bootloader/rustsbi-k210/src/main.rs
```

对应 RustSBI 的未处理 trap 分支：

```rust
cause => panic!(
    "unhandled trap! mcause: {:?}, mepc: ..., mtval: ...",
    ...
)
```

这说明主机收不到 ACK 并不是简单丢包，而是板端已经 panic 并停止正常
执行。此时继续进行 DATA 重试没有意义，必须复位开发板。

### 4.2 用低速实验排除 UART 波特率

为了验证是否由 `460800/500000` 的速率补偿引起，使用全程 115200：

```bash
python3 tools/burn.py \
  --baud 115200 \
  --board-baud 115200 \
  /dev/ttyUSB0 target/fs.img
```

低速下仍然在 sector 2 附近崩溃。故障扇区从 27 变成 2，说明：

- 问题不是固定发生在某个镜像扇区。
- 问题不是高速 UART 独有。
- 更像是执行次数、内存分配时序或外设传输引起的内核内存破坏。

### 4.3 扩大串口错误上下文

原 `recv_msg()` 只保留最后 16 字节：

```python
if len(last) > 16:
    del last[:-16]
```

这只能看到 `main.rs:530:18`，最关键的 `mcause`、`mepc` 和 `mtval` 已经
丢失。调试时临时把尾部缓冲扩大到 512 字节，并同时打印可读文本和
十六进制：

```python
if len(last) > 512:
    del last[:-512]

raise TimeoutError(
    f"{context}: ... "
    f"serial='{printable_serial(last)}', "
    f"last_hex={hexdump(last)}"
)
```

重新执行后得到完整 panic：

```text
[rustsbi] panicked at 'unhandled trap!
mcause: Exception(LoadMisaligned),
mepc: 00000000800279ca,
mtval: 000000002016d001',
src/main.rs:530:18
```

三个寄存器的含义：

| 字段 | 含义 | 本次取值 |
|---|---|---|
| `mcause` | trap 类型 | `LoadMisaligned` |
| `mepc` | 发生 trap 的指令地址 | `0x800279ca` |
| `mtval` | 导致异常的访问地址 | `0x2016d001` |

`0x2016d001` 不是 8 字节对齐地址，符合 64 位加载触发
`LoadMisaligned` 的特征。

## 5. 将 mepc 映射回内核源码

### 5.1 使用 addr2line

K210 内核 ELF 为 `target/kernel`。执行：

```bash
riscv64-unknown-elf-addr2line \
  -f -C -e target/kernel 0x800279ca
```

输出：

```text
kalloc_page
kernel/vm/kalloc.c:131
```

### 5.2 使用 objdump 交叉验证

执行：

```bash
riscv64-unknown-elf-objdump -dS \
  --start-address=0x80027980 \
  --stop-address=0x80027a20 \
  target/kernel
```

关键汇编：

```text
800279c2: ld   s3,24(s2)   # r = kmem[id].freelist
800279ca: ld   a5,0(s3)    # r->next
```

对应源码：

```c
r = kmem[id].freelist;
if (r) {
  kmem[id].freelist = r->next;
}
```

所以异常不是普通用户指针未对齐，而是：

```text
kmem[id].freelist == 0x2016d001
```

物理页分配器的空闲链表头已经被破坏，`kalloc_page()` 在读取
`r->next` 时才暴露问题。

### 5.3 为什么 RustSBI 报告了内核错误

K210 使用较旧的 RISC-V 特权规范，当前 RustSBI 没有把
`LoadMisaligned` 委托给 S 态处理，而是在 M 态 trap handler 中进入
默认 panic 分支。

因此：

- RustSBI 是异常报告者。
- 真正执行错误指令的是 xv6 内核。
- 修改 RustSBI 让它忽略异常不能修复 freelist 损坏。

## 6. 从 kalloc_page 反向追踪调用链

烧录程序每写一个扇区，SD 卡设备层会临时分配一页：

```c
char *buf = kalloc_page();
either_copyin(buf, user_src, 512);
sdcard_write_sector((uint8 *)buf, sdcard_sector);
kfree_page(buf);
```

SPI DMA 路径也会分配一页 bounce buffer：

```c
uint32 *write_cmd = kalloc_page();
...
spi_dw_dma_xfer(...);
...
kfree_page(write_cmd);
```

因此烧录过程会高频重复：

```text
kalloc_page -> SPI/DMAC -> kfree_page
```

这与在 sector 2 或 sector 27 随机暴露 freelist 损坏的现象一致。

## 7. SPI0 DMA 路径的风险分析

### 7.1 512 字节传输恰好占满一个页面

SD 卡扇区大小为 512 字节，SPI 数据宽度为 8 位。当前 DMA bounce
buffer 会把每个 8 位元素扩展到一个 `uint32`：

```text
TX: 512 × sizeof(uint32) = 2048 字节
RX: 512 × sizeof(uint32) = 2048 字节
总计                         4096 字节
```

而 `kalloc_page()` 只提供 4096 字节：

```text
┌──────── TX 2048 B ────────┬──────── RX 2048 B ────────┐
0                           2048                         4096
```

`spi_can_dma()` 的边界检查允许“等于 PGSIZE”：

```c
if (frames * 2 * sizeof(uint32) > PGSIZE)
  return false;
```

所以 512 字节恰好进入 DMA，且没有任何 guard、canary 或额外空间。

### 7.2 DMA 完成错误被忽略

两个 channel 的等待结果没有检查：

```c
dmac_wait_done(spi_data->chan_tx, DMAC_WAIT_TIMEOUT);
dmac_wait_done(spi_data->chan_rx, DMAC_WAIT_TIMEOUT);
return 0;
```

即使等待超时，SPI 层也按成功返回，随后复制 RX 数据并释放页面。这会
掩盖 DMA 未按预期结束的情况。

### 7.3 中断处理只清理 channel 0

SPI0 配置使用：

```text
TX = DMAC_CHANNEL0
RX = DMAC_CHANNEL1
```

但 K210 的磁盘中断入口当前固定调用：

```c
dmac_intr(DMAC_CHANNEL0);
```

而 `dmac_set_single_mode()` 会为两个 channel 都启用 channel interrupt。
因此还需要确认 channel 1 的完成状态和中断是否得到正确清理。

### 7.4 当前证据的边界

已经证实：

- 崩溃是 `kalloc_page()` 读取损坏的 freelist 指针。
- 故障在高低 UART 波特率下均出现。
- 烧录期间 SPI0 DMA 和页分配器会高频交互。
- 512 字节 SPI DMA bounce buffer 恰好用满整页。
- DMA 等待错误和 channel 1 中断处理存在缺口。

尚未通过硬件观测完全证实：

- 究竟是 RX 多写一个 DMA 单元、完成时序提前、未清中断，还是其他
  DMA/allocator 竞态直接改写了 freelist。
- 被破坏的是 DMA bounce page 本身，还是它相邻的另一个空闲页。

因此“SPI0 DMA 导致页链表破坏”是目前证据最强的工作结论，但要得到
最终根因，还应增加 guard page、canary 和 DMA 寄存器记录。

## 8. 当前隔离修复

当前先对 SPI0 禁用 DMA：

```c
spi_dw[spi_num]->dma_enable = spi_num != SPI_DEVICE_0;
```

效果：

- SPI0：SD 卡走 `spi_dw_poll_transfer()`。
- SPI1：仍允许 DMA，不影响其他 SPI 设备继续验证 DMA。
- UART 协议、SD 卡设备层和 FAT32 镜像格式不变。

轮询路径会在发送时同步排空 RX FIFO，并带有超时保护，速度可能低于
DMA，但不会使用有风险的整页 bounce buffer。

需要强调：这不表示 K210 的 SPI0 硬件不支持 DMA，只表示当前驱动的
SPI0 全双工 DMA 实现尚未满足安全烧录要求。

## 10. SPI0 DMA 的后续正确修复方向

如果要重新启用 SPI0 DMA，建议按以下顺序改造。

### 10.1 分离 TX/RX bounce buffer

不要把 TX 和 RX 紧密放在同一个页面中。至少使用独立缓冲区，并为 RX
尾部添加 guard/canary：

```text
TX page
RX page + guard
```

传输后检查 canary，确认硬件实际写入长度。

### 10.2 传播 DMA 错误

检查两个 channel 的返回值：

```c
if (dmac_wait_done(tx, timeout) < 0)
  return -1;
if (dmac_wait_done(rx, timeout) < 0)
  return -1;
```

失败时必须：

- 禁止 SPI DMA 请求。
- 禁止并清理两个 DMA channel。
- 清空 SPI RX FIFO。
- 不复制未完成的 RX 数据。
- 在确认 DMA 不再访问缓冲区后才能释放页面。

### 10.3 正确处理中断状态

不要只清理固定的 channel 0。应读取 DMAC channel interrupt status，
分别清理所有触发 channel，或者在纯轮询 DMA 模式下不启用不需要的
完成中断。

### 10.4 增加页分配器完整性检查

在调试构建中，读取 `r->next` 前检查：

```text
r 是否页对齐
r 是否位于 [end, PHYSTOP)
r->next 是否为 0 或合法页地址
```

这样可以在 freelist 第一次损坏时由内核输出更明确的信息，而不是等到
RustSBI 报 `LoadMisaligned`。

### 10.5 增加压力测试

单独编写 SPI0/SD DMA 压力测试：

1. 重复写同一个测试扇区。
2. 每轮分配和释放不同页面。
3. 写后读回并比较 CRC。
4. 检查 guard 和 freelist。
5. 分别测试 1、16、64、511、512 字节边界。
6. 分别测试单核和双核、中断开关、高低 SPI 时钟。

只有压力测试稳定后，才应重新让 SD 卡烧录默认使用 DMA。

## 11. 本次调试方法总结

本次问题的有效定位步骤可以归纳为：

1. 按协议阶段划分故障，确认错误发生在切换波特率之前还是之后。

4. 全部字符发送完后等待约 10 ms；
5. 单独发送换行。

`exec ... failed`。即使实际命令被截断，主机也能立即判断板端没有进入 burn，
而不是把它误判为单纯的 `BURN` 超时。

修改没有扩散到 INFO/DATA/ACK 阶段。镜像帧继续整块发送并使用 CRC32，避免

### 最终发现是要用poll不要用中断
#### 如何定位问题

中断模式之前 1.5M 失败时的日志：raw_buf=7/32767。**含义：**
* 环形缓冲 32KB，里面只有 7 字节
* 如果是"中断处理太慢但字节都到了"，环形缓冲会累积很多字节（满到 32767，dropped 上涨）
* 只有 7 字节 说明绝大多数字节在到达uartintr 之前就被硬件丢了——这正是 FIFO 溢出特征（8 字节装不下的被丢弃）

**从两个已知事实反推：**
* 500k 成功：500k 每字节 20µs，FIFO 8 字节满需要 ~160µs → 中断周期必须 < 160µs 才不溢出
* 1.5M 失败：1.5M 每字节 6.67µs，FIFO 满只需 53µs → 中断周期必须 > 53µs 才会溢出

#### 为什么慢速 DATA 是死路
关键事实：500k 全速之所以不溢出，不是因为它"慢"，而是因为 500k 下板端中断周期（~100µs）内只产生 5 字节 < 8 字节 FIFO，自然装得下。 1.5M 同样 100µs 产生 15 字节 > 8，必溢出。

慢速发送的本质，就是人为把"每中断周期的字节数"压回 ≤8

逐字节慢速（send_msg_slow 现在的写法）每字节 150µs，等效速率 = 1/150µs ≈ 53kbps，比 500k 慢 9 倍。

即使把分组优化到"每发 8 字节正好停一个中断周期"的理想极限，等效速率 = 8字节/(8×6.67µs + 100µs) ≈ 37KB/s ≈ 295kbps，仍然追不上 500k 全速。而一旦中断周期实测比 100µs 更长，慢速更是一无是处。

瓶颈在板端中断消费侧，不在主机发送侧。 慢速 = 迁就慢的中断 = 放弃提速。要提速只有一条路：让板端"每中断周期的字节数"下降，也就是缩短中断周期本身。

#### 真正能提速的方向
中断周期 ~100µs 的构成是：PLIC 中断触发 → RustSBI M 态软委托 → S 态 xv6 uartintr。这个 M→S 委托是每次中断的固定开销，是最大嫌疑。

**两个正道：**
* 改 RustSBI，UARTHS 中断直通 S 态（省掉 M 态跳转）——改动集中在 bootloader/rustsbi-k210，中断周期有望降到几十 µs，1.5M 直接可冲
* burn 阶段轮询接收：DATA 阶段关中断，忙等读 FIFO——中断周期从 100µs → 微秒级，1.5M 轻松，改动集中在 burn.c + console 驱动

## 13. 第四阶段：双口 1.5M 烧写偶发 CRC 错误排查（2026-08-14）

### 13.1 目标与现象

双口模式（console=UARTHS 握手，数据走 uart1=DW UART1 + DMA CH4/CH5）下，`DOWNLOAD_BAUD=1500000` 烧写偶发错误。错误特征**始终一致**：

```
  sec=306 attempt=1 failed: timeout waiting for magic after 3.00s, scanned=0, last=-, in_waiting=0
  sec=306 attempt=2: send DATA len=512
  sec=306 attempt=2: recv NAK seq=306 plen=1
  NAK (seq=306, error=CRC), retry 2/5
  sec=306 attempt=3: send DATA len=512
  sec=306 attempt=3: recv ACK seq=306 reason=OK ticks=0
```

- attempt1 板端**全程沉默**（`scanned=0` = 主机 3 秒内没收到板端任何字节）→ 截断帧让板端卡在 `recv_msg`。
- attempt2 主机重发，字节补齐残帧 → 板端 CRC 校验失败 → NAK。
- attempt3 干净 → ACK。
- 板端 `overrun=0`、`raw_drop=0`（非 FIFO 溢出、非 ring 溢出）。

### 13.2 排查过程（假设 → 实验 → 结论）

**假设 A：硬件 FIFO 溢出**（DMA-done → M/S 转发 ISR 的 ~100µs 窗口丢字节）。
- 加的测试内容：`uart_rx.overrun` 计数（读 LSR.OE 锁存位，harvest 与 uartintr 各清一次）、`uart_get_overrun()`、ioctl `UART_IOCTL_GET_OE`、burn.c 打印 `overrun=%d`。
- 实测：所有轮次 `overrun=0`。**结论：排除。**

**假设 B：帧跨 DMA 512 边界竞态**（527 字节帧 = 512+15，落在两个 DMA 块上）。
- 实验：`UART_RXDMA_SIZE` 512→1024，让一帧放进一块。
- 实测（1.5M 各两轮）：
  - 512 缓冲：错误 0–1 次/轮，吞吐 ~10–11 KiB/s。
  - 1024 缓冲：错误 **5 次、2 次/轮**，吞吐跌到 6–7 KiB/s。
  - 500000 档：**0 错误**。
- 推断（标注）：1024 更差的机制——527 字节帧永远填不满 1024 块，done 不触发，每帧退化为**高频 RDA 收割**（FIFO 到 8 字节触发一次，约 66 次/帧），在 `dar` 传输中途 disable CH5，与 DMA-done 收割互相踩踏。**结论：512 边界假设被证伪，但暴露了 RDA/done 竞争。**

**根因确认：RDA 与 DMA-done 收割竞争。**
- K210 DW UART 在 DMA 模式（FCR[3]=1）下**仍会触发 RDA**（非 16550 标准语义）。原 `uartintr` 让 RDA/CTI 都调 `uart_dma_rx_intr()` 收割 → RDA 在高频下与 done 竞争错乱。
- 修复（**保留**）：`UART_RXDMA_SIZE` 改回 512 + `uartintr` 的 `UART_IIR_RDA` 在 `UART_MODE_DMA` 下直接 `break`（数据由 DMA 搬，收割只走 done=512 满 + CTI=帧尾 15 字节超时兜底）。
- 修复后实测（1.5M 两轮 5016 扇区）：

```
Transfer stats: elapsed=203.89s, throughput=12.3 KiB/s, retries=0, timeouts=0, crc_errors=0, naks=0
Board console tail: ... dup=0 crc=0 io=0 pkt=0 ... overrun=0
Transfer stats: elapsed=207.03s, throughput=12.1 KiB/s, retries=0, timeouts=0, crc_errors=0, naks=0
```

- **结论：RDA 竞争修复生效**，且吞吐从 10–11 升到 12+ KiB/s。

**残留错误（修复后仍偶发）。** 后续一轮 1.5M 出现 3 次（sec=224/3366/4147），特征不变（attempt1 沉默 + attempt2 CRC NAK + attempt3 OK），板端 `crc=3`。错误率约 1–3 次/轮。

**诊断实验：板端读超时**（想抓截断帧实际收到多少字节，定位丢在主机还是板端）。
- 加的测试内容：burn.c 在 DATA 阶段对帧体轮询 ring 占用，超 `RX_ABORT_TICKS` 中止并打印 `rx-timeout sec=N got=M`，发 NAK 让主机立即重试。
- **失败原因：tick 假设错误（关键发现）**。假定 1 tick=5ms → `RX_ABORT_TICKS=400`=2s；实测板端统计 **1 tick≈125ms**（clean 轮 `ticks=1631` 对主机 `elapsed=203.89s`）→ 400 ticks 实际 **50 秒**，远超主机 3s 超时，诊断从未触发；且 `sleep(1)`=125ms 把每帧间隙拖慢，吞吐从 12 掉到 4.0 KiB/s。
- **结论：诊断无效，已整体移除**（本段记录的推断据此修正：丢字节仍是"截断帧"，但**未定位到主机侧还是板端**）。

### 13.3 当前结论与未决项

**已实锤**：
- overrun=0 → 非硬件 FIFO 溢出。
- RXDMA 1024 更差 → 排除 512 边界假设；机制是高频 RDA 收割。
- **RDA/done 竞争是真实 bug，已修复**（两轮零错误 + 吞吐提升验证）。
- 1 tick≈125ms（板端），早先按 5ms 的假设全错。

**未决（推断，未最终确认）**：
- 残留偶发错误 = 截断帧（某帧字节未到齐）。板端 overrun=0、RDA 竞争已修、500k 干净 → **推断主要嫌疑为主机 USB-TTL 适配器在 1.5M 突发写 527 字节时丢尾部字节**；尚未用逻辑分析仪抓 uart1 TX 波形或换适配器验证。按用户要求停止排查，记录到此。

### 13.4 变更清单（本次清理后保留的）

- `kernel/driver/uart.c`：`UART_RXDMA_SIZE`=512；`uartintr` DMA 模式 RDA `break`（保留修复）；LSR.OE 计数与 `uart_get_overrun()`（**已移除**）。
- `kernel/include/uart.h` / `kernel/devsw/uartdev.c`：`UART_IOCTL_GET_OE`（**已移除**）。
- `user/app/burn.c`：读超时诊断、`overrun` 打印（**已移除**）。

## 14. 第五阶段：tick 率修正 + 被动式停顿诊断（2026-08-14）

在阶段 13 停止排查后，用户选择「两条都做」恢复：先修正 tick 语义，再用修正后的诊断抓一次丢帧现场。

### 14.1 tick≈125ms 的确认与影响

**实测**：2026-08-14 burn 日志中，板端 `transfer_ticks=1631`（burn.c `uptime()` 差值，覆盖 DATA 循环），主机 burn.py 同窗口 `elapsed=203.89s`（`data_start` 设在 Phase 2 DATA 循环前）→ **每 tick ≈ 125ms，是 `param.h` 假设 5ms 的 25 倍**。等效 mtime 时基 = `INTERVAL / tick = 1950000 / 0.125 ≈ 15.6MHz`（而非假设的 390MHz）。

**影响**：
- 阶段 13 的 `RX_ABORT_TICKS=400` 诊断本意 2s，实为 50s → 主机 3s 超时前永不触发，`rx-timeout` 永不打印。
- 数据循环 `sleep(1)` 实为 125ms/帧 → 吞吐从 12 跌到 4 KiB/s（与 13 节 4.0 KiB/s 日志吻合）。
- 早先记忆「K210 实机 5ms/tick」是 INTERVAL 反推的**假设**，从未实机验证，本次首次实测修正。

**待确认**：15.6MHz 是「mtime 分频」还是「CPU 时钟本身未提频（内核 main.c 从未配置 PLL）」未定；若为后者，提频 PLL 是更大的独立议题（暂不动）。

### 14.2 修正 INTERVAL（param.h）

`INTERVAL` 按实测时基重算，目标仍 5ms/tick（200Hz），并给 QEMU 加分支：

```c
#ifdef QEMU
#define INTERVAL     (10000000 / 200) // QEMU virt: 10MHz time base -> 5ms/tick
#else
#define INTERVAL     (15600000 / 200) // K210: measured ~15.6MHz time base
#endif
```

**待实机确认**：`/timerfreq 100` 板端跑一次，主机秒表量 begin/end 标记间隔，`tick = wall_s / 100`。若确认 ≈5ms 则定稿；否则按实测值调整（`INTERVAL = mtime_freq/200`，`mtime_freq = 1950000 / tick_s`）。

连带影响（预期正确化）：MLFQ 时间片 1/2/4/8 ticks 从 125ms×… 变为 5/10/20/40ms；boost 200 ticks 从 ~25s 变为 1s。

### 14.3 新增：被动式停顿诊断（burn.c）

设计：不 sleep、不 abort、不改协议时序，纯粹被动测量 **recv_msg 内部相邻 read() 的最大 tick 间隔**。

**签名**：主机丢帧尾 → 板端 `read_bytes` 干等（约主机 3s 超时）→ 重试字节补成垃圾帧 → CRC 失败。故「CRC 失败帧内有长停顿」= 线上截断实锤；停顿≈0 = 字节就地损坏。

**改点**：
- 全局 `diag_stall_ticks`/`diag_stall_at`（当前 recv_msg 最差停顿）、`diag_crc_stall_max`/`_sec`、`diag_long_stalls`。
- `read_bytes` 用 `uptime()` 测相邻 read() 返回间隔，更新运行最大值。
- `recv_msg` 入口重置。
- CRC/IO 失败分支：`uart_fd != console_fd`（数据口=uart1，console 空闲）时 printf 该帧停顿；单口模式仅入最终 stats。
- 最终 stats 加 `stall=%u sec=%u longstall=%u`。

### 14.4 新增：timerfreq 测量程序

`user/test/timerfreq.c`（k210 UPROGS）：`timerfreq [n]` 打印 begin/end 的 `uptime()` 差值，配合主机秒表得到 tick 实值。用户态无法直接读 `time` CSR（未设 scounteren），故用主机做参考钟。

### 14.5 待用户实测

1. `/timerfreq 100`：确认 tick（预期 ≈5ms），据此定稿/调整 INTERVAL。
2. 1.5M 双口烧写一轮：观察 `burn: crc sec=... stall=...` 行——`stall` 数百 ticks（≈3s）→ 主机 TX 丢帧尾实锤；`stall`≈0 → 需另查字节损坏源。

## 16. 第七阶段：主动 NAK——帧中途停顿 >0.5s 提前 NAK（2026-08-14）

### 16.1 动机

被动诊断已实锤截断机制：主机截断帧后，板端在帧中途静默等满**主机 3s 超时**才收到重发（`stall=597/598 ticks ≈ 3.0s`）。2M 一轮烧写 17 次截断 × 3s = **51s 纯停顿**，把 2M 线速优势吞掉（108.56s vs 1.5M 的 69.87s）。3s 是**主机侧** recv 超时——板端可以更快反应：帧中途线上静默 >0.5s 即断定「该帧已截断」，主动 NAK 让主机立刻重发。

### 16.2 实现

- `read_bytes_timeout(fd, buf, n, max_gap_ticks)`：用 `CONSOLE_IOCTL_GET_RX_STATS` 轮询环深度，仅在 `buffered>0` 时调 read()（read 空环会阻塞，环只增不减故 read 必不阻塞）；环空且 `uptime()-t_last > max_gap_ticks` 时返回 `-2`。`max_gap_ticks==0` 回退阻塞读（握手消息，静默不算错）。
- `recv_msg` 加 `stall_nak_ticks` 参数：magic 扫描保持阻塞读（帧间等待=主机节奏，不设超时）；magic 找到后的 hdr/payload/crc 用 `read_bytes_timeout`，`-2` → 返回 `-3`。
- 5 个调用点：INFO/BAUD req/BAUD sync 传 0；DATA 循环与 DONE 传 `RX_STALL_NAK_TICKS=100`（0.5s@5ms）。
- DATA 循环新增 `type==-3` 分支：`stall_errors++`、双口 printf、`show_retry("STALL")`、`send_nak(ERR_CRC)`。
- 关键设计：紧轮询不 sleep——CTI 帧间隙 ~80µs 期间环空，若用 `sleep(1)` 每帧 +5ms = 25.6s 吞吐损失；ioctl 轮询则只在截断时多花 0.5s。

### 16.3 预期收益（2M 实测已确认，2026-08-14）

**2M 实机结果**（5144 扇区，DATA_PORT=/dev/ttyUSB0）：
```

burn: stall sec=1203 gap=101 ticks atbyte=0
burn: stall sec=1444 gap=101 ticks atbyte=3
...
burn: stats ticks=11440 ... dup=0 crc=0 io=0 pkt=0 sd=0 stallnak=9 raw_drop=0 ... stall=0 sec=0 longstall=0
```
- **gap=101 ticks ≈ 0.5s**：正是设计的 `RX_STALL_NAK_TICKS=100`（严格大于，100 临界=101）→ 帧中途停顿超时提前 NAK 实机确认。
- **timeouts=0**：无一个扇区再等满主机 3s 超时；`stallnak=9 = naks=9`，所有重试都走提前 NAK 路径，`crc_errors=0`（零垃圾帧）。
- **elapsed 108.56s → 57.52s，吞吐 23.6 → 44.7 KiB/s**：2M 贴物理天花板（每扇区线时 2.6ms + SD 写 1.7ms + ACK/调度开销 ≈ 11.2ms，固定开销 ~7ms 主导，升更高波特率收益有限）。
