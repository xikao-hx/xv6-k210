# UART 烧录 SD 卡调试记录

# 第一次调试

## 1. `Timeout waiting for magic`

现象：

```text
sec=2 attempt=1 failed: timeout waiting for magic
sec=2 attempt=2 recv ACK seq=2
```

初步怀疑是 ACK 丢失或 SD 写入慢。后来通过 ACK 诊断 payload 看到：

```text
reason=OK ticks=0
```

说明 SD 写入本身不是 10 秒级卡顿。真正原因之一是 OLED 调试输出放在正常 ACK 前后，导致板端不能及时回到 UART 接收路径。

修复：

- 正常路径不再刷 OLED。
- 写 SD 后立即 ACK。
- ACK 后立即回到 `recv_msg()`。
- `tools/burn.py` 保留主机端详细诊断。

## 2. 重复 DATA 与 ACK 幂等

如果主机没收到 ACK，会重发同一个扇区。板端如果已经写入并推进 `sec`，重发包的 `seq` 会小于当前 `sec`。

修复：

```c
if (type == PKT_DATA && plen == 512 && rseq < sec) {
  send_ack_payload(uart_fd, rseq, ACK_DUP, sec);
  continue;
}
```

这样不会重复写 SD，也能让主机恢复同步。

主机端也增加 seq 校验：

```python
if seq != sec:
    # stale response
    continue
```

## 3. `Sector 1/524288` 太多

原因不是整张 SD 卡，而是 `target/fs.img` 原先固定为 256MiB：

```make
dd if=/dev/zero of=$T/fs.img bs=512k count=512
```

256MiB / 512B = 524288 sectors。

后来改为可配置：

```make
FS_SIZE_MB ?= 64
dd if=/dev/zero of=$T/fs.img bs=1M count=$(FS_SIZE_MB)
```

默认 64MiB，对应 131072 个扇区。64MiB 避免了 32MiB FAT32 簇数过低警告，同时比原来的 256MiB 少 4 倍刷写量。

后续进一步优化为：`tools/burn.py` 默认只发送 FAT32 实际使用区域。脚本读取 BPB 和 FAT 表：

- 保留 reserved sector、FSInfo、FAT1/FAT2 等元数据区。
- 扫描 FAT 表中最后一个非 0 的 cluster。
- 发送到该 cluster 结束位置。
- 免费空间尾部不再通过 UART 发送。

示例：

```text
Image: target/fs.img
Size: 2689024 bytes (5252 sectors)
FAT32 trim: full=67108864 bytes, send=2689024 bytes, saved=64419840 bytes (95%)
FAT32 layout: data_start=2050 sectors, spc=1, last_cluster=3203
```

旧行为仍可通过 `--full-image` 保留：

```sh
python3 tools/burn.py --full-image /dev/ttyUSB0 target/fs.img
```

为了验证裁剪结果而不打开串口，可以使用：

```sh
python3 tools/burn.py --dry-run --baud 460800 --board-baud 500000 /dev/ttyUSB0 target/fs.img
```

## 4. `panic: init exiting`

现象：

```text
SDHC/SDXC detected
hart 1 starting
panic: init exiting
```

原因是 `make run platform=k210` 只烧 kernel，不会写 SD 卡文件系统。虽然 make 输出中生成了 `target/fs.img`，但板子启动时读的是 SD 卡上的内容。

后续发现 `/dev/sdc` 不是块设备，而是普通文件：

```text
-rw-r--r-- 1 root root 67108864 /dev/sdc
lsblk: /dev/sdc: not a block device
```

这说明之前 `dd of=/dev/sdc` 时真实块设备不存在，`dd` 在 `/dev` 下创建了普通文件，SD 卡并没有被更新。

修复：

- `sdcard` 目标增加块设备保护：

```make
@test -b "$(dev-sd)" || (echo "$(dev-sd) is not a block device; refusing to write fs.img"; exit 1)
```

- 增加 `verify-sd` 目标，比较 SD 卡开头内容是否和 `target/fs.img` 一致。

验证方式：

```sh
make verify-sd dev-sd=/dev/sdX
```

必须使用整卡设备，如 `/dev/sdc`，不要使用分区 `/dev/sdc1`。

## 5. 高波特率切换

UARTHS 文档说明速率最高可到 5Mbps，但 K210 UARTHS 只有 8 字节 FIFO，且没有硬件流控。最终采用两阶段 baud，并把主机 baud 与板端 baud 分开：

1. 115200 下启动 `burn`。
2. INFO 中携带板端 baud 设置。
3. 板端先在 115200 下发送 INFO ACK。
4. 主机在 115200 下发送 BAUD 请求，板端回 BAUD READY。
5. 板端等待 TX FIFO 空闲后切到板端 baud。
6. 主机切到主机传输 baud，并发送 BAUD 同步包。
7. 板端收到同步包后回 BAUD ACK。
8. 数据阶段开始发送 DATA。

单独测试发现，主机设置为 230400、板端也设置为 230400 时，板端发出的 `BSET\n` 会被主机读成类似：

```text
b'\x82\xb3\x85\xb4\n'
```

这说明两端实际速率没有对齐。使用独立测试程序验证后，主机仍使用 230400，但板端请求 baud 改为约 253400，可以稳定通过：

```sh
python3 tools/uartbaud.py /dev/ttyUSB0 --baud 230400 --board-baud 253400
```

输出：

```text
Board transmitted at new baud
Sending 64-byte pattern at 230400 baud
Board reply: b'OK\n'
UART baud test passed
```

因此 `tools/burn.py` 最初默认使用主机 230400，同时把发给板端的 baud 按 1.10 倍补偿。默认等价于：

```sh
python3 tools/burn.py --baud 230400 --board-baud 253440 /dev/ttyUSB0 target/fs.img
```

如果需要复现本次手动验证的精确值，可以使用：

```sh
python3 tools/burn.py --baud 230400 --board-baud 253400 /dev/ttyUSB0 target/fs.img
```

后续继续测试 460800、921600、1500000 时，也必须先用 `tools/uartbaud.py` 找到对应的板端补偿值。由于没有硬件流控，高速下仍需严格保持 stop-and-wait，或加入更完整的窗口/重传策略。

后续实测结果：

```text
python3 tools/uartbaud.py /dev/ttyUSB0 --baud 460800 --board-baud 500000
Board transmitted at new baud
Sending 64-byte pattern at 460800 baud
Board reply: b'OK\n'
UART baud test passed
```

而 576000、768000、921600 多组补偿值都出现 `BSET` 或返回包无法干净解码的问题。当前工程的 `make download` 使用稳定组合：

```sh
python3 tools/burn.py --baud 460800 --board-baud 500000 /dev/ttyUSB0 target/fs.img
```

64MiB 完整镜像在 460800 baud 下理论仍需二十多分钟；但配合 FAT32 裁剪后，当前实际发送约 2.6MiB，刷写时间大幅缩短。

## 6. `/burn`、`/bin/burn` 与 fs.img 未更新

`tools/mkfs.py` 会递归扫描 `build/user/**/_*`，并把用户程序同时写入根目录和 `/bin`：

```python
vfs.open("/" + name, "wb").write(data)
vfs.open("/bin/" + name, "wb").write(data)
```

因此理论上 `_burn` 会生成：

```text
/burn
/bin/burn
```

调试过程中出现：

```text
exec /burn failed
exec burn failed
/bin/burn 成功
```

以及后续全部路径失败：

```text
Board shell could not exec burn program
```

定位时发现一个容易误判的问题：`build/user/app/_burn` 已经是新版，但 `target/fs.img` 仍是旧时间戳。原因是 Makefile 还包含已经删除的 `_uartbaud` 目标，`make fs` 在生成镜像前失败，导致用户以为刷了新版，实际仍在反复刷旧 `fs.img`。

修复：

- 从 `UPROGS` 移除已经不存在的 `_uartbaud`。
- 重新执行 `make fs`。
- 用 `stat` 确认 `target/fs.img` 时间戳晚于 `build/user/app/_burn`。

验证：

```text
build/user/app/_burn  11:11:32
target/fs.img     11:11:37
```

`tools/burn.py` 也增加了 `--burn-cmd` 和 fallback 顺序。默认先尝试 `/burn`，失败后尝试 `burn`、`/bin/burn`、`bin/burn`。如果当前板子只有 `/bin/burn` 可执行，可以直接指定：

```sh
python3 tools/burn.py --burn-cmd /bin/burn --baud 460800 --board-baud 500000 /dev/ttyUSB0 target/fs.img
```

## 7. 连续刷写第二次 `usertrap(): addr is illegal`

现象：

第一次刷写成功：

```text
Sector 5252/5252 (100%)
Transfer completed successfully! ACK reason=DONE ticks=0
```

不重启马上第二次执行：

```text
Sending '/burn' command to board at 115200 baud...
Waiting for BURN signal...
Timeout waiting for BURN, retrying '/burn' (1); last serial='/burn\nusertrap(): addr is illegal\n$ '
```

原因是板端 `/burn` 通过 `sdcarddev_write()` 直接调用 `sdcard_write_sector()` 覆盖 SD 卡，绕过了 FAT32 文件系统层和 buffer cache。第一次刷写成功后，磁盘内容已经换成新版 `fs.img`，但旧 kernel 内存中仍缓存着旧的 FAT、目录项或文件块。第二次 shell `exec /burn` 时，`exec()` 可能读到“旧缓存 + 新磁盘”的混合内容，导致 ELF 装载错误，用户程序一启动就触发非法地址异常。

修复内容：

- `kernel/fs/bio.c`
  增加 `binvalidate(dev)`，将指定设备中 `refcnt == 0` 的 buffer 标记为 invalid。

- `kernel/fs/fat32.c`
  增加 `fat32_invalidate()`，清除空闲目录项缓存，避免路径查找命中旧目录项。

- `kernel/devsw/sdcarddev.c`
  增加 `SDCARD_IOCTL_INVALIDATE_CACHE`，统一调用 `fat32_invalidate()` 和 `binvalidate(0)`。

- `user/app/burn.c`
  在 DONE 成功后、console 恢复 TTY 模式前调用：

```c
int cache_rc = ioctl(sdcard_fd, SDCARD_IOCTL_INVALIDATE_CACHE, 0);
```

为了验证该修复是否真的在板端 kernel 生效，`burn.c` 成功结束时会打印：

```text
burn: done sectors=5252 bytes=2689024 cache=0
```

其中 `cache=0` 表示新版 kernel 已经执行缓存失效；如果看到 `cache=-1`，说明板子仍是旧 kernel，不认识该 ioctl。

注意：这是 kernel 改动。只刷 `fs.img` 不会让它生效，必须先：

```sh
make run platform=k210
```

然后再刷 SD：

```sh
python3 tools/burn.py --baud 460800 --board-baud 500000 /dev/ttyUSB0 target/fs.img
```

最终验证输出：

```text
Sector 5252/5252 (100%)
Transfer completed successfully! ACK reason=DONE ticks=0
Board console tail:
burn: done sectors=5252 bytes=2689024 cache=0\n$
```

看到 `cache=0` 后，连续第二次刷写不应再因为旧 FAT/buffer cache 触发 `usertrap(): addr is illegal`。


# 第二次调试

## 1. 问题背景

项目通过主机端 `tools/burn.py` 将 FAT32 文件系统镜像经 UART 发送给
K210。板端 shell 启动 `/burn`，用户态烧录程序接收分包、校验 CRC，
再通过 SD 卡设备接口把每个 512 字节扇区写入 SD 卡。

本次调试先后遇到两类表象不同的问题：

1. INFO 握手阶段出现 CRC mismatch。
2. INFO 和波特率切换成功后，传输若干扇区便超时，串口中出现 RustSBI
   panic。

第二类问题最终定位到内核物理页分配器读取了已经损坏的 freelist
指针。故障与 UART 波特率无直接关系，SPI0 的 SD 卡 DMA 路径是当前
最主要的破坏来源嫌疑。现阶段采用的隔离措施是让 SPI0 使用轮询传输，
SPI1 仍可使用 DMA。

本文重点记录完整的排查过程、证据链、使用的命令，以及哪些结论已经
证实、哪些仍需要进一步实验确认。

## 2. 烧录链路

烧录链路如下：

```text
主机 tools/burn.py
  -> UART 帧协议
  -> K210 UARTHS
  -> /burn 用户程序
  -> write(sdcard_fd, payload, 512)
  -> sdcarddev_write()
  -> sdcard_write_sector()
  -> spi_write(SPI_DEVICE_0, ...)
  -> SPI0 轮询或 DMAC
  -> SD 卡
```

UART 帧格式为：

```text
magic(4) + seq(4) + type(1) + plen(2) + payload(plen) + crc32(4)
```

正常的 INFO ACK：

```text
seq     = 0
type    = ACK
plen    = 5
payload = reason(1) + ticks(4)
```

这个固定格式是分析第一阶段 CRC 错误的重要依据。

## 3. 第一阶段：INFO ACK CRC mismatch

### 3.1 原始现象

第一次失败发生在 115200 波特率的 INFO 握手阶段：

```text
Board ready, sending image info...
ValueError: INFO ACK: CRC mismatch seq=0 type=ACK plen=12905
got=0x64612031 expected=0x1DA22926
```

此时尚未切换到 `host=460800, board=500000`，因此不能把问题直接归因于
高速波特率误差。

### 3.2 从错误字段判断数据流被插入

INFO ACK 的 `plen` 应固定为 5，但读到：

```text
12905 = 0x3269
```

按 UART 收到的字节顺序，`0x69 0x32` 对应 ASCII：

```text
i2
```

收到的 CRC：

```text
0x64612031
```

按小端字节查看为：

```text
31 20 61 64 -> "1 ad"
```

仓库中存在如下内核错误输出：

```c
printf("i2cdev: transfer failed ret=%d addr=%x nmsgs=%d\n", ...);
```

它包含 `"i2cdev"`、`"-1 addr"` 等片段，与损坏帧中的 ASCII 特征高度
一致。板端 `/burn` 又会在进入 RAW 模式后更新 OLED，OLED 地址正是
I2C `0x3c`。

因此第一阶段的判断是：二进制 ACK 与控制台文本共用同一 UART，当
I2C/OLED 错误日志同步输出时，文本可能插入 UART 缓冲发送的协议帧。

### 3.3 I2C 独立验证

随后运行：

```text
$ i2ctest
scan: 0x3C 0x68
OLED probe: 0x3C OK
OLED display updated
I2C test PASSED
```

再次烧录时 INFO ACK 也成功：

```text
INFO ACK seq=0 reason=INFO ticks=0
```

这说明 OLED/I2C 并非持续不可用。第一阶段更像瞬时 I2C 错误或控制台
输出与二进制协议帧的并发串流问题，不是后续板端崩溃的根因。

### 3.4 这一阶段得到的调试经验

- 先确定错误发生在哪个协议阶段，再判断波特率是否已经切换。
- CRC mismatch 不一定说明 CRC 算法错误，也可能是帧中混入其他输出。
- 将数值按小端拆成字节并转换为 ASCII，常能发现日志插入痕迹。
- RAW 二进制协议期间不应通过同一 UART 输出普通内核日志。
- 二进制发送与同步 `printf` 应共享发送锁，或者 RAW 模式应抑制非协议
  输出。

## 4. 第二阶段：传输若干扇区后超时

### 4.1 高速传输下的现象

INFO 和 BAUD 握手成功后，传输到 sector 27 时超时：

```text
INFO ACK seq=0 reason=INFO ticks=0
BAUD READY seq=0 reason=BAUD target=500000
BAUD ACK seq=0 reason=BAUD actual=500000
Sector 27/6298
timeout waiting for magic
last=... /main.rs:530:18
```

`main.rs:530:18` 位于：

```text
bootloader/rustsbi-k210/src/main.rs
```

对应 RustSBI 的未处理 trap 分支：

```rust
cause => panic!(
    "unhandled trap! mcause: {:?}, mepc: ..., mtval: ...",
    ...
)
```

这说明主机收不到 ACK 并不是简单丢包，而是板端已经 panic 并停止正常
执行。此时继续进行 DATA 重试没有意义，必须复位开发板。

### 4.2 用低速实验排除 UART 波特率

为了验证是否由 `460800/500000` 的速率补偿引起，使用全程 115200：

```bash
python3 tools/burn.py \
  --baud 115200 \
  --board-baud 115200 \
  /dev/ttyUSB0 target/fs.img
```

低速下仍然在 sector 2 附近崩溃。故障扇区从 27 变成 2，说明：

- 问题不是固定发生在某个镜像扇区。
- 问题不是高速 UART 独有。
- 更像是执行次数、内存分配时序或外设传输引起的内核内存破坏。

### 4.3 扩大串口错误上下文

原 `recv_msg()` 只保留最后 16 字节：

```python
if len(last) > 16:
    del last[:-16]
```

这只能看到 `main.rs:530:18`，最关键的 `mcause`、`mepc` 和 `mtval` 已经
丢失。调试时临时把尾部缓冲扩大到 512 字节，并同时打印可读文本和
十六进制：

```python
if len(last) > 512:
    del last[:-512]

raise TimeoutError(
    f"{context}: ... "
    f"serial='{printable_serial(last)}', "
    f"last_hex={hexdump(last)}"
)
```

重新执行后得到完整 panic：

```text
[rustsbi] panicked at 'unhandled trap!
mcause: Exception(LoadMisaligned),
mepc: 00000000800279ca,
mtval: 000000002016d001',
src/main.rs:530:18
```

三个寄存器的含义：

| 字段 | 含义 | 本次取值 |
|---|---|---|
| `mcause` | trap 类型 | `LoadMisaligned` |
| `mepc` | 发生 trap 的指令地址 | `0x800279ca` |
| `mtval` | 导致异常的访问地址 | `0x2016d001` |

`0x2016d001` 不是 8 字节对齐地址，符合 64 位加载触发
`LoadMisaligned` 的特征。

## 5. 将 mepc 映射回内核源码

### 5.1 使用 addr2line

K210 内核 ELF 为 `target/kernel`。执行：

```bash
riscv64-unknown-elf-addr2line \
  -f -C -e target/kernel 0x800279ca
```

输出：

```text
kalloc_page
kernel/vm/kalloc.c:131
```

### 5.2 使用 objdump 交叉验证

执行：

```bash
riscv64-unknown-elf-objdump -dS \
  --start-address=0x80027980 \
  --stop-address=0x80027a20 \
  target/kernel
```

关键汇编：

```text
800279c2: ld   s3,24(s2)   # r = kmem[id].freelist
800279ca: ld   a5,0(s3)    # r->next
```

对应源码：

```c
r = kmem[id].freelist;
if (r) {
  kmem[id].freelist = r->next;
}
```

所以异常不是普通用户指针未对齐，而是：

```text
kmem[id].freelist == 0x2016d001
```

物理页分配器的空闲链表头已经被破坏，`kalloc_page()` 在读取
`r->next` 时才暴露问题。

### 5.3 为什么 RustSBI 报告了内核错误

K210 使用较旧的 RISC-V 特权规范，当前 RustSBI 没有把
`LoadMisaligned` 委托给 S 态处理，而是在 M 态 trap handler 中进入
默认 panic 分支。

因此：

- RustSBI 是异常报告者。
- 真正执行错误指令的是 xv6 内核。
- 修改 RustSBI 让它忽略异常不能修复 freelist 损坏。

## 6. 从 kalloc_page 反向追踪调用链

烧录程序每写一个扇区，SD 卡设备层会临时分配一页：

```c
char *buf = kalloc_page();
either_copyin(buf, user_src, 512);
sdcard_write_sector((uint8 *)buf, sdcard_sector);
kfree_page(buf);
```

SPI DMA 路径也会分配一页 bounce buffer：

```c
uint32 *write_cmd = kalloc_page();
...
spi_dw_dma_xfer(...);
...
kfree_page(write_cmd);
```

因此烧录过程会高频重复：

```text
kalloc_page -> SPI/DMAC -> kfree_page
```

这与在 sector 2 或 sector 27 随机暴露 freelist 损坏的现象一致。

## 7. SPI0 DMA 路径的风险分析

### 7.1 512 字节传输恰好占满一个页面

SD 卡扇区大小为 512 字节，SPI 数据宽度为 8 位。当前 DMA bounce
buffer 会把每个 8 位元素扩展到一个 `uint32`：

```text
TX: 512 × sizeof(uint32) = 2048 字节
RX: 512 × sizeof(uint32) = 2048 字节
总计                         4096 字节
```

而 `kalloc_page()` 只提供 4096 字节：

```text
┌──────── TX 2048 B ────────┬──────── RX 2048 B ────────┐
0                           2048                         4096
```

`spi_can_dma()` 的边界检查允许“等于 PGSIZE”：

```c
if (frames * 2 * sizeof(uint32) > PGSIZE)
  return false;
```

所以 512 字节恰好进入 DMA，且没有任何 guard、canary 或额外空间。

### 7.2 DMA 完成错误被忽略

两个 channel 的等待结果没有检查：

```c
dmac_wait_done(spi_data->chan_tx, DMAC_WAIT_TIMEOUT);
dmac_wait_done(spi_data->chan_rx, DMAC_WAIT_TIMEOUT);
return 0;
```

即使等待超时，SPI 层也按成功返回，随后复制 RX 数据并释放页面。这会
掩盖 DMA 未按预期结束的情况。

### 7.3 中断处理只清理 channel 0

SPI0 配置使用：

```text
TX = DMAC_CHANNEL0
RX = DMAC_CHANNEL1
```

但 K210 的磁盘中断入口当前固定调用：

```c
dmac_intr(DMAC_CHANNEL0);
```

而 `dmac_set_single_mode()` 会为两个 channel 都启用 channel interrupt。
因此还需要确认 channel 1 的完成状态和中断是否得到正确清理。

### 7.4 当前证据的边界

已经证实：

- 崩溃是 `kalloc_page()` 读取损坏的 freelist 指针。
- 故障在高低 UART 波特率下均出现。
- 烧录期间 SPI0 DMA 和页分配器会高频交互。
- 512 字节 SPI DMA bounce buffer 恰好用满整页。
- DMA 等待错误和 channel 1 中断处理存在缺口。

尚未通过硬件观测完全证实：

- 究竟是 RX 多写一个 DMA 单元、完成时序提前、未清中断，还是其他
  DMA/allocator 竞态直接改写了 freelist。
- 被破坏的是 DMA bounce page 本身，还是它相邻的另一个空闲页。

因此“SPI0 DMA 导致页链表破坏”是目前证据最强的工作结论，但要得到
最终根因，还应增加 guard page、canary 和 DMA 寄存器记录。

## 8. 当前隔离修复

当前先对 SPI0 禁用 DMA：

```c
spi_dw[spi_num]->dma_enable = spi_num != SPI_DEVICE_0;
```

效果：

- SPI0：SD 卡走 `spi_dw_poll_transfer()`。
- SPI1：仍允许 DMA，不影响其他 SPI 设备继续验证 DMA。
- UART 协议、SD 卡设备层和 FAT32 镜像格式不变。

轮询路径会在发送时同步排空 RX FIFO，并带有超时保护，速度可能低于
DMA，但不会使用有风险的整页 bounce buffer。

需要强调：这不表示 K210 的 SPI0 硬件不支持 DMA，只表示当前驱动的
SPI0 全双工 DMA 实现尚未满足安全烧录要求。

## 10. SPI0 DMA 的后续正确修复方向

如果要重新启用 SPI0 DMA，建议按以下顺序改造。

### 10.1 分离 TX/RX bounce buffer

不要把 TX 和 RX 紧密放在同一个页面中。至少使用独立缓冲区，并为 RX
尾部添加 guard/canary：

```text
TX page
RX page + guard
```

传输后检查 canary，确认硬件实际写入长度。

### 10.2 传播 DMA 错误

检查两个 channel 的返回值：

```c
if (dmac_wait_done(tx, timeout) < 0)
  return -1;
if (dmac_wait_done(rx, timeout) < 0)
  return -1;
```

失败时必须：

- 禁止 SPI DMA 请求。
- 禁止并清理两个 DMA channel。
- 清空 SPI RX FIFO。
- 不复制未完成的 RX 数据。
- 在确认 DMA 不再访问缓冲区后才能释放页面。

### 10.3 正确处理中断状态

不要只清理固定的 channel 0。应读取 DMAC channel interrupt status，
分别清理所有触发 channel，或者在纯轮询 DMA 模式下不启用不需要的
完成中断。

### 10.4 增加页分配器完整性检查

在调试构建中，读取 `r->next` 前检查：

```text
r 是否页对齐
r 是否位于 [end, PHYSTOP)
r->next 是否为 0 或合法页地址
```

这样可以在 freelist 第一次损坏时由内核输出更明确的信息，而不是等到
RustSBI 报 `LoadMisaligned`。

### 10.5 增加压力测试

单独编写 SPI0/SD DMA 压力测试：

1. 重复写同一个测试扇区。
2. 每轮分配和释放不同页面。
3. 写后读回并比较 CRC。
4. 检查 guard 和 freelist。
5. 分别测试 1、16、64、511、512 字节边界。
6. 分别测试单核和双核、中断开关、高低 SPI 时钟。

只有压力测试稳定后，才应重新让 SD 卡烧录默认使用 DMA。

## 11. 本次调试方法总结

本次问题的有效定位步骤可以归纳为：

1. 按协议阶段划分故障，确认错误发生在切换波特率之前还是之后。
2. 对异常数值做小端拆分和 ASCII 检查，识别文本日志混入二进制帧。
3. 使用独立 `i2ctest` 验证 OLED/I2C，避免把两个不同问题混为一谈。
4. 通过降低 UART 波特率做控制变量实验。
5. 扩大串口错误上下文，保留完整 RustSBI panic。
6. 根据 `mcause` 判断异常类型。
7. 使用 `addr2line` 和 `objdump` 将 `mepc` 精确映射到源码和指令。
8. 根据 `mtval` 判断实际访问的坏地址。
9. 从崩溃点反向追踪分配、设备、SPI 和 DMA 调用链。
10. 先用最小隔离修改验证嫌疑路径，再设计长期正确修复。

其中最关键的一点是：超时只是主机看到的表象。只有继续读取并保存板端
串口输出，才能发现真正原因是 RustSBI 报告的内核内存破坏。

## 12. 第三阶段：shell 命令被截断，始终等不到 `BURN`

### 12.1 现象

前两阶段问题处理后，主机再次执行：

```bash
make download
```

出现：

```text
Sending '/burn' command to board at 115200 baud...
Waiting for BURN signal...
Timeout waiting for BURN, retrying '/burn' (1);
last serial='/bur\nexec /bur failed\n$ '
Timeout waiting for BURN, retrying '/burn' (2);
last serial='/bur\nexec /bur failed\n$ /bur\nexec /bur failed\n$ '
```

此时不能先修改 DATA 帧、CRC、SD 卡驱动或高速波特率，因为传输协议尚未开始。
板端明确回显：

```text
/bur
exec /bur failed
```

shell 实际收到并执行的是 `/bur`，最后的 `n` 丢失。burn 用户程序没有启动，
自然不会发送 `BURN`。

### 12.2 旧发送方式

原主机工具清理 shell 输入后，立即整段写入命令和换行：

```python
ser.write(b"\x15")
ser.write((command + "\n").encode())
```

在当前 UARTHS、SBI console 和 shell 输入链路组合下，连续写入可能出现字符
丢失。日志已证明最后一个字符没有到达 shell；若要进一步区分具体硬件 FIFO
时序或软件消费速度，还需要串口逻辑分析数据。

### 12.3 修复策略

只对 shell 命令阶段增加保守节流：

1. 发送 Ctrl-U，清除残留输入；
2. 等待约 20 ms；
3. 命令逐字节发送，字符间隔约 3 ms；
4. 全部字符发送完后等待约 10 ms；
5. 单独发送换行。

同时把失败检测从“只匹配当前预期命令”改为识别通用
`exec ... failed`。即使实际命令被截断，主机也能立即判断板端没有进入 burn，
而不是把它误判为单纯的 `BURN` 超时。

修改没有扩散到 INFO/DATA/ACK 阶段。镜像帧继续整块发送并使用 CRC32，避免
为了低速 shell 握手降低整个下载过程的吞吐。

### 12.4 主机侧验证

```bash
python3 -m py_compile tools/burn.py
python3 tools/burn.py --dry-run /dev/null target/fs.img
```

两条命令分别验证 Python 语法和镜像参数/裁剪计算，但不能证明串口链路恢复。

### 12.5 实机复验

板端进入 shell 后执行：

```bash
make download
```

按顺序确认：

1. 板端完整回显 `/burn`，不能再是 `/bur`；
2. 主机收到 `BURN`；
3. INFO 帧被确认；
4. DATA 帧持续收到 ACK；
5. 传输结束后波特率恢复；
6. 重启或重新挂载后，SD 卡中的 FAT32 文件可以读取。

截至本节编写时，代码已通过 `py_compile` 和 `--dry-run`，但尚未收到新的板端
`make download` 结果，因此状态为**已完成主机侧验证，待 K210 实机复验**。

### 12.6 阶段判断表

| 最后观察到的信息 | 所在阶段 | 优先检查 |
| --- | --- | --- |
| `exec /bur failed` | shell 命令 | 字符丢失、回显、发送节奏 |
| 完整执行 `/burn`，但无 `BURN` | burn 启动 | 用户程序启动、设备打开、首个输出 |
| 收到 `BURN`，INFO 无 ACK | 协议协商 | 波特率、INFO 格式、串口残留日志 |
| DATA 序号附近超时 | 数据传输 | CRC、帧号、串口日志混入 |
| 板端 panic | SD/SPI 写入 | 用对应 ELF 解析 `sepc` 和回溯 |

将问题定位到正确阶段后再修改，可以避免在多个层次同时打补丁。
