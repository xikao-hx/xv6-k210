# 文件设备重构调试记录

## 1. 文档目的

本文记录文件与设备操作抽象重构后，在 K210 实机上暴露出的启动、中断、
I2C、SPI 和 UART 下载问题。重点不只是保存最终改动，还要保留完整证据链，
方便以后快速判断相似故障位于哪一层。

本文使用三种状态：

- **已实机确认**：已有板端输出证明问题消失或功能恢复。
- **已完成代码验证**：代码检查和双平台构建通过，尚无新板端结果。
- **待定位**：证据不足，需要继续采集板端输出或总线波形。

> 构建成功不能代替 K210 实机验证。

## 3. 调试基线

### 3.1 保存故障现场

发生 panic 或外设异常后先保存：

```text
Git 分支、提交和 git status --short
完整串口输出
本次烧录使用的 target/kernel
本次烧录使用的 target/k210.bin
```

建议记录摘要：

```bash
sha256sum target/kernel target/kernel.bin target/k210.bin
```

`sepc` 和回溯地址只对产生它们的 ELF 有意义。重新构建后地址可能变化，不能
用新 ELF 解析旧串口日志。

### 3.2 先划分故障阶段

K210 运行链路：

```text
上电/RustSBI
  -> 内核入口与 C 运行环境
  -> trap/PLIC
  -> 文件与设备抽象
  -> board controller
  -> 底层驱动
  -> FPIOA/引脚/外设芯片
  -> 用户态测试
```

UART 下载链路：

```text
shell 命令
  -> 等待 BURN
  -> 波特率切换
  -> INFO/DATA/ACK
  -> SD 卡写入
```

例如板端实际执行了 `/bur`，故障仍在 shell 命令阶段。此时修改 CRC、DATA
帧超时或 SD 卡驱动都没有作用。

### 3.3 基础代码验证

```bash
make build platform=qemu
make build platform=k210
git diff --check
```

这只能发现接口、条件编译和链接问题。涉及 K210 外设时，仍须重新烧录并执行
对应板端测试。

## 4. I2C panic：定位到 `.bss` 未清零

### 4.1 现象

```text
scause 0x0000000000000005
sepc=0x0000000080029f5e stval=0x0000000409942100
panic: kerneltrap
```

`scause=5` 是 supervisor load access fault。`sepc` 是非法读指令地址，
`stval` 是该指令试图读取的地址。

### 4.2 地址与调用链

必须使用故障发生时对应的 ELF：

```bash
riscv64-unknown-elf-addr2line -e target/kernel -f -C \
  0x80029f5e 0x80029628 0x8002ab78
riscv64-unknown-elf-objdump -dS target/kernel | less
```

关键调用链为：

```text
i2c_init
  <- i2c_controller_transfer
  <- i2cdev_ioctl
  <- 文件/设备 ioctl 路径
```

故障指令在 `i2c_init()` 中访问 `i2c[]` 控制器数组。结合数组基址、元素大小和
`stval` 反推，传入的 `bus_num` 不是 0 或 1，而是类似 `0x71322374` 的垃圾值。

### 4.3 垃圾值来源

`bus_num` 来自没有显式初始化的板级对象：

```text
i2c_controllers[0].bus_num
```

按 C 语言规则，该对象位于 `.bss` 并应自动为零。检查符号与段：

```bash
riscv64-unknown-elf-nm -n target/kernel | rg \
  '__bss|i2c_controllers'
riscv64-unknown-elf-readelf -S target/kernel
riscv64-unknown-elf-readelf -l target/kernel
ls -l target/kernel target/kernel.bin
```

证据链：

1. `i2c_controllers` 位于 `.bss`；
2. `.bss` 是 ELF 的 `NOBITS` 段；
3. 裸 `kernel.bin` 不携带 `.bss` 内容；
4. 原 K210 入口没有在进入 C 前清零 `.bss`；
5. 静态零初始化对象继承了 RAM 旧值。

因此，I2C 只是首先暴露问题的使用者，真正缺陷是 C 运行环境初始化不完整。

### 4.4 修复

1. 链接脚本导出 `__bss_start` 和 `__bss_end`；
2. hart 0 在使用 C 静态状态前逐字清零 `.bss`；
3. 完成后用内存屏障发布位于 `.data` 的完成标志；
4. 其他 hart 等待该标志后再继续。

等待标志不能放在尚未清零的 `.bss` 中。也不能只给
`i2c_controllers[0].bus_num` 赋 0，因为其他静态对象仍会继承脏数据。

### 4.5 验证

```bash
make build platform=k210
make build platform=qemu
riscv64-unknown-elf-readelf -S target/kernel
riscv64-unknown-elf-objdump -d target/kernel | less
```

实机再次运行 `i2ctest` 后已能到达 OLED probe，不再在 `i2c_init()` panic。
因此 `.bss` 问题为**已实机确认修复**。

## 5. IRQ 34 风暴

### 5.1 现象与含义

```text
unexpected interrupt irq=34
unexpected interrupt irq=34
...
```

IRQ 34 对应 K210 GPIOHS0。当前内核没有为它注册处理函数，因此不应 enable。
持续打印说明该中断一直 pending 且 PLIC 对当前 hart 开放。

原 PLIC 初始化使用按位或来增加内核需要的 IRQ，却没有清除 RustSBI 或上一
启动阶段遗留的 enable 位。只在 trap 层忽略或限频打印不能解决问题，中断仍会
持续抢占 CPU。

### 5.2 修复

内核接管 PLIC 时直接覆盖确定的 enable bitmap：

- IRQ 27：现有磁盘/DMAC0 路径；
- IRQ 33：现有 UART 路径；
- IRQ 34：关闭；
- 其余 enable word：明确清零；
- threshold：设为 0。

原则是只打开内核已有处理函数、且能够完成 claim/complete 的中断。

### 5.3 复验

最新冷启动结果中，FAT32 目录恢复正常，IRQ 34 连续打印已经消失，因此 PLIC
enable 覆盖修复记为**已实机确认**。后续每次增加新的 K210 中断源时，仍应
重复以下回归：

1. 烧录最新镜像并断电重启；
2. 观察 shell 启动前后至少 30 秒；
3. 确认没有 unexpected IRQ 连续打印；
4. 验证磁盘与串口，确保 IRQ 27/33 保持可用。

若仍出现 IRQ 34，应读取 PLIC enable/pending 与 GPIOHS pending 寄存器，
确认是 enable 未覆盖、源状态未清除，还是其他代码再次打开 GPIOHS0。

## 6. SPI：`JEDEC FF FF FF`

### 6.1 接线语义

```c
fpioa_set_function(15, FUNC_SPI1_D0);    // MOSI
fpioa_set_function(16, FUNC_SPI1_D1);    // MISO
fpioa_set_function(17, FUNC_SPI1_SCLK);  // SCLK
fpioa_set_function(18, FUNC_SPI1_SS0);   // CS
```

| K210 | W25Q64 |
| --- | --- |
| IO15 / SPI1_D0 | DI、IO0、D0，即 MOSI |
| IO16 / SPI1_D1 | DO、IO1、D1，即 MISO |
| IO17 / SPI1_SCLK | CLK |
| IO18 / SPI1_SS0 | `/CS` |
| 3.3V | VCC；`/WP`、`/HOLD` 应为高 |
| GND | GND |

所以这里的 `D0` 对应 W25Q64 的 DI/IO0/D0；`D1` 对应 DO/IO1/D1。

### 6.2 `FF FF FF` 能说明什么

它表示 MISO 在采样期间一直为高，但不能单独证明接线错误。可能原因包括：

- CS 没拉低；
- 没有正确 SCLK；
- MOSI 没发出 `0x9f`；
- mode、帧宽或收发模式错误；
- SPI 时钟远高于请求值；
- FPIOA 配置错误；
- Flash 未供电，或 `/WP`、`/HOLD` 状态错误。

同一块板和接线在旧驱动可用时，应优先比较新旧软件行为。

### 6.3 调用链

```text
spitest
  -> open/ioctl/read/write
  -> file operations
  -> spidev
  -> K210 board SPI controller
  -> kernel/driver/spi.c
  -> FPIOA 与 SPI1
```

逐层确认：

1. `/dev/w25q64` 是否绑定到预期控制器和片选；
2. mode、速度、数据宽度是否保存到当前打开实例；
3. board controller 是否完整传参；
4. 底层是否生成连续的“发送 `0x9f` + 接收 3 字节”事务；
5. CS 是否覆盖全部 32 个时钟。

### 6.4 本轮发现的高优先级回归点

重构后的 `SPI_IOCTL_INIT` 会实际调用 `spi_set_clk_rate()`。K210 SPI threshold
位域在当前环境下不适合用于反推 SPI 输入时钟。如果得到 0 或异常值，分频器
会退化为最小除数 2，导致实际 SCLK 远高于用户请求的 1 MHz/2 MHz。

当前修复在 threshold 为 0 的启动配置下，用 CPU 时钟计算 SPI0/SPI1 的偶数
`BAUDR`，并保留最小、最大值约束。例如 390 MHz 输入、2 MHz 目标会得到约
196 的分频值，实际约 1.99 MHz，而不是除以 2。

### 6.5 复验与波形

当前只完成代码和双平台构建验证，状态为**待实机复验**：

```text
1. 烧录并冷启动
2. 确认无 IRQ 34 风暴
3. 运行 spitest
4. 保存完整 JEDEC 输出
5. 若仍为 FF FF FF，连接逻辑分析仪
```

同时观察 CS、SCLK、MOSI、MISO：

- CS 是否在整个事务期间为低；
- 是否恰好有 32 个有效时钟；
- MOSI 首字节是否为 `0x9f`；
- mode 0 的变化/采样边沿是否正确；
- MISO 是否在命令后返回 3 字节；
- 实测 SCLK 是否接近请求值。

若 CS、时钟与 `0x9f` 均正确但 MISO 始终为高，再检查供电、共地、
`/WP`、`/HOLD` 和 MISO 方向。若没有完整 32 个时钟，继续比较旧驱动的
EEPROM-read/receive 模式与新通用全双工路径。

`spitest` 只读 JEDEC ID，适合作为无破坏性首测。不要直接用擦除或写入未知
区域来验证通信。

## 7. I2C：解释 probe 和软件绑定测试

```text
FAIL: probe OLED at 0x3C
fixed-address binding: PASS
OLED display updated
```

三行属于不同层次：

- probe 失败：总线事务没有获得 ACK；
- fixed-address binding 通过：设备文件地址约束的软件测试通过；
- display updated：历史路径只表示后续调用走完，若库忽略 ioctl 错误，不能
  证明 OLED 真正更新。

因此，用户库应传播底层错误，测试只在所有关键写入成功后打印更新成功。

当前板级配置：

| K210 | I2C |
| --- | --- |
| IO30 | SCL |
| IO31 | SDA |
| 3.3V/GND | VCC/GND |

常见 7 位地址：SSD1306 为 `0x3c`，MPU6050 在 AD0 为低时为 `0x68`。

probe 仍失败时：

1. 确认 SDA/SCL 空闲为高；
2. 确认 3.3V 上拉存在；
3. 检查 FPIOA 控制器选择；
4. 观察是否产生 START；
5. 确认地址字节为 `0x3c << 1` 加方向位；
6. 观察第九个时钟是否 ACK；
7. 无 START 时检查控制器 busy/abort；
8. 有 START 但 NACK 时检查地址、电源、上拉和器件。

能越过 `.bss` panic 只证明控制器索引问题已修复；OLED 通信仍须独立验证。

最新实机结果中，MPU6050 的 `WHO_AM_I` 已返回 `0x68`，说明 I2C0 控制器、
IO30/IO31 及基本读事务能够工作。该结果进一步把 OLED 问题收敛到 OLED
模块自身、`0x3c` 地址、上拉/供电、首次 probe 时序或 OLED 专用写入路径，
不应再把它描述为整个 I2C0 总线不可用。

## 8. UART 下载：`/burn` 变成 `/bur`

### 8.1 现象

```text
Sending '/burn' command to board at 115200 baud...
Waiting for BURN signal...
Timeout waiting for BURN, retrying '/burn' (1);
last serial='/bur\nexec /bur failed\n$ '
```

板端执行的是 `/bur`，最后的 `n` 没进入 shell。burn 没启动，自然不会发送
`BURN`。此时问题仍在 shell 阶段，与 CRC、SD 卡写入和高速 DATA 帧无关。

### 8.2 修复与验证

主机端现在：

1. 发送 Ctrl-U；
2. 等约 20 ms；
3. 逐字节发送命令，间隔约 3 ms；
4. 等约 10 ms；
5. 单独发送换行。

并识别通用 `exec ... failed`，而不是只匹配预期命令。节流仅用于 shell
命令，INFO/DATA/ACK 和 CRC32 分帧仍整块发送。

已完成：

```bash
python3 -m py_compile tools/burn.py
python3 tools/burn.py --dry-run /dev/null target/fs.img
```

仍须执行 `make download`，确认完整回显 `/burn`、收到 `BURN` 并完成传输。
当前为**待实机复验**。专项过程见
[10.UART烧录SD卡故障调试记录.md](./10.UART烧录SD卡故障调试记录.md)。

## 11. 通用结论

1. 裸机镜像必须显式建立 C 运行环境，尤其是清零 `.bss`。
2. 内核接管 PLIC 时应覆盖 enable 状态，不能依赖固件遗留值。
3. 旧驱动可用而重构后失败时，应先比较新旧寄存器配置和事务时序。
4. `FF FF FF`、NACK、软件绑定通过分别代表不同层次。
5. panic 地址必须使用故障当时的 ELF 解析。
6. UART 下载应先判断失败位于 shell 握手还是二进制传输阶段。
7. 构建、QEMU 和 K210 外设通过是三个不同结论。
8. 未完成实机验证前，不能把修复记录成“硬件问题已解决”。

## 12. devtest 双失败：`fileopen()` 返回值被忽略 + `statsinit()` 未注册

### 12.1 现象

```text
devsw interface test
====================
open /dev/console: fd=3
FAIL: stats accepted write-only open
FAIL: invalid minor accepted
console actual baud: 115200
devsw test FAILED, failures=2
```

两个 FAIL 之后跟随 panic：

```text
panic: fileclose
backtrace:
0x00000000802037e2
...
```

### 12.2 两个 FAIL 的根因

**FAIL 1 — "stats accepted write-only open"**

`sys_open()`（`kernel/syscall/sysfile.c`）中对设备文件的处理顺序为：

```c
fileopen(f);            // 调用 statsopen()，此时 f->writable 还是 0（零初始化）
// ...
f->writable = writable; // 这里才赋值，太晚
```

`statsopen()` 用 `f->writable` 判断是否拒绝写打开：

```c
static int
statsopen(struct file *f) {
    if(f->minor != 0 || f->writable)
        return -1;
    return 0;
}
```

因为 `filealloc()` 返回零初始化结构体，`f->writable` 始终为 0，检查形同虚设。

**FAIL 2 — "invalid minor accepted"**

```c
mknod("/dev/_bad_console", DEV_CONSOLE, 99);
open("/dev/_bad_console", O_RDWR);  // 期望失败
```

`consoleopen()` 正确检查 minor：

```c
static int
consoleopen(struct file *f) {
    return f->minor == 0 ? 0 : -1;
}
```

但 `sys_open()` 直接丢弃 `fileopen()` 的返回值：

```c
if (ep->attribute & ATTR_DEVICE) {
    f->type = FD_DEVICE;
    f->major = ep->first_clus;
    f->minor = ep->file_size;
    fileopen(f);           // ← 返回值未检查
}
```

所以即使 `consoleopen()` 返回 -1，`sys_open()` 仍然返回一个有效 fd。

### 12.3 panic 链

修复 FAIL 2 时在第一版代码增加了 `fileopen()` 返回值检查，但没有清理 `fdalloc()` 的副作用：

```c
// 第一版修复——不完整
if (fileopen(f) < 0) {
    fileclose(f);            // 释放文件结构体
    eunlock(ep);
    eput(ep);
    return -1;               // 但 p->ofile[fd] 仍指向已释放的 f
}
```

执行流程：

```
sys_open()
  → fdalloc(f)          // p->ofile[fd] = f
  → fileopen(f)         // 失败
  → fileclose(f)        // f->ref = 0, f->type = FD_NONE
  → return -1           // 用户程序得到 -1，不知道 fd 被占用

用户进程 exit()
  → for(fd=0; fd<NOFILE; fd++)
  → p->ofile[4] != NULL → fileclose(f) 再次调用
  → f->ref == 0 → panic("fileclose")
```

`exit()` 遍历所有 ofile 槽位并逐一调用 `fileclose()`，碰到已释放的结构体即 panic。

### 12.4 额外发现：`statsinit()` 从未被调用

`kernel/main.c` 的初始化序列中遗漏了 `statsinit()`，stats 设备压根没有注册。重启前后对比：

- **修复前**：因为 `fileopen()` 返回值被忽略，stats 未注册的 `device_get()` 返回 NULL 不影响打开结果，漏洞被掩盖；
- **第一版修复**：检查了返回值，stats RO open 也失败了（`FAIL: open stats read-only`）；
- **最终修复**：加入 `statsinit()` 调用后正常。

### 12.5 修复

涉及三个文件、两处逻辑修改和一处初始化补充：

**`kernel/syscall/sysfile.c`** — 调整顺序并检查返回值，同时清理 fd 槽位：

```c
f->ep = ep;
f->readable = readable;
f->writable = writable;          // 移到 fileopen 之前

if (ep->attribute & ATTR_DEVICE) {
    f->type = FD_DEVICE;
    f->major = ep->first_clus;
    f->minor = ep->file_size;
    if (fileopen(f) < 0) {
        myproc()->ofile[fd] = 0; // 清除 fdalloc 的副作用
        fileclose(f);
        eunlock(ep);
        eput(ep);
        return -1;
    }
}
```

**`kernel/main.c`** — 补充注册调用：

```c
#include "stats.h"

fileinit();
statsinit();   // ← 添加
```

### 12.6 验证

QEMU 输出：

```text
devsw interface test
====================
open /dev/console: fd=3
console actual baud: 115200
devsw test PASSED, failures=0
```

状态为**已完成代码验证**（QEMU 通过，K210 待实机复验）。

### 12.7 教训

1. **不要忽略返回值。** `fileopen()` 的返回值反映了设备是否接受本次打开，忽略它等同于伪造打开成功。
2. **资源分配顺序要有统一约定。** 设备打开时使用 `f->readable`/`f->writable`，但调用前尚未赋值——这种"先使用后定义"的时序错误应在代码审查中发现。
3. **`fdalloc` 有副作用。** 它在失败路径上留下了进程 ofile 表的引用，清理时必须显式 `p->ofile[fd] = 0`。
4. **掩盖不等于修复。** 忽略 `fileopen()` 返回值让 stats 设备缺失注册的问题从未暴露，直到返回值检查被加上才显现。

## 13. console device register panic：BSS 未清零的第二次体现

### 13.1 现象

在重构（I2C 控制器和板级配置分离到 `kernel/board/i2c_board.c`）后的
K210 实机启动时出现：

```text
0x1ab
[rustsbi] Kernel entry: 0x80020000
panic: console device register
backtrace:
0x00000000800239ac
0x000000008002071a
0x0000000080020072
```

panic 发生在 `consoleinit()` 中调用 `device_register(DEV_CONSOLE, ...)`
时。比第 4 节记录的 I2C panic（`i2c_init` 中 load fault）更早。

### 13.2 根因

**与第 4 节是同一个根因：K210 入口未清零 `.bss`。**

`devices[]` 是全局零初始化数组，位于 `.bss` 中：

```text
0000000080039040 B devices     # 符号属性 B = BSS
```

核验 ELF 段：

```text
.bss  0x80031000  0x0b1834   (NOBITS，ELF 不携带内容)
```

`device_register` 在 console 之前没有被任何代码调用过，所以
`devices[1].ops` 非零只能来自 DRAM 残留值。

两次暴露的对比：

| | 第 4 节 I2C panic | 本次 console panic |
|---|---|---|
| 脏变量 | `i2c_controllers[0].bus_num` | `devices[1].ops` |
| BSS 偏移 | 靠前位置 | 0x80039040（紧跟 boot_stack） |
| 暴露条件 | `i2cdev_init()` 访问控制器数组 | `consoleinit()` 注册设备 |
| 是否新问题 | 首次发现 | 同一根因二次暴露 |

本次暴露的直接原因是重构将 `i2c_ctrls[]` 和 `i2c_init()` 移入
`kernel/board/i2c_board.o`，改变了 BSS 链接布局，使 `devices[]` 落到
了此前未被脏数据覆盖的位置。

### 13.3 修复

第 4 节 4.4 的设计方案当时只停留在文档，入口代码中从未实际添加。本次
在所有入口点补充了 BSS 清零，hart 0 在使用任何 C 静态变量之前执行。

**`kernel/entry_k210.S` 和 `kernel/entry_qemu.S`**：

```asm
    la a0, _bss_start
    la a1, end
1:  sd zero, 0(a0)
    addi a0, a0, 8
    blt a0, a1, 1b
```

**`linker/k210.ld` 和 `linker/qemu.ld`**：

```ld
.bss : {
    . = ALIGN(16);
    PROVIDE(_bss_start = .);    /* 新增 */
    *(.bss.stack)
    . = ALIGN(16);
    *(.sbss .sbss.*)
    . = ALIGN(16);
    *(.bss .bss.*)
}
PROVIDE(end = .);               /* 已有 */
```

`_bss_start` 为零循环的起始地址，`end` 为 BSS 结束地址。

构建验证：

```bash
make clean && make build platform=k210
make build platform=qemu
riscv64-unknown-elf-objdump -d target/kernel --start-address=0x80020000
```

`_start` 反汇编确认清零 loop 正确：

```text
80020010: auipc a0,0x11      → a0 = _bss_start (0x80031000)
80020018: auipc a1,0xc3      → a1 = end       (0x800E2834)
80020020: sd    zero,0(a0)    → *a0 = 0
80020024: addi  a0,a0,8       → a0 += 8
80020026: blt   a0,a1,loop    → if a0 < a1, continue
8002002a: jal   main
```

### 13.4 验证状态

- 代码：**已完成代码验证**（双平台构建通过，清零指令在反汇编中确认）。
- QEMU：模拟 RAM 初始为零，不依赖此修改，但运行正常。
- 实机：**待实机复验**。需要烧录并冷启动确认：
  1. 不再 panic `console device register`；
  2. shell 正常启动，`ls` 可见目录项；
  3. 运行 `i2ctest` 确认 I2C 路径正常；
  4. 运行 `spitest` 确认 SPI 路径正常。

验证通过后更新第 2 节状态表和本节实机状态。

### 13.5 教训

1. **同一根因可以有多个不同表象。** 第一个被观测到的 panic 地址不一定是最早
   触发的——本次 console panic 的发生时序比第 4 节的 I2C panic 更早。
2. **设计方案必须落实到代码。** 第 4 节在论证层面已经完整地识别了 BSS 问题
   （链接脚本符号、hart 0 清零、多 hart 等待），但入口清零一直没有实际提交，
   直到第二次 panic 出现。
3. **裸机 BSS 不可信。** 上电 DRAM 内容、warm reset 保留值和 ELF loader 行为
   都可能导致 BSS 非零。hart 0 必须在首次使用静态变量前显式清零。
4. **hart 间同步仍是空白。** 当前清零只在 hart 0 入口路径上，没有等待机制。
   xv6-k210 目前只实际使用一个 hart，该问题尚未暴露。
