# oledfb 调试记录 —— Step1 验证通过总结

> 项目：xv6-k210 教学 OS 上移植 DinoGame，用 SSD1306 OLED（128x64，1bpp）显示。
> 关键路径：用户进程 mmap `/dev/oledfb` 帧缓冲 → 画图 → `ioctl(FLUSH)` → 内核 I2C 驱动把整帧 1024B 推到面板。
>
> 本文件记录 Step1 验证过程中遇到的所有问题、现象、排查思路和最终根因，按时间线组织，方便面试讲述。

---

## 0. 总体背景

- 帧缓冲：`/dev/oledfb`，`OLEDFB_FB_SIZE = 1024` 字节（128 列 × 8 页，SSD1306 页格式，每字节是一列的 8 个垂直像素）。
- 显示链路：`mmap 页面` → 用户直接写字节 → `ioctl(OLEDFB_IOCTL_FLUSH)` → `oledfb_flush()` 构造 I2C 消息 → `i2c_transfer()` → K210 I2C 控制器 → SSD1306。
- I2C：K210 硬件 I2C0，DMA 使能。消息长度 ≥ 16 字节走 DMA（`i2c_send_data_dma`），否则走轮询（`i2c_send_data`）。
- 一个 tick = OS 时钟中断间隔（K210 实机约 5ms，QEMU 下偏差大）。

**Step1 中遇到的五个真问题，按时间线：**

| # | 问题 | 类型 | 严重度 |
|---|------|------|--------|
| A | oledfbtest 比 i2ctest 慢约 7 倍（200ms vs 30ms） | 性能误归因 | 中 |
| B | I2C DMA staging 越界写（1025 字节 > 4096B 页） | 内存越界（静默） | 高 |
| C | DMA 等待超时窗口太短 → FLUSH 失败 + 总线卡死 | 超时（并发/时序） | 高 |
| D | `xv6 DINO` 显示乱码（F6x8 字体位序 + 板上旧镜像） | 显示错误 + 烧录环境 | 高 |

## 1. 问题 B：oledfbtest 为什么比 i2ctest 慢 7 倍

### 1.1 现象

加了测时打印后：

```
$ i2ctest      total=6 ticks (30ms)
$ oledfbtest   open=40 ticks (200ms), flush=0 ticks
```

用户问："所以为什么 oledfb 刷新慢，当前已经可以正常显示"。

### 1.2 错误的初步归因

`open=40 ticks` 让我一度以为 open 里有 ~200ms 的耗时。结合"第一次 DMA 传输"这个印象，我**错误猜测**是 DMA 首次传输慢/预热。但两个事实马上打脸：

1. 所有 `i2c_transfer` 返回值都是 0（无 timeout、无 abort 日志）；
2. 没有任何证据指向 DMA。

> 反思：我拿"40 ticks 这个数" + "DMA" 这两个印象拼了一个故事，没先逐项审计 open 路径。这是典型的**用结论找证据**。

### 1.3 正确的缩小范围：逐项审计 open 里做了什么

`oledfb_open()` 只做三件事：

1. `kmalloc` + `kbuf_create` 分配内存 —— 审计：<1ms，不是瓶颈；
2. `oledfb_init_panel()` —— **里面有个 `oledfb_delay_ms(100)` 上电延时（我加的保守值）** ← 大头；
3. `oledfb_flush()` 清屏 —— 1024B DMA，总线 7ms 量级。

疑点立刻集中到那 100ms。但"上电延时"听起来像必需的，怎么证明它多余？

### 1.4 对照实验（关键一步）

**i2ctest 能正常显示，而它的 OLED 初始化只用 `sleep(1)` = 5ms。** 同一个面板，5ms 延时初始化后显示完全正常。

- 我们的板子**常供电**，面板早就上电，不需要重新上电延时；
- 5ms 够，100ms 纯属我加的冗余。

### 1.5 修复与验证

- 修复：`oledfb_delay_ms(100)` → `oledfb_delay_ms(5)`。
- 验证：`open` 从 40 ticks → **4 ticks（200ms → 20ms）**，显示依旧正常。
- 结论：95ms 的 delta 全是延时。**"首次 DMA 慢"是彻底误判**，真实问题是我的保守延时。

### 1.6 面试要点

- **对照实验 > 猜测**：同一个面板 5ms 能初始化好，就是 100ms 冗余的最强证据。
- **逐项审计 > 整体归因**：把 open 的每个步骤单独量化，瓶颈自然浮出。
- 敢于推翻自己的结论：先入为主的"DMA 慢"被实测数据推翻，要坦然修正。
- 量化：40 ticks → 4 ticks 的下降，证明修复对了。

## 2. 问题 C：I2C DMA staging 越界写（静默 bug）

### 2.1 现象

**没有可观测故障**——显示一直正常。但代码审查发现一个真实的越界写，一旦触发可能踩坏任意内存。

### 2.2 排查路径：为什么 oledfb 会走 DMA、i2ctest 不会

`i2c_transfer` 的路径选择：

```c
if (i2c_data->dma_enable && msgs[i].len >= DMA_THRESHOLD)   // THRESHOLD = 16
  ret = i2c_send_data_dma(...);   // DMA 路径
else
  ret = i2c_send_data(...);       // 轮询路径
```

- **i2ctest**：所有消息都是 2 字节（写寄存器/探测），`len < 16` → **全走轮询**，不碰 DMA；
- **oledfb FLUSH**：一条 `{0x40, fb[0..1023]}` 消息，`len = 1025` → 走 DMA。

这就是"为什么 i2ctest 没这个问题"的答案：**它根本没进 DMA 路径**。

### 2.3 根因：staging 页大小与消息长度的关系

看 `i2c_send_data_dma` 的核心逻辑：

```c
uint32_t *buf = kalloc_page();            // 4096 字节 = 1024 个 32 位字
buf[0] = send_buf[0];                     // 首字节（必要时加 RESTART 位）
for (i = 1; i < send_buf_len; i++)        // send_buf_len = 1025
  buf[i] = send_buf[i];                   // buf[1024] 越界！写到 staging 页后面 4 字节
```

- DMA 源要求**连续的 4096B 页**，每字节要展开成 32 位 `DATA_CMD` 字（带 RESTART/STOP 位），所以必须 staging；
- `kalloc_page()` 给 4096B = 1024 字，消息却有 **1025 字节 → 越界写 4 字节**。

### 2.4 为什么"没崩" ≠ "没 bug"

越界的 4 字节落在 staging 页后面的物理内存（可能是相邻空闲页或仍映射的页）。K210 没有 MMU 保护越界（直接物理地址访问），写坏恰好没踩到关键数据 → 静默通过。**内核内存越界常常不立即崩溃，但随时可能炸。**

### 2.5 修复（双层防御）

**第一层（改调用方 oledfb.c）**：不再构造 1025 字节消息，拆成 3 条消息，单条 DMA 正好 1024 字节：

```
msg[0]  cursor 命令    7B    {0x00,0x21,0x00,0x7F,0x22,0x00,0x07}   设置列/页地址
msg[1]  DMA            1024  {0x40, fb[0..1022]}                   前缀 + 前 1023 数据
msg[2]  polling tail   2B    {0x40, fb[1023]}                      末字节（自带前缀）
```

- `msg[1]` 首字节 0x40 是 SSD1306 的"数据控制字节"，后面 1023 字节数据，正好装满 staging 页；
- fb 只剩最后 1 字节放不进 1024，拆到 `msg[2]` 单独送（轮询，无 staging 上限）。

**第二层（改驱动 i2c.c）**：加守卫，防止任何新用户重蹈覆辙：

```c
#define I2C_DMA_MAX_LEN 1024
// 超过 staging 容量的消息回退轮询，绝不越界
if (i2c_data->dma_enable && msgs[i].len >= DMA_THRESHOLD &&
    msgs[i].len <= I2C_DMA_MAX_LEN)
```

### 2.6 面试要点

- 为什么必须 staging：DMA 需要预先排好的 32 位 `DATA_CMD` 字（字节 + 命令位），DMA 不做格式转换。
- **`DMA_THRESHOLD` 决定路径、`I2C_DMA_MAX_LEN` 决定上限**，两个常量一个管触发、一个管安全。
- 防御性编程：驱动不该信任调用方，超长消息要兜底（回退轮询）而非越界。
- "没崩"不等于"没 bug"——内核裸内存操作尤其要审查边界。

## 3. 问题 D：DMA 等待超时窗口太短 → FLUSH 失败 + 总线卡死

### 3.1 现象（用户实机贴出的输出）

```
$ oledfbtest
oledfbtest: fd=3 fb=0x0000003FFFFFC000
oledfbtest: mmap readback MISMATCH
oledfbtest: FLUSH failed (I2C?) - display may be blank   ← FLUSH ioctl 返回失败
$ i2ctest
I2C dev test
============
FAIL: probe OLED at 0x3C                                ← 紧接着 I2C probe 也失败
fixed-address binding: PASS
OLED display updated
I2C test FAILED, failures=1
```

屏幕全白。

关键事实：
- `FLUSH failed (I2C?)` 是**用户程序 oledfbtest.c 自己的失败提示**（`ioctl` 返回 < 0）。当时没有开内核 DEBUG 日志，**没有 `LOG_E` 可看**——根因只能靠代码分析 + 修复后行为反推。
- 决定性对照：**FLUSH 失败后紧接着 `i2ctest` probe OLED 也失败** → FLUSH 把总线停在半截事务上（没发 STOP），占住了总线，后续 I2C 全挂。
- `DMAC_WAIT_TIMEOUT` 10000→10000000 后：FLUSH OK + i2ctest PASSED（用户后续输出确认）→ 超时窗口太短是根因（由修复生效反证）。

### 3.2 根因：自旋窗口 0.4ms 装不下毫秒级的大帧传输

`dmac_wait_done` 是**自旋计数器**：

```c
#define DMAC_WAIT_TIMEOUT 10000UL   // 每次迭代 ~40ns → 总窗口仅 ~0.4ms
```

FLUSH 的 129B 数据消息走 DMA，但 I2C 总线很慢：

| 速率 | 129B 帧传输时间 |
|---|---|
| 400kHz | ≈2.9ms |
| 100kHz | ≈11.6ms |

DMA 传一半就超时 → 返回 -1 → FLUSH 失败；且 DMA 停在**半截事务上（没发 STOP）**，总线被占住 → 后续任何 I2C 操作（i2ctest probe）也失败。

### 3.3 为什么 i2ctest 和 SPI 没爆

- i2ctest 全是 ≤2B 消息（PIO 或极短 DMA），传输微秒级，远在窗口内；
- SPI 的 dmactest 用同样的 10000 没炸，因为 **SPI 比 I2C 快一个数量级**。

### 3.4 修复与验证

`DMAC_WAIT_TIMEOUT` → `10000000UL`（≈400ms 窗口，100kHz 下 35× 余量）：

```c
// dmac_wait_done spins on a counter, ~40ns per iteration.  I2C is slow: a
// 129-byte frame takes ~2.9ms at 400kHz (11.6ms at 100kHz), which the old
// 10000-count window (~0.4ms) could never cover - large DMA writes timed
// out mid-frame and left the bus wedged.  Must exceed a full frame even at
// 100kHz (10000000 * 40ns = 400ms).
```

修复后 FLUSH OK、i2ctest 恢复 PASSED。

### 3.5 面试要点

- **自旋超时窗口要以最坏情况传输时间为基准**，不是"一般情况"——I2C 大帧是毫秒级，微秒级窗口必然超时。
- 超时的次生灾害 > 超时本身：**总线停在半截事务（无 STOP）会卡住所有后续 I2C**，这就是 `i2ctest` 紧接着 FAIL 的原因。
- 同一段代码在不同设备（I2C vs SPI）表现完全不同，因为物理速率差一个数量级。
- 现象要写"用户实际贴的输出"，不能把代码里的 `LOG_E` 当成必然打印——当时没开 DEBUG 日志，根因是靠修复生效反推的。

## 4. 问题 E：`xv6 DINO` 显示乱码（一维数组声明导致 stride 错误）—— 含两次误判复盘

> 这个问题我一开始也归错了因，真实根因是 C 数组声明维度，不是 bit 方向、也不是旧镜像。记录完整的曲折排查过程，反而更有面试价值。

### 4.1 现象

mmap 写读全部正常（readback OK），但屏幕上 **`OLED`（F8x16 字体）正常、`xv6 DINO`（F6x8 字体）乱码**。

### 4.2 排查过程（含两次误判）

**第 1 步：排除写入/内存路径 ✓**
用户侧 readback OK + 内核侧 FLUSH 时 dump 物理页，两边数值一致 → mmap 写读没问题。

**第 2 步：排除 I2C 传输路径 ✓（ORDER SWAPPED 诊断）**
两行 swap：`xv6 DINO`(6x8) 第一行、`OLED`(8x16) 第二行。判读：

```
burst 尾部被破坏 → 第二行乱（无论内容）
F6x8 渲染本身错 → 第一行乱
```

实测第二行（OLED）正常 → **排除传输**，锁定字体渲染。

**第 3 步：误判 #1 —— 怀疑 bit 方向，加 `reverse8`（错）**
对比两个字体认为 F6x8 的 bit 方向与 SSD1306 页字节相反，`draw_char6` 加了 `reverse8`。验证时被上下对称的 `'x'` 判读误导，一度以为方向对了。**用 `'v'`/`'6'`/`'N'` 这类不对称字形重新判别后发现：`reverse8` 把 `v` 变成 Λ、`6` 倒置——F6x8 本来就是 bit0=顶部，reverse8 是错的，立即移除。**

**第 4 步：误判 #2 —— 怀疑 SD 卡旧镜像（错）**
移除 reverse8 后仍乱，且用户读回 `fb[43]=0x60` 在当前字库 "xv6 DINO" 用到的字符列里不存在 → 一度判定"板上跑的是 SD 卡旧 FS"（`make run` 只 kflash 内核、不更新 SD 卡 FS 是真实存在的坑）。**但用户重烧 FS 后：F8x16（line2 'O'）正常 → 板上确实在跑新程序；而 F6x8 仍读出错字节，且是固定的错字形** → 排除旧镜像。

**第 5 步：破案 —— 错字节落在字库"偏移 = 字符码-0x20"处**
用户读到的 `v`=`60 60 0 0 0 20`、`x`=`0 0 0 20 10 8` 在字库真实存在，但位于**偏移 86 / 88**。而 `'v'`=0x76→`0x76-0x20`=86、`'x'`=0x78→`0x78-0x20`=88。**运行的程序按"单字节"索引读字形，而不是每字形 6 字节。**

**根因**：[dino_data.h:33](user/app/dino_data.h#L33)

```c
extern const unsigned char OLED_F6x8[];   // 声明成一维！
```

实际定义是 `const unsigned char OLED_F6x8[][6]`（每字形 6 字节）。extern 声明成一维后，C 编译器 `OLED_F6x8[c-' ']` **不乘每字形步长 6**，`(c-' ')*1` 直接按字节偏移 → 读到相邻字形交叠的垃圾。F8x16 之所以正常，是因为 oledfbtest.c 里声明带 `[16]`（`extern ... OLED_F8x16[][16]`），stride 正确。

**修复**：声明改成 `[][6]`。用反汇编确认编译器现在生成 `(c-0x20)*6` 的步进（`slli ×2` + `add ×3` + `slli ×6`）后才算数——不靠猜，看机器码。

### 4.3 面试要点

- **C 数组 extern 声明的维度必须与定义一致**：声明少了 `[6]` 会导致索引 stride 错误，`OLED_F6x8[c-' ']` 从"第 c 个字形"变成"第 (c-' ') 个字节"。这类 bug 不报错、只出乱码，最难查。
- **对称字形会误导判读**：`x`、`I`、`O` 上下对称，翻转后看不出区别；要选 `v`/`6`/`N` 这类不对称特征做判别。
- **"板上行为与构建产物矛盾"先自查代码，再怀疑烧录**：那次误判旧镜像，是因为我先入为主；用"同一程序里 F8x16 正常"这个对照，就能证明板上在跑新程序。
- **用反汇编确认编译器行为**：怀疑索引步长时，直接看机器码 `×6` 有没有出现，比读 C 代码可靠。
- 两条被推翻的结论（bit 方向、旧镜像）**不是白费**——它们各自被一个对照实验排除，这正是调试该有的"留痕"。

## 8. 可迁移的调试方法论

1. **先分清崩溃是谁抛的**：bootloader panic ≠ 内核 bug，先定位 fault 的归属层。
2. **量化，别猜**：给每个子步骤加计时/计数，让瓶颈自己浮出来。
3. **对照实验是最强证据**：i2ctest 用 5ms 能显示 → 100ms 是冗余。
4. **敢于推翻自己的结论**：误归因到 DMA 后，用数据修正为延时。
5. **审查越界要算"字节 → 字"的容量**：DMA staging 页 / 32 位 = 1024 字，是硬上限。
6. **防御性边界检查**：驱动不信任调用方，超限兜底而非越界。
7. **协议约束要画时序图**：repeated START 段的控制字节解析点，画一遍就懂为什么不能省前缀。
8. **超时窗口以最坏情况传输为基准**：I2C 大帧毫秒级，自旋窗口微秒级必超时；超时无 STOP 会卡死整条总线。
9. **"板上行为与构建产物矛盾"先自查代码，再怀疑烧录环境**：那次归咎"旧镜像"是误判——用"同程序里 F8x16 正常"做对照，就证明了板上在跑新程序，真凶是数组 stride。烧录介质问题（内核 flash / FS SD 卡双介质不同步）确实存在，但要用对照实验确认，别先入为主。
10. **分层排除，每层一个证据**：写读 → 传输 → 渲染 → 构建 → 烧录，别跨层猜；宿主侧渲染/模拟能把"代码对错"和"板上是否当前代码"解耦。
