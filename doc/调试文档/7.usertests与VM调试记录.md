# usertests 与 VM 调试记录

## 1. 文档目的

本文记录补充和适配 `usertests` 过程中遇到的主要问题，包括故障现象、排查方法、根因和最终修复。重点覆盖：

- `sys_exec()` 无效参数触发的页面泄漏和内核 panic；
- 进程私有内核页表、内核栈分配失败时的回收问题；
- `sbrkbasic`、`sbrkfail` 暴露出的 OOM、COW 和 `wait()` 回收死结；
- `sbrkmuch` 与当前 QEMU 内存规模不匹配的问题；
- FAT32 语义、目录项模型和用户栈布局与原版 xv6 不同所需的测试适配。

本文描述的是当前实现。调试过程中使用过的 `ukvmmap_try`、`upg2ukpg_try` 等临时接口已经移除：可恢复路径直接调用 `mappages()`，`upg2ukpg()` 本身返回错误。

## 2. 调试环境与结果判定

当前 QEMU 配置只有 8 MiB 内存，内核同时启用了以下机制：

- 用户堆按缺页异常延迟分配；
- `fork()` 后用户页使用 COW；
- 每个进程维护独立的内核页表和内核栈；
- 用户栈位于固定高地址，并带有 guard page；
- 文件系统为 FAT32，而非原版 xv6 文件系统。

因此，测试输出中的 page fault 不一定代表失败。例如 `countfree()`、`sbrkbasic` 和 `sbrkfail` 会故意持续申请并触碰页面，直到内存耗尽；`kernmem` 和 `stacktest` 也会故意访问禁止区域。

判断测试是否真正失败时，需要结合完整执行链路：

- 预期的子进程 page fault 后，测试继续输出 `OK`，属于正常现象；
- 出现内核 panic、父进程异常退出、`FAILED` 或重复执行后可用页持续减少，才属于真实缺陷；
- 对异常地址使用 `addr2line` 定位到具体测试语句，区分“测试主动制造的异常”和“测试框架自身异常”。

## 3. `sys_exec()` 无效参数造成页面泄漏和 panic

### 3.1 现象

向 `exec()` 传入无效参数地址、无效字符串地址或过多参数时，测试可能出现以下结果：

- `sys_exec()` 提前返回，但此前为参数分配的页面没有释放；
- 多次重复失败后可用页面逐渐减少；
- 内存耗尽时触发 `panic: sys_exec kalloc`，整个内核停止运行。

### 3.2 排查过程

沿 `sys_exec()` 的参数复制流程检查每一个失败出口：

1. 内核为每个 `argv[i]` 分配一页临时缓冲区；
2. 随后调用 `fetchaddr()` 获取用户参数地址；
3. 再调用 `fetchstr()` 复制参数字符串；
4. 任一步失败时，原实现直接 `return -1`；
5. 已经分配的前序参数页不会经过统一清理。

同时，临时页分配失败被视为内核不可恢复错误，直接调用 `panic()`，这与系统调用对无效用户输入应返回失败的语义不符。

### 3.3 根因

`sys_exec()` 存在多个分散的失败返回点，没有统一的资源所有权和清理出口。用户输入错误与内存不足都可能发生在已经分配部分临时页之后，因此直接返回或 panic 都会破坏正常的失败回收路径。

### 3.4 解决方法

- 使用统一的 `out` 清理出口；
- `fetchaddr()`、`fetchstr()`、参数页分配和 `exec()` 失败都跳转到该出口；
- 清理所有已经分配的 `argv` 临时页面；
- 参数数量达到 `MAXARG` 且仍未结束时返回失败；
- 内存不足只让当前系统调用返回 `-1`，不再触发内核 panic。

修复后，无论无效参数出现在哪个位置，`sys_exec()` 都能完整释放临时资源。

## 4. `forkforkfork`、`reparent2` 触发 `panic: ukvmmap`

### 4.1 现象

大量、快速创建进程时，`forkforkfork` 和 `reparent2` 会触发：

```text
panic: ukvmmap
```

这不是用户进程普通的创建失败，而是整个内核被终止。

### 4.2 排查过程

最初只检查了用户页和 `struct proc`，但这两个测试并不会为每个子进程分配大量用户内存。继续跟踪 `allocproc()` 后发现，每个进程还会创建：

- 一套私有内核页表；
- 映射内核、MMIO 和 trampoline 所需的 Sv39 中间页表页；
- 一页内核栈。

高并发创建进程会先耗尽这些内核资源。原 `ukvmmap()` 将 `mappages()` 的分配失败直接转换成 panic，内核栈分配失败也缺少完整的失败回收。

### 4.3 根因

进程创建路径把可预期的内存不足当作内核不变量被破坏：

- 页表映射失败不能返回给 `allocproc()`；
- 部分建立的页表层级没有统一释放；
- 内核栈分配失败时，前面已经分配的 trapframe、用户页表和内核页表可能残留。

### 4.4 解决方法

- 可恢复的进程页表初始化路径直接调用原有 `mappages()` 并检查返回值；
- `ukvminit()` 在任意映射失败时释放已经建立的页表层级并返回失败；
- `ukvmfree()` 递归释放页表页，但不释放叶子项所映射的设备或内核物理资源；
- `allocproc()` 对 trapframe、用户页表、内核页表和内核栈建立完整的逆序回收路径；
- 只有那些调用者明确认为绝不允许失败的路径继续通过 `ukvmmap()` panic。

修复后，内存紧张只会使 `fork()` 返回失败，不会终止内核，`forkforkfork` 和 `reparent2` 均可通过。

## 5. `sbrkbasic`：预期 OOM 后父进程再次 page fault

### 5.1 现象

`sbrkbasic` 中用于耗尽内存的子进程先在约 `0x29b000` 处发生 page fault，这本来是测试的预期行为；随后父进程却又在较低堆地址附近发生 page fault，最终测试失败。

单看第一条 page fault 容易误判为 lazy allocation 或 `sbrk()` 的错误，但真正异常的是第二条父进程 fault。

### 5.2 排查过程

1. 使用 `addr2line` 将异常 PC 映射到 `usertests.c`；
2. 确认第一次 fault 位于子进程逐页触碰超大内存区域的循环中，属于预期 OOM；
3. 确认第二次 fault 发生在父进程继续执行测试时；
4. 对比 `wait(0)` 与 `wait(&xstatus)` 的行为：前者能回收子进程，后者在 OOM 后可能失败；
5. 跟踪 `wait()`，发现原实现先向父进程复制退出状态，再调用 `freeproc()` 回收僵尸子进程。

### 5.3 根因

父进程传给 `wait(&xstatus)` 的状态地址位于用户栈。`fork()` 后，该栈页可能仍与子进程 COW 共享。

OOM 时形成了资源依赖环：

```text
子进程耗尽内存并退出
        ↓
僵尸子进程仍持有用户页和页表页
        ↓
wait() 先 copyout(xstatus)
        ↓
父进程栈页需要执行 COW 分配
        ↓
没有空闲页，copyout() 失败
        ↓
wait() 返回 -1，未执行 freeproc()
        └──────── 僵尸资源继续占用 ────────┘
```

这解释了为什么 `wait(0)` 可以成功：它不需要写父进程的 COW 栈页，可以直接进入回收流程。

### 5.4 解决方法

从 `freeproc()` 中拆出可重复调用的 `freeprocvm()`，专门释放：

- trapframe；
- 用户页表及用户物理页；
- 私有内核页表；
- 内核栈。

`wait()` 找到僵尸子进程后，处理顺序调整为：

1. 保存子进程的 pid 和退出状态；
2. 先调用 `freeprocvm()` 释放大部分内存；
3. 再向父进程复制退出状态，此时已有空闲页可完成 COW；
4. 复制成功后释放剩余的进程槽元数据。

如果状态地址本身无效，`wait()` 仍返回 `-1`，但僵尸进程的 pid、退出状态、父子关系和状态元数据继续保留，后续可以再次等待；`freeprocvm()` 是幂等的，不会重复释放资源。

## 6. `sbrkfail`：极限内存测试无法完成回收

### 6.1 现象

`sbrkfail` 的最后阶段会创建子进程并持续触碰新页面。子进程发生预期 OOM 后，父进程此前会在固定高地址用户栈附近再次 fault，测试不能正常结束。

### 6.2 排查与根因

该问题与 `sbrkbasic` 是同一个回收死结：

- OOM 子进程已经退出，但其大部分 VM 仍由僵尸进程持有；
- 父进程执行 `wait(&xstatus)` 时需要拆分 COW 栈页；
- `copyout()` 无法获得物理页；
- `wait()` 失败又阻止了子进程资源释放。

另外，测试需要通过 `kill()` 结束特定进程。内核原本已有信号发送能力，但缺少完整的用户态 `kill` 系统调用入口。

### 6.3 解决方法

- 使用第 5 节的 `freeprocvm()` 和 `wait()` 回收顺序修复，打破 OOM/COW/僵尸资源依赖环；
- 增加 `kill` 系统调用，内部复用现有 `signal_send_pid(pid, SIGKILL)`；
- 同步补充系统调用号、分发表、内核实现和用户态声明/桩代码。

修复后，`sbrkbasic` 和 `sbrkfail` 都能在出现预期 OOM fault 后继续运行并输出 `OK`。

## 7. lazy allocation 同步内核页表时的失败回滚

### 7.1 风险现象

缺页异常为用户地址分配物理页后，还需要把该用户页同步到进程私有内核页表。如果用户页映射成功，而同步内核页表时才发生 OOM，原实现可能：

- 直接 panic；
- 留下只存在于用户页表、未同步到内核页表的映射；
- 泄漏刚分配的物理页。

### 7.2 根因

`upg2ukpg()` 原本没有向调用者报告页表页分配失败，调用链也没有定义“用户映射已经建立、内核映射失败”时由谁负责回滚。

### 7.3 解决方法

- `upg2ukpg()` 改为返回成功或失败，不再额外保留 `try` 后缀版本；
- `uvmlazymalloc()` 在同步失败时撤销刚建立的用户映射并释放新页面；
- 缺页处理路径将该失败视为当前进程无法继续，结束进程而不是 panic 内核；
- 其他逻辑上要求同步必定成功的调用点显式检查返回值，并保留原有的不变量检查语义；
- 进程内核页表的可恢复固定映射继续直接使用 `mappages()`，不引入 `ukvmmap_try` 包装层。

这样既保留了原有接口层次，也明确了 OOM 时的资源所有权。

## 8. `sbrkmuch` 与 8 MiB QEMU 内存规模不匹配

### 8.1 现象

原版测试申请并实际触碰约 100 MiB 用户内存。在当前 QEMU 只配置 8 MiB、且内核页表和文件系统缓存也需要占用内存的情况下，测试会在约数 MiB 处自然耗尽物理页。

该现象不是页面泄漏：即使回收正确，也不可能在 8 MiB 物理内存上同时驻留约 100 MiB 被写过的匿名页。

### 8.2 排查过程

- 检查 QEMU 启动参数和 `PHYSTOP`，确认可用物理内存上限；
- 确认 `sbrkmuch` 不只是扩大虚拟地址空间，而是逐页写入，所有页面都会实际分配；
- 对比失败位置和剩余页数量，确认符合容量耗尽，而非每轮测试后递增的泄漏；
- 将极限 OOM 测试与一般扩缩容测试分开：`sbrkbasic`、`sbrkfail` 继续负责失败回收，`sbrkmuch` 负责正常范围内的扩缩容正确性。

### 8.3 解决方法

将 `sbrkmuch` 的测试终点适配为 1 MiB，同时保留原测试的关键语义：

- 扩大堆；
- 逐页触碰多个页面；
- 检查末字节；
- 缩小并重新扩大；
- 检查重新分配页面已清零；
- 最后恢复原始 program break。

`sbrkbasic` 和 `sbrkfail` 中用于制造 OOM 的大尺寸申请不缩小，用于继续覆盖极限内存和失败回收路径。

## 9. FAT32 和地址空间差异导致的测试适配

### 9.1 FAT32 非法文件名

`createdelete` 通过字符递增生成文件名，过程中会出现 `"`、`*`、`/`、`:`、`<`、`>`、`?`、`\`、`|` 等 FAT32 不允许的字符。测试改为跳过这些字符。

同时修复清理阶段错误使用 `name[0] = 'p' + i` 的问题，使删除阶段使用与创建阶段一致的字符 `pi`。

### 9.2 硬链接和目录项模型不等价

当前 FAT32 实现不支持原版 xv6 的硬链接语义，`sys_link()` 返回失败。因此从一般目录测试 `subdir` 中移除了硬链接专属步骤，并继续跳过以下无法保持等价语义的用例：

| 测试 | 不等价原因 |
| --- | --- |
| `linkunlink`、`linktest` | 核心验证硬链接及 link count |
| `concreate` | 依赖原版 xv6 目录项布局，并生成 FAT32 非法文件名 |
| `fourteen` | 依赖 xv6 `DIRSIZ=14` 的文件名截断规则 |
| `bigdir` | 通过大量硬链接验证 xv6 inode 间接块目录 |
| `iref` | 验证 xv6 inode cache 引用模型，与 FAT32 dirent cache 生命周期不同 |

这些跳过项属于文件系统模型差异，不应伪装成已经通过的内核功能。

### 9.3 固定用户栈 guard page

原版 `stacktest` 根据旧式连续地址空间布局推导栈下方 guard page。当前用户栈位于固定高地址，因此测试改为直接访问 `USER_STACK_GUARD`，验证该页不能被用户态读写。

### 9.4 其他适配

- FAT32 路径上限恢复为 260 字节；
- 大文件测试恢复到本项目原适配规模 512 块；
- 镜像中不保证存在 `README`，相关测试改用镜像必有的 `echo` 文件；
- 添加并启用 `kill` 系统调用，满足进程控制测试依赖。

## 10. 双核 QEMU 无输出停滞：hart1 在启用分页前访问高虚拟 UART

### 10.1 问题现象

内存布局重构后，同一个 QEMU 镜像呈现出明显的单核/双核差异：

- 单核运行时，完整 `mmaptest` 和 `signaltest` 均能通过；
- 默认双核运行时，测试会在进程退出、权限故障或等待子进程附近偶发停滞；
- 停滞后没有新的测试输出、page fault 日志或 panic，QEMU 进程本身仍然存在；
- 从最后可见输出判断，很像 scheduler 没有再次选中进程，或者 `exit()`、`wait()`、僵尸进程回收发生死锁。

其中一个稳定触发点是 mmap 只读权限测试。子进程按测试设计写只读映射，内核应该打印非法 page fault，结束子进程，然后由父进程继续测试。但双核下这条故障日志和后续输出都可能完全消失。

这种“运行位置接近 fork/exit，又没有任何输出”的表象最容易把排查方向带到调度器、进程锁和回收路径。

### 10.2 排查过程

排查按以下顺序逐步缩小范围：

1. **对比单核与双核。** 同一内核、用户程序和文件系统镜像在单核完整通过，只有启用 hart1 后停滞，说明 mmap 基本语义和确定性的用户地址检查不是首要嫌疑。
2. **验证权限故障路径。** mmap 只读页的 PTE 权限、用户 page fault、`killed` 标记和退出状态均符合预期，故障子进程没有落入无限 fault 循环。
3. **验证 `kill`、`exit` 和 `wait`。** 在关键阶段增加标记，确认子进程能够进入预期故障/退出路径；没有证据表明进程表锁形成稳定的循环等待，因此没有扩大范围修改 scheduler 或回收算法。
4. **检查“为什么一条日志都没有”。** 如果只是某个用户进程停滞，其他 hart 的内核日志理论上仍应出现。所有输出同时消失，说明 console/`printf` 自身可能成为共享阻塞点。
5. **临时跟踪 `printf` 锁。** 无锁诊断标记显示全局 `pr.lock` 的持有者是 `hart1/pid0`。hart1 在启动阶段取得锁后没有释放，hart0 随后打印 page fault 时一直等待同一把锁。
6. **回查 hart1 启动顺序。** 设备地址上移后，UART 驱动只访问 `UARTHS_V`。但次级 hart 的启动分支当时按如下顺序执行：

   ```c
   printf("hart %d starting\n", hartid);
   kvminithart();
   trapinithart();
   ```

   也就是说，hart1 在安装内核页表和本 hart trap 向量之前就调用了依赖高虚拟 MMIO 地址的 `printf()`。

### 10.3 根因分析

设备地址重构后，UART 的 CPU 访问地址从物理地址改为：

```text
UARTHS_V = UARTHS + VIRT_OFFSET
```

hart0 负责创建全局内核页表，但 RISC-V 的 `satp` 是每个 hart 独立的控制状态。`started` 和内存屏障只能保证 hart1 看见 hart0 已完成的全局初始化，不能替 hart1 执行 `kvminithart()`，也不能自动让 hart1 使用该页表。

旧启动顺序形成了以下执行链：

```text
hart1 观察到 started == 1
        ↓
printf() 获取全局 pr.lock
        ↓
console/UART 驱动访问 UARTHS_V
        ↓
hart1 尚未执行 kvminithart()，高虚拟地址不可用
        ↓
输出无法完成，pr.lock 永远没有释放
        ↓
hart0 在用户权限故障、exit 或其他路径中调用 printf()
        ↓
hart0 永久等待 pr.lock，系统不再产生任何串口输出
```

因此，这个问题包含一个可见的锁等待，但首因不是 scheduler 或进程回收锁设计，也不是普通意义上两把锁互相等待的死锁。真正的首因是 **hart1 在地址空间尚未就绪时访问高虚拟 UART**；`printf` 全局锁把一个 hart 的启动故障放大成了所有 hart 的无输出停滞。

这也解释了几个关键现象：

- 单核能够完整通过，因为 hart0 在首次 UART 输出前已经执行 `kvminithart()`；
- 测试看起来停在权限故障或进程退出附近，是因为这些路径恰好需要打印日志或继续依赖持锁的内核输出；
- 后续增加的普通 `printf` 调试信息同样看不到，因为它们也必须先取得已经遗留的 `pr.lock`；
- hart1 没有输出完整的 `hart 1 starting`，不是 scheduler 没有运行它，而是它已经进入 `printf()` 并卡在 UART 访问中。

### 10.4 解决方法

将次级 hart 的初始化顺序调整为：

```c
while(started == 0)
  ;
__sync_synchronize();
kvminithart();
trapinithart();
printf("hart %d starting\n", hartid);
scheduler();
```

关键约束是：

- 每个 hart 都必须自行执行 `kvminithart()`；
- 在任何 `printf()`、console 操作或 `*_V` MMIO 访问之前，当前 hart 必须已经启用内核页表；
- 在进入 scheduler 前安装本 hart 的 trap 向量；
- 保留 `started` 发布和内存屏障，确保 hart1 使用的是 hart0 已完整建立的全局内核页表。

没有采用以下规避方案：

- 不关闭 `printf` 锁，否则会破坏多核串口输出的原子性；
- 不把 UART 驱动改回物理地址，否则会破坏设备高虚拟地址布局；
- 不删除启动日志，因为这只能隐藏错误，其他早期日志或 MMIO 访问仍会再次触发。

### 10.5 修复验证与调试经验

修复后验证结果如下：

- 默认双核 QEMU 稳定输出 `hart 1 starting` 并进入 shell；
- `mmaptest: all tests succeeded`；
- `signaltest: ALL PASSED`；
- 后续新增的 `memlayouttest: all tests succeeded`；
- QEMU 与 K210 构建均通过；
- 临时无锁诊断标记和测试裁剪已移除，没有为该问题修改 scheduler、`exit()` 或进程回收策略。

本问题留下的通用排查经验是：多核系统“完全没有输出”时，不能只沿最后一条业务路径检查。应先确认输出锁的持有者、每个 hart 的页表/异常向量状态，以及日志后端依赖的 MMIO 地址是否已经可访问。尤其在设备从恒等映射迁移到高虚拟地址后，初始化顺序本身就是内存布局不变量的一部分。

## 12. 后续排查同类问题的建议

遇到 OOM 或 page fault 时，可以按以下顺序缩小范围：

1. 先确认 fault 属于父进程还是测试主动创建的子进程；
2. 使用异常 PC 和 `addr2line` 定位具体语句；
3. 检查 fault 之后是否仍输出 `OK`，不要把预期异常当成失败；
4. 对比 `wait(0)` 和 `wait(&status)`，检查是否涉及 COW 写入；
5. 检查僵尸进程是否仍持有用户页、页表页、内核页表或内核栈；
6. 检查所有“分配一半后失败”的路径是否能逆序回滚；
7. 重复运行并比较空闲页数量，区分固定容量不足与持续泄漏；
8. 对文件系统测试先判断其验证的是通用 POSIX 行为，还是原版 xv6 的 inode、目录项和文件名细节。

本轮问题的共同点是：内存不足本身可以是正常、可预期的测试输入，真正的缺陷往往出现在失败后的资源所有权、回滚顺序和不同内存机制之间的依赖关系中。
