# 调试过程与技巧总结（面试用）

> 主题：把 xv6 教学操作系统移植到嘉楠 K210（双核 RISC-V），并实现「主机经 UART 把 FAT32 文件系统镜像刷写进 SD 卡」这一完整功能。本文沉淀整个调试历程的方法论、软件/硬件问题与量化结果，面试可直接讲。

---

## 1. 项目背景与系统链路

**一句话**：让 K210 板子上的 xv6 内核能够通过串口接收主机的 FAT32 镜像，并逐扇区写入 SD 卡，实现「一键刷写文件系统」。

**烧写链路**：

```
主机 tools/burn.py（Python + pyserial）
  → UART 帧协议（magic(4) + seq(4) + type(1) + plen(2) + payload + crc32(4)）
  → K210 UART
  → /burn 用户程序（shell 启动）
  → write(sdcard_fd, 512)
  → sdcarddev_write → sdcard_write_sector → SPI → SD 卡
```

**双 UART 分工**（后续演进）：
- **console = UARTHS**：115200 握手（shell 启动 /burn、INFO、BAUD 切换），8 字节 FIFO、无流控。
- **数据 = DW UART1**（通用异步收发器，APB 8250 风格）：DMA CH4 TX / CH5 RX，传输波特率最高 2M。运行时由 INFO 帧的 payload[8] 选择，彻底摆脱"编译时定死数据口"。

**帧协议**：stop-and-wait（发一帧等一 ACK/NAK），CRC32 校验，重试上限 5。

## 2. 调试方法论（可复用的十条）

这十条是贯穿全程、每次排查都在用的方法，面试时可以按"方法 → 具体例子"讲。

### 2.1 按协议阶段划分故障，先定位在哪一层

先把问题钉死到协议阶段，再动手改。烧写协议的阶段判断表（实际写在文档里当排查地图）：

| 最后观察到的信息 | 所在阶段 | 优先检查 |
| --- | --- | --- |
| `exec /bur failed`（字符丢失） | shell 命令 | 发送节奏、回显 |
| 完整执行 `/burn` 但无 `BURN` | burn 启动 | 程序启动、设备打开 |
| 收到 `BURN` 但 INFO 无 ACK | 协议协商 | 波特率、帧格式 |
| DATA 序号附近超时 | 数据传输 | CRC、帧号、日志混入 |
| 板端 panic | SD/SPI 写入 | 用 ELF 解析 sepc 和回溯 |

> 关键教训：`exec /bur failed` 时**绝不能**去改 DATA 帧/CRC/SD 驱动——传输协议还没开始。

### 2.2 现象用实测，推断要标注（最重要的一条纪律）

被用户纠正过两次：把"从代码/转录推断的现象"当事实写进文档，会被一眼拆穿，也会误导下一步。

**做法**：
- 现象段**原样粘贴**串口/逻辑分析仪实测输出，不改写。
- 结论若来自代码分析或推理，明确标注「推断」，并给出验证方式（修复后行为反证、反汇编确认）。
- 被推翻的中间结论也保留，标注「误判」。

**例子**：丢帧根因从「推断主机侧」升级为「实锤主机侧」，靠的是板端被动停顿诊断实测 `stall≈598 ticks≈3.0s`＝恰好主机超时，而不是推理。

### 2.3 被动诊断优先于主动干预

主动诊断（加 sleep、加超时中止）会**改变被观测系统的时序**，可能毁掉吞吐或掩盖问题。先用被动测量（只记录、不改行为）。

**例子**：加板端读超时诊断（主动中止）时，`sleep(1)` 把吞吐从 12 拖到 4 KiB/s，且超时阈值按错误 tick 假设算成了 50 秒、从未触发。而**被动式停顿诊断**（只记录相邻 read() 之间的最大间隔，不改任何时序）成功抓到了截断现场。

### 2.4 控制变量实验

只动一个变量，其余不变。

**例子**：
- 怀疑高速 UART → 全程 115200 复现，故障扇区从 27 变 2 → 排除波特率，指向内存破坏。
- 怀疑帧跨 DMA 512 边界 → `RXDMA_SIZE` 512→1024，错误反而变多 → 证伪边界假设，暴露真正的 RDA 竞争。

### 2.5 扩大错误上下文

默认的错误日志太短，关键信息已被截断。临时扩大缓冲。

**例子**：原 `recv_msg` 只保留最后 16 字节，只能看到 `main.rs:530:18`，关键的 `mcause/mepc/mtval` 丢失。扩到 512 字节后拿到完整 panic，才定位到 `LoadMisaligned`。

### 2.6 把数值拆成字节流解码

CRC mismatch 不一定说明 CRC 算法错，可能是帧里混入了文本。

**例子**：INFO ACK 的 `plen=12905=0x3269`，按收到顺序 `0x69 0x32` 是 ASCII `"i2"`；收到的 CRC `0x64612031` 小端是 `31 20 61 64` = `"1 ad"`。拼起来正是内核日志 `"i2cdev: ... -1 addr"` 的片段——**文本日志插进了二进制协议帧**。

### 2.7 异常地址 → 精确映射回源码

K210 用 RustSBI，板端 panic 时报 M 态 trap；但真正执行错误指令的是 xv6 内核。

**流程**：
```
mcause=LoadMisaligned, mepc=0x800279ca, mtval=0x2016d001
  → addr2line -e target/kernel 0x800279ca → kalloc_page, kernel/vm/kalloc.c:131
  → objdump -dS 交叉验证 → ld a5,0(s3)  // r->next
  → 结论：kmem freelist 头已被破坏成 0x2016d001
```

### 2.8 统计思维：零错误 vs 偶发是两种问题

- 稳定复现 → 确定性 bug（逻辑、时序、配置）。
- 偶发（几百帧错 1-2 个）→ 竞态或物理层，需要用**统计口径**量化：两轮各 5016 扇区零错误才算修复生效。

### 2.9 逻辑分析仪验证物理层

波特率问题的最终裁判是示波器/逻辑分析仪，不是软件能不能通。

**例子**：主机"标称 500000"早期量到 17~26µs 周期、解出乱码——是**采样率不足（≤1MS/s）对 4µs 方波欠采样混叠**。提到 2MS/s 立即正确解出 0x55。**测 500k UART 至少 2MS/s（4 采样/bit 起步，推荐 5MS/s+）。**

### 2.10 先最小隔离修复，再设计长期根治

确认嫌疑路径后，先上最小改动止血，验证后另开正确方案。

**例子**：SPI0 DMA 破坏页链表 → 先对 SPI0 禁 DMA 走轮询（一行，立刻稳定），再单独设计正确的 DMA 修复（分离 TX/RX bounce buffer、传播错误、guard/canary、压力测试）。

## 3. 软件问题及解决

### 3.1 调试输出阻塞 UART 接收路径 → ACK 超时

**现象**：`sec=2 timeout waiting for magic`，怀疑 ACK 丢失或 SD 写慢。
**定位**：ACK payload `reason=OK ticks=0` 证明 SD 写不慢；真正原因是板端在正常 ACK 前后刷 OLED（I2C 慢），不能及时回到 UART 接收。
**修复**：正常路径不刷 OLED；写 SD 后立即 ACK；ACK 后立即回到 `recv_msg()`。
**经验**：**时序敏感路径上，调试输出本身会成为 bug**。数据口模式下整个 DATA 阶段保持 printf-free（printf 只在 console 空闲的双口模式才开）。

### 3.2 重复 DATA 与 ACK 幂等

**现象**：主机没收到 ACK 重发同一扇区，板端已推进 sec → 重复写 SD。
**修复（板端）**：`seq < sec` 的 DATA 包只回 `ACK_DUP`，不写 SD。
**修复（主机）**：`seq != sec` 视为 stale response 重试。
**经验**：**分布式协议必须有幂等 + 序号校验**，否则网络重发会把"写一次"变"写两次"。

### 3.3 文本日志混入二进制协议帧（见 2.6）

**根因**：RAW 模式期间，内核/驱动的同步 printf 与协议帧共用同一 UART，文本插入帧中段，CRC 校验失败。
**修复**：RAW 二进制协议期间抑制非协议输出；二进制发送与 printf 共享发送锁。
**经验**：RAW 协议和设备控制台要**分层隔离**，这就是后来「UART 与 Console 分层重构」的动机。

### 3.4 超时表象下的内核内存破坏（kalloc freelist 被 SPI0 DMA 打穿）

**现象**：传输到 sector 27（或 2）后主机超时，串口只有 `main.rs:530:18`。
**定位链**（最完整的 root cause 案例，见 2.7）：
1. 扩大错误上下文 → `LoadMisaligned @ 0x800279ca, mtval=0x2016d001`
2. addr2line + objdump → `kalloc_page` 读 `freelist->next`，freelist 头被改写成非对齐垃圾地址
3. 反向追踪：每写一扇区高频 `kalloc_page → SPI DMA → kfree_page`
4. 证据：512 字节扇区 → TX/RX 各 2048 字节 bounce buffer → **恰好占满一页，无 guard/canary**；`dmac_wait_done` 返回值被忽略；channel 1 完成中断没被清理
**修复**：先隔离（SPI0 禁 DMA 走轮询），后根治（见 2.10）。
**经验**：**板端 panic 才是超时根因时，继续重试主机端毫无意义**；必须把板端串口输出留全。

### 3.5 直写 SD 绕过 FAT 缓存 → 连续第二次刷写崩溃

**现象**：第一次刷写成功，不重启马上第二次，`exec /burn` 后 `usertrap(): addr is illegal`。
**根因**：`/burn` 直接调 `sdcard_write_sector()` 覆盖 SD，绕过 FAT32 层和 buffer cache。第一次刷完后，内核内存里还是旧 FAT/目录项缓存，第二次 `exec` 读到"旧缓存 + 新磁盘"的混合内容，ELF 装载错误。
**修复**：`sdcarddev` 加 `SDCARD_IOCTL_INVALIDATE_CACHE`（`fat32_invalidate()` + `binvalidate()`），DONE 成功后调用；成功打印 `cache=0` 作为"新版内核已生效"的自检（`cache=-1` = 板子还是旧内核）。
**经验**：**绕过文件系统的直接块写，必须显式失效缓存**；`cache=N` 返回值是一种廉价的"内核版本自检"。

### 3.6 shell 命令字符丢失（`/bur`）

**现象**：`exec /bur failed`，shell 收到的命令缺最后一个字符 `n`。
**定位**：UARTHS + SBI console + shell 输入链路下，连续整段写入命令会丢字符。
**修复**：shell 命令阶段保守节流（Ctrl-U 清残留 → 等待 → 逐字节发送、间隔 3ms → 再单独发换行）；失败检测从"匹配预期命令"改成识别通用 `exec ... failed`。**只影响握手阶段，DATA 帧继续整块突发 + CRC32，不牺牲吞吐。**
**经验**：握手可以慢，数据传输必须快——**节流要按阶段隔离**。

### 3.7 tick 率假设错误：时间类 bug 的放大器

**现象**：板端读超时诊断从未触发，吞吐反而从 12 掉到 4 KiB/s。
**根因**：`param.h` 的 `INTERVAL=390000000/200` 假设 390MHz timebase → 5ms/tick，从未实机验证。实测烧写 `ticks=1631 ↔ elapsed=203.89s` → **1 tick≈125ms，是假设值的 25 倍**（等效 timebase≈15.6MHz）。
**后果**：`RX_ABORT_TICKS=400` 以为 2 秒，实际 50 秒，主机 3 秒超时前永不触发；`sleep(1)`=125ms/帧拖死吞吐。
**修复**：按实测 `INTERVAL=15600000/200`（实机复核 5.03ms/tick）；QEMU 分支另设（10MHz timebase → 195ms/tick，与实机差 39 倍，也是个坑）。
**经验**：**写任何"ticks 换秒"的代码前，先实测 timebase**，不要信注释里的时钟假设。tick 修正连带吞吐 12→36.7 KiB/s（调度/yield 粒度从 ≤125ms 降到 ≤5ms）。

### 3.8 MLFQ 调度把轮询模式的 burn 降级 → 超时

**现象**：改用轮询接收后烧写卡顿、间歇性超时。
**根因**：用户态忙等会被 MLFQ 当 CPU 密集任务，每 5ms tick 都 `yield()` 触发降级，burn 被压到最低优先级，得不到及时调度；定时器抢占若落在收包中途，8 字节 FIFO 立刻溢出。
**修复**：`struct proc` 加 `sched_pin`；`sched_on_yield()` 与定时器 yield 对 `sched_pin` 进程跳过。sleep 型阻塞（SD 写）不受影响，只有"定时器 yield"被压制。
**经验**：**实时性任务需要调度配合**，轮询 + 调度固定缺一不可。

### 3.9 帧截断静默等 3s → 主动 NAK 提速

**现象**：主机 TX 偶发截断帧（527 字节只发出 ~11 字节），板端在帧中途静默等满**主机 3s 超时**才收到重发。2M 一轮 17 次截断 × 3s = 51s 纯停顿，吞掉线速优势。
**修复**：`recv_msg` 对 magic 之后的帧体用 `read_bytes_timeout`（`CONSOLE_IOCTL_GET_RX_STATS` 轮询环深度，仅在 `buffered>0` 时调 read()，保证不阻塞）；环空超 `RX_STALL_NAK_TICKS=100`（0.5s@5ms）返回 `-3` → DATA 循环立即 NAK。前提已验证：burn.py 收 NAK 立即重发（不走 3s 超时）。
**关键设计**：**紧轮询不 sleep**——CTI 帧间隙 ~80µs 期间环空，若 `sleep(1)` 每帧 +5ms = 25.6s 吞吐损失；ioctl 轮询只在截断时多花 0.5s。
**结果**：2M 从 23.6 → **44.7 KiB/s**，timeouts 17→0。
**经验**：**把错误处理的主动权从"对端超时"移到"本端检测"**，可省掉一整个超时周期。

## 4. 硬件问题及解决（K210 特性坑）

K210 是国产 AI 芯片（双核 RISC-V + 硬件卷积），外设驱动有不少"databook 与实测不符"的坑，排查时都先被误判成软件 bug。

### 4.1 UARTHS 8 字节 FIFO 溢出（高速中断接收的天花板）

- UARTHS RX FIFO 只有 8 字节，无硬件流控；中断接收周期约 100µs（PLIC → RustSBI M→S 软转发 → S 态 uartintr）。
- **算术**：500k 每字节 20µs，8 字节满需 160µs > 100µs 中断周期，不溢；1.5M 每字节 6.67µs，满需 53µs < 100µs，**必溢**。
- **证据特征**：`raw_buf=7/32767`（ring 只有 7 字节）＝绝大多数字节在到达中断前就被硬件丢——这正是 FIFO 溢出，不是"处理慢但字节都到了"。
- **解决**：DATA 阶段放弃中断、改轮询接收（见 3.8 的调度配合）。
- **"慢速发送"是死路**：把每中断周期字节数压回 ≤8，等效速率比 500k 慢 9 倍。要提速只能缩短板端接收周期本身。

### 4.2 波特率补偿的根因：主机 USB-TTL 芯片量化

- 板端 UARTHS 准确：390MHz 整数分频，只在能整除的速率精确（500000=390M/780）。
- 主机 USB 转串口芯片（**12MHz 晶振**）高速档量化：标称 230400 → 实际 250,000（+8.5%）；460800 与 500000 都映射到实际 500,000。
- 两端同标称 230400 时实际差 8.5% → 乱码。**逻辑分析仪**实测确认根因。
- **干净解法**：选能同时整除 390M 与 12M 的**公共精确速率**（500000、1500000），免补偿；576000/768000/921600 无法对齐，实测乱码，选型避开。

### 4.3 DW UART LSR bit5 反相（教科书代码永久卡死）

- DW APB 8250 原生模式下 **LSR bit5 反相**：1=发送器忙（不可写），0=就绪。教科书 `while(!(LSR&(1<<5))); THR=c` 会永久卡死在第一个字节。
- 参考官方 SDK：`while(uart->LSR & (1u<<5)) continue;`（等 bit5 **清零**再写）。
- 空闲态实测 `LSR=0x40`（bit5=0, bit6=1）＝健康空闲。
- 另：STET(0xa0) 必须非零，否则 TX 空中断永不触发（大块写卡死）。

### 4.4 UART1 RX 浮空刷 0x00

- FPIOA 路由的 UART RX 是**纯浮空输入**（无上拉无下拉）。IO8 无人驱动时电平悬空，一旦飘低，接收器把低线**连续帧化成 0x00** → `read` 读回无限 `00`、ring 持续增长。
- **排查提示**：UART 读全零先查 FPIOA 上拉，再查接线。修复：`fpioa->io[UART_RX_IO].pu = 1`。

### 4.5 DW UART DMA 模式仍触发 RDA（非 16550 标准语义）

- K210 DW UART 在 DMA 模式（FCR[3]=1）**仍会触发 RDA**。若 RDA 与 DMA-done 都调收割，RDA 在 `dar` 传输中途 disable CH5，与 done 中断互相踩踏，偶发帧错乱。
- 排查：overrun=0 排除 FIFO 溢出；`RXDMA_SIZE` 512→1024 反而更差（527 字节帧填不满 1024 块，每帧退化为 ~66 次高频 RDA）。
- 修复：**DMA 模式 RDA 直接 break**，收割只走 done（512 满）+ CTI（帧尾 15 字节超时兜底）；`RXDMA_SIZE` 必须 < 帧长。修复后两轮 5016 扇区零错误。

### 4.6 DMAC cmpltd_blk_size 恒 0（字段语义与实测不符）

- `channel[n].status.cmpltd_blk_size` 数的是**完成的块**，不是已搬字节数；单块配置下未传满整块时恒读 0。
- 用 dar 寄存器取进度：`n_words = (dar - buf_base) / 4`（每搬 1 字 +4）。曾因此丢前 9 字节。

### 4.7 SPI0 DMA 全双工整页 bounce buffer 破坏页分配器

- 512 字节扇区 → TX/RX 各 2048 字节 bounce = 恰好 4096 = 一页，**无 guard**；`dmac_wait_done` 返回值被忽略；channel 1 中断未清。DMA 越界写打穿相邻空闲页的 freelist 指针（见 3.4）。

### 4.8 内核无 FPU

- K210 有硬件 FPU，但 xv6 不保存/恢复 FP 上下文，内核里任何 `double/float` 运算会生成 FPU 指令 → illegal-instruction trap。**内核代码只用整数算术**。

### 4.9 sysctl 总线不支持子字访问

- **字节读**一律回 0xFF；**字节写**（`sb`）静默失效；**整字读写**可靠。
- 官方 SDK 的 `sysctl_clock_set_threshold` 走 `sb`，在本板失效。任何 8/16 位阈值字段用整字 RMW（lw→掩码→sw）。

### 4.10 exec 漏刷 icache/TLB（RustSBI panic 复发）

- `exec` 更新页表后若漏 `sfence_vma`/`fence.i`，RustSBI 会因陈旧 icache 取指错页，报 invalid-instruction panic。TLS 加载也受此影响。**页表切换后必须刷 icache + TLB**。

### 4.11 用户程序必须显式 exit

- `main` 用 `return` 结束会 `ret` 到 `ra=0`，从地址 0 跑垃圾代码，退出期页错误。**必须 `exit()`**。

## 5. 性能优化之路（量化）

| 阶段 | 吞吐 | 驱动因素 |
| --- | --- | --- |
| 中断接收（PIO），未修 tick | ~4 KiB/s | 中断周期 100µs + 慢速发送迁就 FIFO |
| 改轮询接收 + 调度固定 | 12 KiB/s | 板端接收不再依赖 100µs 中断 |
| **修正 tick（125ms→5ms）** | **36.7 KiB/s（1.5M）** | 调度/yield 粒度从 ≤125ms 降到 ≤5ms |
| **主动 NAK（0.5s 提前）** | **44.7 KiB/s（2M）** | 每帧截断成本 3s→0.5s，17 次×3s 停顿消失 |

**关键对比（2M）**：
- 修复前：108.56s，23.6 KiB/s，timeouts=17，naks=17（每帧截断等满 3s）
- 修复后：57.52s，44.7 KiB/s，timeouts=0，naks=9，`gap=101 ticks≈0.5s`（提前 NAK）

**物理极限分析**：每扇区 ~11.2ms 中，线时仅 2.6ms、SD 写 1.7ms，**固定开销 ~7ms 主导**（ACK 往返 + 调度 + 主机 Python 延迟）。再升波特率收益有限——2M 已接近该架构（stop-and-wait + 逐扇区 ACK）的实用上限。真正的下一步是**改 stop-and-wait 为滑动窗口**，但那要动协议和主机/板端两侧的可靠性语义。

**可量化优化维度**：
1. 传输波特率：选公共精确速率（500k/1.5M/2M）
2. 接收路径：中断→轮询（省 100µs 周期）
3. 时间基准：tick 修正（省调度粒度代价）
4. 错误恢复：被动等待→主动 NAK（省超时周期）
5. 数据量：FAT32 裁剪（只发实际使用区域，省 95% 传输量）

## 6. 面试谈资：一条完整 root cause 链条示例

面试最有说服力的是"从表象一层层挖到根因"的过程。选最完整的讲：

**题目：为什么 2M 烧写慢、还偶发 CRC 错？**

1. **表象**：2M 烧写 108s，只有 23.6 KiB/s，偶发 NAK。
2. **假设 A（FIFO 溢出）**：加 LSR.OE 计数 → 实测 `overrun=0` → **排除**。
3. **假设 B（帧跨 DMA 边界）**：`RXDMA_SIZE` 512→1024 → 错误反而变多 → **证伪**，但暴露真正的 RDA/done 竞争 → 修复后两轮零错误。
4. **新证据（被动诊断）**：`stall=597/598 ticks≈3.0s`＝恰好主机超时，且 `atbyte=3` 表明 attempt1 只到 ~11 字节——**不是丢尾部，是帧几乎整体未送达**。板端 RX 全程健康（overrun=0、raw_drop=0、其余 5128 帧全对）→ **字节丢在主机 pyserial write() 之后、线上**。
5. **定性**：主机 USB-TTL 适配器在高速突发下间歇性只发帧头。
6. **对策**：既然丢的是主机侧、无法在板端修，就把**错误处理主动权拿到本端**——帧中途静默 0.5s 提前 NAK（原等 3s）。2M → 44.7 KiB/s。

这条链展示了：假设-实验-证伪的循环、用实测区分板端/主机端、统计口径验证、以及"硬件问题在软件侧缓解"的思路。

**另一个值得讲的小故事**：tick 修正。一个从未实机验证的时钟假设（390MHz→5ms）让所有时间诊断失真 25 倍，也悄悄压低了吞吐。**先在实机量 timebase，再写任何时间相关代码。**

## 7. 我犯过的错（体现成长，面试加分项）

| 错误 | 后果 | 修正 |
| --- | --- | --- |
| 把推断当事实写文档 | 误导排查方向，被用户当场纠正两次 | 现象贴实测，结论标「推断/误判」 |

## 8. 一句话总结

> 这次调试的核心收获：**把"现象"和"推断"分开，用控制变量和统计口径逼近根因；遇到时序相关 bug 先校时间基准；遇到高速 UART 先分清是中断路径还是物理层，再决定是软件优化还是硬件换方案。** 最终把 UART 刷写从 4 KiB/s 提到 44.7 KiB/s，并沉淀了一套可以在任何嵌入式系统上复用的排查方法论。
