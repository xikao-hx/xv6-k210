# 外设驱动架构与开发记录

# 当前总体架构

文件与设备操作抽象重构后，普通文件、管道和设备文件统一由 `struct file`
表示，但根据 `file.type` 进入不同的数据通路：

```text
用户程序
  -> open/read/write/ioctl/mmap/close
  -> syscall
  -> struct file
       ├── FD_ENTRY  -> FAT32
       ├── FD_PIPE   -> pipe
       └── FD_DEVICE -> struct file_operations
                          -> console/stats/spidev/i2cdev/sdcarddev/oledfb/uartdev
                             kbufdev/eagerdev
                          -> board controller
                          -> K210 底层驱动
                          -> 外设控制器与芯片
```

设备不再通过一个只接收 `major` 的全局 `devsw[]` 读写函数处理。每个 major
在启动时注册自己的 `struct file_operations`：

```c
struct file_operations {
  int (*open)(struct file *);
  int (*close)(struct file *);
  int (*read)(struct file *, uint64, int);
  int (*write)(struct file *, uint64, int);
  int (*mmap)(struct file *, struct vma_area *, uint64);
  int (*ioctl)(struct file *, uint64, uint64);
};
```

设备打开后，`struct file` 保存：

- `major/minor`：设备类型和逻辑设备编号；
- `ops`：该设备的操作表；
- `private_data`：本次打开实例的状态。

`dup()` 和 `fork()` 共享同一个 `struct file`，因此也共享 `private_data`。
只有最后一个引用关闭时才调用设备的 `close()` 并释放打开实例状态。

## 设备节点、major 和 minor

`/dev/*` 现在是 FAT32 中的真实目录项。init 启动时先 `mkdir("/dev")`，再逐个
`mknod(path, major, minor)` 创建设备节点（`ATTR_DEVICE` 属性）。设备节点
复用 `first_clus` 保存 major、`file_size` 保存 minor，不占用数据簇，
`ealloc()` 对 `ATTR_DEVICE` 跳过簇分配；已存在的节点会被重新写入
major/minor，因此 init 重复创建是幂等的。

`kernel/devsw/device.c` 不再做路径映射，只维护 major → 操作表的注册表：

```c
struct device devices[NDEV];

int device_register(int major, const char *name,
                    const struct file_operations *ops);
struct device *device_get(int major);
```

`sys_open()` 先通过 FAT32 `ename(path)` 解析目录路径，再按目录项属性分发：
普通文件/目录走 `FD_ENTRY`，`ATTR_DEVICE` 目录项进入设备通路：

```text
open("/dev/w25q64")
  -> sys_open()
  -> ename() 在 FAT32 中找到 /dev/w25q64 目录项
  -> ep->attribute & ATTR_DEVICE
       f->type  = FD_DEVICE
       f->major = ep->first_clus
       f->minor = ep->file_size
  -> fileopen(f)
       device_get(major) -> f->ops = dev->ops
       ops->open(f)      -> 分配 per-open 状态
  -> fdalloc()
```

stable major/minor 定义在 `kernel/include/dev.h`：

| 路径 | major | minor | 平台 | 设备实现 |
| --- | ---: | ---: | --- | --- |
| `/dev/console` | `DEV_CONSOLE` | 0 | QEMU/K210 | `console.c` |
| `/dev/stats` | `DEV_STATS` | 0 | QEMU/K210 | `stats.c` |
| `/dev/sdcard` | `DEV_SDCARD` | 0 | K210 | `sdcarddev.c` |
| `/dev/w25q64` | `DEV_SPI` | `SPI_DEV_W25Q64` | K210 | `spidev.c` |
| `/dev/oled` | `DEV_I2C` | `I2C_DEV_OLED` | K210 | `i2cdev.c` |
| `/dev/mpu6050` | `DEV_I2C` | `I2C_DEV_MPU6050` | K210 | `i2cdev.c` |
| `/dev/oledfb` | `DEV_OLEDFB` | 0 | K210 | `oledfb.c` |
| `/dev/ttyS0` | `DEV_UART1` | 0 | K210 | `uartdev.c` |
| 测试自行创建 | `DEV_KBUF` | 0 | QEMU/K210 | `kbufdev.c` |
| 测试自行创建 | `DEV_EAGER` | 0 | QEMU/K210 | `eagerdev.c` |

除 `DEV_KBUF`、`DEV_EAGER` 外，表中的固定路径由 init 启动时创建；两个 mmap
测试设备由 `testcase/mmaptest.c` 分别创建 `/dev/kbuftest` 和
`/dev/eagertest`。用户程序也可以用 `mknod()` 创建临时设备节点，`devtest`
即用该方式验证完整链路。旧的 `dev(omode, major, minor)` 系统调用
和 `device_path_lookup()` 静态路径映射已经删除，设备统一走 `/dev/*` 的
mknod + open 路径。`user/include/user.h` 中残留的 `int dev(int, int, int)`
声明是无实现的过期声明，不再对应任何系统调用。

## 注册和初始化顺序

hart 0 的主要初始化顺序为：

```text
consoleinit()
  -> uarthsinit()
  -> 注册 DEV_CONSOLE
...（kinit/kvminit/procinit/trapinit/plicinit/binit 等基础初始化）...
fileinit()
  -> statsinit()
       -> 注册 DEV_STATS
  -> kbufdev_init()
       -> 注册 DEV_KBUF
  -> eagerdev_init()
       -> 注册 DEV_EAGER
#ifndef QEMU
  -> fpioa_pin_init()   // 配置 SPI0、SPI1、I2C0、I2C1 引脚复用
  -> dmac_init()        // DMA 控制器
  -> spidev_init()
       -> 配置 W25Q64 片选 GPIO（GPIOHS）
       -> spi_init()
       -> 注册 DEV_SPI
  -> i2cdev_init()
       -> i2c_init()
       -> 注册 DEV_I2C
  -> sdcarddev_init()
       -> 注册 DEV_SDCARD
  -> oledfbdev_init()
       -> 注册 DEV_OLEDFB
  -> uartdev_init()     // 注册 /dev/ttyS0（DW UART1，DMA 数据通路）
#endif
  -> disk_init()        // QEMU virtio / K210 SD
  -> userinit()         // 第一个用户进程，之后 init 创建 /dev/* 节点
```

其中：

- `consoleinit()` 初始化 console 锁、UART 并注册 DEV_CONSOLE，是最早注册的
  设备；
- `fileinit()` 初始化全局 file table；
- `spi_init()`、`i2c_init()` 分别初始化当前 controller 锁，由各自的
  `*dev_init()` 在注册前调用；
- 各 `*dev_init()` 初始化底层框架并注册 major 到操作表；
- `disk_init()` 初始化内核文件系统使用的磁盘通路；
- `kbufdev_init()` 和 `eagerdev_init()` 在两个平台都会注册，供设备 mmap 测试
  使用；fpioa/dmac 和 SD/SPI/I2C/OLEDFB/UART1 注册位于 `#ifndef QEMU` 内，
  因此 QEMU 注册 console、stats、kbuf 和 eager；`uartdev_init()` 在
  `oledfbdev_init()` 之后调用，
  初始化 DW UART1 并注册 DEV_UART1，为 UART 烧写提供 DMA 数据通路；
- `/dev/*` 目录项由 init 以用户态 `mkdir/mknod` 创建，是 FAT32 磁盘上的真实
  目录项，不是内核侧逻辑路径；QEMU 同样创建 `/dev/console` 与 `/dev/stats`。

## 分层职责

| 层次 | 代表文件 | 职责 |
| --- | --- | --- |
| 系统调用/文件层 | `kernel/syscall/sysfile.c`、`kernel/fs/file.c` | fd、访问权限、引用计数、设备 `open/read/write/ioctl` 分发 |
| 设备映射层 | `kernel/vm/mmap.c`、`kernel/vm/kbuf.c` | 调用设备 `mmap` 回调、管理 VMA/映射对象和页支持缓冲区 |
| 设备注册表 | `kernel/devsw/device.c`、`kernel/include/dev.h` | major → `struct file_operations` 表；stable major/minor 常量 |
| 设备节点 | `user/init.c`、`sys_mknod()`、`kernel/fs/fat32.c` | FAT32 `ATTR_DEVICE` 目录项：`first_clus`=major、`file_size`=minor |
| 字符设备适配 | `kernel/devsw/*.c` | 用户参数校验、copyin/copyout、per-open 状态 |
| 板级绑定 | `kernel/board/spi_board.c`、`kernel/board/i2c_board.c` | controller 实例、片选、地址和频率上限；`spi_board.h`/`i2c_board.h` 只保留声明与查询接口 |
| 底层驱动 | `kernel/driver/*.c` | 寄存器、FIFO、DMA、轮询和硬件时序 |

重要边界：

- 用户指针只在设备适配层通过 `copyin/copyout` 访问；
- controller 和底层驱动只接收内核缓冲区；
- 逻辑设备只描述板级事实，不直接实现寄存器访问；
- 同一总线由 controller `sleeplock` 串行化；
- 设备不支持的 `read/write/mmap/ioctl` 不设置对应回调或明确返回 `-1`；当前
  `fileioctl()` 对缺失的 ioctl 回调返回 0，新增设备时应避免依赖这一兼容行为。

## 启动期约束

`spi_ctrls[]`、`i2c_ctrls[]` 等静态对象依赖 `.bss` 零初始化。
K210 使用裸二进制镜像，`.bss` 不包含在 `kernel.bin` 中，因此启动汇编必须
在进入 C 代码前清零 `__bss_start..__bss_end`，并在双核间同步完成状态。

这不是 I2C 的局部约束，而是整个 C 运行环境的前置条件。曾经出现的
`i2c_ctrls[0].bus_num` 脏值和 `i2c_init()` load fault，就是启动入口
未清零 `.bss` 的表现。

# I2C 驱动框架

## 当前调用链

```text
open("/dev/oled") 或 open("/dev/mpu6050")
  -> sys_open()
  -> ename() 找到对应 FAT32 设备节点目录项
  -> ep->attribute & ATTR_DEVICE
       f->type = FD_DEVICE，f->major = DEV_I2C
       f->minor = I2C_DEV_OLED / I2C_DEV_MPU6050
  -> fileopen(f)
       device_get(DEV_I2C) -> f->ops = i2cdev_ops
  -> i2cdev_open()
  -> 分配 per-open i2cdev_data
       dev = 固定地址的 i2c_device
       lock = 当前 file context 锁

ioctl(fd, I2C_IOCTL_TRANSFER, &rdwr)
  -> fileioctl()
  -> i2cdev_ioctl()
  -> copyin i2c_rdwr_ioctl_data、i2c_msg 和数据
  -> i2c_transfer(dev, msgs, nmsgs)
  -> 获取设备绑定的 I2C0/I2C1 controller sleeplock
  -> 配置 TAR；SCL、中断和 DMA 能力已在 i2c_init() 中初始化
  -> 依次执行全部 message
       首条 START
       后续 message 使用 Repeated START
       最后一条 message 的最后一个命令使用 STOP
  -> 释放 controller sleeplock
  -> copyout 读消息
```

当前静态设备绑定为：

| 逻辑设备 | minor | controller | 地址 | 地址宽度 | FPIOA 引脚 |
| --- | ---: | --- | ---: | ---: | --- |
| OLED | 0 | I2C0 | `0x3c` | 7 bit | 30(SCL) / 31(SDA) |
| MPU6050 | 1 | I2C1 | `0x68` | 7 bit | 32(SCL) / 33(SDA) |

两个设备**分属不同总线**（OLED 独占 I2C0、MPU6050 独占 I2C1），避免并发
访问同一条 I2C 时的时序干扰。设备地址由打开的逻辑设备固定，不允许每次
用户消息任意覆盖。`i2cdev_ioctl()` 会检查地址是否匹配绑定地址，所以
`/dev/oled` 不能用于访问 MPU6050。

设备对象和 `i2c_devices[]` 当前定义在独立板级 C 文件
`kernel/board/i2c_board.c` 中，`kernel/include/i2c_board.h` 只保留 controller
表声明和 `i2c_device_get()` 查询接口，不存在头文件内直接定义设备对象的
`i2c_config.h`。

当前 I2C 设备只实现 ioctl，不提供通用 `read()`/`write()`。组合事务使用最多
两个 `i2c_msg` 表示，例如“写寄存器地址 + repeated START + 读寄存器数据”。

## 用户态消息 ABI

用户态使用 `i2c_msg` 传输数据：

```c
struct i2c_msg {
  uint16 addr;    // 7-bit slave address，必须匹配打开的逻辑设备
  uint16 flags;
#define I2C_M_RD  0x0001
  uint16 len;
  uint8 *buf;     // user-space pointer
};
```

ioctl 参数：

```c
struct i2c_rdwr_ioctl_data {
  uint32 nmsgs;
  struct i2c_msg *msgs;
};
```

内核不能直接解引用 `msgs` 或 `buf`。设计要求的封送顺序为：

1. copyin 顶层 `i2c_rdwr_ioctl_data`；
2. 逐项 copyin `i2c_msg`；
3. 为每个消息分配内核缓冲区；
4. 写消息 copyin，读消息在事务完成后 copyout；
5. 无论成功或失败都释放已分配缓冲区。

当前入口在顶层 `copyin()` 失败、`nmsgs == 0` 或
`nmsgs > I2C_MAX_MSGS` 时立即返回。逐消息校验包括：地址必须匹配设备绑定、
flags 只能包含 `I2C_M_RD`、长度必须在 1～1024 字节之间。已分配的 bounce
buffer 通过统一 `done` 出口释放，读消息只在底层事务成功后 copyout。

## 底层传输策略

`i2c_transfer()` 逐项处理消息：

- 第一条消息正常 START；
- 后续消息设置 repeated START；
- 最后一条消息设置 STOP；
- 读消息先向 `data_cmd` 写入 `I2C_DATA_CMD_CMD` 产生接收时钟；
- 每次事务结束读取 clear 寄存器，清除 TX_ABRT/STOP_DET。

```c
(void)i2c_adapter->clr_tx_abrt;
(void)i2c_adapter->clr_stop_det;
```

底层使用 `DMA_THRESHOLD=16` 自动选择中断/DMA：I2C0 的 `dma_enable=true`，
长度至少 16 字节且不超过 1024 字节时走 DMA；短消息走 FIFO 中断路径。I2C1
当前 `dma_enable=false`，所有 MPU6050 事务都走中断路径。DMA 命令页每个字节
使用一个 32 位 `DATA_CMD`，所以设备层和底层都把上限限制为 1024 字节。

中断路径由 `TX_EMPTY` 填充发送 FIFO、`RX_FULL`/`STOP_DET` 排空接收 FIFO，
`TX_ABRT` 记录 `-EIO`。DMA 路径使用 `dmac_wait_idle_timeout()` 等待通道完成，
并继续等待 STOP/abort；超时、abort 和 FIFO 错误会向 `i2c_transfer()` 传播。
当前仍需注意 `i2c_dw_init()` 中 controller enable/disable 的两个轮询没有超时。

## 锁与事务边界

当前 I2C 的锁边界是框架中比较合理的部分：

```text
i2c_controller.lock
  -> i2c_controller.isr_lock
      -> 配置目标地址
      -> 执行全部组合消息
      -> STOP/abort/timeout 清理
```

controller sleeplock 覆盖完整 message 数组，`isr_lock` 协调进程等待者与 I2C/
DMAC ISR。当前 OLED 和 MPU6050 位于不同 controller，不会互相争用；同一总线
增加第二个设备时，仍由 controller 锁保证组合事务不被插入。`i2cdev_data` 中
保留了 per-open sleeplock 字段，但当前 `i2cdev_ioctl()` 未获取它，fd 级串行化
实际依赖 controller 锁。`i2c_init()` 使用静态二维字符数组保存锁名称，不存在
返回后悬空的锁名指针。

## 当前框架边界

当前 I2C 框架已经具备双 controller、组合事务、FIFO 中断、可选 DMA、超时与
错误传播：

- `i2c_controller`、`i2c_device`、`i2c_msg` 分别描述控制器、板级固定设备和
  单条消息；
- controller 锁覆盖完整 message 数组，后续消息产生 Repeated START，最后一
  条消息产生 STOP；
- 用户数据通过内核 bounce buffer 中转，底层和 DMA 不直接访问用户虚拟地址；
- I2C0（OLED）和 I2C1（MPU6050）均已实例化，I2C2 尚未配置；
- 入口已校验 device、bus、controller、7 位地址、minor、flags 和消息长度；
- 时钟由 `i2c_clk_init()` 显式使能并设置 threshold，两个 controller 当前均
  配置为 400 kHz。

仍需完善的边界是：`i2cdev_data.lock` 未实际使用、controller enable/disable
轮询缺少超时、公开结构仍带有 `address_width` 但底层只支持 7 位地址，以及
DMA 超时后的通道复位策略仍可进一步收口。

## 当前实机状态

- `.bss` 清零修复后，I2C controller 的 `bus_num` 不再是脏值；
- MPU6050 `WHO_AM_I` 已实机读到 `0x68`，证明 I2C1 和基本组合读事务可用；
- OLED 已通过 `/dev/oledfb` 的 mmap + flush 路径接入 I2C0；若出现 NACK 或空白
  屏，应检查模块地址、上拉、供电、FPIOA 30/31 和底层 abort 日志。

详细证据链见
[2.文件设备重构K210实机调试记录.md](5.文件设备重构调试记录.md)。

# SPI 驱动框架

## 当前实现思路

SPI 设备层通过 `/dev/w25q64` 暴露给用户态，数据事务只使用 ioctl
`SPI_IOC_MESSAGE(n)`；通用 `read()` 和 `write()` 当前明确返回 `-1`。

当前分层：

```text
open("/dev/w25q64")
  -> spidev_open()
  -> 分配 per-open spidev_data
       speed_hz = 1 MHz
       dev = 静态 W25Q64 spi_device
             bus = SPI1
             CS = CS0
             mode = mode 0
             bits_per_word = 8
             max_speed_hz = 10 MHz
       lock = 当前 file context 锁

SPI_IOC_MESSAGE(n)
  -> spidev_ioctl()
  -> copyin transfer 数组和 TX 数据
  -> 保留分段，TX/RX 数据放入每次打开预分配的两页 bounce buffer
  -> spi_transfer(dev, transfers, n)
  -> 获取 SPI1 controller sleeplock
  -> __spi_transfer()
       spi_dw_init()
       整条 message 开始时拉低 CS
       每段由 spi_can_dma() 选择中断或 DMA
       整条 message 结束后释放 CS
  -> 释放 controller sleeplock
  -> copyout 各段 RX 数据
```

板级 W25Q64 当前绑定为 SPI1、CS0、mode 0、8 bit，spidev 打开时的逻辑默认
速度为 1 MHz，设备声明的最大速度为 10 MHz。controller 锁保护 SPI1 的寄存器
和单次 `spi_transfer()`；per-open 锁保护当前 fd 的 ioctl 和 `speed_hz`。
锁顺序为：

```text
spidev_data.lock -> spi_controller.lock
```

用户缓冲区复制和临时页管理发生在设备适配层，底层控制器只接收内核地址。

需要区分“接口保存的配置”和“硬件实际配置”：

- `SPI_IOC_WR_MAX_SPEED_HZ` 当前只修改 `spidev_data.speed_hz`，
  `spidev_message()` 没有把该值传给底层，也没有在事务前调用
  `spi_set_clk_rate()`，因此速度 ioctl 目前不会改变实际 `BAUDR`；
- mode 不在 per-open context 中，而是直接修改共享的静态 `spi_device.mode`。
  fd A 修改 mode 会影响 fd B，且 per-open 锁不能保护另一个 fd 对共享字段的
  并发访问；
- `bits_per_word` 当前固定保存在静态 device 中，没有用户态配置接口。

目标设计应让静态 `spi_device` 只保存板级约束，让 per-open context 保存
speed、mode 和 bits_per_word；在 controller 锁内应用本次事务配置后再访问
FIFO。

DesignWare SSI 底层同时保留中断、polling 和 DMA。调度器启动后的普通设备事务
优先走中断路径；启动期 `myproc()==0`（主要是 SD 卡初始化）才走 polling；
满足 `spi_can_dma()` 的大块、对齐传输走 DMA。SPI1 的 `dma_enable=false`，所以
W25Q64 的 JEDEC ID 等用户事务实际走中断路径。

SPI 采用全双工传输模型：发送一个字节的同时也会接收一个字节。对于 W25Q64 这类 flash，读 JEDEC ID 的真实总线行为不是“只写命令再单独读”，而是：

```text

CS 拉低

发送 0x9f

继续发送 dummy 字节 0xff 0xff 0xff，用这些 dummy 产生时钟

同时从 MISO 收到 ff ef 40 17

CS 拉高

```

用户态可以使用 Linux spidev 风格的 `SPI_IOC_MESSAGE(n)`，把多段 message
传给内核，例如一段发送命令、一段接收数据。内核保留这些段并一次调用
`spi_transfer(..., n)`；底层在遍历全部段之前拉低 CS，遍历完成后才释放。

## ioctl message 长度解析

`spidev_ioctl()` 支持从 ioctl command 中解析传输数组长度，逻辑与 Linux spidev 类似：

```text

检查 _IOC_TYPE(cmd) == SPI_IOC_MAGIC

检查 _IOC_NR(cmd) == _IOC_NR(SPI_IOC_MESSAGE(0))

检查 _IOC_DIR(cmd) == _IOC_WRITE

通过 _IOC_SIZE(cmd) 得到 struct spi_ioc_transfer 数组总大小

n_ioc = _IOC_SIZE(cmd) / sizeof(struct spi_ioc_transfer)

```

这样用户态调用 `SPI_IOC_MESSAGE(2)` 时，内核可以知道本次 message 中有 2 段 transfer。旧的 `SPI_IOCTL_TRANSFER` 单段兼容入口已经移除，SPI 数据传输统一走 `SPI_IOC_MESSAGE(n)`。

## CS 保持策略

SPI flash 的很多命令要求 CS 在命令、地址、dummy、数据阶段之间保持拉低。如果每段 transfer 后都释放 CS，外设会把后续字节当作新事务，读出来常见是 `0xff 0x00 0x00` 或全 `0xff`。

当前策略是：

```text
用户态多段 spi_ioc_transfer
  -> spidev_message() 为每段构造一个内核 spi_transfer
  -> 每段数据指向 per-open TX/RX bounce buffer 的对应区间
  -> 调用底层 spi_transfer(..., num = n_xfers)
  -> __spi_transfer() 在循环外拉低/释放 CS
```

对于 rx-only 段，内核会填充 `0xff` 作为 dummy 发送数据，用于产生 SCLK。

当前每次打开预分配一页 TX bounce buffer 和一页 RX bounce buffer。所有段的
总 TX 时钟长度不能超过 `PGSIZE`，带 `rx_buf` 的段的总接收长度也不能超过
`PGSIZE`。rx-only 段在 TX 页对应区间发送 `0xff` dummy；copyout 只处理声明了
`rx_buf` 的段，因此命令段同时收到的无效字节不会被误当作 JEDEC ID。

## 已修复问题

* 8 bit frame 不能用 `uint32` 读写 FIFO
	* SPI 初始化为 8 bit data frame 时，每个 FIFO entry 对应 1 字节。旧代码在 polling 路径里按 `uint32` 写入和读取，会导致收到的数据错位，JEDEC ID 表现为 `ff 00 00` 或异常值。

	 * 当前根据 frame width 分别使用：

   ```text

   SPI_TRANS_CHAR  -> uint8

   SPI_TRANS_SHORT -> uint16

   SPI_TRANS_INT   -> uint32

   ```

* 长读不能先把 TX 全部塞完再读 RX
	* SPI 是全双工，发送时 RX FIFO 也会不断产生数据。K210 SSI FIFO 深度有限，长读时如果只写 TX、不及时读 RX，RX FIFO 会满，后续传输卡住。
	* 当前 polling 逻辑改成边读边写：

   ```text

   while rx_left:
     先尽量 drain RX FIFO
     再根据 TX FIFO 空位继续填 TX
     如果长时间没有任何进展，触发 timeout 返回错误
   ```

* 等待必须有超时
	* 中断路径使用 `SPI_INT_TIMEOUT_TICKS`，DMA 使用
	  `SPI_DMA_TIMEOUT_TICKS`，启动期 polling 使用 `SPI_POLL_WAIT_TIMEOUT`。
	  任一路径失败都会退出当前 message 并释放 CS。诊断日志集中在 timeout、
	  FIFO overflow 和事务边界，避免逐字节日志改变总线时序。

## 调试方法

### 1. 确认构建和测试程序

当前正式代码不保留临时 SPI 调试日志，避免串口输出影响正常测试。排查问题时先确认内核和文件系统都已经更新：

```bash
make build platform=k210
make fs platform=k210
make run platform=k210
```

注意：只执行 `make download` 只会更新 `target/fs.img`，不会更新内核驱动代码。修改内核驱动后必须重新构建并启动/烧录新的内核镜像。

最小验证命令是读 JEDEC ID：

```bash
spitest
w25q64
```

正常情况下，W25Q64 应返回类似：

```text
JEDEC: ef 40 17
```

判断要点：
* 用户态应调用 `SPI_IOC_MESSAGE(2)` 或 `SPI_IOC_MESSAGE(1)`，不要再使用旧的 `SPI_IOCTL_TRANSFER`。
* 读 ID 的总线发送内容应是 `9f ff ff ff`，命令后面的 dummy 字节用于产生时钟。
* 第一个接收字节通常是发送命令同时收到的无效字节，真正 ID 是后续 `ef 40 17`。
* 若需要进一步定位，可以临时在 `spidev_message()`、
  `spi_dw_int_transfer()`/`spi_dw_poll_transfer()` 和 timeout 分支加日志，调完
  后移除。

如果看到：

```text
JEDEC: ff 00 00
JEDEC: ff ff 81
JEDEC: ff ff ff
```

优先怀疑 CS、MISO/MOSI 接线、frame width、dummy clock 或多段 message 期间 CS 被释放。

### 2. 用逻辑分析仪确认总线

建议连接 4 个通道：

```text
CLK  -> SCLK
MOSI -> MOSI
MISO -> MISO
CS#  -> CS0
GND  -> GND
```

采样率建议至少是 SPI 时钟的 8 到 10 倍。当前 1 MHz SPI 时，逻辑分析仪设置 10 MHz 或更高更稳。

触发方式：

```text
CS# 下降沿触发
```

读 JEDEC ID 时，应该看到：

```text
CS# 先拉低并保持
CLK 出现连续 32 个周期
MOSI 第一个字节是 0x9f，后面是 0xff 0xff 0xff
MISO 第一个字节通常无效，后面是 0xef 0x40 0x17
CS# 最后拉高
```

如果逻辑分析仪上只有 MOSI 有一个脉冲、CLK 基本不动，说明没有产生完整时钟，检查底层 transfer 是否真的发送了总长度字节。

如果 CLK 正常、MOSI 正常，但 MISO 一直高，读到通常是 `0xff`，重点检查：
* MISO 是否接反或悬空。
* flash 是否供电正常，3V3/GND 是否可靠。
* CS 是否接到实际使用的 CS0。
* WP#/HOLD# 是否被拉到有效电平，部分模块需要上拉。

如果 CS 在命令段后短暂拉高，再进入读数据段，说明底层错误地在 segment
循环内切换了 CS，外设会重新解释后续 dummy 字节。

### 3. 调试顺序

推荐按下面顺序排查，不要一开始就改代码：

```text
确认用户态调用
  -> 必要时临时记录 message/n_ioc/tx bytes
确认底层配置
  -> 必要时记录 INT/POLL 路径、frame_width 和 baudr
确认 FIFO 收发
  -> 看 poll tx/poll rx 和 timeout
确认物理总线
  -> 用逻辑分析仪看 CLK/MOSI/MISO/CS
确认外设响应
  -> JEDEC ID 是否为 ef 40 17 或同类厂商 ID
```

调试时先用最小命令 `spitest` 或 `w25q64` 的 JEDEC ID，不要直接做 erase/program。只有 JEDEC ID 稳定正确后，再继续测试读、擦、写。

### 4. 常见现象解释

* `JEDEC: ff 00 00`：命令阶段可能有响应，但后续读数据错位或没有正确采样，常见于 frame width/FIFO 读写宽度错误。
* `JEDEC: ff ff ff`：MISO 一直为高，常见于外设未响应、MISO 悬空、CS 不对、flash 未供电。
* `w25q64` 无法退出或 shell 卡死：驱动可能在等待 FIFO/DMA 完成时没有超时，或长读时 RX FIFO 满后没有继续进展。
* 逻辑分析仪只看到很慢的边沿或单个脉冲：检查 SPI 时钟是否真正启动、采样率是否足够、触发条件是否正确。
* OLED 没显示、SPI flash 也不响应：优先检查 FPIOA 复用和引脚冲突，两个外设可能复用了同一 SPI bus 或 GPIO。

## 注意事项

* `SPI_IOC_WR_MAX_SPEED_HZ` 当前只保存 per-open 数值，尚未应用到硬件
  `BAUDR`。在该链路修复前，不能把 ioctl 返回成功当作实际频率已经改变。
* 底层已有 `spi_set_clk_rate()`，使用 CPU 时钟计算偶数分频值。正确接入方式
  是在 controller 锁内、传输开始前应用当前 context 的速度，同时受
  `spi_device.max_speed_hz` 限制。
* DMA 路径涉及对齐、transfer width 和一页临时缓冲区容量。
  `spi_can_dma()` 已限制双向 buffer、长度、frame 对齐和命令页容量，
  `dmac_wait_idle_timeout()` 的失败会向上传播；修改时仍需重点检查未对齐访问、
  DMA 通道恢复和错误后的 controller 状态。
* 在 RISC-V 上，未对齐的 16/32 bit 访问可能触发异常或行为不稳定。处理用户态字节流时应优先逐字节搬运，除非明确保证对齐。
* 多段 SPI message 中，只要外设协议要求一个完整事务，就必须保证 CS 在这些段之间不释放。

## controller、事务与 CS 边界

正常的 W25Q64 用户事务通过 `spi_transfer()` 获取 controller 锁，锁内完成
controller 配置和一组保持 CS 的全双工 segment。这条路径的 bus 互斥是成立的。

但 SPI0 的 SD 卡通过 `spi_write()`/`spi_read()` 直接调用无锁的
`__spi_transfer()`。SD 卡自身的锁只能防止两个 SD 请求互相交错，不能阻止
未来同一 SPI0 上的第二个设备插入 SD 命令、响应和数据之间。之所以保留无锁
路径，是因为 SD 卡初始化发生在 `userinit()` 之前，而当前 sleeplock 依赖
进程上下文。

启动期需求不能成为正常运行期永久绕过 controller 锁的理由。推荐的事务边界
为：

```text
校验 device、配置和 message
  -> 获取 controller 锁
  -> 应用 mode、速度和字宽
  -> 拉低硬件 CS 或统一描述的 GPIO CS
  -> 执行全部 segment
  -> 释放 CS，清理 controller/DMA
  -> 释放 controller 锁
```

启动阶段应提供命名明确、只允许单 hart 使用的专用入口，进入正常调度后所有
SPI0/SPI1 访问都应遵循同一 controller 事务锁。

SD 卡当前还同时使用 GPIOHS7 手工 CS 和 `spi_sd_dev.chip_select =
SPI_CHIP_SELECT_3`，导致协议层、controller 和 device 描述都参与片选。若板级
确实需要 GPIO CS，应把 GPIO 信息放入 device 描述，由统一片选操作执行；
SD 协议层只定义事务边界。

## 当前框架边界

当前 SPI 框架已经具备 controller/device/transfer、PIO/DMA 和 spidev 骨架，
但仍属于“固定设备组合下基本可用”：

- `spi_transfer()`、`__spi_transfer()` 和 `spidev_open()` 仍缺少完整的 device、
  bus、CS、mode、字宽、空指针和零长度校验，尤其 `spidev_open()` 未检查
  `spi_device_get()` 返回值；
- 枚举定义 SPI0～SPI3，当前只实例化 SPI0/SPI1，未注册项可能被直接解引用；
- `spi_init()` 已用静态二维字符数组保存锁名称；
- spidev 的 rx-only dummy TX 来自预填 `0xff` 的 per-open bounce buffer，
  但 SD 卡 `spi_read()`/`spi_write()` 的临时 `kmalloc()` 仍缺少判空；
- DMA 临时页已经判空且等待超时会传播，但错误后的通道/controller 恢复仍需
  持续验证；
- `__spi_transfer()` 在整个 segment 数组外控制 CS，多段内核 transfer 之间
  会保持 CS；
- spidev 单次消息总长度限制为一页，尚不支持 `cs_change`、段间延时和
  per-segment 配置。

因此扩展 SPI 设备前，应先统一 controller 事务与配置模型，再补齐参数检查、
内存/DMA 错误传播和板级设备注册；不要在 spidev、SD 协议层和 controller
三处分别增加特例。

## 当前 SPI1 引脚与实机状态

| K210 FPIOA | SPI 信号 | W25Q64 |
| --- | --- | --- |
| IO15 / `SPI1_D0` | MOSI | DI、IO0、D0 |
| IO16 / `SPI1_D1` | MISO | DO、IO1、D1 |
| IO17 / `SPI1_SCLK` | SCLK | CLK |
| IO18 / `GPIOHS8` | GPIO 片选 | `/CS` |

`SPI1_D0` 在当前标准 SPI 发送路径中就是接 W25Q64 的 D0/DI/MOSI，
`SPI1_D1` 接 D1/DO/MISO。Flash 使用 3.3V 并共地，`/WP` 和 `/HOLD` 应保持
高电平。

W25Q64 使用 GPIOHS8 手工片选，同时设置 SSI 的 `SER` 以产生时钟。当前底层
具备按输入时钟计算分频值的函数，但 per-open `speed_hz` 尚未接入事务配置，
因此实际频率仍以 `BAUDR` 和逻辑分析仪测量结果为准。若读到全 `0xff`，按
“GPIOHS8 CS、32 个 SCLK、MOSI 的 `0x9f`、MISO 响应、实测频率”顺序采集
四通道波形，并确认用户事务走的是全双工中断路径。


SPI 采用全双工是为了提供统一事务模型。receive-only 阶段仍要发送 dummy
字节产生时钟；`ctrlr1` 等接收数量寄存器必须按 frame 数而不是字节数配置。
DMA 中把字节指针直接强转为 `uint16 *` 或 `uint32 *` 前必须证明地址和长度
满足对齐要求，否则 RISC-V 上可能触发异常或产生不可移植行为。

完整静态分析、问题分级和推荐对象关系分别见：

- [SPI 驱动框架分析](../框架分析/spi-driver-framework-analysis.md)；
- [I2C 驱动框架分析](../框架分析/i2c-driver-framework-analysis.md)。

# 设备 mmap 与 OLED framebuffer

## 设备 mmap 调用链

`struct file_operations` 现在包含设备 `mmap` 回调。系统调用先创建
`VMA_KBUF` 类型的 VMA 和 `mmap_object`，再让设备校验映射并设置私有数据：

```text
mmap(..., MAP_SHARED, fd, offset)
  -> sys_mmap()
  -> vma_map_device()
       -> 检查 FD_DEVICE 和 file->ops->mmap
       -> vma_map_create(..., VMA_KBUF, file)
            mmap_object 持有 file 引用
       -> file->ops->mmap(file, vma, offset)
            vma->data = struct kbuf
            可选 vma_populate() 立即建立 PTE
  -> 缺页时 kbufdev_vma_fault()
       kbuf_page_get() -> 安装共享物理页
```

映射对象持有设备 `struct file`，因此用户即使在 mmap 后关闭 fd，设备的
`private_data` 也会存活到最后一个 VMA 释放。`fork()` 复制 VMA 时增加同一
映射对象的引用，`MAP_SHARED` 的父子进程看到同一组 backing pages。

## kbufdev 与 eagerdev

这两个设备只用于验证设备 mmap 框架，在 QEMU 和 K210 都注册，但 init 不创建
固定节点；`testcase/mmaptest.c` 自行创建：

| 设备 | 大小 | 映射方式 | 节点 |
| --- | ---: | --- | --- |
| `DEV_KBUF` | 2 页 | 按缺页请求安装 backing page | `/dev/kbuftest` |
| `DEV_EAGER` | 2 页 | `mmap` 时调用 `vma_populate()` 预装全部页 | `/dev/eagertest` |

两者每次 open 都通过 `kbuf_create(2 * PGSIZE)` 分配独立、清零的页集合，只接受
`MAP_SHARED`、非可执行、页对齐 offset，且映射范围不能超过设备大小。它们不
实现 read/write/ioctl；用途是覆盖 VMA 创建失败回滚、按需/预填充、fork 共享、
关闭 fd 后映射生命周期和 munmap。

## `/dev/oledfb`

`oledfb` 把 SSD1306 的 128×64、1 bpp page-format 显存暴露为 1024 字节共享
映射。每次 open：

1. 分配 `struct oledfb` 和一个 1024 字节 `kbuf`；
2. 通过 I2C0 初始化 SSD1306；
3. 把全零 framebuffer 刷到屏幕；
4. 把上下文存入 `file->private_data`。

用户态的标准路径为：

```c
int fd = open("/dev/oledfb", O_RDWR);
uint8 *fb = mmap(0, OLEDFB_FB_SIZE,
                 PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
/* 按 fb[page * 128 + column] 绘制 */
ioctl(fd, OLEDFB_IOCTL_FLUSH, 0);
```

映射只接受 `MAP_SHARED`、非 `PROT_EXEC`、页对齐 offset，范围不能超过 1024
字节，并在 mmap 时 eager populate。flush 先发送 7 字节光标设置消息，再发送
1024 字节 DMA 数据消息（控制字节 + 前 1023 字节显存），最后用 2 字节中断
消息补上末字节；三条 I2C message 位于同一个 controller 事务中。设备层只
负责显存映射和整屏刷新，字体、图元和游戏渲染位于 `user/libc/oled.c` 及用户
程序中。

`oledfb` 的 per-open sleeplock 只串行化 flush；用户进程若在另一个线程/进程
共享映射的同时写 framebuffer，驱动不会提供像素级快照一致性，需要应用自行
协调。当前 `oledfb_open()` 也没有把 SSD1306 初始化命令或首次清屏的 I2C
失败返回给 open 调用者；open 成功只表示内核上下文与 backing buffer 创建成功，
显示链路是否可用仍应以 `OLEDFB_IOCTL_FLUSH` 返回值和 I2C abort 日志判断。

对应验证入口为：QEMU 执行 `mmaptest`，覆盖 kbuf/eager 两种设备映射；K210
执行 `oledfbtest` 验证映射、越界和 flush，执行 `i2ctest`/`rendertest` 验证
显示与传感器组合路径。

# SD 卡设备框架

## 两条 SD 使用路径

K210 SD 卡同时服务于：

1. FAT32 文件系统内部的 block/buffer cache 路径；
2. 用户态 `/dev/sdcard` 的原始扇区路径。

两条路径最终都访问同一张卡，但语义不同：

```text
普通文件 open/read/write
  -> FAT32
  -> buffer cache
  -> disk/sdcard driver

open("/dev/sdcard")
  -> sdcarddev
  -> raw 512-byte sector read/write
  -> sdcard driver
```

原始扇区写会绕过 FAT32 和 buffer cache。因此 burn 写完镜像后必须执行
`SDCARD_IOCTL_INVALIDATE_CACHE`，使 FAT 和 buffer cache 丢弃旧内容。否则磁盘
已经更新，内核仍可能继续读取旧目录和旧数据。

## per-open 扇区位置

`sdcarddev_open()` 为每次打开分配：

```c
struct sdcard_file_context {
  struct sleeplock lock;
  uint32 sector;
};
```

初始 sector 为 0。每次成功读写一个完整的 512 字节扇区后自动加一。
`dup()`/`fork()` 共享同一 `struct file`，因此也共享 sector 位置和锁；不同
`open()` 得到独立位置。

当前只接受 `n == 512` 的 read/write，防止设备层隐式处理半扇区读改写。用户
缓冲区先复制到内核页，原始 SD 驱动不直接访问用户地址。

## SD ioctl

| 命令 | 参数 | 说明 |
| --- | --- | --- |
| `SDCARD_IOCTL_SEEK` | 扇区号值 | 设置当前扇区 |
| `SDCARD_IOCTL_TELL` | `uint32 *` | 返回当前扇区 |
| `SDCARD_IOCTL_NSECTORS` | `uint32 *` | 返回卡片总扇区数 |
| `SDCARD_IOCTL_INVALIDATE_CACHE` | 无 | 原始写后失效 FAT/buffer cache |

原始写测试可能破坏文件系统。调试时先确认目标扇区和数据备份，优先使用只读
测试；不要把文件系统正在使用的元数据扇区当作临时测试区。

## SPI0/DMAC 风险

SD 卡底层使用 SPI0，并可能使用 DMAC。DMA 描述、传输宽度、缓冲区所有权或
等待时序错误会表现为文件系统损坏、allocator 异常，甚至在 UART burn 过程中
由 RustSBI 报内存访问异常。发生这类问题时，应：

1. 保存板端完整 panic；
2. 用对应 `target/kernel` 对 `sepc/mepc` 执行 `addr2line`；
3. 检查 `mtval/stval` 指向的实际坏地址；
4. 临时切到 SPI0 polling 做控制变量；
5. 通过固定测试扇区、读回 CRC、guard 和 freelist 检查验证 DMA。

详细 UART 烧录与 SPI0/SD DMA 调试过程见
[4.UART烧录SD卡调试记录.md](../调试文档/4.UART烧录SD卡调试记录.md)。

# UART 驱动框架

当前有**两套 UART 驱动**，分别服务不同硬件和用途：

| 驱动 | 硬件 | 设备节点 | 用途 |
| --- | --- | --- | --- |
| `kernel/driver/uarths.c` | K210 UARTHS / QEMU 16550A | `/dev/console` | shell、TTY/RAW 终端语义 |
| `kernel/driver/uart.c` | K210 DW UART1（8250 风格） | `/dev/ttyS0` | 通用字节流，PIO/DMA 双模式数据通路 |

两套驱动接口对齐（`*_read/_write/_flush_rx/_set_baud/_get_baud_info/
_get_rx_stats`），并共用从 UART 驱动中剥离的通用环形缓冲
`kernel/driver/ringbuffer.c`（`ringbuffer.h`）。

当前 TTY 回显发生在 `console_read()` 的字符处理阶段，而不是 RX 中断阶段。
因此终端有输入但没有进程执行 read 时不会立即回显；这是当前非规范 Console
实现的行为边界。Ctrl-C 例外，它由 RX observer 在字节进入 ring 前识别并向
前台进程组发信号。

## 当前分层（console + uarths）

UART 与 Console 已拆分为字节流驱动层和终端语义层：

```text
用户程序（shell / burn / consoletest）
                │
                │ read / write / ioctl
                ▼
       /dev/console（console.c）
        ├── TTY：回显、控制字符、CR/LF、Ctrl-C/SIGINT
        └── RAW：原始二进制字节流
                │
                │ uarths_read / uarths_write
                ▼
          uarths.c（UARTHS 驱动）
        ├── 唯一 RX 软件 ring（RX observer 在入 ring 前处理字节）
        ├── TX 软件 ring
        ├── RX/TX 中断
        └── 波特率与硬件状态
                │
                ▼
       QEMU 16550A / K210 UARTHS
```

依赖方向固定为：

```text
console.c -> uarths.c
```

`uarths.c` 不包含 `console.h`，UART 中断也不会调用 Console 的字符处理函数。
用户态只保留 `/dev/console`。旧 UARTHS 专用的 `/dev/uart`、`DEV_UART` 和
UARTHS 的 `UART_IOCTL_*` 在 UARTHS/Console 分层重构时已删除；当前
`/dev/ttyS0` 是新增加的 DW UART1 字符设备（见下文），与旧 `DEV_UART` 不是
同一个东西，其 `UART_IOCTL_SET_MODE` 也是为 DW UART1 新增的，并非旧 UARTHS
ioctl 的残留。

## 寄存器访问

K210 UARTHS 和 DW UART 的寄存器都用“基地址 + 偏移”表示，分别在
`uarths-dw.h` 和 `uart-dw.h` 中定义偏移与位掩码。K210 路径通过
`readl()`/`writel()` 进行 32 位 MMIO 访问，中断使能等共享寄存器使用
读-改-写；QEMU 16550A 路径仍按硬件布局使用 8 位寄存器访问。

DMAC 通道的 `DAR` 和 `INTCLEAR` 是 64 位寄存器，UART DMA 路径使用
`readq()`/`writeq()`，不与 UART 本身的 32 位寄存器访问混用。

## UARTHS 驱动状态

UARTHS 驱动维护独立的 RX/TX 锁和环形缓冲，ring 本体使用从驱动剥离的通用
`struct ringbuffer`（head/tail 索引）：

```c
#define UARTHS_RX_BUF_SIZE 32768
#define UARTHS_TX_BUF_SIZE 4096

struct uarths_rx {
  struct spinlock lock;
  char buf[UARTHS_RX_BUF_SIZE + 1];
  struct ringbuffer ring;
  uint dropped;        // ring 满时丢弃的字节数
  uint epoch;          // flush_rx 时递增，唤醒阻塞读者
  uarths_rx_observer_t observer;
};

struct uarths_tx {
  struct spinlock lock;
  char buf[UARTHS_TX_BUF_SIZE + 1];
  struct ringbuffer ring;
};
```

环形缓冲保留一个空槽区分”空”和”满”，`ringbuffer_capacity()` 返回实际可用
容量（32768 / 4096），因此调用方不需要关心保留槽。RX 和 TX 各用一个独立
`struct spinlock`，RX 控制标志与 TX 状态互不干扰。

锁的职责如下：

| 锁 | 保护内容 |
|----|----------|
| `uarths_rx.lock` | RX 数据、ring、dropped、epoch 和 observer |
| `uarths_tx.lock` | TX 数据、ring 以及 TX 中断启停状态 |
| `cons.lock` | Console mode、ANSI 回显、CR/LF、EOF 和前台进程组状态 |

Console 不持有 `cons.lock` 调用可能睡眠的 `uarths_read()` 或
`uarths_write()`，避免 Console 与 UART 形成锁顺序环路。

## UARTHS RX 接收路径

`uarths_dw_isr()` 在 IRQ 中调用 `uarths_rx_service()`，循环读取硬件 FIFO，
每个字节先交给 RX observer 过滤，再写入唯一 RX ring：

```text
硬件 RX FIFO
  -> uarths_hw_getc()
  -> RX observer（可消费字节，Console 用于识别 Ctrl-C）
  -> RX ring
  -> wakeup_reason(&uarths_rx.ring, WAKEUP_DEVICE)
  -> uarths_read()
  -> console TTY/RAW 处理
```

RX ring 满时丢弃新字节并增加 `dropped`，不会覆盖尚未读取的数据。一次 IRQ
搬完当前 FIFO 后只唤醒一次读者，避免逐字节重复唤醒。

主要接口：

```c
int  uarths_read(char *dst, int n);
int  uarthsgetc(void);             // 非阻塞单字节轮询读（绕过 ring）
void uarths_flush_rx(void);
void uarths_get_rx_stats(uint32 *info);
void uarths_set_rx_observer(uarths_rx_observer_t);
```

`uarths_read()` 在 ring 为空时睡眠；出现数据后返回当前可用的最多 `n` 字节，
不要求等待填满。读取使用 `sleep_interruptible()`，被已加入
`sig_pending` 的信号打断时返回 `-1`。

`uarths_flush_rx()` 同时清空硬件 FIFO 和软件 RX ring、清零 dropped，并递增
`epoch`。阻塞读取者被唤醒后发现 epoch 改变，会返回到 Console 层重新判断
当前 TTY/RAW 模式。注意 `uarths.h` 中 `uarths_try_read()` 只是过期声明，
UARTHS 当前没有实现非阻塞 ring 读；非阻塞读走 `uarthsgetc()`。

## UARTHS TX 发送路径

用户态 Console 写入使用 4096 字节 TX ring：

```text
consolewrite()
  -> 分块 copyin
  -> uarths_write()
  -> TX ring
  -> uarths_tx_service()
  -> 硬件 TX FIFO
```

TX ring 满时，进程通过 `sleep(&uarths_tx.ring, &uarths_tx.lock)` 等待空间
（可睡眠上下文用 `sleep_interruptible()`，panicked 时返回 -1 停止写入）。
`uarths_tx_service()` 从 ring 向硬件 FIFO 搬运数据，并在索引前进后唤醒写者。

TX 中断按需管理：

```text
TX ring 非空 -> 开启 TX IRQ
TX IRQ       -> 继续填充硬件 FIFO
TX ring 为空 -> 关闭 TX IRQ
```

这样既能持续发送长输出，也不会在空闲时产生 TX 空中断风暴。

内核 `printf()`、panic 和不允许睡眠的上下文继续通过 `consputc()` ->
`uarthsputc_sync()` 使用同步轮询输出。不能让持有 printf spinlock 的路径进入
可能睡眠的 TX ring。

## RX 观察者与 Ctrl-C（SIGINT）

UARTHS 在每个 RX 字节进入 ring 之前先交给一个可选观察者。`uarths.h` 定义
两个动作码：

```c
#define UARTHS_RX_KEEP           0  // 保留，字节照常进入 ring
#define UARTHS_RX_CONSUME        1  // 消费，字节不进入 ring
```

`consoleinit()` 通过 `uarths_set_rx_observer()` 注册 `console_rx_observer`：
TTY 模式且存在前台进程组时，`Ctrl-C`（`0x03`）被识别为 SIGINT 事件——观察者
返回 `UARTHS_RX_CONSUME`，只消费控制字符，而不是把 `^C` 当普通输入交给
shell。随后 `console_dispatch_events()` 向当前前台进程组发送 `SIGINT`，
`signal_mark_locked()` 置 pending 并统一唤醒可中断睡眠。

该机制的要点：

- 观察者运行在 UART 中断上下文，只做识别和标志置位，不发送信号；实际
  发送推迟到 trap 返回路径，避免在中断里调用可睡眠的信号逻辑；
- UART 不维护 Ctrl-C 取消状态，不清空 ring，不绕过 handler/mask 强行让
  `read()` 返回；输入行是否清理由 Console/Shell 决定；
- `usertrap()` 是主派发点，idle `kerneltrap()` 在 `myproc()==0` 时兜底，
  保证全部前台进程睡眠时 Ctrl-C 仍能转成 pending 并唤醒它们；
- RAW 模式或没有前台进程组时观察者原样返回 `UARTHS_RX_KEEP`，行为与旧版
  相同。

## K210 TX watermark 注意事项

K210 UARTHS 的 TX watermark 条件是：硬件 TX FIFO 中的字节数小于 `txcnt` 时置位 `txwm`。

初始化必须使用：

```c
writel(UARTHS_V, UARTHS_REG_TXCTRL, UARTHS_TXEN | UARTHS_TXWM(1));
```

不能设置为 0。FIFO 字节数不可能小于 0，因此 `txcnt = 0` 时 TX IRQ 永远不会触发。其典型现象是：

```text
执行 ls 后只输出一部分
必须敲一次回车才继续输出一段
```

原因是回车产生了 RX IRQ，公共 `uarths_dw_isr()` 在处理 RX 后顺带调用
`uarths_tx_service()`，暂时掩盖了 TX IRQ 不工作的事实。设置 `txcnt = 1`
后，FIFO 清空会触发 TX IRQ，软件 TX ring 能自行持续发送。

## QEMU 16550A 中断位

QEMU 16550A 的 IER 位定义为：

```c
#define IER_RX_ENABLE (1 << 0)
#define IER_TX_ENABLE (1 << 1)
```

RX/TX 中断启停使用 IER 读改写，不能为了切换某一类中断而覆盖另一类中断的状态。bit 0/bit 1 如果写反，会表现为 shell 无法接收输入或 TX 中断行为异常。

## DW UART1 驱动（/dev/ttyS0）

`kernel/driver/uart.c` 驱动 K210 的 DW UART1（8250 风格），通过
`/dev/ttyS0` 暴露为 RAW 字节流设备。它的用途是给 UART 烧写提供独立的
DMA 数据通路：shell 握手留在 console（UARTHS），DATA 阶段切到 UART1 高速
收发，避免二进制帧与 shell 回显/ANSI 处理互相干扰。

### 接线与初始化

```text
IO7 = FUNC_UART1_TX（TX）
IO8 = FUNC_UART1_RX（RX）
```

`FUNC_UART1_RX` 是浮空输入（pu=0），RX 线悬空时会被连续帧化成 0x00 流，
因此初始化必须 `fpioa->io[IO8].pu = 1` 上拉。时钟使能/复位走
`sysctl_clock_enable(SYSCTL_CLOCK_UART1)` 和 `sysctl_reset`。

波特率用 20 位分频器（`DLH:DLL:DLF`，4 位小数分频），输入时钟是 APB0：
`actual = apb0_freq / (DLH<<12 | DLL<<4 | DLF)`。`uart_set_divisor()` 通过
置位 LCR 的 DLAB 位锁存分频寄存器，完成后必须清除 DLAB 并恢复行格式。

### PIO / DMA 双模式

UART 收发统一选择 PIO（中断驱动）或 DMA，由 `uart.h` 定义：

```c
#define UART_MODE_PIO 0
#define UART_MODE_DMA 1
#define UART_IOCTL_SET_MODE 0x21
```

默认由 `uart_init()` 切到 DMA 模式。RX DMA 使用 CH5，单块
`UART_RXDMA_SIZE` 为 512；DMAC 每个 32 位目的单元只保存一个 UART
字节，所以已搬运字节数由 `DAR` 与 `rx_dma_buf` 的地址差除以 4
得到。`rx_dma_active` 表示软件已挂载一次 RX DMA；硬件已 done 但
尚未收取时，该标志仍为 1。

RX 的三类事件共用同一组停止、收取和重挂逻辑：

| 事件 | PIO 模式 | DMA 模式 |
| --- | --- | --- |
| RDA | `uart_rx_fifo_drain()` 排空 FIFO | 不读 FIFO；仅在 CH5 done 时代替迟到的 DMA ISR 调用 `uart_rx_dma()` |
| CTI | `uart_rx_fifo_drain()` 排空 FIFO | 停 DMA，收取部分 DMA 块，CPU 排空 FIFO，再重挂 DMA |
| DMA done | 无 | `uart_dma_rx_isr()` 收取 DMA 块并重挂 CH5 |

CTI（Character Timeout Interrupt）表示 RX FIFO 内仍有数据，但已连续数个
字符时间没有收到新字节，用于收取不足一个 DMA 块的帧尾。DMA
模式必须先停 CH5，再由 CPU 读 FIFO，避免 DMA 与 CPU 同时消费数据。

DMA 模式下的 RDA 不在传输中途读 `DAR` 或排空 FIFO。当 DMA 块已完成
而 DMAC IRQ 尚未处理时，UART RDA 是由于 FIFO 继续入数而保持的电平
中断；RDA 处理器检查 `dmac_is_done()` 并直接完成收取与重挂，新 DMA
随后继续搬运 FIFO 数据。迟到的 DMAC ISR 会在 `rx.lock` 内重新检查
done 状态，不会重复收取。

上述 RX 路径都在 `rx.lock` 下串行执行，一次事件收取完成后最多唤醒
读者一次。`uart_flush_rx()` 会停止并清除在途 DMA，丢弃硬件 FIFO 和
软件 ring 中的数据，递增 `epoch` 以使阻塞读者返回，最后按当前模式
重挂 RX DMA。

这个恢复路径使正确性不再依赖 UART 与 DMAC IRQ 的相对优先级。两者均使用
`irq_register()` 的默认优先级；无需再将 CH5 IRQ 单独设为 2。旧实现会
无条件忽略 RDA，同优先级时电平型 RDA 可能反复抢在 DMAC IRQ 前面，
当时提高 DMA 优先级是避免 CH5 完成事件得不到处理的时序补丁。

DMA 模式下 RX 触发阈值为 `SRT=2`（FIFO 半满），PIO 模式为
`SRT=0`（一个字节）。TX DMA 使用 CH4，`uart_write_dma()` 按
`UART_TXDMA_SIZE` = 256 分块，每块通过 `dmac_wait_idle_timeout()` 等待
完成，并由 `UART_DMA_TIMEOUT_TICKS` 限制等待时间。

PIO TX 只有一个 ring→FIFO 搬运入口：`uart_write()` 只写 TX ring，并在
ring 由空变为非空时开启 THRE IRQ；`uart_dw_isr()` 的 THRE 分支调用
`uart_tx_isr()` 填充 FIFO，ring 空后关闭 THRE IRQ。DMA 模式下 CH4 独占
TX FIFO，因此忽略可能残留的 THRE 事件。

当前 TX DMA 写路径只在填充缓冲和挂载通道时持有 `tx.lock`，等待
DMA 完成时会释放锁；因此多个并发 DMA 写者以及与 `uart_set_mode()`
并发的模式切换尚未完全串行化，调用层需保证单传输会话。

另一个 K210 硬件约束是 DW UART 的 `LSR[5]` 在本实现中按 1=发送忙、
0=可写解释。`uart_hw_tx_ready()` 使用 `!(LSR & UART_LSR_TX_BUSY)`，
不能直接套用标准 16550 THRE 位的判断方向。

### 硬件 overrun 统计

UART1 的 RX ring `dropped` 只统计"软件 ring 满"，看不到硬件 FIFO 在 DMA/
中断接管前就丢掉的字节。`uart_dw_isr()` 的 LSERR 分支读取 LSR 的 `OE` 位并累加
`overrun`，`uart_get_rx_stats()` 的 `info[4]` 上报。console 的 UARTHS 没有
overflow 状态位，`info[4]` 恒为 0。

### /dev/ttyS0 设备层（uartdev.c）

`kernel/devsw/uartdev.c` 在 DW UART1 上实现 RAW 字节流设备。ioctl 命令号
与 `CONSOLE_IOCTL_*` 对齐，因此 `burn.c` 切换数据设备时协议逻辑不用改：

- `CONSOLE_IOCTL_FLUSH_INPUT`：`uart_flush_rx()`；
- `CONSOLE_IOCTL_SET_MODE`：只接受 `CONSOLE_MODE_RAW`（字节流设备没有 TTY
  行编辑语义），`GET_MODE` 恒返回 RAW；
- `CONSOLE_IOCTL_SET_BAUD` / `GET_BAUD_INFO`：走 `uart_set_baud()` /
  `uart_get_baud_info()`；
- `CONSOLE_IOCTL_GET_RX_STATS`：`info[3]` 是当前统一模式（PIO/DMA），
  `info[4]` 是硬件 overrun；
- `UART_IOCTL_SET_MODE`：同时切换收发方向的 PIO/DMA 路径。

`uart_set_mode()` 是 `uart.h` 的公开入口，devsw 层只负责参数透传。切换前先
排空 TX 并禁用 RX IRQ，再停 RX DMA、收取在途字节和 FIFO 尾部，随后
统一重配 RX/TX 路径。DMA 模式关闭 THRE IRQ，由 DMA 独占 TX FIFO。

### burn 双口数据通路

`tools/burn.py` 支持 `--data-port <uart1_port>`，在 INFO 包第 9 字节
（payload[8]）告知板端 `data_port=1`。板端 `burn.c` 收到后打开
`/dev/ttyS0` 并立即把线速复位到 console baud、清空 RX 残留，把 INFO ACK 和
DATA/DONE 全部切到该口（DMA RX CH5 / TX CH4）；shell 握手和板端最终摘要
仍走 console。

默认日志保持精简：板端将 CRC、I/O、丢包和最长停顿等异常累加，传输
结束后只输出一行 `burn: ok ...` 或 `burn: fail ...`；PC 端默认约输出
5 行进度与结果，`-v` 才展开重试分类、逐项统计和完整板端尾部。
使用单 console 口时（默认，`data_port=0`），DATA 阶段和握手共用
`/dev/console`，行为与旧版一致。

## Console TTY 与 RAW 模式

Console 当前提供两种全局模式：

```c
#define CONSOLE_MODE_TTY 0
#define CONSOLE_MODE_RAW 1
```

TTY 模式保持项目原有约定：

* 非规范模式，收到字符即可交给读者。
* 退格、Tab 补全和行编辑由 shell 处理。
* 只回显可打印字符和换行，ANSI 转义序列不回显。
* `Ctrl-P` 在 Console 读取路径中执行 `procdump()`。
* `Ctrl-D` 保持 EOF 语义。
* `Ctrl-C` 由 RX 观察者消费，向当前前台进程组发送 `SIGINT`（见
  「RX 观察者与 Ctrl-C」一节），不会作为输入进入 shell。
* QEMU 将 `\r` 转换为 `\n`。
* K210 将 Enter 的 `\r\n` 合并为单个 `\n`。

Console 维护 `foreground_pgid` 和 `foreground_owner_pgid` 两个前台进程组
状态。shell 通过 `CONSOLE_IOCTL_SET_FG_PGRP` 在运行前台命令时把自己/子进程
的进程组设为前台，命令结束后交回 shell 进程组；只有当前前台进程组和所有者
可以修改该状态。TTY 模式下 `Ctrl-C` 只有在 `foreground_pgid > 0` 时才触发
SIGINT，避免 shell 收到非预期的中断。

RAW 模式不做任何字符解释：

* `0x00` 到 `0xff` 原样读取。
* 不回显。
* 不处理控制字符。
* 不转换 `\r`/`\n`。
* 读写均使用 UART ring。

设备框架已经支持 `struct file.private_data`，SPI 和 SD 都使用 per-open 状态。
Console 没有使用该字段，而是有意把 TTY/RAW mode 保持为全局终端状态，因为
所有 `/dev/console` fd 最终对应同一个物理控制台和同一条 RX ring。同一时间
仍只允许一个二进制传输会话；某个进程进入 RAW 后，其他 Console 读者也会
受到影响。这是 Console 当前语义选择，不是通用设备框架的限制。

## Console ioctl

当前 Console ioctl 定义如下：

```c
#define CONSOLE_IOCTL_FLUSH_INPUT    0x01
#define CONSOLE_IOCTL_SET_MODE       0x02
#define CONSOLE_IOCTL_GET_MODE       0x03
#define CONSOLE_IOCTL_SET_BAUD       0x04
#define CONSOLE_IOCTL_GET_BAUD_INFO  0x05
#define CONSOLE_IOCTL_GET_RX_STATS   0x06
#define CONSOLE_IOCTL_SET_FG_PGRP    0x07
#define CONSOLE_IOCTL_GET_FG_PGRP    0x08
```

统计结构：

```c
struct console_baud_info {
  uint32 requested;
  uint32 actual;
  uint32 div;
  uint32 clock;
};

struct console_rx_stats {
  uint32 dropped;
  uint32 buffered;
  uint32 capacity;
  uint32 mode;
  uint32 overrun;   // FIFO overrun（OE）。DW UART1 统计真实 LSR OE；
                    // UARTHS 没有 overflow 状态位，恒为 0
};
```

`CONSOLE_IOCTL_GET_MODE` 直接通过 ioctl 返回值返回当前 mode；baud info 和
RX stats 通过用户指针 copyout。`GET_RX_STATS` 输出 5 个字段，`info[4]` 是
硬件 overrun。`SET_FG_PGRP`/`GET_FG_PGRP` 管理前台进程组（见「Console TTY
与 RAW 模式」），供 shell 的作业控制使用。

模式切换按以下顺序执行：

```text
暂停 RX IRQ
  -> 清空硬件 FIFO 和 RX ring
  -> 重置 Console TTY 状态（esc/drop_lf/eof/事件标志）
  -> 更新 mode
  -> 恢复 RX IRQ
```

TTY→RAW 和 RAW→TTY 都清空输入，避免 shell 残留字符污染二进制协议，也避免协议尾部字节进入 shell。

## 波特率切换

`CONSOLE_IOCTL_SET_BAUD` 由 Console 校验参数，再调用 UART 层的
`uarths_set_baud()`（DW UART1 走 `uart_set_baud()`）。UARTHS 的 K210 切换
顺序为：

```text
等待软件 TX ring 清空
  -> 等待硬件 TX 完成
  -> 暂停 RX IRQ
  -> 排空硬件 RX FIFO（软件 ring 中已读出的字节保留）
  -> 更新 UARTHS 分频寄存器
  -> 恢复 RX IRQ
```

`uarths_set_baud()` 只排空硬件 FIFO，不碰软件 RX ring——切波特率前已经从
FIFO 读入 ring 的字节属于应用程序，必须跨切换保留。UARTHS 是
Console 专用设备，K210 实现在切换结束后重新开启 RX IRQ；QEMU 路径仅
保留接口，不修改硬件分频。DW UART1 的 `uart_set_baud()` 会保存 RX IRQ
的原状态；DMA 模式下还会在切分频前停 CH5，收取在途数据和 FIFO
尾部，切换后按新线速重新挂载。

`burn` 使用同一个 Console fd 完成：

```text
TTY -> RAW -> 可选高波特率 -> 二进制传输
    -> 115200 -> 获取 RX stats -> TTY
```

数据阶段若走 `/dev/ttyS0`（`--data-port`），波特率切换作用于 uart fd，
握手仍留在 console。正常完成和协议错误路径都会经过统一清理逻辑，恢复默认
波特率及 TTY 模式。当前 QEMU 路径不实际修改 UART 波特率，只保留接口兼容。

## 构建与验证

基础构建：

```bash
make build platform=qemu
make build platform=k210
make fs
```

QEMU 验证：

```text
启动 shell
执行 consoletest
确认显示：Console test PASSED
执行长文本输出，确认无停顿或死锁
```

K210 实机验证：

```text
1. 在 115200 波特率启动 shell。
2. 连续执行 ls，确认无需敲回车即可完整输出。
3. 执行 consoletest，确认 TTY -> RAW -> TTY 往返。
4. 检查 Enter 的 CR/LF 只产生一次换行。
5. 执行 uarttest，验证 /dev/ttyS0 的 PIO/DMA 双向收发。
6. 执行完整 burn 高波特率传输（单 console 口和 --data-port 双口各一次）。
7. 人为制造 CRC/协议错误，确认恢复 115200 和 TTY。
8. 检查 RX dropped，并确认 UART 空闲时没有 TX 中断风暴。
```

若长输出必须依靠输入才能继续，优先检查 K210 `TXCTRL.txcnt` 和
`IE.txwm`；若 shell 完全收不到输入，优先检查 RX IRQ、PLIC 和 QEMU
16550A IER 位定义。UART1 数据通路出现 CRC 错误时，优先确认 RDA 只在
`dmac_is_done()` 成立时补位 DMA ISR，CTI 严格按“停 DMA→收取部分块→
排空 FIFO→重挂 DMA”执行，以及 DMA ISR 在锁内重新检查 done 状态；
不应再依赖提高 CH5 IRQ 优先级来保证正确性。
