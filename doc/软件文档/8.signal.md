# SIGNAL 系统调用实现总结（面试版）

> 面向面试的口述版技术总结。用「项目动机 → 架构 → 核心实现 → 关键设计决策 → 高频问题」的组织方式，帮你把一段代码讲成一个有逻辑、有取舍、可深入追问的项目故事。

---

## 0. 一句话概括

在自研的 RISC-V xv6-k210 教学操作系统上，从零实现了一套轻量级 POSIX 风格信号子系统：用户态可注册/忽略/恢复 handler，内核可向 PID 或进程组发信号，`Ctrl+C` 能通过前台进程组中断管道与后台任务隔离，并支持唤醒阻塞在 `sleep()`/pipe/Console `read()` 中的可中断睡眠进程。

---

## 1. 项目背景与动机

**原状**：xv6 原本只有一个 `int killed` 字段，只能表达「进程该退出了」，无法表达：

- 信号编号（被谁杀的）；
- 用户自定义 handler；
- 忽略某个信号；
- 向一组进程（管道、后台任务）发送。

**要解决的问题**（按难度递增）：

1. 用户程序能注册、忽略、恢复信号处理；
2. 内核能向指定进程或进程组发信号；
3. `Ctrl+C` 要能中断前台 CPU 死循环和阻塞任务，但不退出 Shell、不影响后台任务；
4. 信号要能唤醒阻塞在 `sleep()`、pipe、Console `read()` 中的进程；
5. QEMU 与 K210 实机共用同一套上层语义，且 RAW 模式（烧录/二进制下载）绝不解释控制字符。

**规模约束**：项目定位是教学 OS，不追求完整 POSIX。第一阶段刻意砍掉：信号排队、实时信号、`sigaction` 完整 flag、嵌套 handler、`SIGTSTP/SIGSTOP` job control。

**一个有取舍的设计决定**：原 `kill(pid)` 系统调用（语义模糊：「发任意信号」和「杀死进程」混在一起）被删除，统一由语义明确的 `sigsend(target, signum)` 承担发送职责。

---

## 2. 总体架构

```text
信号来源                                       投递路径
─────────────────────────────────────────────  ─────────────────────────────
用户 syscall: sigsend(PID/PGID)  ─┐             usertrap()/kerneltrap()
UART RX 中断 → console observer ─┼─→ sig_pending 位图 → signal_deliver()
pipe 无读端: SIGPIPE            ─┤                  │
子进程退出: SIGCHLD             ─┘                  ├─ 默认终止 → killed=1 → exit(-signum)
                                                    ├─ 忽略       → 继续运行
                                                    └─ 用户 handler → 改 trapframe → SIGTRAMP → sigreturn
```

**模块依赖方向**（保持单向，是面试时值得强调的架构洁癖）：

```text
来源模块 (syscall/console/pipe/proc) → signal core
signal core ─/ 不依赖 Console / UART / Shell / File
console → uarths（UART 只提供通用 observer，不含任何 TTY/信号语义）
```

## 3. 系统调用接口 ABI

定义见 [kernel/include/signal.h](../../kernel/include/signal.h)、[kernel/include/syscall.h](../../kernel/include/syscall.h)。

```c
typedef void (*sighandler_t)(int);
#define SIG_DFL ((sighandler_t)0)
#define SIG_IGN ((sighandler_t)1)
#define SIG_ERR ((sighandler_t)-1)

sighandler_t signal(int signum, sighandler_t handler);   // SYS 31，返回旧 handler
int sigsend(int target, int signum);                     // SYS 32，target>0=PID, target<0=进程组
int sigreturn(void);                                     // SYS 33，仅由 trampoline 调用
int setpgid(int pid, int pgid);                          // SYS 34
int getpgrp(void);                                       // SYS 35
```

- `sigsend(target, signum)`：`target > 0` 发 PID；`target < 0` 发进程组 `-target`；`target == 0` 拒绝（避免隐式依赖调用者进程组语义）。
- Console 前台组通过既有 `ioctl(fd, CONSOLE_IOCTL_SET_FG_PGRP, pgid)` 设置（`0x07/0x08`），不新增 TTY 专用系统调用。

**信号集合**：`NSIG = 32`。重点实现 `SIGINT`(2)、`SIGKILL`(9)、`SIGPIPE`(13)、`SIGTERM`(15)、`SIGCHLD`(17)。`SIGKILL` 不可捕获、不可忽略。

| 信号 | 来源 | 默认动作 |
|---|---|---|
| SIGINT | Ctrl+C | 终止 |
| SIGKILL | 强制 | 终止（不可捕获/忽略）|
| SIGTERM | 请求退出 | 终止 |
| SIGPIPE | 向无读端 pipe 写 | 终止 |
| SIGCHLD | 子进程退出 | 忽略 |

## 4. 数据结构

`struct proc` 中新增字段，见 [kernel/include/proc.h:117-147](../../kernel/include/proc.h#L117-L147)：

```c
int pgid;                        // 进程组 ID
uint32 sig_pending;              // 待投递信号位图（同一信号最多保留一次）
uint32 sig_mask;                 // 内部屏蔽集合（防重入）
uint64 sig_handlers[NSIG];       // SIG_DFL / SIG_IGN / 用户 handler 地址
int sig_handling;                // 是否正在执行用户 handler（禁止嵌套）
int sig_current;                 // 当前正在处理的信号编号
int sig_term;                    // 导致最终退出的信号编号
int interruptible_sleep;         // 这次睡眠能否被普通信号唤醒
struct trapframe sig_saved_trapframe;  // handler 执行前的用户寄存器快照
```

**设计要点**：用 `uint32` 位图而非链表存 pending——非实时信号同一信号只保留一次，位图天然去重，且置位/清除是 O(1) 原子位运算。用一份 trapframe 快照（而非用户栈 signal frame）换掉 handler 嵌套能力，是「教学 OS 用复杂度换简单性」的典型取舍。

## 5. 核心实现：投递与恢复

核心逻辑全部收敛在 [kernel/proc/signal.c](../../kernel/proc/signal.c)，不散落在 `trap.c`/`proc.c`。

### 5.1 发送信号

```c
// signal.c:108 signal_mark_locked —— 所有来源汇聚到这里
static void signal_mark_locked(struct proc *p, int signum) {
  if(handler == SIG_IGN || (SIG_DFL && default_ignored))  return; // 生成时即忽略，不进 pending
  p->sig_pending |= 1U << signum;
  if(signum == SIGKILL) { p->sig_term = signum; p->killed = 1; }
  if(p->state == SLEEPING && p->interruptible_sleep)
    p->state = RUNNABLE;   // 合成 wakeup：唤醒可中断睡眠
}
```

三种发送入口：
- `signal_send_pid(pid, signum)`：扫描进程表匹配 PID；
- `signal_send_pgrp(pgid, signum)`：扫描匹配 PGID，**逐个进程加锁**，避免多进程锁顺序依赖；
- `signal_send_locked(p, signum)`：调用方已持有 `p->lock` 时使用（如 exit 给父进程发 SIGCHLD）。

### 5.2 投递时机与优先级

投递发生在 `usertrap()` 返回用户态**之前**（[kernel/trap/trap.c:129](../../kernel/trap/trap.c#L129)）：

```c
console_dispatch_events();   // 处理 Ctrl+C 延迟事件（见 §7）
if(p != 0 && p->state == RUNNING && (which_dev == 2 || mycpu()->need_resched))
  yield();
signal_deliver(p);           // ← 关键：每次返回用户态前检查并投递
if(p->killed) exit(signal_exit_status(p));
```

**为什么放在这里**：定时器中断保证 CPU 死循环进程也会周期性进内核，因此无需等进程主动发起系统调用。

`signal_deliver()` 选择信号逻辑（[signal.c:213](../../kernel/proc/signal.c#L213)）：

1. `pending = sig_pending & ~sig_mask`，`SIGKILL` 永远穿透 mask；
2. **正在执行 handler 时不再投递新信号**（除 SIGKILL）——禁止嵌套；
3. 优先级：`SIGKILL` 最高 → 其余按编号从小到大；
4. 按「终止 → 忽略 → 用户 handler」三分支处理。

### 5.3 用户 handler 的执行与恢复

投递 handler（[signal.c:282-291](../../kernel/proc/signal.c#L282-L291)）：

```c
p->sig_saved_trapframe = *p->trapframe;  // 快照完整用户寄存器
p->sig_handling = 1;
p->sig_current = signum;
p->sig_mask |= 1U << signum;             // 本次处理期间屏蔽自身
p->trapframe->a0 = signum;               // handler 参数
p->trapframe->ra = SIGTRAMP;             // handler 返回地址 = 固定 trampoline
p->trapframe->epc = handler;             // 下一跳 = 用户 handler
```

handler 返回后自动落入 `sigtramp`（[kernel/trap/sigtramp.S](../../kernel/trap/sigtramp.S)）：

```asm
sigtramp:
  li a7, SYS_sigreturn
  ecall
```

`signal_sigreturn()`（[signal.c:294](../../kernel/proc/signal.c#L294)）：

```c
signum = p->sig_current;
a0 = p->sig_saved_trapframe.a0;
*p->trapframe = p->sig_saved_trapframe;   // 恢复全部寄存器
p->sig_mask &= ~(1U << signum);
p->sig_handling = 0;
...
return a0;   // ← 关键细节：返回恢复现场的原始 a0
```

**这个 `return a0` 是全文最容易翻车的细节**：系统调用分发器会执行 `p->trapframe->a0 = syscalls[num]()`。如果 `sys_sigreturn()` 返回普通 0，就会用 0 覆盖掉被中断现场里 a0 原本的值。所以必须返回保存的 `a0`。

### 5.4 SIGTRAMP 固定映射页

`SIGTRAMP = TRAPFRAME - PGSIZE`（[kernel/include/memlayout.h:113](../../kernel/include/memlayout.h#L113)），每个进程地址空间映射同一 VA：

```c
// proc.c:435
if(mappages(pagetable, SIGTRAMP, PGSIZE,
            (uint64)sigtramp, PTE_R | PTE_X | PTE_U) < 0)
```

**为什么用固定映射页而不是链接进每个 ELF**：所有进程共享同一 `SIGTRAMP` VA，trapframe 只存一个常量地址；且 `PTE_U|PTE_R|PTE_X`，不映射 `PTE_W`——用户 handler 想借此读/改内核保存的 trapframe 快照（`TRAPFRAME` 页未映射给用户）也读不到。

## 6. 可中断睡眠

**问题**：信号发给一个阻塞在 `sleep()`/pipe/Console `read()` 的进程时，进程不在内核 → 无法立即投递 → 必须把它唤醒回用户态再投递。

**方案**：把原 `sleep()` 抽成公共核心，加一个 `interruptible` 参数（[proc.c:881-941](../../kernel/proc/proc.c#L881-L941)）：

```c
static int sleep_on(void *chan, struct spinlock *lk, int interruptible) {
  ...
  if(interruptible && signal_pending_locked(p)) { interrupted = 1; goto out; }  // ①入睡前：已带信号就不睡
  p->chan = chan;
  p->interruptible_sleep = interruptible;   // ②睡下时：标记「可被信号唤醒」
  p->state = SLEEPING;
  sched();
  p->chan = 0;
  p->interruptible_sleep = 0;
  if(interruptible && signal_pending_locked(p)) interrupted = 1;  // ③醒来后：带信号则返回 -1
  ...
  return interrupted ? -1 : 0;
}
void sleep(void *chan, struct spinlock *lk)           { sleep_on(chan, lk, 0); }
int  sleep_interruptible(void *chan, struct spinlock *lk) { return sleep_on(chan, lk, 1); }
```

**三处 pending 检查是完整的闭合**：入睡前查一次（信号优先，干脆不睡）、睡下时打标记、醒来后查一次（被信号唤醒则返回 `-1`）。配合 5.1 里「置 pending 时若目标在可中断睡眠就置 RUNNABLE」的合成 wakeup，一条闭环就打通了。

**谁决定是否可中断**：`signal_mark_locked` 只在 `state == SLEEPING && interruptible_sleep` 时唤醒，**不根据 chan 或设备类型推断**——磁盘 I/O、锁等待这类不可中断路径继续用 `sleep()`，信号只打 pending 标记，等它自然完成。

**调用方负责语义转换**：业务代码把 `-1` 翻译成 syscall 返回值（`sys_sleep` 返回 -1；pipe 返回 partial write；`wait()` 返回 -1 让用户重试）。改造点：`sys_sleep`、`wait`、`pipewrite`/`piperead`、Console `read`。

## 7. Ctrl+C 全链路（核心亮点）

这是整个系统里最绕、也最值得讲清楚的部分。**核心矛盾**：UART 中断上下文里不能持进程锁、不能扫描进程表、不能输出；但 Ctrl+C 必须在字节进 ring 时就被识别。

**设计**：观察者模式 + 中断上下文只置位 + 延迟到 trap 安全上下文处理。

```
UART RX 中断 (uarths.c:423 uartintr)
  └─ uart.rx_observer(c) —— Console 注册的通用 observer
       └─ console_rx_observer (console.c:29)
            仅原子读 mode / foreground_pgid / 比较 c==0x03
            是 TTY 且有前台组 → __atomic_fetch_or(tty_events, SIGINT) → 返回 UART_RX_CONSUME_CANCEL
usertrap()/kerneltrap() 中调用 console_dispatch_events()
  └─ 原子取走 tty_events → 读 foreground_pgid → 输出 ^C\n → signal_send_pgrp(foreground_pgid, SIGINT)
```

**三个细节分别解决三个坑**：

1. **observer 用原子读写**（`__atomic_*`），不在中断上下文碰进程锁——这是锁序安全的根；
2. **`UART_RX_CONSUME_CANCEL`**（区别于 `CONSUME`）：不仅消费 `0x03`，还清空整个 RX ring 并置 `rx_cancel_pending`，让阻塞在 `read()` 的进程返回 -1。为什么？如果只清 ring，会出现「控制字节早于进程下一次 read 到达 → 信号投递在 userret 完成 → 阻塞进程到不了 userret → 永远睡死」的时序空洞；
3. **`console_dispatch_events()` 的双触发点**：`usertrap`（用户态 trap 路径）是主路径；`kerneltrap` 中 `myproc()==0`（空闲调度器）是兜底——保证没有用户进程在跑时 Ctrl+C 也能被处理。

**RAW 模式**：observer 直接返回 `UART_RX_KEEP`，`0x03` 原样进 ring、不置事件、不产生信号——保证 K210 烧录、串口二进制传输协议完全不受影响。这也是 QEMU/K210 双平台共用同一套语义的关键。

## 8. 进程组与前台终端

**为什么用进程组而不用单一前台 PID**：`producer | consumer` 这样的管道里有两个进程，Ctrl+C 的正确目标必须是整组。

**进程组规则**：
- `fork()` 子进程继承父进程 `pgid`（[proc.c:574](../../kernel/proc/proc.c#L574)）；
- `setpgid(pid, pgid)`：`pgid==0` 表示「以 pid 自己的 pid 建新组」，支持把自己或子进程拉进组（[proc.c:599](../../kernel/proc/proc.c#L599)）；
- `allocproc()` 时默认 `pgid = pid`。

**Console 前台归属**（[console.c:107-146](../../kernel/devsw/console.c#L107-L146)）——这里有一个容易忽略的权限模型：

```c
cons.foreground_pgid       // 信号目标
cons.foreground_owner_pgid // 终端控制者（Shell）
```

- 只有「当前前台组成员」或「控制者」能改前台组——防止后台任务任意抢占终端；
- 控制者组消失时（init 重启 Shell），下一次设置操作回收陈旧归属，允许新 Shell 接管；
- Shell 执行前台任务：`fork 首子 → setpgid(child, child) → 管道其余子 setpgid(_, first_child) → ioctl(SET_FG_PGRP, first_child) → wait → ioctl(SET_FG_PGRP, shell_pgid)` 收回终端。

**Shell 信号策略**：Shell 自身 `signal(SIGINT, SIG_IGN)`，子进程 `exec` 前显式恢复 `SIG_DFL`——因为 `SIG_IGN` 按 POSIX 语义跨 exec 保留，如果不显式恢复，所有外部命令都会继承「忽略 Ctrl+C」。

## 9. 信号来源扩展（SIGPIPE / SIGCHLD）

**SIGPIPE**（[pipe.c:94](../../kernel/ipc/pipe.c#L94)）：pipe 写端发现无读端时，`signal_send_pid(pr->pid, SIGPIPE)`。注意顺序：**先释放 pipe 锁再发信号**，避免锁序反转；pipe 写要分别在写入前、满缓冲睡眠醒来后检查读端。

**SIGCHLD**（[proc.c:713](../../kernel/proc/proc.c#L713)）：子进程首次转 ZOMBIE 的 `exit()` 路径，`signal_send_locked(original_parent, SIGCHLD)`。默认忽略 → 生成时即丢弃，不进 pending，不打断父进程 `wait()`；只有显式注册 handler 的父进程才会收到。`wait()` 仍是唯一回收入口。

## 10. 生命周期管理

| 时机 | 处理 | 位置 |
|---|---|---|
| allocproc | 清零 pending/mask，handler 全置 SIG_DFL | [signal.c:40](../../kernel/proc/signal.c#L40) |
| fork | 继承 mask + handler 表；**不继承** pending、handling、当前信号 | [signal.c:52](../../kernel/proc/signal.c#L52) |

| exit | `signal_exit_status()` 返回 `-signum` 作为退出码，Shell 可区分「普通退出」和「信号终止」 | [signal.c:322](../../kernel/proc/signal.c#L322) |

## 11. 安全校验与错误处理

- 编号校验：`0 < signum < NSIG`；信号 0 保留用于「探测进程是否存在」的语义；
- `SIGKILL` 不可捕获/忽略（`signal_set_handler` 拒绝）；
- **handler 地址校验**：不是简单地 `handler < sz`，而是用 `walk()` 查页表，确认 `PTE_V|PTE_U|PTE_X` 齐全（[signal.c:26](../../kernel/proc/signal.c#L26)），防止跳进内核地址或不可执行页；
- 非法 PID/PGID 返回 -1；进程组发送只要命中至少一个进程就返回 0；
- 非 handler 上下文调用 `sigreturn()` 返回 -1，**不恢复未初始化的 trapframe**；
- `signal_reset_on_exec`/`signal_proc_fork` 全程持 `p->lock`，防止 proc slot 复用泄漏。

---

## 12. 锁与并发

这是能体现系统级思维的加分点：

1. **UART RX observer 不获取任何进程锁**，只用原子指令——中断上下文锁序安全；
2. `console_dispatch_events()` 先从 `cons.lock` 拷贝出 `foreground_pgid` 再释放，之后才扫进程表，绝不持有 Console 锁调用可能睡眠的代码；
3. `signal_send_pgrp()` **一次只持有一个 `p->lock`**，逐个加锁解锁，避免「持 A 锁取 B 锁」的锁顺序依赖；
4. `sig_pending`/`killed`/`pgid` 等跨 hart 可见状态全部由目标 `p->lock` 保护——不能假设「当前进程不会被并发访问」，因为其他 hart 可能同时在向它发信号。

## 14. 面试高频问题（提前准备）

**Q1：为什么用 `killed` 字段而不是直接 exit？**
`killed` 是既有「进程应退出」的安全退出标志，被 trap、pipe、UART 等多条阻塞路径检查。新信号层把「默认终止/SIGKILL」翻译成 `killed = 1 + sig_term`，就能复用所有既有退出检查点，一次性改造所有阻塞路径的风险最小。

**Q2：信号怎么唤醒睡着的进程？**
可中断睡眠三步闭环：入睡前查 pending 不睡 → 睡时打 `interruptible_sleep` 标记 → 发信号时把可中断睡眠进程置 RUNNABLE（合成 wakeup）→ 醒来后查 pending 返回 -1。普通信号不唤醒磁盘/锁等待等不可中断睡眠。

**Q3：为什么信号投递要放在返回用户态前，而不是收到时立刻？**
因为 handler 是用户态代码，投递 = 改写 trapframe 寄存器。唯一安全时机是准备 `sret` 回用户态那一刻。定时器中断保证死循环进程也会周期性进内核，所以这个时机不会迟到。

**Q4：为什么 handler 返回地址是固定 SIGTRAMP 页？**
所有进程共享同一 VA，trapframe 只存一个常量；链接进每个 ELF 依赖符号存在且地址可能不同。另外映射为 `R|X|U` 不映射 W，用户 handler 读不到内核保存的 trapframe。

**Q5：sigreturn 返回原始 a0 是什么坑？**
系统调用分发器 `p->trapframe->a0 = syscalls[num]()` 会用返回值覆盖 a0。若 `sys_sigreturn()` 返回 0，被中断现场的 a0 就丢了。所以必须把快照里的 a0 一路传回。

**Q6：Ctrl+C 在中断上下文里做了什么？为什么不直接在中断里发信号？**
中断里只做原子读 + 置事件位 + 消费字节，零锁零进程表访问。真正的组扫描和发送延迟到 `usertrap`/空闲 `kerneltrap` 里 `console_dispatch_events()` 执行，从根上避免锁序问题。

**Q7：RAW 模式怎么办？**
observer 返回 `UART_RX_KEEP`，`0x03` 原样进 ring。这保证烧录和串口二进制传输协议（burn.c）在 RAW 模式下完全不受 Ctrl+C 语义影响。

**Q8：`SIG_IGN` 和注册的 handler 在 exec 后有什么区别？**
注册的 handler 地址在旧地址空间，新程序里失效，必须恢复 `SIG_DFL`；`SIG_IGN` 是语义而非地址，按 POSIX 跨 exec 保留。所以 Shell 子进程要显式恢复 `SIG_DFL`。

**Q9：进程组发送会不会死锁？**
不会。`signal_send_pgrp` 一次只持一个 `p->lock`，逐个进程扫描，不构成「持锁等锁」的环。

**Q10：为什么非实时信号用位图不用队列？**
位图天然满足「同一信号只保留一次」，置位/清除 O(1)、原子、省内存（32 个信号 = 1 个 uint32）。代价是不支持排队计数，这正是第一阶段明确砍掉的非目标。
