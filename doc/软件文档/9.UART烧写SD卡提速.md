# UART 烧写 SD 卡：波特率选择与 1500000 支持

本文是 [2.UART刷写SD卡.md](2.UART刷写SD卡.md) 的续篇，记录两件事：

1. 如何**选择** SD 卡 UART 烧写的波特率（Makefile 变量 + burn.py 档位表 + 实测状态）。
2. 把烧写速率提升到 **1500000** 的完整方案（放弃中断接收、改用轮询 + 调度固定），以及**高速直接启动**（板端一开机就处于高波特率）这一特殊场景的适配。

> 状态说明：本文「波特率选择」一节描述的能力已随代码落地（Makefile `DOWNLOAD_BAUD`、burn.py 单一 `--baud`，主机与板端同速，无补偿）。「1500000 支持」一节的代码已落地：第 1 步（内核轮询原语 + 3 个 ioctl + `sched_pin`）与第 3 步（burn.c 接轮询 + 钉住）均已实现并通过 QEMU/K210 双平台编译；第 0/2/4/5 步为硬件验证步骤（逻辑分析仪、实机烧写），尚未执行；默认档位 `DOWNLOAD_BAUD=1500000`。

---

## 1. 为什么需要更快的烧写波特率

当前 `make download` 使用主机 460800、板端 500000，FAT32 裁剪后有效镜像约 2.6MiB，实际烧写仍需数分钟。瓶颈在两处：

- 每次只能发送一个 512 字节扇区并等待 ACK（stop-and-wait）。
- 传输波特率受板端中断接收能力限制（见第 3 节），无法直接提到 1.5M。

实测已经确认两个关键事实，说明 1.5M 是可行的：

- 逻辑分析仪（采样率 ≥5MS/s）确认：板端 UARTHS 与主机 USB 转串口在 1500000 这个档位**两侧都精确**（390M÷260 = 1.5M，12M÷8 = 1.5M），可以正常互通。
- `kflash.py` 以 1500000 波特率向板载 Flash 下载（板端运行的是轮询式 ISP 固件）成功，吞吐约 54kiB/s。这证明 UARTHS 硬件本身在 1.5M 下完全可用——xv6 里接不住，是**软件接收路径**的问题。

预期 1.5M 下每扇区约 4.7ms（527B 传输 3.5ms + SD 写 ~1ms + ACK 0.13ms），吞吐约 110KB/s，比当前快 2~3 倍。

## 2. 波特率选择

### 2.1 单一 baud 参数

主机 baud 与板端 baud 使用同一个值。命令行只暴露 `--baud`：它同时是主机串口实际速率（`ser.baudrate`）与 INFO payload 发往板端的 `CONSOLE_IOCTL_SET_BAUD` 目标值。不做任何 11/10 补偿。

### 2.2 实测档位表

| `--baud` | 状态 | 说明 |
|---|---|---|
| 115200 | ✅ 稳定 | 全程低速，最保守 |
| 230400 | ✅ 稳定 | 低速保守组合 |
| 500000 | ✅ 稳定 | 公共精确速率 |
| 1500000 | 🚧 目标 | 公共精确速率，需轮询+调度固定（第 4 节） |
| 576000 / 768000 / 921600 | ❌ 不可用 | 主机芯片档位量化与板端无法对齐，实测乱码 |

两侧同速时，主机 USB 芯片（12MHz 晶振）与板端 UARTHS（390MHz 整数分频）需同时落在同一实际值。优先选公共精确速率（500000、1500000）；高速档（576000、768000、921600）无法与板端对齐，实测乱码，选型时避开。

### 2.3 使用方式

Makefile `download` 目标只暴露 `DOWNLOAD_BAUD` 一个变量：

```sh
make download                          # DOWNLOAD_BAUD 默认 1500000
make download DOWNLOAD_BAUD=500000
make download DOWNLOAD_BAUD=1500000    # 需先落地第 4 节方案（板端支持轮询）
make download DOWNLOAD_BAUD=115200     # 全程低速最保守
```

等价地，绕过 Makefile 直接调用 `tools/burn.py`：

```sh
python3 tools/burn.py --baud 1500000 /dev/ttyUSB0 target/fs.img
python3 tools/burn.py --baud 500000  /dev/ttyUSB0 target/fs.img
python3 tools/burn.py --baud 230400  /dev/ttyUSB0 target/fs.img
```

## 3. 为什么 1.5M 必须放弃中断接收

UARTHS 的 RX FIFO 只有 8 字节，无硬件流控。中断接收的延迟约 100µs，构成如下：

```text
UARTHS RX FIFO 有数据
  -> PLIC 触发
  -> RustSBI M 态 trap（_start_trap 汇编保存 16 个寄存器）
  -> start_trap_rust 里 mip.set_ssoft() 转发为 S 态软中断
  -> S 态 devintr() -> plic_claim() -> uartintr()
```

K210 使用 1.9.1 特权规范，没有 S 态外部中断，`mideleg::set_sext()` 在 `bootloader/rustsbi-k210/src/main.rs` 中被注释掉，所以 UARTHS 中断只能走 M→S 软转发。这条路径每次约 100µs。

按波特率估算 FIFO 满的时间：

| 波特率 | 每字节 | 8 字节 FIFO 满 | 是否溢出 |
|---|---|---|---|
| 500000 | 20µs | 160µs | ✅ 160µs > 100µs 中断周期，不溢 |
| 1500000 | 6.67µs | **53µs** | ❌ 53µs < 100µs，必溢 |

1.5M 下每 100µs 到达约 15 字节 > 8 字节 FIFO，绝大多数字节在到达 `uartintr()` 之前就被硬件丢弃。日志里 `raw_buf=7/32767`（RX ring 只有 7 字节、dropped 上涨）正是这个特征：如果只是"中断处理慢但字节都到了"，ring 会累积到满；只有 7 字节说明是 **FIFO 溢出**。

> 「慢速发送」是死路：把每中断周期的字节数压回 ≤8，等效速率只有几十 kbps，比 500k 还慢 9 倍。真正要提速只有一条路——让板端接收不再依赖 100µs 一次的中断，也就是**轮询**。

## 4. 方案：DATA 阶段轮询接收 + 调度固定

轮询接收把中断周期从 100µs 压到微秒级，1.5M 轻松承接。但用户态忙等会被 MLFQ 调度器当作 CPU 密集任务处理：

- burn 进入轮询循环后不再 sleep，每个定时器 tick（5ms）都会 `yield()` 并触发 `sched_on_yield()` 降级；
- 顶层时间片只有 1 tick，burn 很快被降到最低级，得不到及时调度；
- 且定时器抢占若落在收包中途，8 字节 FIFO 立刻溢出。

因此方案分两部分：**轮询接收原语** + **调度固定**。

### 4.1 内核改动

**`kernel/driver/uarths.c` / `kernel/include/uarths.h` — 轮询接收原语**

```c
static int uart_rx_poll_mode;   // =1 时 uartintr 跳过 RX 路径

void
uart_set_rx_poll(int on)
{
  uart_rxenable(0);
  uart_hw_drain_fifo();
  uart_rx_poll_mode = on;
  if (!on)
    uart_rxenable(1);
}

// 一次取走硬件 FIFO 里所有可用字节（绕过 ring），最多 max 个。
int
uart_poll_rx(uint8 *dst, int max)
{
  int n = 0, c;
  while (n < max && (c = uart_hw_getc()) != -1)
    dst[n++] = (uint8)c;
  return n;
}
```

`uart_rx_service()` 开头加 `if (uart_rx_poll_mode) return;`，防止 ACK 发送期间 TX 中断触发的 `uartintr()` 把 FIFO 读走（TX 与 RX 共用同一个 `uartintr`）。

**`kernel/devsw/console.c` / `kernel/include/console.h` — 3 个新 ioctl**

| ioctl | arg | 作用 |
|---|---|---|
| `CONSOLE_IOCTL_RX_POLL_MODE` | 1 / 0 | 进入/退出轮询接收（调 `uart_set_rx_poll`） |
| `CONSOLE_IOCTL_RX_POLL` | `{dst, max}` | 调 `uart_poll_rx` + copyout，返回字节数 |
| `CONSOLE_IOCTL_SCHED_PIN` | 1 / 0 | 设置 `myproc()->sched_pin` |

**`kernel/proc/proc.c` / `kernel/include/proc.h` / `kernel/trap/trap.c` — 调度固定（约 6 行）**

- `struct proc` 增加 `int sched_pin;`（`allocproc` 时清 0）。
- `sched_on_yield()` 开头 `if (p->sched_pin) return;` —— 不降级。
- `usertrap()` 的 yield 条件加 `&& !p->sched_pin`，`kerneltrap()` 加 `&& !myproc()->sched_pin` —— 轮询循环不被定时器打断。

> sleep 型阻塞（SD 写、OLED I2C）不受影响：burn 在 I/O 等待时仍会释放 CPU。只有"定时器 yield"被压制，这正是轮询需要的。

### 4.2 用户态改动（`user/app/burn.c`）

只在切波特率之后生效，整体流程：

1. `CONSOLE_IOCTL_SET_BAUD(1500000)` 成功后立即 `RX_POLL_MODE(1)` + `SCHED_PIN(1)`。
2. 把 `recv_msg()` 的字节源从 `read(fd, ...)`（中断 ring）换成轮询循环：
   - 循环 `ioctl(RX_POLL, {buf, 64})` 取字节并累积，先扫 magic(4)、再读 hdr(7) 得 plen、再等满 plen+4；
   - 用户态用 `uptime()` 做接收超时（钉住后 ticks 照常走），超时回 NAK；
   - CRC 校验逻辑完全复用现有 `recv_msg()` 的解析。
3. 退出路径（成功/失败都要）：**先** `SCHED_PIN(0)`、`RX_POLL_MODE(0)`，**再** `SET_BAUD(115200)`、`SET_MODE(TTY)`。顺序不能反：先恢复轮询模式再切波特率，否则残留字节混进 115200 的 ring。
4. ACK/TX 继续走现有 `send_msg()`（板端 TX 1.5M 已由 kflash 实测验证）。
5. 统计里加 `poll_timeout` 计数，并在 DEBUG 构建观测 `queue_level`，验证"钉住"生效。

### 4.3 主机端改动（`tools/burn.py`）

- 默认组合改为 `--baud 1500000`（主机与板端同速；板端支持后），保留 `--baud` 覆盖。
- 板端轮询后，主机整包突发发送（`send_msg` 一次 `ser.write`）不再需要逐字节慢速，删掉为绕过中断溢出加的 `send_msg_slow`；shell 命令逐字节节流（115200 阶段，与 1.5M 无关）保留。
- 更新 `--help` 与失败提示中的档位说明。

## 5. 适配：高速直接启动场景

调试记录里有一个特殊场景（`doc/调试文档/4.UART烧录SD卡调试记录.md`「初步发现时突发传输的问题」）：

> 板端一开机就处于 1500000（绕开 115200→1.5M 的两阶段切换），进行 SD 卡刷写时不成功，卡在发送 INFO(image_size, board_baud)，板端没有回应。

根因：INFO 是一个 **23 字节一次性突发写**。板端此时仍在中断接收路径，FIFO（8 字节）在中断周期（100µs）内被 15 字节灌满，前 8 字节之后的字节全部丢失，板端永远等不到完整的 magic 起始帧。

本方案的**适配原则**：burn 进入 RAW 模式后，**依据当前 console 波特率决定何时进轮询**，而不是假设"必然先 115200 后切换"。

- 标准流程（115200 启动 → 切换）：INFO、BAUD 握手仍走中断路径；`SET_BAUD(1500000)` 之后才进轮询。
- 高速直启（console 已是高波特率）：burn 发完 `BURN\n` 后，若 `CONSOLE_IOCTL_GET_BAUD_INFO` 显示 `actual >= 1000000`，则**立即进入轮询 + 钉住**，再 `recv_msg()` 收 INFO。这样 INFO 的 23 字节突发由轮询逐字节取走，不会溢出。

配套约束：

- 高速直启时，板端 shell 阶段由主机 `send_shell_command` 的逐字节节流保证不溢出（已有能力），`/burn` 命令、INFO、DATA、DONE 全程都在高波特率下完成，`burn.py` 用 `--console-baud 1500000` 即可。
- 板端开机波特率由内核默认 console baud 决定（`uartinit()` 的 115200），要真正"开机即 1.5M"需把该默认值做成可配置。**推荐仍走两阶段切换**；高速直启只是让方案在"已经处于高波特率"的板子上也能工作，不新增必须配置项。

## 7. 风险与回退

- **轮询原语漏字节** → 回到中断路径（新增 ioctl 全部可逆，不破坏现有逻辑），保持 460800/500000 默认。
- **钉住后其他进程饿死** → burn 只在收包间隙占 CPU，SD 写 / OLED 刷新会 sleep；若实测有影响，退化为"只禁降级、不禁 yield"（Tier 1），靠顶层 RR 即时被选回来。
- **1.5M 烧写仍不稳** → 备选方案：改 RustSBI 让 UARTHS 中断直通 S 态（`main.rs` 软转发去掉，`mideleg::set_sext()` 使能）。该改动集中在 bootloader，风险高，与 burn 路径解耦单独排期。
- **主机 1.5M 档位掉线** → 逻辑分析仪已确认主机 1500000 精确（12M÷8），kflash 1.5M 下载成功佐证；步骤 0 会再确认真机 USB 芯片不掉线。

## 8. 验证清单

- 逻辑分析仪（≥5MS/s）在 1.5M 下解码板端发送与接收的 `0x55` 字节流，无 stop-bit error。
- `burn.py --dry-run --baud 1500000` 输出正确的裁剪大小。
- 完整烧写 6.7MiB（约 6786 扇区）`make download DOWNLOAD_BAUD=1500000`：
  - 全部扇区 ACK，timeout / CRC error / retry 数量记录；
  - 无 10s 级超时；
  - 掉电重启后 FAT32 可挂载，抽查文件内容一致；
  - 不重启连续第二次刷写不再触发 `usertrap(): addr is illegal`（`burn: done ... cache=0`）。
- 高速直启场景（板端已处于 1.5M）：`burn.py --console-baud 1500000 --baud 1500000` 能收到 BURN、正常完成 INFO 与全部 DATA。
