# DinoGame 游戏实现 —— xv6-K210 上的 OLED 恐龙快跑

> 面试向技术总结：一个自研教学 OS 上从零移植的《Chrome 恐龙快跑》。
> 覆盖 硬件驱动 → 内核设备框架 → 用户态渲染库 → 并发游戏逻辑 全栈链路，
> 以及 4 个核心设计点 + 5 个真实调试故事。
>

## 1. 一句话概述

在 **嘉楠 K210（RISC-V 双核）** 教学操作系统 xv6-k210 上，用 **SSD1306 OLED（128×64，1bpp）** 显示、**MPU6050 六轴传感器**作为输入，跑通了经典《Chrome 恐龙快跑》：前倾设备跳跃躲避仙人掌，速度随分数加快，碰撞后显示成绩并可重开。

一条完整的 "**裸机传感器 → 内核设备框架 → 用户态游戏**" 数据链路，体现了从底层硬件驱动到应用逻辑的全栈工程能力。

## 2. 运行环境与硬件

| 部件 | 型号 / 参数 | 挂载 |
|---|---|---|
| 主控 | 嘉楠 K210（RV64 双核 @400MHz，无 MMU 保护的裸外设访问） | — |
| 显示 | SSD1306 OLED，128×64，1bpp 页格式，显示 RAM 1024B | I2C0 @ 0x3C |
| 输入 | MPU6050 六轴（本游戏只用 X 轴加速度判倾斜） | I2C0 @ 0x68 |
| I2C | K210 硬件 I2C0，提至 **400kHz**（快模式） | — |
| OS | 自研 xv6-k210：自扩展了 Linux 风格 mmap / 设备框架 / 信号 / FAT32 等 | — |

**核心硬约束：内核不保存/恢复 FPU 上下文** → 内核与游戏代码**全部纯整数**，任何 `double/float` 都会产生非法指令 trap。这条约束贯穿整个设计。

## 3. 系统架构（全栈数据流）

```text
  MPU6050(倾斜)                SSD1306 OLED(128×64)
     │                              ▲
     │ I2C 读 2B                     │ I2C 批量推屏(DMA)
     ▼                              │
 ┌───────────────────────────────────────┐
 │ 内核  kernel/                          │
 │  driver/i2c.c   i2c_transfer() 多 msg+DMA│
 │  devsw/oledfb.c 帧缓冲设备(mmap+FLUSH)  │
 │  devsw/i2cdev.c  /dev/mpu6050 透传      │
 │  vm/mmap.c      VMA_KBUF / vma_populate │
 └───────▲───────────────────────▲───────┘
         │ syscalls              │ open/mmap/ioctl
 ┌───────┴──────────┬────────────┴───────┐
 │ 用户态 user/                            │
 │ libc/oled.c      渲染库+open/mmap/flush│
 │ libc/game_data.c 精灵位图+字体(唯一数据)│
 │ libc/mpu6050.c   传感器库               │
 │ app/dino.c       游戏主逻辑+双进程编排   │
 └────────────────────────────────────────┘
```

**分层原则**：设备层（oledfb）只做"帧缓冲页 + 推屏"，**不做渲染**；渲染完全在用户态写 mmap 帧缓冲；传感器 I2C 只被采样子进程访问。依赖单向：`dino → oled(mmap) → oledfb → i2c → 硬件`。

## 4. 核心设计点

### 4.1 零拷贝帧缓冲：设备 mmap（对比"逐字节 write"）

**旧方案（性能陷阱）**：`user/libc/oled.c` 每个字节一次 2 字节 I2C 事务 → 全屏 1024B 要 1024 次系统调用 + 1024 次 I2C 往返，游戏渲染完全不可用。

**新方案（设备 mmap）**：

```c
fd  = open("/dev/oledfb", O_RDWR);
fb  = mmap(0, OLEDFB_FB_SIZE, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);
fb[p*128 + col] |= bit;          // 用户直接写映射页 —— 零拷贝、零系统调用
ioctl(fd, OLEDFB_IOCTL_FLUSH);   // 一帧一次批量推屏
```

- 内核 `oledfb` 分配 1 页（1024B = 128×64/8）帧缓冲，复用 `kbufdev` 的 **VMA_KBUF** 基础设施（`vma_map_device` + `vma_populate`），驱动只需提供 `file_operations.mmap` 回调设置 `vma->data`，零新内核机制。
- **映射即指针**：用户态拿到的是内核物理页的直接映射，画一整帧不需要任何系统调用，唯一的 syscall 是画完后的 `ioctl(FLUSH)`。
- **边界安全（一个细节坑）**：`mmap(1024)` 会被 `PGROUNDUP` 对齐成 4096 的 VMA。设备校验长度必须用 `vma->valid_end - vma->start` 而非 `end - start`（后者是页对齐后的值，1024 会被拒）。fault 只放行 index 0（帧缓冲页），`≥4096` 的越界写 → SEGV，天然护栏。

### 4.2 批量 I2C DMA 推屏（性能的关键）

SSD1306 走 I2C，总线速率是唯一瓶颈。两种优化叠加：

1. **400kHz 快模式**：DW I2C 控制器按 `(CPU/4)/speed/2` 自动算分频，无需改驱动。全屏刷新 **100kHz→400kHz：约 90ms → 23ms**，直接决定游戏能否 ≥20fps。
2. **一次 FLUSH = 3 条 I2C 消息，主数据走 DMA**：

```
msg[0]  7B   cursor 命令 {0x00, 0x21,0x00,0x7F, 0x22,0x00,0x07}  设列/页地址
msg[1]  1024 {0x40, fb[0..1022]}  控制字节+前 1023 字节 —— DMA 路径
msg[2]  2B   {0x40, fb[1023]}     最后 1 字节（轮询尾）
```

- SSD1306 水平寻址模式：列地址跨页自动递增，整帧可一次数据突发。
- **DMA 为什么必须 staging**：DMA 源要求连续 4096B 页，且每个字节要展开成 32 位 `DATA_CMD` 字（字节 + RESTART/STOP 命令位），DMA 不做格式转换 → 内核先 `kalloc_page()` 把数据排成字再交给 DMA。

**性能实测**：帧循环 `sleep((30-Game_Speed)/12 ticks)` 只占 ~10ms，**全屏 FLUSH ~24ms 才是单帧大头**（→ 优化方向：脏页/局部刷新，见 §7）。

### 4.3 双进程 + 共享内存并发采样（替代线程）

游戏需要"**一边读传感器、一边跑游戏**"。xv6 无 `clone`/pthread，于是用最朴素的内核原语组合：

```c
tilt = mmap(0, 4096, PROT_READ|PROT_WRITE,
            MAP_SHARED|MAP_ANONYMOUS, -1, 0);   // 1 页共享内存
fork();  // 采样子进程 + 游戏父进程

/* 子进程（采样器）：10ms 周期读 MPU6050，写共享页 */
for (;;) { sample_tilt(); sleep(2); }            // sleep 单位=tick，K210=5ms

/* 父进程（游戏）：每帧读 *tilt_state，边缘触发跳跃 */
DinoGame_key_Num = *tilt_state ? KEY_UP : KEY_NONE;
```

- **单写者/单读者、一个对齐的 `int`，刻意无锁**——演示级一致性，word 读写在 RISC-V 上原子。
- 共享的是**采样值**而非帧缓冲：帧缓冲只有游戏进程写，避免画面撕裂。
- **退出语义优雅**：父进程注册 `SIGINT` handler 清屏退出；采样子进程与父进程同进程组，Ctrl+C 的 SIGINT 按默认动作直接杀掉它，无需 quit 标志协调（`ps` 确认无残留）。
- 传感器缺失时游戏照常滚动，只是无跳/无重开输入——**故障降级**，不 panic。

### 4.4 纯整数移植（硬约束下的等价替换）

| 参考实现（FreeRTOS，浮点/libc） | xv6 移植（纯整数） |
|---|---|
| `acos()` 计算倾斜角度 > 90° | `mpu6050_tilt()`：`ax > 2000 LSB` 直接判前倾（±2g，1g=16384 LSB；12° 前倾实测 +3400 LSB，2000 阈值远在噪声之上） |
| `rand()` | 16 位 LCG：`state = state*1103515245 + 12345` |
| `nanosleep()` | `sleep(ticks)`，K210 1 tick = 5ms |
| `pthread` 采样线程 | `fork()` + MAP_SHARED 共享页（见 4.3） |

**验证手段**：`objdump -d` 全量扫描，游戏程序 0 条 FPU 指令（`fadd/fmul/fld/fsd` 等）。这条约束倒逼了对每个浮点用处的整数等价物思考，本身就是个可讲的工程细节。

## 5. 游戏逻辑设计

- **状态机**：封面 → 奔跑（地面/云/恐龙两帧动画）→ 跳跃（上升/下降两相）→ 碰撞 → GAME OVER（显示成绩）→ 前倾重开。
- **边缘触发跳跃**：`Last_key != key` 才跳，即前倾必须从 0→1 变化一次跳一次，**一直前倾不会连跳**。
- **物理**：跳跃用速度表 `Jump_Speed_Arr[]`，最大高度 31px；`Jump_State` 在上升/下降间切换，高度归零复位。
- **碰撞判定**：`height < 16` 且仙人掌横跨恐龙的 `[16,31]` 列区间 → 简化 AABB 碰撞。
- **难度递增**：`Game_Speed = Score/20`，每 6 帧加一分，游戏随分数自动提速（封顶 29）。
- **精灵素材**：12 个位图 + F8x16/F6x8 字体，从参考 `game/OLED.c` 直接提取，只定义在 `game_data.c` 一处（`game_data.h` 纯 extern），**打包进 `libgame.a` 归档按引用提取**——只有真用到游戏符号的程序才链接，普通工具程序零膨胀（实测 `_cat` 12190B → 3339B）。

## 6. 关键调试故事（体现问题定位能力）

> 全部来自实机验证，按时间线，每个都是"现象 → 误判 → 对照实验 → 真根因"的完整闭环。

### 6.1 性能误归因：oledfbtest 比 i2ctest 慢 7 倍

- 现象：`open=40 ticks (200ms)`，一度猜测是"DMA 首次传输慢"。
- 排除：所有 `i2c_transfer` 返回 0，无任何 DMA 超时日志。
- **对照实验定案**：`i2ctest` 用同样的面板、同样的 I2C，初始化只用 `sleep(1)=5ms`，显示完全正常 → 100ms 上电延时是**我加的冗余**。
- 修复：100ms → 5ms，open 从 40 ticks → 4 ticks。**教训：对照实验 > 猜测；逐项审计 open 路径，而不是给整体现象编故事。**

### 6.2 DMA staging 越界写（静默 bug，"没崩"≠"没 bug"）

- 现象：显示正常，但代码审查发现**越界写**——FLUSH 构造 1025 字节消息，而 DMA staging 页 `kalloc_page()` 只有 4096B = 1024 个 32 位字，`buf[1024]` 越界 4 字节。K210 无 MMU 保护裸内存访问，恰好没踩坏关键数据 → 静默通过。
- 修复（双层防御）：调用方拆 3 条消息（DMA 单条正好 1024B）+ 驱动加 `I2C_DMA_MAX_LEN 1024` 守卫，超长回退轮询，**驱动不信任调用方**。

### 6.3 DMA 等待超时窗口装不下毫秒级大帧

- 现象：FLUSH 失败，且紧接着 `i2ctest` probe OLED 也失败——**总线卡死**。
- 根因：`DMAC_WAIT_TIMEOUT 10000` 自旋（~40ns/次）只有 **0.4ms** 窗口，而 400kHz 下全屏 1024B 传输是**毫秒级** → DMA 中途超时返回，事务停在半截（无 STOP）占住总线，后续所有 I2C 全挂。
- 修复：超时扩到 `10000000`（约 400ms，35× 余量）。**教训：自旋超时窗口要以最坏情况传输时间为基准；超时的次生灾害（总线卡死）比超时本身更严重。** 同一段代码在 I2C（慢）与 SPI（快一个数量级）表现完全不同。

### 6.4 `xv6 DINO` 字体乱码：C 数组 stride 陷阱（含两次误判复盘）

- 现象：F8x16 字体正常、F6x8 字体乱码；mmap 写读回、I2C 传输均已逐层排除。
- 误判 #1：怀疑 bit 方向，加 `reverse8`——用上下对称的 `'x'` 判读被误导，换 `'v'`/`'6'` 不对称字形才发现方向本来是对的，移除。
- 误判 #2：怀疑 SD 卡旧镜像——用"同一程序里 F8x16 正常"做对照，证明板上在跑新程序，排除。
- **真根因**：`dino_data.h` 把 `OLED_F6x8` 声明成一维 `[]`，实际定义是 `[][6]`（每字形 6 字节）。编译器索引 `OLED_F6x8[c-' ']` 不乘步长 6，读到相邻字形垃圾。F8x16 正常是因为它的声明带 `[16]`，stride 正确。
- 修复：声明改 `[][6]`，**用反汇编确认生成 `(c-0x20)*6` 步进**才算数。**教训：extern 声明的数组维度必须与定义一致；对称字形会误导判读；"板上行为与构建产物矛盾"先自查代码再怀疑烧录。**

### 6.5 方法论沉淀（可迁移）

量化别猜、对照实验 > 猜测、审查越界要算"字节→字"容量、驱动不信任调用方、分层排除每层一个证据、协议约束画时序图、超时窗口按最坏情况基准。

## 7. 面试问答准备

### 亮点一句话

> 在纯整数约束的教学 OS 上，用"设备 mmap 零拷贝 + I2C DMA 批量推屏 + 双进程共享内存并发采样"打通了一条从 MPU6050 传感器到 OLED 显示的全栈游戏链路，并在实机验证中修掉了 5 个跨层 bug。

### 可能被追问的问题

**Q：为什么用 mmap 而不是 write() 画图？**
答：帧缓冲只有 1KB 且需要高频刷新。write() 每帧都要：用户态→内核拷贝 + 系统调用开销；而 mmap 后用户直接写内核持有的物理页，**画整帧零拷贝、零系统调用**，唯一的 syscall 是画完后的 FLUSH。这就是"零拷贝"在嵌入式显示上的收益——与 Linux fbdev 的 mmap 思路一致。

**Q：为什么双进程而不是线程？**
答：xv6 没有 clone/pthread（在移植范围内的最小内核），fork + MAP_SHARED 匿名页是**零新内核特性**的现成组合。语义上天然是"一个采样生产者、一个游戏消费者"，且进程隔离反而让"传感器挂了不影响游戏"更简单。代价是共享区只有采样值（单 int），需要同步的状态尽量小。

**Q：纯整数限制具体卡了什么？你怎么绕的？**
答：内核不保存 FPU 上下文，浮点指令会 trap。卡住的三处：倾斜角度计算（acos→整数阈值）、随机数（rand→LCG）、休眠（nanosleep→tick）。阈值是实测校准的：平放 ±100 LSB 噪声，12° 前倾 +3400 LSB，取 2000 居中。最后用 objdump 全量验证无浮点指令。

**Q：DMA 为什么要 staging 缓冲？**
答：DMA 源要求**连续**内存且**每字节展开成 32 位命令字**（数据 + RESTART/STOP 位），DMA 引擎不做格式转换。所以内核先用 `kalloc_page` 排好字序列。这引出一个经典 bug：4096B 页 = 1024 个 32 位字，消息 1025 字节就越界——我用拆分消息 + 驱动层守卫双层解决。

**Q：帧率瓶颈在哪？怎么量化？**
答：单帧 = 渲染（<1ms，纯内存写）+ FLUSH（~24ms，I2C 推 1024B）+ sleep（~10ms）。**FLUSH 占大头**，所以当前 ~30fps 的天花板在 I2C 总线。下一步优化是脏页/局部刷新（只推变化行），可把 24ms 摊薄到几 ms。

**Q：为什么 I2C0 提 400kHz？不担心 SSD1306 不支持？**
答：SSD1306 数据手册支持快模式（400kHz），MPU6050 同样兼容。DW 控制器按 `(CPU/4)/speed/2` 自动算分频，改一个板级配置即可。实测全屏刷新从 ~90ms 降到 ~23ms，是游戏可达 fps 的**决定性**优化。

### 可继续深入的方向（表明视野）

- **脏页/局部刷新**：渲染库或 FLUSH 维护 8-bit 脏页掩码，只推变脏页（帧率瓶颈解药）。
- **`clone` + pthread**：真线程替代进程，共享更大状态（但需为 fork 缺的 `CLONE_VM` 补内核支持）。
- **双核并行**：K210 双核，可一核采样/一核渲染 + 共享帧缓冲锁。
