# 内存布局重构方案：用户/内核地址空间分离

日期：2026-08-13

更新：2026-08-25

范围：进程虚拟地址空间布局、内核页表映射、用户栈/堆/mmap 区域划分

目标平台：QEMU 与 K210

状态：设计已确认，后续按本文实施

---

## 1. 目标与已确认决策

本次重构将当前用户空间与内核映射交织的地址布局整理为分离式布局：

- 用户空间为 `[0, MAXUVA)`，按低地址到高地址依次为 ELF、堆、mmap、用户栈。
- 内核镜像仍从 `KERNBASE` 开始恒等映射。
- 设备寄存器映射、进程内核栈、trampoline 等内核结构放到 Sv39 高地址区。
- 用户页与内核映射在 Sv39 L2 页表层分离，`upg2ukpg()` 不再可能覆盖内核或设备 PTE。

已确认的布局决策：

1. `MAXUVA = 0x80000000`，用户地址上限为 2 GiB，上限地址本身不属于用户空间。该边界固定按 1 GiB 对齐，不随平台的 `KERNBASE` 改变。
2. `p->sz` 只表示 ELF 与堆的末尾，不再包含用户栈。
3. 堆紧跟 ELF，从低地址向高地址增长。
4. mmap 采用现代 Linux 常见的 top-down 策略，从用户栈下方往低地址分配。
5. 不设置固定 `MMAP_BASE`；堆与 mmap 共享中间空闲区，并通过动态边界避免碰撞。
6. 用户栈固定在用户空间顶部，预留 1 MiB 虚拟地址区，最低一页作为 guard page。
7. 用户与内核采用 Sv39 L2 完全分离：用户只使用 `L2[0..1]`，内核从 `L2[2]` 开始。

---

## 2. 现有布局与问题

### 2.1 设备映射落在用户 VA 范围内

当前驱动使用 `*_V` 宏访问设备，但多数 `*_V` 与物理地址相同：

- UART0/GPIOHS 位于 `0x38000000` 附近。
- SYSCTL/SPI 位于 `0x50000000~0x54000000`。
- CLINT/PLIC 也使用恒等映射。

这些地址均低于新的用户地址上限，和扩展后的用户空间重叠。进程内核页表中的用户页由 `upg2ukpg()` 同步；如果用户 VA 到达设备地址，现有覆盖写可能破坏设备映射。

### 2.2 mmap 位于内核高地址结构附近

当前 `MMAP_TOP = KSTACK(0)`，`vma_find_address()` 从 trampoline 下方往低地址查找，并以 `PHYSTOP` 为下界。虽然分配方向已经是 top-down，但整个 mmap 区仍位于内核侧高地址区，不属于新的用户布局。

### 2.3 用户栈与 `p->sz`、堆混在一起

`exec()` 当前在 ELF 末尾分配 guard page 和用户栈，并把它们计入 `p->sz`。这会使堆、栈共享同一个连续区间假设，也使 `fork()`、`exec()`、释放页表和懒分配逻辑都默认用户页位于 `[0, p->sz)`。

## 3. 目标内存布局

### 3.1 总体布局图

下图按虚拟地址从低到高排列：

```text
0x0000_0000    ┌────────────────────────────┐
               │ ELF text / data / bss      │
               ├────────────────────────────┤
               │ heap (sbrk)              ↑ │
               ├────────────────────────────┤ ← p->sz
               │                            │
               │       shared unused        │
               │                            │
               ├────────────────────────────┤ ← 最低 VMA；堆的动态上限
               │ 后创建或复用空洞的 mmap VMA │
               ├────────────────────────────┤
               │ 先创建的 mmap VMA         ↓ │
0x7FF0_0000    ├────────────────────────────┤ ← MMAP_TOP / USER_STACK_BOTTOM
               │ guard page（不可映射）      │
0x7FF0_1000    ├────────────────────────────┤
               │ 用户栈，按需分配页面       ↓ │
0x8000_0000    ├────────────────────────────┤ ← USER_STACK_TOP / MAXUVA
               │ 保留、不映射的虚拟地址空洞  │
KERNBASE       ├────────────────────────────┤
               │ 内核 text / data / kalloc  │ ← KERNBASE 因平台而异
0x8060_0000    ├────────────────────────────┤ ← PHYSTOP
               │           unused           │
0x3EC0_0000_00 ├────────────────────────────┤ ← VKSTACK 候选区域
               │ 进程内核栈 / guard page    │
0x3F00_0000_00 ├────────────────────────────┤ ← VIRT_OFFSET
               │ 内核设备映射（PA + offset） │
               │           unused           │
               ├────────────────────────────┤
               │ SIGTRAMP                    │
               ├────────────────────────────┤
               │ TRAPFRAME                   │
0x3F_FFFF_F000 ├────────────────────────────┤ ← TRAMPOLINE
0x40_0000_0000 └────────────────────────────┘ ← MAXVA
```

K210 的保留虚拟地址空洞为 `[0x80000000, 0x80020000)`，QEMU 为 `[0x80000000, 0x80200000)`。这段空洞不属于用户空间，也不需要建立叶子映射。图中高地址仅表达区域顺序，`SIGTRAMP`、`TRAPFRAME` 和 `TRAMPOLINE` 的精确值继续由现有宏按页计算。`VKSTACK` 是否迁移到固定区域可独立实施；保留现有 `KSTACK(p)` 也不影响用户空间方案。

RustSBI 只占用 K210 的物理内存，不是用户虚拟地址布局的一部分：

```text
K210 physical address

0x8000_0000    ┌────────────────────────────┐
               │ RustSBI                    │
0x8002_0000    ├────────────────────────────┤ ← KERNBASE
               │ kernel text / data         │
               │ kalloc managed pages       │
0x8060_0000    └────────────────────────────┘ ← PHYSTOP
```

用户页通过页表映射到 `kalloc` 管理的物理页，不能映射到 RustSBI 的物理范围。内核通过 SBI `ecall` 使用固件服务，不需要在用户页表中映射 RustSBI。

### 3.2 用户区常量

```c
#define MAXUVA              0x80000000L
#define USER_STACK_TOP      MAXUVA
#define USER_STACK_SIZE     (1L << 20)       // 1 MiB virtual reservation
#define USER_STACK_BOTTOM   (USER_STACK_TOP - USER_STACK_SIZE)
#define USER_STACK_GUARD    USER_STACK_BOTTOM
#define MMAP_TOP            USER_STACK_BOTTOM
```

对应地址：

| 名称 | 地址或范围 | 语义 |
| --- | --- | --- |
| `MAXUVA` | `0x80000000` | 用户地址上限，不可访问 |
| 用户栈可用区 | `[0x7ff01000, 0x80000000)` | 从高地址向低地址使用，页面可按需分配 |
| 栈 guard page | `[0x7ff00000, 0x7ff01000)` | 永不映射，用于捕获栈越界 |
| `MMAP_TOP` | `0x7ff00000` | mmap 的固定排他上界 |
| mmap 动态下界 | `PGROUNDUP(p->sz)` | 创建 VMA 时不得越过当前堆顶 |

1 MiB 是虚拟地址预留，不要求一次分配 1 MiB 物理内存。`exec()` 只需建立栈顶初始页，其余可按缺页按需分配。

### 3.3 Sv39 L2 分区

Sv39 顶级页表的每个 L2 项覆盖 1 GiB：

| L2 项 | 地址范围 | 用途 |
| --- | --- | --- |
| `L2[0]` | `[0x00000000, 0x40000000)` | 用户 ELF、堆及共享空闲区 |
| `L2[1]` | `[0x40000000, 0x80000000)` | 用户 mmap 和用户栈 |
| `L2[2]` | `[0x80000000, 0xc0000000)` | 保留虚拟空洞、内核镜像与物理内存恒等映射 |
| `L2[252..253]` | `0x3f00000000` 附近 | 上移后的设备映射 |
| `L2[255]` | Sv39 低半区顶部 | trampoline 等内核结构 |

因此用户 `[0, MAXUVA)` 只占 `L2[0..1]`，内核从 `L2[2]` 开始，二者在 L2 层没有共享项。

清理用户顶级页表项时可以使用：

```c
for(int i = 0; i < PX(2, MAXUVA); i++)
  pagetable[i] = 0;
```

`PX(2, MAXUVA) == 2`，该循环只处理 `L2[0]` 和 `L2[1]`，不会清除内核所在的 `L2[2]`。是否采用整项清理仍应由页表所有权和释放流程决定，不能只因索引安全就直接照搬参考实现。

### 3.4 L2 完全分离决策

本方案明确不采用 `MAXUVA = KERNBASE`。虽然把用户地址延伸到 `KERNBASE` 能额外获得 K210 的 128 KiB 或 QEMU 的 2 MiB 虚拟地址，但会使用户栈和内核映射共同占用 `L2[2]`，导致该顶级页表项不能整体识别、清理或释放。

采用 `MAXUVA = 0x80000000` 后：

- 用户页表生命周期只涉及 `L2[0..1]`。
- 进程内核页表的 `L2[2]` 及以上只承载内核映射。
- `upg2ukpg()` 只要严格检查 `end <= MAXUVA`，就不可能写入内核 L2 分支。
- exec、fork、exit 和页表释放可以使用统一的平台无关边界。
- 放弃的虚拟地址相对 2 GiB 用户空间和约 6 MiB 物理内存没有实际容量价值。

这段保留虚拟空洞的目的仅是顶级页表隔离，不是为 RustSBI 建立页表映射。

### 3.5 核心不变式

```text
0 <= ELF_END <= p->sz <= lowest_vma_start <= MMAP_TOP
MMAP_TOP == USER_STACK_BOTTOM < USER_STACK_TOP == MAXUVA
所有 VMA 均满足：PGROUNDUP(p->sz) <= vma.start < vma.end <= MMAP_TOP
用户页只位于 [0, MAXUVA)
MAXUVA == 0x80000000 < KERNBASE
用户叶子 PTE 不得出现在 L2[2] 及以上
```

guard page 属于预留栈区，但始终保持无有效叶子 PTE。

## 4. 分项设计

### 4.1 引入用户地址上限

在 `memlayout.h` 中引入固定的 `MAXUVA` 和用户栈常量。`MAXUVA` 不能定义成 `KERNBASE`，也不能因 QEMU/K210 平台不同而变化。所有来自用户态的地址与区间都必须满足：

```text
va < MAXUVA
len <= MAXUVA - va
```

先做减法式边界检查，避免 `va + len` 溢出。

### 4.2 设备映射上移

引入：

```c
#define VIRT_OFFSET 0x3F00000000L
```

设备虚拟地址统一定义成 `物理地址 + VIRT_OFFSET`，包括 UART、GPIOHS、DMAC、GPIO、FPIOA、SYSCTL、SPI、I2C、CLINT、PLIC，以及 QEMU 的 VIRTIO。

改动要求：

- `kernel/vm/vm.c` 的 `kvmmap()`、`ukvmmap()`、`ukvmunmap()` 使用对应 `*_V` 虚拟地址。
- PLIC 驱动中寄存器地址统一从 `PLIC_V` 派生，不能混用物理地址。
- QEMU 和 K210 分支都必须检查，不能只修改 K210 外设。
- 驱动继续通过 `*_V` 访问寄存器，避免在驱动实现中散落偏移计算。

### 4.3 用户栈移到用户空间顶部

用户栈使用固定预留区 `[USER_STACK_BOTTOM, USER_STACK_TOP)`：

- `exec()` 在 `USER_STACK_TOP - PGSIZE` 建立初始栈页，初始 `sp = USER_STACK_TOP`。
- `[USER_STACK_GUARD, USER_STACK_GUARD + PGSIZE)` 永不映射。
- 其余栈页可在缺页时按需分配，但只能位于栈可用区。
- `p->sz` 在加载 ELF 后页对齐，之后只表示 ELF 与堆，不包含栈。

栈离开 `[0, p->sz)` 后，不能继续依赖按连续区间处理全部用户页的接口。应提供集中式栈区辅助函数，分别负责：

- 创建初始栈页。
- 判断地址是否属于可分配栈区。
- fork 时复制已存在的栈页。
- exec/exit 时解除用户页表和进程内核页表中的栈映射。
- 在 `upg2ukpg()` 同步点同步实际存在的栈页。

受影响位置至少包括 `exec()`、`uvmcopy()`/fork、`proc_freepagetable()`、exec 旧空间清理、缺页处理、`copyin()`/`copyout()` 触发的 `faultin_page()` 和信号帧压栈。

### 4.4 mmap 在用户空间自高向低分配

`mmap(NULL, length, ...)` 的默认分配规则：

1. 将 `length` 向上按页对齐。
2. 在 `[PGROUNDUP(p->sz), MMAP_TOP)` 中寻找能够容纳该长度的最高地址空洞。
3. 返回空洞的低地址作为 VMA `start`。
4. 后续映射继续优先选择当前最高可用空洞；`munmap()` 产生的高地址空洞可以被复用。
5. 找不到完整空洞时返回失败，不跨越堆、栈 guard 或 `MAXUVA`。

`vma_find_address()` 不能遇到任意一个重叠 VMA 后就直接跳到它的起点，否则 VMA 数组无序时可能跳过可用空洞。实现应在每轮选择与候选区间重叠且 `start` 最高的 VMA，或者先按地址排序后执行 top-down gap search。

本项目 `NVMA == 16`，直接扫描全部 VMA 寻找最高冲突项即可，没必要引入树结构。

需要删除的旧约束：

```c
if(start < PHYSTOP)
  return 0;
```

物理地址 `PHYSTOP` 不能作为用户虚拟地址分配边界。新的动态下界是 `PGROUNDUP(p->sz)`。

### 4.5 堆与 mmap 的碰撞规则

`vma_heap_limit()` 返回所有 VMA 中最低的 `start`；没有 VMA 时返回 `MMAP_TOP`：

```text
heap_limit = min(lowest_vma_start, MMAP_TOP)
```

`growproc(n > 0)` 必须保证新 `p->sz <= heap_limit`。创建 mmap 时又必须保证 `vma.start >= PGROUNDUP(p->sz)`。这两个检查形成双向约束：

- 已存在的 mmap 阻止堆向上侵入。
- 已存在的堆阻止 mmap 向下侵入。

堆和 mmap 之间不额外保留固定 guard page；页对齐和区间碰撞检查已经足以保证隔离。

### 4.6 mmap 地址参数范围

当前实现只接受 `addr == 0`，本次重构保持该语义，不顺带实现 `MAP_FIXED` 或完整的地址 hint。

`munmap()` 的系统调用入口检查应保证 `addr < MMAP_TOP`、区间计算无溢出且至少命中一个 VMA。不能用当前 `p->sz` 直接拒绝旧 VMA，因为 VMA 创建之后堆大小可能缩小；堆/VMA 不相交由创建和 `growproc()` 不变式保证。

## 5. 实施计划

### 阶段 1：建立地址边界

- 新增 `MAXUVA`、用户栈和 mmap 上界常量。
- 补齐用户地址及区间的上限检查。
- 验证 QEMU/K210 构建。

成功标准：任何用户区间都不能到达 `MAXUVA` 及以上；用户映射只占 `L2[0..1]`，内核映射从 `L2[2]` 开始。

### 阶段 2：上移设备映射

- 引入 `VIRT_OFFSET` 和全部 `*_V` 宏。
- 修改内核页表与进程内核页表的设备映射。
- 修正直接使用设备物理地址的驱动代码。

成功标准：内核只能通过高虚拟地址访问设备；QEMU 可启动，K210 可构建并通过外设路径检查。

### 阶段 3：迁移用户栈

- `exec()` 在 `USER_STACK_TOP` 下方创建初始栈页。
- 将栈的复制、释放、kpagetable 同步和缺页处理从 `[0, p->sz)` 连续区间逻辑中拆出。
- 保证 guard page 永不映射。

成功标准：exec、fork、exit、信号压栈正常；栈按需增长；越过 guard 后进程被终止且无页表泄漏或 `freewalk()` panic。

### 阶段 4：mmap 移入用户空间

- `MMAP_TOP` 改为 `USER_STACK_BOTTOM`。
- 保留 top-down 方向，将下界从 `PHYSTOP` 改为动态堆顶。
- 修正最高空洞查找与 `munmap()` 边界。
- 保持文件、匿名和设备 VMA 的 fault/populate 行为不变。

成功标准：首次 mmap 位于栈区下方，后续 mmap 向低地址分配或复用高地址空洞；堆与 mmap 双向碰撞均返回失败。

### 阶段 5：收口与清理

- 检查所有 `[0, p->sz)` 假设，只保留确实属于 ELF/堆的用途。
- 检查用户页表和进程内核页表的创建、同步、切换与释放是否成对。
- 更新正式测试与架构说明。

## 6. 验证方案

### 6.1 构建与基础运行

- `make build platform=qemu`
- `make fs`
- `make run platform=qemu`
- `make build platform=k210`

运行 `init`、`sh`、fork/exec/exit 循环，确认没有页表释放 panic。

### 6.2 布局与边界测试

- 首个 mmap 的结束地址不超过 `MMAP_TOP`。
- 连续 mmap 返回逐渐降低的地址。
- `munmap()` 高地址 VMA 后，新 mmap 优先复用该空洞。
- 堆增长到最低 VMA 起点时失败。
- 大 mmap 向下到达当前堆顶时失败。
- 所有用户映射均低于 `MAXUVA`。

### 6.3 栈测试

- exec 参数能正确压入顶部栈页。
- fork 后父子进程栈内容独立且可继续执行。
- 深层递归逐页触发栈分配。
- 访问固定 guard page 或越过 `USER_STACK_BOTTOM` 时进程被终止。
- signal frame 跨入未分配栈页时能够正常补页。

### 6.4 设备与双页表测试

- QEMU UART、virtio、PLIC/CLINT 正常。
- K210 UART、SD、SPI、I2C、GPIOHS、DMAC 等路径至少完成构建与地址审查。
- `procdump` 和多进程并发下，用户页同步不会覆盖设备、内核或 trampoline 映射。

## 7. 本次不处理的内容

- 不实现 ASLR。
- 不实现 `MAP_FIXED`、`MAP_FIXED_NOREPLACE` 或完整的非零地址 hint。
- 不引入 Linux 的 maple tree/RB tree；继续使用固定大小 VMA 数组。
- 不在本次布局重构中改变 mmap backing object、COW 或文件回写语义。
- 不强制同时迁移 `KSTACK(p)` 到 `VKSTACK`；该项可以作为独立内核地址布局改动。
