# 文件与设备操作抽象重构方案

日期：2026-07-12  
范围：`kernel/fs/file.c`、`kernel/syscall/sysfile.c`、`kernel/devsw/`、总线控制器驱动及相关用户态接口  
目标平台：QEMU 与 K210

---

## 1. 重构目标

当前项目已经具备 `fd -> struct file -> 普通文件/管道/设备` 的基本框架，但设备操作仅包含 `read`、`write` 和 `ioctl`，没有完整表达设备的打开、关闭、每次打开状态以及设备与硬件控制器的绑定关系。

本次重构参考 Linux 的 `file_operations`、打开文件描述对象和总线设备模型，但只实现适合 xv6 的核心子集，不引入完整 VFS、inode 设备节点、device tree、driver core 或 sysfs。目标如下：

1. 建立统一的 `open/read/write/ioctl/close` 文件操作抽象。
2. 让一次设备打开拥有明确的生命周期和私有状态。
3. 使 `dup()`、`fork()` 和 `close()` 具有正确的共享与引用计数语义。
4. 区分控制器、挂载设备和打开实例，消除从 `minor` 位域推导总线参数的做法。
5. 将 SPI/I2C 设备与控制器、片选或从机地址的绑定放在内核板级描述中。
6. 集中处理控制器锁、硬件配置和传输串行化。
7. 第一阶段保持现有 `dev(flags, major, minor)` 用户 ABI，降低迁移风险；后续再统一为 `/dev/*` 路径打开。

---

## 2. 当前实现的问题

### 2.1 设备操作集不完整

当前 `struct devsw` 只有：

```c
struct devsw {
  int (*read)(int, uint64, int);
  int (*write)(int, uint64, int);
  int (*ioctl)(int, uint64, uint64);
};
```

因此：

- `sys_dev()` 分配文件后不会通知驱动执行打开。
- `fileclose()` 对设备不执行资源释放。
- 驱动无法建立每次打开的上下文。
- 打开时无法统一校验 `minor`、访问模式和设备能力。

### 2.2 设备 read/write 调用参数错误

`fileread()` 和 `filewrite()` 当前以硬编码的 `1` 调用设备：

```c
devsw[f->major].read(1, addr, n);
devsw[f->major].write(1, addr, n);
```

这个值实际表达用户地址标志，不包含 `minor`，设备也无法获得 `struct file`、文件位置或私有数据。`ioctl` 又单独传递 `minor`，形成不一致的接口约定。

### 2.3 设备状态归属不清晰

SD 卡的当前位置是全局变量，两个独立打开会互相影响。SPI 使用全局收发缓冲区，I2C 将时钟配置保存在总线级数组中，也没有完整的并发保护。

正确语义应为：

- 两次独立打开拥有独立的 per-open 状态。
- `dup()` 和 `fork()` 共享同一个 `struct file`，因而共享文件位置和 per-open 状态。
- 最后一个引用关闭时才执行驱动 `close()`。
- 控制器寄存器、DMA 和传输缓冲属于控制器级共享资源，由控制器锁保护。

### 2.4 minor 混合了设备身份和硬件拓扑

当前 SPI 通过：

```c
spi_device_num_t spi_bus = SPI_MINOR_BUS(minor);
spi_chip_select_t chip_sel = SPI_MINOR_CS(minor);
```

从 `minor` 解码控制器和片选；I2C 则通过：

```c
i2c_device_number_t i2c_bus = I2C_BUS(minor);
```

选择控制器，再由 `I2C_IOCTL_INIT` 从用户态传入从机地址和频率。这会造成：

- 用户程序必须了解板级接线。
- `minor` 不是稳定的逻辑设备身份。
- 总线、片选、地址和频率没有形成可验证的绑定对象。
- 同一个 fd 可以在运行期被重新解释成不同硬件设备。
- 板级接线变化会迫使用户程序修改。

### 2.5 open flags 校验分散

`sys_open()` 和 `sys_dev()` 分别解析 `omode`，没有统一拒绝非法访问模式和不支持的标志。由于 `O_RDONLY` 为零，任何 `flags & O_RDONLY` 判断都恒为假，访问模式必须通过 `flags & O_ACCMODE` 后显式比较。

## 3. 设计原则

### 3.1 对象职责分离

目标模型包含四类对象：

```text
进程 fd
  │
  ▼
struct file（一次打开实例，可被 dup/fork 共享）
  │
  ▼
struct device（逻辑设备，如 W25Q64、OLED、MPU6050）
  │
  ▼
struct spi_controller / i2c_controller（物理总线控制器）
  │
  ▼
K210 寄存器、DMA、GPIO/FPIOA
```

- `struct file`：一次打开的生命周期、权限、位置和私有上下文。
- `struct device`：major/minor 对应的逻辑设备及文件操作集。
- 总线设备对象：逻辑外设与控制器、CS/地址及约束的绑定。
- controller：控制器共享资源、锁和实际传输执行。

### 3.2 minor 只标识逻辑设备

重构后：

```text
major = 设备类别
minor = 该类别中的逻辑设备实例
```

例如：

| major | minor | 逻辑设备 | 内核绑定 |
|---|---:|---|---|
| `DEV_SPI` | 0 | W25Q64 | SPI1 + CS0 |
| `DEV_SPI` | 1 | LCD | SPI0 + CS2 |
| `DEV_I2C` | 0 | OLED | I2C0 + 0x3c |
| `DEV_I2C` | 1 | MPU6050 | I2C0 + 0x68 |

不再将 bus 和 CS 编码进 minor，也不让普通设备通过 ioctl 设置 I2C 地址。

### 3.3 控制器绑定是内核板级信息

控制器编号、CS、I2C 地址、最大频率和默认模式属于硬件描述，应在内核板级设备表中声明。用户态只选择逻辑设备并提交数据传输。

### 3.4 ioctl 只修改允许变化的运行属性

ioctl 不再承担“创建设备绑定”或“初始化设备身份”的职责。它可以用于：

- 查询设备状态。
- 修改当前打开允许变化的 SPI mode 或 speed。
- 提交结构化 SPI/I2C 传输。
- 执行设备特有控制命令。

bus、CS 和固定 I2C 地址不得由普通设备 fd 修改。

## 4. 统一文件操作抽象

### 4.1 file_operations

建议以 `struct file *` 作为所有设备回调的第一个参数：

```c
struct file;

struct file_operations {
  int (*open)(struct file *f);
  int (*read)(struct file *f, uint64 dst, int n);
  int (*write)(struct file *f, uint64 src, int n);
  int (*ioctl)(struct file *f, uint64 cmd, uint64 arg);
  int (*close)(struct file *f);
};
```

这里的 `dst/src` 仍是用户虚拟地址，驱动使用 `copyin/copyout` 或 `either_copyin/either_copyout`。不再把 `user_dst/user_src` 作为与设备身份混杂的整数参数。

### 4.2 struct file 扩展

```c
struct file {
  enum { FD_NONE, FD_PIPE, FD_ENTRY, FD_DEVICE } type;
  int ref;
  char readable;
  char writable;

  struct pipe *pipe;
  struct dirent *ep;
  uint off;

  short major;
  short minor;
  const struct file_operations *ops;
  void *private_data;
};
```

- `ops` 在设备打开时绑定，后续不再反复索引全局设备表。
- `private_data` 保存 per-open 上下文或对应的静态设备对象。
- 对普通文件和管道，新增字段保持为空。

### 4.3 设备注册对象

```c
struct device {
  const char *name;
  const struct file_operations *ops;
};

int device_register(int major, const char *name,
                    const struct file_operations *ops);
const struct device *device_get(int major);
```

注册时检查 major 范围、重复注册和空操作表。各驱动不再直接逐项修改全局 `devsw[]`。

第一阶段仍可用固定大小数组保存注册项，不需要动态 driver core。

## 5. 文件操作调用流程

### 5.1 设备打开

增加内部接口：

```c
int fileopen_device(struct file *f, int major, int minor, int flags);
```

执行顺序：

1. 解析并校验访问模式。
2. 查找已经注册的 major。
3. 初始化 `struct file` 公共字段并设置 `f->ops`。
4. 调用 `f->ops->open(f)`。
5. 驱动根据逻辑 minor 查找设备对象并设置 `private_data`。
6. 驱动打开失败时回收全部资源。
7. 设备打开成功后再安装到进程 fd 表。

应避免先安装 fd、后调用驱动 open，从而减少失败回滚路径。

### 5.2 read/write/ioctl

系统调用层只负责获取参数和 fd；具体类型分发集中在文件层：

```c
int fileread(struct file *f, uint64 addr, int n);
int filewrite(struct file *f, uint64 addr, int n);
int fileioctl(struct file *f, uint64 cmd, uint64 arg);
```

设备路径分别调用：

```c
f->ops->read(f, addr, n);
f->ops->write(f, addr, n);
f->ops->ioctl(f, cmd, arg);
```

由文件层统一检查：

- `n >= 0`。
- fd 是否可读或可写。
- 操作回调是否存在。
- 文件类型是否支持该操作。

### 5.3 close 和引用计数

`dup()` 和 `fork()` 只增加 `struct file::ref`，不重复调用设备 open。`close(fd)` 移除进程 fd，只有最后一个引用释放时才调用设备 close。

驱动 close 必须在 `ftable.lock` 外执行，避免驱动释放资源、睡眠或获取其他锁时持有全局文件表锁。

首版可以延续当前复制栈上 `struct file ff` 的方式，并规定 `close()`：

- 只能读取传入文件字段并释放 `private_data`。
- 不得保存传入的 `struct file *`。
- 不得假设该指针仍位于全局文件表。

## 6. 控制器与设备绑定模型

### 6.1 SPI 控制器

```c
struct spi_controller {
  spi_device_num_t bus_num;
  struct spinlock lock;
  int initialized;
};
```

控制器接口：

```c
int spi_controller_transfer(struct spi_controller *ctl,
                            const struct spi_device *dev,
                            const struct spi_file_context *ctx,
                            struct spi_transfer *xfers,
                            int nxfers);
```

控制器层负责：

1. 获取该 SPI 控制器的总线锁。
2. 按本次设备和打开实例配置 mode、频率、位宽。
3. 选择设备绑定的 CS。
4. 执行 DMA 或轮询传输。
5. 恢复必要状态并释放锁。

全局 SPI 收发缓冲必须被同一控制器锁覆盖整个“填充、传输、拷出”周期，或者改为每次请求独立分配。

### 6.2 SPI 设备

```c
struct spi_device {
  const char *name;
  int minor;
  struct spi_controller *controller;
  spi_chip_select_t chip_select;
  uint32 max_hz;
  uint8 mode;
  uint8 bits_per_word;
};
```

板级绑定示例：

```c
static struct spi_device spi_devices[] = {
  {
    .name = "w25q64",
    .minor = SPI_DEV_W25Q64,
    .controller = &spi_controllers[1],
    .chip_select = SPI_CHIP_SELECT_0,
    .max_hz = 10000000,
    .mode = SPI_WORK_MODE_0,
    .bits_per_word = 8,
  },
};
```

### 6.3 SPI 打开实例

若只使用固定配置，`f->private_data` 可直接指向静态 `spi_device`。若允许每个 fd 调整 mode 或速度，则分配：

```c
struct spi_file_context {
  const struct spi_device *device;
  uint32 speed_hz;
  uint8 mode;
  uint8 bits_per_word;
};
```

open 时复制默认值，close 时释放。允许写入的速度不得超过 `device->max_hz`；bus 和 CS 不允许修改。

原有 `SPI_IOCTL_INIT` 应删除，改为默认配置以及可选的属性读写命令，例如：

```text
SPI_IOC_RD_MODE
SPI_IOC_WR_MODE
SPI_IOC_RD_MAX_SPEED_HZ
SPI_IOC_WR_MAX_SPEED_HZ
SPI_IOC_MESSAGE
```

### 6.4 I2C 控制器

```c
struct i2c_controller {
  i2c_device_number_t bus_num;
  struct spinlock lock;
  int initialized;
};
```

控制器接口：

```c
int i2c_controller_transfer(struct i2c_controller *ctl,
                            const struct i2c_device *dev,
                            struct i2c_msg *msgs,
                            int nmsgs);
```

同一 I2C 控制器上的 OLED、MPU6050 等设备共享控制器锁，每次传输在锁内按目标设备设置地址和频率。

### 6.5 I2C 设备

```c
struct i2c_device {
  const char *name;
  int minor;
  struct i2c_controller *controller;
  uint16 address;
  uint32 max_hz;
};
```

板级绑定示例：

```c
static struct i2c_device i2c_devices[] = {
  {
    .name = "oled",
    .minor = I2C_DEV_OLED,
    .controller = &i2c_controllers[0],
    .address = 0x3c,
    .max_hz = 400000,
  },
  {
    .name = "mpu6050",
    .minor = I2C_DEV_MPU6050,
    .controller = &i2c_controllers[0],
    .address = 0x68,
    .max_hz = 400000,
  },
};
```

普通逻辑设备的传输消息不再允许用户指定其他从机地址。内核将消息地址统一设置为 `device->address`，原有 `I2C_IOCTL_INIT` 删除。

### 6.6 可选的原始总线接口

如果测试和调试确实需要 Linux `/dev/i2c-N` 或通用 spidev 语义，应将其注册为独立的 raw bus 设备：

```text
/dev/i2c-0       原始 I2C0，总线消息可以携带地址
/dev/spidev1.0   原始 SPI1 CS0，可设置受限传输属性
/dev/mpu6050     固定绑定 I2C0 + 0x68
/dev/w25q64      固定绑定 SPI1 + CS0
```

原始总线接口与具体逻辑设备不能复用同一种 minor 语义。产品应用优先使用具体设备，raw bus 只用于诊断或尚未实现专用驱动的场景。

## 7. 板级设备描述

当前项目没有设备树，首版使用静态板级描述表。建议新增：

```text
kernel/board/k210_devices.c
kernel/board/qemu_devices.c
kernel/include/device.h
kernel/include/spi_device.h
kernel/include/i2c_device.h
```

设备描述表应为具有完整生命周期的 `static const` 数组。注册函数可以复制描述，也可以长期引用静态数组，但不能保存栈对象或临时复合字面量的地址。

建议初始化顺序：

```text
底层时钟/FPIOA/DMAC 初始化
        ↓
SPI/I2C controller 初始化
        ↓
板级逻辑设备注册与绑定
        ↓
字符设备 file_operations 注册
        ↓
用户进程启动
```

QEMU 不具备的 K210 设备不应注册，公共文件层仍需正常构建。平台差异通过构建文件或 `#ifdef QEMU` 限制在板级描述和底层控制器层，避免扩散到系统调用层。

## 8. 各设备迁移方案

### 8.1 Console

- open 校验 `minor == 0`。
- 通常不分配 per-open 状态。
- console mode、波特率和 RX ring 属于终端设备级状态，多个 fd 共同观察。
- close 无特殊资源时留空。

### 8.2 Stats

- open 阶段拒绝包含写权限的模式。
- 只提供 read，未实现操作统一返回失败。

### 8.3 SD 卡

每次打开分配：

```c
struct sdcard_file_context {
  uint32 sector;
};
```

- open 将 sector 初始化为零。
- read/write 使用并递增该上下文的位置。
- SEEK/TELL 操作该打开实例，而不是全局变量。
- close 释放上下文。
- NSECTORS 属于设备级查询。
- INVALIDATE_CACHE 属于全局副作用操作，需要清楚记录并加适当锁。

SD 卡应作为验证 per-open、dup、fork 和最后引用关闭语义的首要设备。

### 8.4 SPI

- minor 查找逻辑 `spi_device`，不再解码 bus/CS。
- open 将静态设备绑定及默认传输参数放入 `private_data`。
- ioctl 只提交消息或修改允许变化的 per-open 参数。
- controller 层在总线锁内应用配置和执行传输。
- close 释放打开上下文。

### 8.5 I2C

- minor 查找逻辑 `i2c_device`，不再等同于 bus。
- 地址、控制器和最大频率来自板级绑定。
- 删除总线级 `saved_clk_rate[]` 和 `I2C_IOCTL_INIT`。
- 普通逻辑设备传输不能越过绑定访问其他地址。
- controller 层负责总线锁和每次传输前的硬件配置。

## 9. 用户接口演进

### 9.1 第一阶段：保持 dev() ABI

暂时保留：

```c
dev(flags, major, logical_minor);
```

例如：

```c
dev(O_RDWR, DEV_SPI, SPI_DEV_W25Q64);
dev(O_RDWR, DEV_I2C, I2C_DEV_MPU6050);
```

`dev()` 内部改走统一的 `fileopen_device()`。现有应用只需替换 minor 常量并删除 INIT ioctl，不必同时引入设备文件系统。

### 9.2 第二阶段：提供 /dev 路径

通过静态名称映射支持：

```c
open("/dev/console", O_RDWR);
open("/dev/w25q64", O_RDWR);
open("/dev/oled", O_RDWR);
open("/dev/mpu6050", O_RDWR);
```

路径解析结果映射到 major/minor，再复用 `fileopen_device()`。首版无需在 FAT32 中实现 Linux 式字符设备 inode。

待所有调用方迁移后，再决定是否废弃 `dev()` 系统调用。

## 10. flags 与错误处理

增加访问模式掩码：

```c
#define O_ACCMODE 0x003
```

统一解析：

```c
switch(flags & O_ACCMODE) {
case O_RDONLY:
  readable = 1;
  writable = 0;
  break;
case O_WRONLY:
  readable = 0;
  writable = 1;
  break;
case O_RDWR:
  readable = 1;
  writable = 1;
  break;
default:
  return -1;
}
```

第一阶段继续统一返回 `-1`，但必须保证：

- 未注册 major、未知逻辑 minor 和非法 flags 打开失败。
- 只读设备在 open 阶段拒绝写模式。
- 缺失操作返回失败，不触发 panic。
- open 失败不占用 fd、不泄漏 `struct file/private_data`。
- close 即使驱动清理失败，也不能遗留进程 fd。
- ioctl 命令使用 `uint64`，避免编码扩展时被 `int` 截断。

## 11. 锁与生命周期规则

建议固定以下锁顺序和边界：

1. `ftable.lock` 只保护文件对象分配和引用计数，不在持锁期间调用驱动。
2. controller lock 保护一个物理 SPI/I2C 控制器的寄存器、DMA 通道使用和共享传输缓冲。
3. 设备级锁只保护该逻辑设备的共享状态，不替代 controller lock。
4. per-open 上下文通常由共享同一个 `struct file` 的调用方访问；涉及可变位置或配置时需要文件级锁或设备明确的串行规则。
5. 不在持有 spinlock 时执行可能睡眠的 `copyin/copyout` 或阻塞 I/O；若控制器传输可能睡眠，应使用适合该内核调度模型的 sleep lock。

SPI/I2C 传输需要进一步核对底层 DMA 实现是否睡眠，再选择 spinlock 或 sleeplock。不能仅因为当前函数是同步接口就默认可以全程持有 spinlock。

## 12. 推荐实施步骤

### 阶段一：公共文件层

1. 增加 `file_operations`、`ops` 和 `private_data`。
2. 实现设备注册与查询接口。
3. 实现统一 flags 解析。
4. 增加 `fileopen_device()` 和 `fileioctl()`。
5. 修正设备 read/write 分发，删除硬编码参数 `1`。
6. 在最后一个文件引用释放时调用设备 close。

### 阶段二：简单设备验证

1. 迁移 console。
2. 迁移 stats。
3. 迁移 SD 卡并实现 per-open sector。
4. 验证 open/dup/fork/close 生命周期。

### 阶段三：控制器与绑定层

1. 建立 SPI/I2C controller 对象及控制器锁。
2. 建立 K210 板级逻辑设备描述表。
3. 将 minor 改为逻辑设备编号。
4. 在 open 时完成 `file -> logical device -> controller` 绑定。

### 阶段四：SPI/I2C 迁移

1. 删除 `SPI_MINOR_BUS/SPI_MINOR_CS/I2C_MINOR_BUS` 在设备操作路径中的使用。
2. 删除 `SPI_IOCTL_INIT` 和 `I2C_IOCTL_INIT`。
3. 将可变 SPI 参数放到 per-open 上下文。
4. 将固定 I2C 地址放到设备描述。
5. 所有硬件传输统一经过 controller 层。
6. 更新应用、libc 和测试用例。

### 阶段五：统一设备路径

1. 增加 `/dev/*` 静态名称映射。
2. 让 `open()` 和 `dev()` 复用相同设备打开实现。
3. 迁移用户程序到 `open("/dev/...")`。
4. 评估是否废弃 `dev()`。

每个阶段完成后分别构建 QEMU 和 K210，避免在一次提交中同时改变文件生命周期、驱动并发和用户 ABI。

## 13. 验证要求

### 13.1 文件生命周期

- 两次独立打开 SD 卡具有独立 sector。
- `dup(fd)` 后两个 fd 共享 sector 和 per-open 配置。
- `fork()` 后父子进程共享同一打开实例。
- 关闭一个共享 fd 不触发设备 close。
- 最后一个引用关闭时恰好调用一次设备 close。
- 驱动 open 失败后 `NFILE/NOFILE` 配额不泄漏。

### 13.2 权限与错误路径

- 非法 major/minor 打开失败。
- stats 等只读设备拒绝写方式打开。
- 未实现的 read/write/ioctl 返回失败而不是 panic。
- 不支持的 flags 和 ioctl 命令稳定返回失败。
- 用户指针 copyin/copyout 失败时释放临时内存和锁。

### 13.3 设备绑定

- W25Q64 只通过绑定的 SPI controller 和 CS 访问。
- OLED 和 MPU6050 可共享 I2C0，但各自使用固定地址。
- 普通 I2C 逻辑设备不能通过消息访问其他从机地址。
- 修改板级绑定后用户程序不需要修改 bus/CS/address 参数。

### 13.4 并发

- 同一 SPI 控制器上的两个设备并发传输不会交叉配置或覆盖缓冲。
- 同一 I2C 控制器上的两个设备并发传输被正确串行化。
- 不同控制器在硬件允许时可以并行工作。
- ioctl 失败路径不会遗留 controller lock。

### 13.5 构建与平台

- `make build platform=qemu` 通过。
- `make build platform=k210` 通过。
- K210 专有设备未注册时不影响 QEMU 公共文件层。
- 更新设备测试程序后运行 SPI、I2C、SD 卡和 console 对应测试。

## 14. 首轮不实现的内容

为控制重构范围，首轮不实现：

- Linux 完整 VFS、inode/dentry superblock 模型。
- 动态设备树解析。
- sysfs、udev 和驱动热插拔。
- 完整 errno 体系。
- poll/select/epoll 和异步 I/O。
- 通用 seek 操作；首轮仍可保留设备专用 ioctl，后续再评估 `llseek`。
- 完整 Linux spidev/i2c-dev ABI 兼容。

这些能力可以在统一文件操作和设备绑定模型稳定后按实际需求增加。

## 15. 最终约束

本方案的核心约束如下：

```text
minor 只识别逻辑设备
设备对象保存板级硬件绑定
open 建立 file 与设备对象的关系
private_data 保存每次打开状态
controller 负责锁、配置和实际传输
ioctl 只控制允许变化的运行属性
最后一个 file 引用释放时才执行设备 close
```

按照这一模型重构后，用户程序不再需要知道 W25Q64、OLED 或 MPU6050 连接在哪个控制器、哪个 CS 或哪个 I2C 地址；板级接线变化集中修改设备描述表，文件生命周期、设备身份和控制器资源也具有清晰边界。
