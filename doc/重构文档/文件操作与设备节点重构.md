日期：2026-07-28  
涉及范围：
- 第一轮：`kernel/fs/file.c`、`kernel/syscall/sysfile.c`、`kernel/include/file.h`
- 第二轮：`kernel/fs/fat32.c`、`kernel/include/fat32.h`、`kernel/device.c`、`kernel/include/device.h`、`kernel/syscall/sysfile.c`、`kernel/syscall/syscall.c`、`user/init.c` + 用户态测试程序

## 第一轮：文件操作层剥离（sysfile.c → file.c）

### 目标

将文件操作业务逻辑从系统调用层下沉到 `fs/file.c`，让 `syscall/sysfile.c` 只保留参数提取和 fd 分配的"胶水"职责。

### 重构前状态

```c
// sysfile.c 混合了参数提取 + 业务逻辑
uint64 sys_read(void) {
    // argfd + fileread     ← 少量胶水
}
uint64 sys_write(void) {
    // argfd + filewrite     ← 少量胶水
}
uint64 sys_close(void) {
    // argfd + fileclose     ← 少量胶水
}
uint64 sys_ioctl(void) {
    // argfd + fileioctl     ← 少量胶水
}
uint64 sys_open(void) {
    // argstr + argint + file_parse_access_mode
    // + device_path_lookup + create/ename
    // + filealloc + fdalloc + file_setup
    // ← 60 行，混合了大量业务逻辑
}
```

### 改动

#### 1. `fs/file.c` 新增 `fileopen()`

将 `sys_open` 中的路径解析、设备路径检查、目录项创建/查找、file 初始化逻辑提取为：

```c
int fileopen(struct file *f, const char *path, int omode)
```

- 接收已分配的 `struct file*`，初始化后返回
- 内部调用 `device_path_lookup()`（当时还存在）判断设备路径
- 处理 FAT32 目录项的创建和查找
- 错误路径自行清理 dirent 资源

#### 2. `create()` 从 static 导出

`create()` 原本是 `sysfile.c` 中的 static 函数，被 `sys_open` 和 `sys_mkdir` 使用。改为非 static 并声明到 `fat32.h`，以便 `file.c` 也能调用。

#### 3. `sys_open` 简化为薄层

```c
uint64 sys_open(void) {
    // argstr + argint           ← 参数提取
    // filealloc + fileopen()    ← 委派
    // fdalloc                   ← fd 分配
}
```

#### 4. `sys_dev` 同步简化

去掉对 `devicefdalloc` 的依赖，改为 `filealloc + fileopen_device + fdalloc` 模式。`devicefdalloc` 静态函数删除。

### 分层变化

```
重构前:                             重构后:
syscall/sysfile.c                  syscall/sysfile.c
  sys_read: argfd + fileread         sys_read: argfd → fileread
  sys_write: argfd + filewrite       sys_write: argfd → filewrite
  sys_close: argfd + fileclose       sys_close: argfd → fileclose
  sys_ioctl: argfd + fileioctl       sys_ioctl: argfd → fileioctl
  sys_open: 60行混合逻辑              sys_open: 25行薄层
                                        ↓
                                     fs/file.c
                                       fileread/filewrite/fileclose/fileioctl
                                       fileopen()  ← 新的下沉函数
```

## 第二轮：设备节点重构（sys_dev → mknod）

### 目标

去掉 `device_path_lookup()` 硬编码设备路径表和 `sys_dev` 专用系统调用，改为 Unix 标准的 `mknod + open` 模式，统一路径解析。

### 重构前状态

```
sys_mknod()  → 返回 -1 (stub，说"use sys_dev instead")

设备节点不是 FAT32 文件系统中的目录项，而是编译期数组：
  static const struct device_path device_paths[] = {
      { "/dev/console", DEV_CONSOLE, 0 },
      { "/dev/stats",   DEV_STATS,   0 },
      ...
  };

open("/dev/console")
  → device_path_lookup() 查数组 → 匹配 → fileopen_device()

sys_dev(major, minor)
  → 不经过文件系统，直接按编号打开设备
```

### 核心设计

将设备节点信息存储在 FAT32 目录项中：

```
FAT32 32 字节目录项:
  byte 11:    attribute      = ATTR_DEVICE (0x40)   ← 标记设备节点
  byte 20-27: first_clus     = major                 ← 设备主号
  byte 28-31: file_size      = minor                 ← 设备次号
  byte 0-10:  filename       = "console"             ← 文件名
```

- 设备节点**不需要分配数据簇**（没有文件内容）
- `first_clus` 和 `file_size` 对设备节点而言是闲置字段，复用存储 major/minor
- 目录项写入磁盘后，设备节点名可被 `ls` 看到、被 `ename()` 解析

### 详细改动

#### 1. `kernel/include/fat32.h`

新增常量 `ATTR_DEVICE 0x40`。`create()` 声明增加 major/minor 参数。

#### 2. `kernel/fs/fat32.c` — `ealloc()`

`ealloc` 增加 `ATTR_DEVICE` 分支：不分配簇、不加 `ATTR_ARCHIVE` 标记：

```c
if (attr == ATTR_DIRECTORY) {
    // 分配簇, 创建 "." 和 ".."
} else if (attr == ATTR_DEVICE) {
    ep->attribute |= ATTR_DEVICE;    // 仅设标记，不分配任何簇
} else {
    ep->attribute |= ATTR_ARCHIVE;
}
```

#### 3. `kernel/syscall/sysfile.c` — `create()`

增加 `T_DEVICE` 处理逻辑：

```c
if (type == T_DIR) {
    mode = ATTR_DIRECTORY;
} else if (type == T_DEVICE) {
    mode = ATTR_DEVICE;
} else if ((mode & O_ACCMODE) == O_RDONLY) {
    mode = ATTR_READ_ONLY;
} else {
    mode = 0;
}
// ... ealloc ...
if (type == T_DEVICE) {
    ep->first_clus = major;      // 存储到 FAT32 目录项
    ep->file_size = minor;       // 存储到 FAT32 目录项
    ep->dirty = 1;               // 确保 eput 时写入磁盘
}
// 类型检查增加 T_DEVICE 分支
if (/* ... */ ||
    (type == T_DEVICE && !(ep->attribute & ATTR_DEVICE)) ||
    /* ... */) {
    // 类型不匹配
}
```

#### 4. `kernel/syscall/sysfile.c` — `sys_mknod` 恢复，`sys_dev` 删除

```c
uint64
sys_mknod(void)
{
    char path[FAT32_MAX_PATH];
    int major, minor;
    struct dirent *ep;

    if(argstr(0, path, FAT32_MAX_PATH) < 0 ||
       argint(1, &major) < 0 || argint(2, &minor) < 0)
        return -1;

    if((ep = create(path, T_DEVICE, 0, major, minor)) == 0)
        return -1;

    eunlock(ep);
    eput(ep);
    return 0;
}
```

`sys_dev()` 整个函数删除。

`sys_mkdir()` 的 `create()` 调用更新为 5 参数。

#### 5. `kernel/fs/file.c` — `fileopen()`

去掉 `device_path_lookup()` 调用，改为统一的 `ename()` + `ATTR_DEVICE` 检查：

```c
// 之前:
if(device_path_lookup(path, &major, &minor) == 0)
    return fileopen_device(f, major, minor, omode);

// 之后:
// ... 统一的 ename() / create() 路径 ...
if(ep->attribute & ATTR_DEVICE) {
    int major = ep->first_clus;
    int minor = ep->file_size;
    eunlock(ep);
    eput(ep);         // 设备节点不需要持有 dirent
    return fileopen_device(f, major, minor, omode);
}
```

同时移除 `#include "device.h"`。

#### 6. 删除 `device.c` + `device.h`

- `device.c` 中仅有 `device_path_lookup()` 和 `device_paths[]` 数组 → 整个文件删除
- `device.h` 中仅有 `device_path_lookup` 和 `k210_devices_init` 声明（后者从未实现/调用） → 整个文件删除
- Makefile 移除 `$K/device.o`
- 清理所有 `#include "device.h"`：
  - `kernel/main.c`
  - `kernel/include/spi_config.h`
  - `kernel/include/i2c_config.h`
  - `kernel/syscall/sysfile.c`（已在上一轮加上，本轮删除）
  - `kernel/fs/file.c`（第一轮新增，本轮删除）

#### 7. 系统调用表清理

| 位置 | 删除内容 |
|---|---|
| `kernel/syscall/syscall.c` | `extern sys_dev`，`[SYS_dev]` 的 name/argc/dispatch 条目 |
| `kernel/include/syscall.h` | `#define SYS_dev 27` |
| `user/usys.pl` | `entry("dev")` |
| `user/include/user.h` | `int dev(int, int, int)` |

#### 8. `user/init.c` — 启动时创建设备节点

```c
mkdir("/dev");
mknod("/dev/console", DEV_CONSOLE, 0);
mknod("/dev/stats", DEV_STATS, 0);
// K210 only:
mknod("/dev/sdcard", DEV_SDCARD, 0);
mknod("/dev/w25q64", DEV_SPI, SPI_DEV_W25Q64);
mknod("/dev/oled", DEV_I2C, I2C_DEV_OLED);
mknod("/dev/mpu6050", DEV_I2C, I2C_DEV_MPU6050);
```

`mkdir`/`mknod` 是幂等的——后续重启时路径已存在，返回 -1 但不影响启动流程。

#### 9. 用户态测试更新

- `devtest.c` 重写：从 `dev(O_RDWR, major, minor)` 改为 `mknod(path, major, minor); open(path, O_RDWR)`
- `mpu6050.c`、`w25q64.c` 错误信息从 `"dev() failed"` 改为 `"open /dev/xxx failed"`

其余测试程序（consoletest、sdtest、spitest、dmactest、i2ctest）已使用 `open("/dev/xxx", ...)`，无需修改。

设备节点现在：
- 是 FAT32 文件系统中的真实目录项（`ls /dev` 可见）
- 存储 major/minor 在 `first_clus`/`file_size` 字段（设备节点不需要数据簇）
- 打开路径统一走 `ename()`，不再有第二条路径
- 运行时动态创建（`mknod`），不再依赖编译期数组
- 删除 `sys_dev` 系统调用，减少入口

## 设计决策记录

### 为什么用 `first_clus`/`file_size` 存 major/minor？

FAT32 32 字节目录项没有现成的 major/minor 字段。但设备节点没有文件内容（不需要簇链）也没有文件大小，这两个字段对其完全闲置。复用它们不需要修改 FAT32 磁盘布局。

### 为什么 `ATTR_DEVICE` 节点不分配簇？

设备节点是文件系统中的一个"名字+编号"的占位符。真实设备是内核运行时注册的（`device_register()`），设备节点的作用只是在 FAT32 中提供一个可被 `ename()` 解析的路径。

### 为什么 `ep->dirty = 1`?

`ep->dirty` 标记确保在 `eput()` 调用 `eupdate()` 时将 `first_clus`/`file_size` 写入磁盘。这保证了重启后 `ename()` 能读回正确的 major/minor。设备驱动则需要在启动时重新注册（`device_register()`）。

### 为什么 init 的 mknod 是幂等的？

`create(T_DEVICE)` 内部调用 `ealloc()`，后者如果发现同名目录项已存在且类型匹配，直接返回现有 entry。所以重复调用 `mknod` 不会报错，只会重新设置 major/minor（相同值，无副作用）。

## 遗留问题

1. **第一轮保留的 `fdalloc` 在 sysfile.c 中**：`fdalloc` 操作 `myproc()->ofile[]`，是纯进程层逻辑。未来可评估是否迁到 `proc.c`。
2. **`mmap_handler`/`find_vma`/`sys_mmap`/`sys_munmap` 仍在 sysfile.c 中**：它们与文件操作有关但混杂了 VMA 管理，后续可迁到 `vm/` 目录。
3. **K210 启动失败问题**：重构后 K210 硬件上报 `SDHC/SDXC detected` 后卡住，可能与 SD 卡驱动或设备初始化顺序有关，需要独立排查。
