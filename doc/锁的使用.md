# 锁的使用

# 不同 CPU freelist 之间锁的使用

## 为什么本 CPU 分配仍然需要 freelist 锁

单看本 CPU 的分配动作，关闭中断后确实不需要防范本 CPU 上的中断重入。但是当前设计允许一个 CPU 在本地 freelist 为空时，从其他 CPU 的 freelist 偷取页面，因此每条 freelist 都可能被多个 CPU 并发访问。

假设本地分配路径不加锁，初始状态为：

```text
kmem[0].freelist -> A -> B
```

可能发生以下交错：

```text
CPU 0 本地分配                    CPU 1 偷取
r = freelist;  // A
                                  acquire(&kmem[0].lock);
                                  r = freelist;  // A
                                  freelist = B;
                                  release(&kmem[0].lock);
freelist = r->next;  // B
返回 A                            返回 A
```

最终两个 CPU 都返回页面 `A`，造成同一个物理页面被重复分配。

CPU 1 获取锁并不能防止 CPU 0 无锁访问同一条链表。锁只有在所有可能并发访问该共享数据的路径都遵守时才有效。因此：

- 如果其他 CPU 永远不会访问本 CPU 的 freelist，本地分配在关闭中断后可以不加锁。
- 当前设计允许其他 CPU 直接偷取该 freelist，因此本 CPU 分配也必须获取对应的 `kmem[id].lock`。

如果需要实现真正无锁的本地分配，就必须改变偷取机制，使其他 CPU 不再直接修改本地链表。例如，可以使用原子交换、远程请求队列或者批量页面移交机制。

## 页面从 freelist 摘除后的所有权

正常情况下，页面从 freelist 摘除后，其所有权已经转移给当前这次 `kalloc_page()`，即使分配函数尚未返回。分配过程为：

```text
从 freelist 摘除 r
释放 freelist 锁
更新 COW 引用计数
memset(r)
返回 r 给调用者
```

在 `return r` 之前：

- 其他 CPU 无法再从 freelist 分配到 `r`，因为它已经被摘除。
- 调用者还没有获得 `r`，因此不可能合法调用 `kfree_page(r)`。
- allocator 中只有当前函数栈里的局部变量 `r` 持有这个新分配页面。

`kmem[id].lock` 保护的是 freelist 链表结构，以及页面从空闲状态转为已分配状态时的所有权转移。页面离开 freelist 后，不需要继续持有 freelist 锁来保护页面内容。

即使释放 freelist 锁并执行 `pop_off()` 后发生调度，也不会产生并发释放问题。此时页面不属于任何 freelist，只是暂时由尚未执行完的 `kalloc_page()` 独占；当前执行流恢复后会继续设置引用计数、填充页面并返回。

如果另一个 CPU 能在这个窗口执行：

```c
kfree_page(r);
```

说明它已经提前持有同一页面的旧引用，通常意味着存在更严重的所有权错误，例如：

- double free；
- use-after-free；
- 页面仍被引用时就被放回 freelist；
- COW 引用计数错误。

延长 freelist 锁的持有时间不能修复这类错误，因为问题的根源是同一个页面同时存在多个非法所有者。

分配路径需要保证以下不变量：

```text
页面在 freelist 中       ⇒ 引用计数为 0
页面从 freelist 分配完成 ⇒ 引用计数为 1
页面对调用者可见之前     ⇒ 引用计数设置和 memset 已完成
```

只要 `kalloc_page()` 在返回页面之前完成引用计数设置和 `memset()`，对调用者的发布顺序就是安全的。`cow_map.lock` 负责保护引用计数，`kmem[id].lock` 负责保护 freelist，两者职责不同。

# per-CPU freelist 与 COW 引用计数锁设计

## 设计目标

页面释放过程不需要同时持有 `cow_map.lock` 和 `kmem[id].lock`。关键是利用页面所有权状态，将引用计数更新和 freelist 发布拆成两个阶段。

设计需要维护以下不变量：

```text
引用计数 > 0：页面正在使用，不得出现在 freelist
引用计数 = 0：页面由最后一个释放者临时独占，随后才能加入 freelist
页面在 freelist：只能通过对应的 kmem[i].lock 访问
```

当引用计数从 `1` 减到 `0` 时，执行这次减法的 CPU 获得页面的临时独占权。此时已经没有合法引用，其他 CPU 不应再访问该页面或增加它的引用计数。

## 推荐的页面释放实现

```c
static void
kfree_page_to(int id, void *pa)
{
  struct run *r;
  int cnt;

  if (((uint64)pa % PGSIZE) != 0 ||
      (char *)pa < end ||
      (uint64)pa >= PHYSTOP)
    panic("kfree_page");

  acquire(&cow_map.lock);
  cnt = --cow_map.cow_quota[(uint64)pa / PGSIZE];
  release(&cow_map.lock);

  if (cnt < 0)
    panic("kfree_page: negative quota");

  if (cnt > 0)
    return;

  // cnt == 0，页面由当前释放路径独占，尚未发布到 freelist。
  memset(pa, 1, PGSIZE);

  r = (struct run *)pa;

  acquire(&kmem[id].lock);
  r->next = kmem[id].freelist;
  kmem[id].freelist = r;
  release(&kmem[id].lock);
}
```

这样设计有以下优点：

- 永远不会同时持有 `cow_map.lock` 和 `kmem[id].lock`。
- 从根本上消除两类锁之间的 ABBA 死锁。
- `memset()` 不在自旋锁内执行，缩短关中断和锁占用时间。
- 页面只有完成初始化后才发布到 freelist，其他 CPU 不会分配到正在执行 `memset()` 的页面。

## 当前锁序及风险

原释放路径的锁序是：

```text
cow_map.lock → kmem[id].lock
```

分配路径则是：

```text
持有 kmem[id].lock
释放 kmem[id].lock
获取 cow_map.lock
```

当前分配路径没有同时持有两把锁，因此仅就该实现而言，还没有形成下面的 ABBA 环路：

```text
CPU A：持有 cow_map.lock，等待 kmem[id].lock
CPU B：持有 kmem[id].lock，等待 cow_map.lock
```

但是这种锁序比较脆弱。如果以后把分配路径改成在持有 `kmem[id].lock` 时获取 `cow_map.lock`，就会立即产生死锁风险。

因此应遵守以下约束：

> `cow_map.lock` 和任意 `kmem[i].lock` 永远不嵌套持有。

## per-CPU freelist 完整规则

### 1. `kmem[i].lock` 保护对应的 freelist

本 CPU 分配、其他 CPU 偷取以及页面归还，都必须持有对应的 `kmem[i].lock`。由于允许其他 CPU 偷取页面，freelist 只是 CPU 优先使用的链表，并不是真正的 CPU 私有数据。

### 2. 每次最多持有一把 `kmem` 锁

偷取页面时：

```c
acquire(&kmem[n_id].lock);
// 摘取一个或一批页面。
release(&kmem[n_id].lock);
```

不要同时持有本地和远端两把 freelist 锁。需要转移多个页面时，应先从远端链表摘下页面并释放远端锁，再将页面加入本地链表。

### 3. `cow_map.lock` 只保护引用计数

引用计数的增加、减少，以及“是否减到零”的判断，必须在同一个 `cow_map.lock` 临界区内完成。

### 4. 引用计数减到零后，由最后释放者临时拥有页面

释放 `cow_map.lock` 后，最后释放者可以安全执行 `memset()` 和链表节点初始化。直到获得 `kmem[id].lock` 并将页面插入链表，该页面才重新对分配器可见。

这依赖一个基本前提：引用计数变为零后，不再存在可以合法访问或重新引用该页面的旧引用。违反此前提意味着已经发生 double free、use-after-free 或引用计数错误。

### 5. 页面从 freelist 摘除后，由分配者临时拥有

分配路径可以分为以下阶段：

```text
获取 kmem 锁
从 freelist 摘除页面
释放 kmem 锁
把引用计数设置为 1
执行 memset
返回给调用者
```

页面被摘除后，其他 CPU 无法再从 freelist 分配到它；在分配函数返回之前，调用者也无法释放它。

### 6. `cpuid()` 与 freelist 锁职责不同

如果目标是把页面释放到当前 CPU 的 freelist，应在读取 `cpuid()` 前关闭中断，防止进程在读取 CPU ID 后被调度到其他 CPU：

```c
push_off();
int id = cpuid();
kfree_page_to(id, pa);
pop_off();
```

两者分别解决不同问题：

- `push_off()` 保证读取和使用 CPU ID 期间不会发生 CPU 迁移。
- `kmem[id].lock` 防止其他 CPU 同时修改该 freelist。

## 总结

整体设计原则是：

```text
引用计数锁：决定页面是否仍然存活
freelist 锁：负责页面的发布和取出
计数变为 0 或页面从 freelist 摘除：形成两个锁之间的独占所有权过渡
```

利用这个所有权过渡，可以避免同时持有 `cow_map.lock` 和 `kmem[i].lock`，降低死锁风险，并缩短自旋锁临界区。

# Buffer Cache 中的 LRU 与 CLOCK

## 算法对比

| 算法 | 访问时操作 | 淘汰时操作 | 特点 |
| --- | --- | --- | --- |
| 精确 LRU | 把 buffer 移到链表头部 | 从链表尾部选择可回收 buffer | 精确淘汰最久未使用的对象，但每次访问都要修改链表 |
| 时间戳 LRU | 更新 `timestamp` | 扫描并寻找最小时间戳 | 不移动链表，但淘汰时需要扫描和比较时间戳 |
| CLOCK | 设置 `referenced = 1` | 使用 `clock_hand` 循环扫描并给予第二次机会 | 近似 LRU，访问开销低，不依赖全局时间戳 |

## CLOCK 的基本含义

`clock_hand` 不是时间值，而是指向下一次淘汰候选项的循环扫描指针。每个 buffer 还维护一个引用位：

```c
uint referenced;
```

访问 buffer 时只需要设置：

```c
b->referenced = 1;
```

这表示该 buffer 最近被访问过，CLOCK 扫描到它时应先给予一次继续留在缓存中的机会。

假设一个 bucket 中的状态为：

```text
                 clock_hand
                      ↓
head <-> A(1) <-> B(0) <-> C(1) <-> D(0) <-> head
```

括号中的数字表示 `referenced`。扫描过程如下：

1. 扫描到 `A(1)` 时，将 `A.referenced` 清零并跳过。
2. 扫描到 `B(0)` 时，如果 `B.refcnt == 0`，选择 `B` 作为 victim。
3. `clock_hand` 移动到 `C`，下次从 `C` 继续扫描。

这就是 CLOCK 又称“第二次机会算法”的原因：近期访问过的 buffer 第一次被扫描时不会立即淘汰；如果在下一轮扫描前没有再次被访问，它才会成为可淘汰对象。

## `refcnt` 与 `referenced` 的区别

| 条件 | 含义 | CLOCK 行为 |
| --- | --- | --- |
| `refcnt > 0` | buffer 正在使用或被 pin | 必须跳过，绝不能淘汰 |
| `refcnt == 0 && referenced == 1` | 当前无人使用，但近期访问过 | 清除 `referenced`，给予第二次机会 |
| `refcnt == 0 && referenced == 0` | 当前无人使用，近期也未访问 | 可以作为 victim |

CLOCK 的核心判断可以表示为：

```c
if (b->refcnt != 0)
  continue;

if (b->referenced) {
  b->referenced = 0;
  continue;
}

return b;
```

## 每个 bucket 使用独立 CLOCK

每个哈希桶维护自己的锁、链表和扫描指针：

```c
struct hashbuf {
  struct spinlock lock;
  struct buf head;
  struct buf *clock_hand;
};
```

访问 buffer 时已经持有对应的 bucket 锁，因此可以直接更新：

```c
b->refcnt++;
b->referenced = 1;
```

淘汰扫描也必须在同一把 bucket 锁保护下完成。该锁保护：

- bucket 双向链表；
- `clock_hand`；
- buffer 的 `refcnt` 和 `referenced`。

如果当前 bucket 没有可回收 buffer，可以依次扫描其他 bucket。跨 bucket 转移 buffer 时仍然遵守“每次最多持有一把 bucket 锁”的规则：

```text
锁住来源 bucket
摘除 victim，并推进来源 bucket 的 clock_hand
释放来源 bucket
锁住目标 bucket
插入 victim
释放目标 bucket
```

victim 从来源链表摘除后、插入目标链表前，由当前执行路径临时独占，其他 CPU 无法通过任何 bucket 找到它。

## CLOCK 的优缺点

优点：

- 命中时只设置一个引用位，不需要移动双向链表。
- 不需要读取全局 `ticks`，可以避免热点路径竞争 `tickslock`。
- 不存在时间戳精度不足或整数回绕后的比较问题。
- 每个 bucket 可以独立扫描，更适合多核并发。

缺点：

- CLOCK 是近似 LRU，不能保证淘汰全局最久未使用的 buffer。
- 内存压力较大时可能需要扫描多项甚至多轮。
- 单个引用位只能表示最近是否访问过，不能区分访问频率。

在分桶 buffer cache 中，CLOCK 用少量淘汰精度换取更短的热点路径和更低的锁竞争，通常比全局精确 LRU 更容易扩展。
